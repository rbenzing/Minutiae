# Invariants: case, evidence and audit

Covers `internal/evidence` outside the record tables: artifacts, the manifest, the audit log, the case lock, anchors, `OpenArtifact` and the core of `case verify`. Part of the [forensic invariants](../invariants.md), which say how to add or change a row. Each row is enforced by the tests it names: keep them green.

| `case verify` honours cancellation in the phases that can take long: the artifact re-hash (checked before each artifact and every 32 KiB read, so a multi-gigabyte hash stops promptly), the record checks and P11 (the verify context reaches `verifyRecords`, the index pass and the localization of the failing buckets). The phases that do not take the context are fast and always run to the end: the audit read, `checkDerived`, the audit and database cross-checks, `checkTmp`, `verifyRecovered`, the schema, unmanifested-file and staging checks. When a phase was actually cut short the report carries one `reproduce: verification cancelled` line, so a cut verify is never OK and never a silent partial pass; the read errors the cancel itself causes are not listed (they would look like corruption), and a cancel that lands after every cancellable phase finished marks nothing when no composed check runs (with composed checks, as on the CLI, it is a cancelled verify). A problem found before the cancel stays in the report, so an integrity failure is never masked by a cancel; a cancel during the localization keeps the findings of the index pass, adds the cancelled line and names the batches it did not localize, with no cancel noise and no scratch area left (`TestVerifyCancelDuringLocalizationKeepsTheFindings`). The CLI exits 1 (a plain cancelled error, as a cancelled parse run) when the cancelled line is the only problem and 4 when any other problem exists. The structure check stays quiet on a cancelled context (the cancellation is the report) and reports a read error on a live one | `TestVerifyCancelledDuringP11` (a cancel during the index pass, after an integrity problem), `TestVerifyCancelDuringLocalizationKeepsTheFindings`, `TestVerifyCancelBetweenLocalizationRoundsKeepsTheFindings`, `TestVerifyCancelDuringTheIndexPassKeepsTheKnownFailingBuckets` (a cancel that ends the index pass still names the failing buckets it knew, so the run is never a bare cancel and the CLI exits 4), `TestVerifyCancelDuringTheRebuildStreamOfALocalizationRound`, `TestVerifyCancelAddsOnlyTheCancelledLine`, `TestVerifyCancelledBeforeTheHashPhaseHashesNothing`, `TestHashReaderContextStopsSoonAfterACancel`, `TestVerifyCancelAfterEveryPhaseFinishedStaysClean`, `TestVerifyCancelAtTheEndOfEveryPhase` (a cancel at the end of each of the phases, `fts.selftest` and `records.stream/fts.expected` included, of the P11 index-pass steps `fts.index/<table>/<step>` (`decode`, `totals`, `config`, `unreferenced`), for `records_fts` and `records_fts_sub`, is a clean cut; a cancel at the end of `fts.index` itself, after the last cancellable step, is a clean pass when no composed check runs), `TestVerifyCancelAtFTSCompareWithAComposedCheck` (the same cancel with a composed check is a cancelled verify), `TestHashPhaseMarksTheVerifyAsCut`, `TestCancelCausedErrorsNeedADeadVerifyContext` (an error wrapping `context.Canceled` counts as a cut only when the verify context really ended), `TestCaseVerifyCleanCancelExits1`, `TestCaseVerifyCancelWithAnotherProblemExits4`, `TestFTSStructureCheckIsQuietWhenCancelled`, `TestFTSStructureReadErrorOnALiveContextIsReported` |
| The verify progress observer only observes: `VerifyObserved` with an observer returns the report `VerifyWith` returns (clean and altered), `*VerifyProgress` has no exported mutator (its only exported method is `Snapshot`, safe from any goroutine; composed checks feed it only through `Case.VerifyPhase`, which names the phase `checks/<name>`, is a no-op without an observer or hook and cannot change a check; R6 counts bytes in `checks/reproduce`), and its counters move once per chunk and never per row. | The per-row work of `case verify` runs on a bounded worker pool and changes nothing it reports: the row digest, `NewFTSDoc`, the tokenizer replicas and the keyed posting MACs of each record chunk are computed on `min(GOMAXPROCS, 8)` workers (`mapOrdered`; pure functions of the row), and everything that depends on the order of the rows (the batch digests, the buckets, the problem lists and their caps, the progress counters) is folded on the stream goroutine in id order, so the report (problems, notices, counts, `FTSDocsChecked`) is byte-identical to a one-worker run on a clean case and on a damaged one. A worker that panics fails the verify closed (a `scan` problem naming the digests that could not be computed, the stream ends, no document counts as checked), and a panic is reported even when the context ended at the same moment; a cancel stops the workers and is a cut, never a problem (D111-D120, D162). At most as many rows are in flight as there are workers and the results held are those of one chunk | `TestVerifyParallelEqualsSerial`, `TestMapOrderedKeepsInputOrderAtAnyWorkerCount`, `TestMapOrderedPanicFailsClosed`, `TestMapOrderedPanicIsNotMaskedByACancel`, `TestMapOrderedHonoursCancellation`, `TestMapOrderedNeverExceedsTheWorkerCount`, `TestMapOrderedLeavesNoGoroutine`, `TestVerifyUsesTheConfiguredWorkers`, `TestVerifyWorkerPanicFailsClosed`, `TestVerifyParallelCancelKeepsFindings`, `TestVerifyParallelProgressCounters` |
| The phases of `case verify` that overlap change nothing it reports: P10 (`records.integrity_check`) runs on its own goroutine and its own read-only connection to `artifacts.db` (`query_only`, the single-connection exception in `docs/architecture.md`) beside the record stream and the index pass, and the two full-text tables are decoded together, each on a private view that is merged in table order; the problems of P10 are put where the serial order has them (right after the schema problems), so the report is byte-identical to the serial order on a clean case and on a damaged one. The second connection never writes and is closed on every path. The phase hook is never entered twice at once and a snapshot taken in it names the phase that ended; the status line names the phases running together; phase times overlap, so a sum counts only top-level wall time (the `records.overlap` span in place of the phases inside it, `VerifyPhaseOverlapped`, D183) | `TestVerifyConcurrentPhasesEqualSerial`, `TestVerifyConcurrentCancelKeepsFindings`, `TestVerifyIntegrityCheckConnectionIsReadOnly`, `TestVerifyIntegrityCheckRunsBesideTheStream`, `TestVerifyPhaseHookCallsNeverOverlap`, `TestSnapshotNamesConcurrentPhases`, `TestVerifyPhaseTimesSumToWallTime`, `TestVerifyIntegrityCheckFlagged`, `TestRenderStatusNamesPhasesRunningTogether` |
