# Invariants: HFS+ reader

Covers the HFS+ and HFSX reader `internal/filesys/hfsplus`, its builder `hfsplustest` and the shared `internal/filesys/decmpfs`. The rules every reader shares are under [filesystems](filesystems.md). Part of the [forensic invariants](../invariants.md), which say how to add or change a row. Each row is enforced by the tests it names: keep them green.

| Invariant | Test |
|---|---|
| The HFS+/HFSX reader equals an independent oracle for each of the six committed fixtures: five empty volumes built by `mkfs.hfsplus` (`hfsplus-empty`; `hfsx-empty`, case-sensitive; `hfsplus-journal`, `-J`, journal never initialised; `hfsplus-1k`, 1 KiB blocks; `hfsplus-wrapped`, a classic HFS wrapper embedding the volume at byte 45056) and `hfsplus-populated`, written by the Linux `hfsplus` driver under QEMU (a 3-level catalog, a 600-entry directory, a 3 MiB file, an 18-extent file with extents-overflow records, symlinks, a three-link hard-link group with its private folder, decomposed UTF-8 names, a 255-unit name). The oracle is a second hand-written parse (never Minutiae) cross-checked against `fsck.hfsplus` and `blkid`, and for the populated image against the source tree the volume was filled from. The test asserts the image sha256 equals the oracle's `generator.image_sha256` (a stale oracle fails first); `Info` (type `hfsplus` or `hfsx`, label, volume id, block size, size, features) equals the oracle with no warnings and `Encrypted` false; the live tree is exactly the oracle's path set, none missing, none extra, with no `Deleted` entry, the oracle's types, permission bits, owners, all four times (UTC, `ZoneKnown` true), directory valences, sizes, content SHA-256, symlink targets and hard-link attributes (`hardlink=file`, link count, inode); the private metadata folder is listed (with a `~raw~` name, since it holds NULs) and is the only entry carrying `private_metadata`; every file's `File.Runs` equal, in logical order, the oracle's extents (inline plus overflow, merged by hand, cut at the size, wrapper offset included); and `Unallocated` equals exactly the oracle's free blocks (same runs, same count), with no free run overlapping live data, a system file, a header or any allocated extent. NOT covered by a real image: deleted entries (HFS+ keeps none), compressed files, extended attributes, resource forks, non-BMP names (the Linux driver cannot create them), HFSX with content, a journal with transactions, and any volume written by macOS or iOS (those paths are verified on builder images only, checked by `fsck.hfsplus`; see docs/limitations.md) | `TestHFSPlusMatchesOracle`, `TestUnallocatedMatchesOracle`, `TestPopulatedFixtureHoldsWhatItClaims` |
| HFS+ builder images are not just self-consistent: they are checked by Apple's own `fsck.hfsplus -n -f`. 12 of the 15 images the builder writes pass (plain, multi-level catalog with 512-byte nodes, HFSX case-sensitive and case-folding, root-owned hard links, overflow extents, a fragmented catalog file, attributes, resource fork, compressed, wrapped, 1 KiB blocks); three are exempt with a recorded reason: `hardlinks-owned` (files with a non-zero uid/gid make fsck count the link chain differently; cause unconfirmed), `journaled-clean` (the builder writes the journal but no `.journal`/`.journal_info_block` catalog files) and `wrapped-hfsx` (Apple never embeds HFSX in a wrapper; the reader accepts it on purpose). Running the check is manual (`MINUTIAE_WRITE_BUILDER_IMAGES=<dir> go test -run TestBuilderImagesPassFsck ./internal/filesys/hfsplus`, then `hfsplus.sh check-builder <dir>` in the fixture image); the two builder defects it found are pinned by a test that runs by default | `TestBuilderMatchesFsckExpectations`, `TestBuilderImagesPassFsck`, `TestBuilderVolumeIsSelfConsistent` |
| The HFS+ hard-link private folder is named with four NUL units, and the reader's case-folding comparison sorts NUL last (it folds to 0xFFFF, not ignorable), CONFIRMED on the kernel-written populated fixture: the private folder is the last child of the root, after names up to U+65E5, every catalog key pair of that image is in order under the reader's comparison (`fsck.hfsplus` accepts the same order), and resolving a hard link finds the folder by catalog descent with no directory-budget spend. Should the descent still miss on a case-folding catalog (a volume ordered otherwise), a budgeted scan of the root's children finds the folder independent of sort order; a binary (case-sensitive HFSX) catalog sorts NUL first and skips that scan | `TestRealPrivateFolderSortsLastAndIsFoundByDescent`, `TestBuilderPrivateFolderSortsLastLikeARealVolume`, `TestHardLinkPrivateFolderFoundInAnyOrdering`, `TestFoldAndCompare` |
| HFS+ entry IDs are `cnid:<canonical decimal>` (a uint32 that is 2 or at least 16); any other spelling (leading zero, sign, space, hex, wrong prefix, overflow, a reserved CNID) is `ErrNotFound` without reading the disk, and `Open`/`ReadDir` derive everything from the catalog via the ID: a forged `Size`, `Type`, `Deleted`, `Encrypted` or attribute changes nothing, a folder forged as a file (or the reverse) stays what the disk says, and an `Entry{ID: ...}` built outside `ReadDir` opens. HFS+ lists no deleted entries (the catalog keeps no deletion marker); stale record bytes left in node slack after a delete are never listed (`TestStaleNodeSlackIsNotListed`); the reader has no code path that reads unused nodes or the journal for entries (not separately tested; recovery is sub-project 3) | `TestEntryIDsMustBeCanonical`, `TestForgedEntryFieldsAreIgnored` (HFS+, F2FS and FAT), `TestForgedIDsAreRejectedQuickly`, `TestEntryBuiltOutsideReadDirOpens`, `TestOpenForgedEntryFieldsAreIgnored`, `TestStaleNodeSlackIsNotListed` |
| HFS+ catalog node ids are never trusted to be unique, and a shared id never makes one path return another object's bytes or listing. When a catalog record's id has a thread record that does not point back at the (parent id, name) the record was found under (or is a thread of the other kind), the entry is flagged `cnid_conflict=true`, one filesystem warning names it (quoted), and its ID is `conflict:<id>:<parent>:<base64url of the raw name>` instead of `cnid:<id>`: `Open` and `ReadDir` of a well-formed conflict ID, and a `Lookup` path that passes through a conflicting folder, are a `CorruptError` (no read is made; a malformed spelling is `ErrNotFound`), while the record the thread does name keeps `cnid:<id>` and opens normally; the children of a duplicated folder id are keyed by that id and cannot be told apart, so the warning is the signal that the owning folder's listing may mix them | `TestDuplicateCNIDEntryIsConflictAndNeverOpens`, `TestDuplicateCNIDFolderIsConflictAndNeverListed`, `TestConflictIDsAreStrict`, `TestDuplicateCNIDInListingIsWarned`, `TestDirHostile` (folder id equals an ancestor) |
| HFS+ decompresses a file only when the OS would: the BSD `UF_COMPRESSED` flag (0x20 in the catalog record's owner flags) decides, and a `com.apple.decmpfs` attribute on a file without it never replaces the data fork. Such a file is read from its data fork (size and bytes), carries `decmpfs_ignored=true` and its `xattr` attribute, and one warning says the attribute is ignored | `TestDecmpfsAttributeWithoutFlagIsIgnored` |
| HFS+ B-trees and forks never believe a structure that cannot be trusted, and never loop. An extents-overflow lookup that makes no progress (a zero-block record, an empty extent, a repeated start, an overshooting record, a leaf chain that loops back) is `ErrCorrupt`, never an endless lookup; a B-tree leaf chain that revisits a leaf, points outside the tree, reaches a non-leaf or ends before the header's last leaf is `ErrCorrupt` (a cut chain also warns that later records are not listed); an index that loops, has the wrong height or kind is `ErrCorrupt`; a file whose fork is damaged (an overflow record missing, overshooting or outside the volume, an allocation shorter than the size, an extent past the end of a truncated image) opens with the bytes that can be trusted (a warning; `File.Runs` is a valid prefix, `filesys.CheckRunsPrefix`; the tail reads as `ErrCorrupt`, never zeros) and `extract` keeps that prefix as an artifact flagged `incomplete` with the prefix runs recorded; `File.Runs` reproduce the content byte for byte, and on a wrapped volume they are offsets from the start of the image, not of the embedded volume | `TestExtentsOverflowNoProgressIsCorrupt`, `TestBTreeLeafChainCycleIsCorrupt`, `TestBTreeLeafChainEndsEarly`, `TestBTreeIndexLoopIsCorrupt`, `TestBrokenOverflowExtentKeepsTrustedPrefix`, `TestForkShorterThanSizeIsTrustedPrefix`, `TestTruncatedImageEndsTrustedPrefix`, `TestRunsReproduceContent`, `TestWrapperRunsAreRelativeToWrapperStart`, `TestExtractHFSPlusBrokenForkIsIncomplete` |
| HFS+ name lookup order and case rule: in each folder a name matches in the order exact spelling, then the `~raw~` display alias (canonical bytes only), then (case-insensitive catalogs only) case-fold, so an exact spelling is never shadowed by a folded one and the alias needs no fold scan; HFS+ is always case-insensitive and HFSX is case-sensitive only when the catalog's `keyCompareType` is 0xBC (a `0xBC` on a plain HFS+ volume only warns); names are compared as stored with no Unicode normalization, so a composed (NFC) path does not find a name stored decomposed (NFD), and a name is shown as stored (a stored `:` is not turned into `/`) unless it is empty, `.`, `..`, holds `/` or NUL or is not valid UTF-16, in which case it is shown in the `~raw~<base64url>` form with `RawName` set | `TestLookupCaseSensitivityHFSXvsHFSPlus`, `TestLookupPrefersExactOverFolded`, `TestLookupAliasNeedsNoFoldScan`, `TestOpenVolumeHeaderFields`, `TestBTreeCaseModes`, `TestUnicodeNamesDecomposedAsStored`, `TestNamePolicies` |
| HFS+ hard links, thread-less records and data protection are never guessed. A file hard link (`hlnk`/`hfs+`) resolves through the private folder's `iNode<N>` record: size, times, mode, owner, forks and attributes come from the inode while the name and the `cnid:` ID stay the link's, and the entry carries `hardlink=file`, `hardlink_inode` and `links`; a directory hard link (`fldr`/`MACS`) is listed as an `other` entry and never followed; a link whose inode is missing, whose private folder is missing or only a look-alike user folder, is flagged `hardlink=dangling` and `Open` is a `CorruptError`; a link whose iNode is itself a link is flagged `hardlink=invalid` and `Open` is `ErrCorrupt`. A file whose catalog has no thread record is listed with `thread=missing` and IS opened by a catalog scan with its own 256 MiB id-scan budget, only below the volume's next catalog id and never for a file that has a thread; the id must be provably unique (a second record, an undecodable record or a spent budget is a `CorruptError`, counted and warned, nothing opened), a thread-less folder id is `ErrUnsupported`, and a folder without a thread cannot be listed by ID. A thread position (the id, empty name) that holds a record of unknown type is UNREADABLE, never missing: the entry is flagged `thread=unreadable` with a warning, listing the folder by ID is a `CorruptError`, and a file whose own thread is unreadable is opened only when the catalog scan FINDS its record and proves the id unique (a scan that finds no file record, or an id past the volume's next id, is a `CorruptError`, never "not found"); every unknown-type record a thread lookup walks past is warned about (one warning with the scan's when the open fails closed on that record). An entry with a `cprotect` attribute is flagged `Encrypted` (per entry; its content is extracted as ciphertext) while `Info.Encrypted` stays false; resource forks are shown in attributes only (`rsrc_size`, `rsrc_blocks`) and `Open` returns the data fork | `TestHardLinkResolvesToIndirectNode`, `TestHardLinkDanglingIsFlagged`, `TestHardLinkChainIsCorrupt`, `TestDirectoryHardLinkIsNotFollowed`, `TestMissingThreadIsFlagged`, `TestOpenFileWithoutThreadByCatalogScan`, `TestThreadPresentNeverScans`, `TestNoThreadIDBeyondNextCNIDDoesNotScan`, `TestNoThreadFolderIDIsNotAFile`, `TestNoThreadDuplicateIDIsConflict`, `TestNoThreadDamagedRecordMakesTheIDUnprovable`, `TestNoThreadUnknownRecordTypeMakesTheIDUnprovable`, `TestNoThreadForeignEmptyNameUnknownRecordFailsClosed`, `TestNoThreadOwnParentNonEmptyNameUnknownRecordFailsClosed`, `TestNoThreadFileOwnParentNonEmptyNameUnknownRecordFailsClosed`, `TestReadDirUnreadableThreadIsCorrupt`, `TestReadDirByIDWarnsOnPassedUnknownRecord`, `TestEntryUnreadableThreadIsNotMissing`, `TestEntryWarnsOnPassedUnknownRecord`, `TestOpenFoldsLookupWarningIntoUnprovable`, `TestOpenFoldAbsorbsOnlyOneDuplicateKeyRecord`, `TestOpenUnreadableThreadWithNoFileRecordIsCorrupt`, `TestOpenUnreadableThreadBeyondNextCNIDIsCorrupt`, `TestOpenOwnUnreadableThreadOpensWhenScanProvesUnique`, `TestNoThreadScanBudget`, `TestNoThreadScanRecordCap`, `TestNoThreadEmptyCatalogIsNotFound`, `TestOpenNoThreadFileOnRealImage`, `TestCProtectMarksEncrypted`, `TestResourceForkOnlyInAttrs` |
| HFS+ compressed (decmpfs) files are never returned as empty or wrong bytes. A zlib file of type 3 (data in the attribute) or type 4 (blocks in the resource fork) is decompressed on read: `Size` is the uncompressed size, `File.Runs` is nil (so a derived artifact records no image runs, because the bytes are decoded, not copied), the entry carries `compressed=zlib`, `decmpfs_type` and `uncompressed_size`; every size claim is bounded (header size against payload with a ratio cap, block table against the resource fork, block count equal to the size, each block inflating to exactly its expected size) and a table or block that lies is `ErrCorrupt`. The shared decoder `internal/filesys/decmpfs` (`decmpfs.Open`) allocates from no declared size: a block or inline payload is inflated through a read capped at the declared size plus one byte into a buffer that grows with the bytes produced, and a declared size above 16 MiB or above 1100 times the compressed length is `ErrCorrupt` before anything is inflated (HFS+ decodes through that package; it has no decoder of its own). Any other type (for example LZVN or LZFSE), or a `UF_COMPRESSED` file whose decmpfs header cannot be read, is `ErrUnsupported` with attribute `compressed=<type>` or `unknown`, never an empty file, and `extract` skips it with an `analysis.warning`. An unsupported type is a `*decmpfs.UnsupportedError` and its raw attribute and resource fork remain readable through `XattrReader` | `TestUnsupportedCompressionKeepsRawBytesReachable`, `TestOpenXattrNamesAndLimits`, `TestOpenXattrResourceForkIsAllOrNothing`, `TestXattrsDamagedAttributeRecordIsAnError`, `TestDecmpfsZlibInline`, `TestDecmpfsZlibResourceFork`, `TestDecmpfsResourceForkBlockTableHostile`, `TestOtherTypesAreUnsupported`, `TestCompressedFileUnsupportedNotEmpty`, `TestExtractHFSPlusCompressedIsSkippedWithWarning`, `TestExtractHFSPlusEmptyFiles`, `decmpfs.TestInflateBlockDoesNotAllocateFromTheDeclaredSize`, `decmpfs.TestInflateBlockOverrunAndCeiling` |
| HFS+ `Unallocated` never reports an allocated, metadata or untrusted block as free. It refuses with an error wrapping `ErrUnsupported` when the journal has pending transactions (the bitmap on disk may lag the journal) or cannot be parsed, and accepts a clean journal (either byte order); bitmap bits at or past `totalBlocks` are ignored whatever their value; the boot area, both volume headers, every extent of the allocation, extents-overflow, catalog, attributes and startup files (overflow extents included), the bad-block file, the journal info block and the journal are never reported even when the bitmap says free; when a system file's extents cannot be fully resolved (a missing overflow record, an unreadable or invalid bad-block record) it reports nothing, with a warning, rather than a possibly incomplete protected set; a bitmap shorter than the volume leaves the uncovered blocks not free (warning); runs are offsets from the start of the image (wrapper included) and capped at 1<<24 with a warning; on a truncated image runs are clipped to the whole blocks the image holds, with one warning when a free block is dropped; a header/bitmap free-count mismatch or a volume not cleanly unmounted warns | `TestUnallocatedPendingJournalRefused`, `TestUnallocatedUnknownJournalRefused`, `TestUnallocatedCleanJournalOK`, `TestUnallocatedPaddingBitsIgnored`, `TestUnallocatedExcludesMetadata`, `TestUnallocatedProtectsEachStructure`, `TestUnallocatedIncompleteSystemFileReportsNothing`, `TestUnallocatedBadBlockExtentOutsideVolumeIsClippedAndWarned`, `TestUnallocatedBitmapTooShort`, `TestUnallocatedWrapperOffsets`, `TestUnallocatedRunCap`, `TestUnallocatedRunsStayInsideTruncatedImage`, `TestFreeCountMismatchWarns`, `TestUnallocatedUncleanUnmountWarns` |
| An HFS+ volume is bounded by what the container and the image really hold. A classic HFS wrapper is followed to the embedded HFS+ volume (offsets are by the master directory block; a plain HFS volume without an embedded one is `ErrUnsupported`); the volume is clamped to the wrapper's embedded extent, so the wrapper's own area after it is never reported as free or counted in `Info.Size` (a warning says so); a truncated image (a volume claiming more than the image holds, a truncated wrapped volume too) opens clamped with a warning, not as a corrupt volume, and every run stays inside `Info.Size`; a volume whose primary header fails its sanity or geometry checks is read through the alternate header (a warning), when both fail `Open` is a `CorruptError`, and a read error of the alternate is an I/O error, never a corruption verdict | `TestWrapperOffsetFound`, `TestWrapperPlainHFSIsUnsupported`, `TestWrappedVolumeIsBoundedByTheWrapperExtent`, `TestAltVolumeHeaderUsedWhenPrimaryBad`, `TestBothVolumeHeadersBadIsCorrupt`, `TestAlternateHeaderIOErrorIsNotCorrupt`, `TestOpenHostileGeometry` |
| HFS+ images flow through the same analysis path as the other filesystems: extracting every fixture (`extract -r /`) gives artifacts whose SHA-256, size and UTC mtime equal the oracle, whose `ParentSHA256` and `FSType` are right, with every hard link and the private iNode extracted, symlinks as their target text, no filesystem warning and nothing skipped; `unalloc -p` equals the oracle's free ranges (plus the wrapper offset) and `case verify` reports OK; 255-character names (ASCII and CJK, 765 bytes) extract under capped local names; empty and inline-compressed files are extracted with nil runs and no warning; `image info` shows an HFS+, an HFSX and a wrapped volume as partition filesystems | `TestExtractFromHFSPlusFixture`, `TestExtractHFSPlusLongNames`, `TestExtractHFSPlusEmptyFiles`, `TestInfoDetectsHFSPlusPartition` |
