# Invariants: APFS reader

Covers the APFS reader `internal/filesys/apfs` and its builder `apfstest`. The rules every reader shares are under [filesystems](filesystems.md). Part of the [forensic invariants](../invariants.md), which say how to add or change a row. Each row is enforced by the tests it names: keep them green.

| APFS name hashes and name lookup. A hashed directory-record key carries a 22-bit CRC-32C (no final complement) of the UTF-32 little-endian code points, without the terminating NUL, of NFD of the name (of NFD(case-fold(NFD(name))) on a case-insensitive volume), the hash being `name_len_and_hash >> 10` (the format reference's published mask, `J_DREC_HASH_MASK`, has a typo that loses bit 11); the reader recomputes it for every name, ASCII or not, and a mismatch keeps the entry, adds the attribute `name_hash=bad` and one `%q`-quoted warning (a bad hash never hides an entry from `Lookup`). A name that is not valid UTF-8, or holds a code point not assigned in Unicode 9.0 (the version understood to be frozen for APFS; newer normalization or folding tables could disagree), is NOT verified: no attribute, no warning, and its stored hash is not trusted for searching. All 678 stored hashes of `apfs-populated` (17 non-ASCII names in Latin, Greek, Cyrillic, Hangul, Japanese, emoji and special folds) and the two of each `mkapfs` fixture are reproduced with 0 mismatches and no warning, and the builder's copy of the recipe agrees (a consistency check only: it shares the `golang.org/x/text` tables with the reader, so the independent evidence is the real images and their Python oracle). On a volume that is normalization-insensitive (the incompatible flag `0x8`, which a case-insensitive volume also implies: `incompat & (0x1|0x8)`), `Lookup` matches a name equal after NFD (and after full case folding when the volume is also case-insensitive), so an NFC query finds an NFD-stored name and the reverse, in the order exact spelling, then the `~raw~` alias, then the insensitive match; a case-sensitive but normalization-insensitive volume matches NFD-equal names only, without case folding; a normalization-sensitive volume is exact. A lookup searches the B-tree by hash (the records of one hash are adjacent); when that run holds the exact name the lookup ends there, so an exactly spelled query reads fewer bytes than listing the directory and can find an entry past the 262144-entry listing cap. An exact name is never taken to be absent, and never answered with another file: a record stored under a wrong hash is not in the run, so when the run holds no exact name (nothing, an alias, or only a case/normalization-insensitive neighbour) the directory is scanned for an exact name before any other match is accepted (`/Foo` plus a bad-hash `/foo` on a case-insensitive volume: `Lookup(foo)` returns `foo`, not `Foo`).
