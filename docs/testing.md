# Testing

## Check forms
Two whole-suite forms (the per-task AFFECTED form follows below): FAST, `CGO_ENABLED=0 go run ./tools/check` (no `-race`; must print `CHECK PASSED`; it uses Go's test cache, so unchanged packages print `(cached)` and the cache invalidates on any source, dependency, environment or opened-file change; for a full uncached fast run use `go clean -testcache` first), and RACE, plain `go run ./tools/check` on a machine with a C toolchain (REQUIRED before a plan merges to main; it runs every test uncached, `-count=1`). The RACE test step is split in three, because `internal/evidence` and `internal/records` exceed the 30 minute per-package timeout under `-race` (modernc sqlite instrumented for the race detector is very slow; no test hangs): (1) `go test -count=1 ./...` without `-race`, so every test runs; (2) `go test -race -timeout 30m` on every other package (listed at run time with `go list`); (3) `go test -race -timeout 30m -run` an explicit anchored list of the concurrency tests of those two packages (`raceConcurrencyTests` in `tools/check/main.go`; the check fails if a listed name matches no test). Both must pass where they apply.

Three ways to run the check, every `go test` step with an explicit `-timeout 30m`:
- Per-task commits: AFFECTED, `CGO_ENABLED=0 go run ./tools/check -affected -base <BASE>` (agents: `bash .superpowers/sdd/check.sh -affected -base <BASE>`, BASE from the brief, so a main merged in counts as changed; without `-base` it is `git merge-base HEAD main`; a base starting with `-` is refused and git gets it after `--end-of-options`). The check fails closed: it may test more than needed, never less, and nothing is dropped silently. The changed set is `git diff --name-only <base>` (committed, staged and unstaged) plus the untracked files that are not ignored; a failing git call is an error, never an empty set. A changed file belongs to its NEAREST ANCESTOR package directory (so `fixtures/`, `schema/` and `testdata/` under a package count for it). The affected packages are those plus every package that reaches one through Imports, TestImports or XTestImports, transitively; they get `go vet` and `golangci-lint run`. The TEST step depends on what changed. If only `.go` files changed: `go test -short` (cached) on the affected packages (the reverse closure). If ANY non-`.go` file changed (testdata, fixtures, docs, `CLAUDE.md`, anything), or a `.go` file under a `testdata/` directory or one that belongs to no package: `go test -short -timeout 30m ./...` with the cache on, in place of the scoped test step. Every run prints "changed files mapped to no package:" and the `-list` output says which test form runs and why. The race detector and `-affected`/`-block` exclude each other (the race gate is always the full form; the per-task check runs with `CGO_ENABLED=0`).
- Data-file changes rely on Go's test cache: it records every file and environment variable a test opens or reads (through the `os` package) and reruns a cached result exactly when one of them changed, so the cached `./...` run reruns only the tests that read the changed file, in whichever package they live (a package reading another package's `testdata/` included), plus the reverse closure of changed Go packages. Limitation: a test that reads a file outside the module, or through a non-`os` API (for example a memory-mapped file opened by another library), is not tracked by the cache. A data change that such a test depends on needs the full form, and the builder must say so in the report.
- Global block, on every `-affected` and `-block` run, so a run can never pass having run nothing: `go mod tidy -diff`, `tools/parserhash -check`, `go build ./...`, the build-tag vets (`scaleVet`, `realdataVet`, `realimagesVet`), the host build of `cmd/minutiae` and the two `CGO_ENABLED=0` cross-builds, and `go test -short` of the packages that check the repository as a whole: `internal/archtest` (repo-wide source scans) and `tools/check` (its test reads this file). The table is `docConsistencyPackages` in `tools/check/plan.go`. The run prints every package it tested.
- Escalation to the full form (the reason is printed): a change to `go.mod`, `go.sum`, `.golangci.yml`, anything under `tools/check/`, a `.go` file whose `//go:build` line or file name names cgo, unix, a GOOS or a GOARCH (a deleted file is read from the base with `git show`), or a deleted package directory.
- Blocks, `-block <name>` (repeatable; plus the global block; an unknown name is an error listing the valid ones): `acquisition` (`internal/android`, `ios`, `device`, `transport`, `protocol`), `image` (`internal/image`, `volume`), `filesys`, `sqlite` (`internal/sqlitefile`, `dbrecover`), `parsers` (`internal/parse`, `parsers`, `decode`, `artparse`, `recordtypes`), `case` (`internal/evidence`, `records`, `examine`, `version`), `cli` (`internal/cli`, `cmd`), `tools` (`internal/archtest`, `tools`); the table is `blocks` in `tools/check/plan.go`, and every package is in exactly one (`TestEveryPackageIsInExactlyOneBlock`).
- `-list` prints the changed files, the files mapped to no package, the affected packages with their blocks and the steps, and exits 0 without running anything. Run it directly, `CGO_ENABLED=0 go run ./tools/check -affected -base <BASE> -list`, not through `check.sh`, which would queue it behind the machine-wide lock for nothing.
- Merge gate: RACE, `check.sh --race`, the whole suite, uncached, never `-short`. The full form (no flag) never passes `-short` either.

## Rules and fixtures
- Check modes: per-task commits use the AFFECTED check (see "Check forms"); the whole-suite FAST check (`CGO_ENABLED=0 go run ./tools/check`, no `-race`) uses the test cache; the RACE check (plain `go run ./tools/check`: all tests without `-race`, then `-race` on all packages but `internal/evidence` and `internal/records`, then `-race` on the named concurrency tests of those two; 30 minute package timeout) is required before a plan merges to main and runs every test uncached (`-count=1`) (CLAUDE.md, Definition of done).
- TDD: write the failing test, see it fail, implement, see it pass.
- Default tests never need hardware: use fakes (fake ADB server, in-memory serial, fake iOS).
- Hardware tests use `//go:build hardware` and are run manually: `go test -tags hardware ./...`.
- Scale and performance (plan 5D): every scale run and benchmark goes through `bash .superpowers/sdd/heavy.sh` (the machine-wide check lock, foreground, at most 240 minutes) with `MINUTIAE_SCALE_DIR` under the session scratchpad; `go test -tags scale -run TestScale ./internal/records/` needs `MINUTIAE_SCALE_LABEL`, `MINUTIAE_SCALE_MACHINE` and `MINUTIAE_SCALE_DIR`, its phases are split across runs, and `tools/check` only vets (compiles) it, in the global block of every plan (guard: `TestEveryPlanVetsTheScaleTag`). The OS temp directory is part of what is measured (ruling D46): `TMP`, `TEMP` and `TMPDIR` must point to a directory under `MINUTIAE_SCALE_DIR` but outside `clean/` and `mut/` (the run refuses otherwise), and `GOTMPDIR` to another directory, so the Go build does not write into it; a sub-phase name `<parent>/<table>/<step>` (the P11 compare steps) is nested inside its parent, so the harness sums only the names without `/` into `other` (`TestTopLevelPhaseSumSkipsSubPhases`; the sub-phases themselves are pinned by `TestVerifyFTSCompareSubPhasesAreTimed`); the `ingest`, `reindex` and `verify` phases list it before and after and fail on any difference, and record the peak resident memory of the process (`peak_rss_<phase>_bytes`; `reindex` is a mutating phase of the copy, like `supersede`, `tamper` and `tamper64`). The `tamper64` phase alters one record in each of `MINUTIAE_SCALE_TAMPER_BATCHES` (default 64, the localization bound) audited batches of a pristine copy and records the verify time, the problems and the not-localized lines; the `probes` phase times the bounded probes of a search page on a case it only reads. `BenchmarkIngest`, `BenchmarkOpenArtifact` and `BenchmarkReadRunLines` run with `go test -run '^$' -bench . ./internal/records ./internal/evidence`. Every recorded number lives in `docs/performance.md`. Default tests assert no duration of their own making (work is bounded with counters); the timing assertions already on main from 5C are listed in `docs/limitations.md`. Parse scale (plan 4H, risk R8): `go test -tags scale -run TestScaleParse ./internal/artparse/` runs ONE phase per process, chosen by `MINUTIAE_SCALE_PHASE` (`gen`, `decode-200m`, `decode-1g`, `ingest-200m`, `jobs-500`, in that order; `gen` needs about 1.5 GiB and the runs about 4 GiB under `MINUTIAE_SCALE_DIR`, and `MINUTIAE_SCALE_GEN=200m` limits `gen` to the small input), with `MINUTIAE_SCALE_DIR`, `_LABEL` and `_MACHINE` as above and the result in `<dir>/parse-results/<label>/<phase>.json`. It is not a default test and `tools/check` only vets it; `TestScaleParseSmoke` (same tag, 2 MiB) proves the harness works. The in-memory phases assert peak resident memory at most input size plus twice `MemBudget`; `decode-1g` and `jobs-500` run with a 256 MiB budget and assert at most 512 MiB; on a platform that cannot read the peak (`peakrss_other_test.go`) the phase skips with "peak RSS not measured on this platform" and never passes silently. The scale directory holds several GiB of generated inputs and cases and must be deleted after a run; peak memory includes the phase setup (capture, generation), so it is an upper bound. `TestRSSVerdict` pins the three outcomes of the memory assertion. Numbers: `docs/performance.md`.
- Real data (`realdata`, plan 4H): `internal/parsers/realdata_test.go` and `internal/cli/realdata_test.go` (`//go:build realdata`) run the fifteen registered parsers and the iOS backup path over examiner-supplied or public-test-image data read from `$MINUTIAE_TEST_DATA`; unset, every test SKIPs with `MINUTIAE_TEST_DATA is not set`. It is an OPERATOR step, never a gate and never part of `tools/check`, which only vets the tag (`go vet -tags realdata ./internal/parsers/... ./internal/cli/...`, guard `TestEveryPlanVetsTheRealDataTag`). Layout: `$MINUTIAE_TEST_DATA/parsers/<parser name>/<set>/` holds the database under its device base name (`mmssms.db`, `calllog.db`, `contacts2.db`, `sms.db`, `CallHistory.storedata`, `AddressBook.sqlitedb`, `History`, `History.db`, `calendar.db`, `Calendar.sqlitedb`; the table is `realDataInputs`); for the iOS WhatsApp parsers the database is `ChatStorage.sqlite`, `CallHistory.sqlite` or `ContactsV2.sqlite` with the optional `.com.apple.mobile_container_manager.metadata.plist` (role `container_meta`), its `-wal` and `-journal`, for `ios.addressbook` also `AddressBookImages.sqlitedb[-wal]`, and an optional one-line file `logical` that overrides the logical path (a legacy `call_history.db`); `$MINUTIAE_TEST_DATA/ios-backup/<set>/` holds one unencrypted or encrypted backup directory as the device wrote it. A parser directory with no sets is a skip naming it; a directory that names no registered parser, an unknown top-level directory or a set without its database file FAILS, so a typo is never a silent skip; these layout rules and the table check (`TestRealDataLayoutRefusesUnknownParserDirectory`, `TestRealDataLayoutRefusesSetWithoutDatabase`, `TestRealDataInputsCoverTheRegistry`) run in the DEFAULT build (`internal/parsers/realdata_inputs_test.go`). The command line tests keep their own copy of the table (`realCLIInputs`, `internal/cli/realdata_inputs_test.go`), also in the DEFAULT build, and `TestRealDataCLIInputsCoverTheRegistry` keeps it in step with the registry (plan 4I task 17 found it missing both WhatsApp parsers). Command: `MINUTIAE_TEST_DATA=<dir> go test -tags realdata -run RealData -v ./internal/parsers/ ./internal/cli/`. `TestRealDataParsers` asserts per set: Probe `applicable` (for Safari and the iOS parsers this is the from-memory schema check against a real database), a lenient run with no rejection, error or broken rule, `parsertest.AssertDeterministic`, every `Range` inside its artifact, every `sqlite:table=..;rowid=..` locator re-resolving to the same row, and for each claimed table that records plus counted row warnings equal `SELECT count(*)` of a copy read by the independent engine; it logs a schema report (real columns the mapping does not read, mapped columns the database lacks) and the job notes. `TestRealDataTypedRecovery` runs the typed pass (no panic, no live `Emit`, every row mapped or reported unmapped, typed plus unmapped plus skipped equals the claimed history rows). `TestRealDataEndToEnd` captures a set whose parser has no primary glob matching `ios:MediaDomain/<remote path>` (the three iOS WhatsApp parsers, whose databases live in an app-group domain, and `ios.calendar`, whose database is in `HomeDomain`) as an unencrypted one-set backup of its own domain (`captureAsBackup`: `ios.backup` acquisition, each file a `backup` artifact at `D1/<aa>/<fileID>`, a `Manifest.db` listing them, `Manifest.plist` and `Status.plist`; plan 4I2-P9) and logs which route it used; every other set stays device files. `TestRealDataEndToEnd` (per set) and `TestRealDataIOSBackup` (per backup) run `parse plan`, `parse run`, `sqlite recover` or `parse recover`, and `case verify` through the command line: no exit 4 anywhere, `case verify` exit 0, exit 1 only with its reasons logged, after `sqlite recover` every typed recovered record read back from the case is deleted, recovered, has a recovery method and a confidence within 0 to 100 (the method's own cap is not reachable from the test) and none is in the live view (`records list --recovered none`), and an encrypted backup ends unparsed with its reason, never exit 0 with nothing. The logs name tables, columns, counts and reasons, never cell contents. A result is recorded by hand in `docs/limitations.md` ("Real-data runs"); a finding becomes a synthetic variant (spec 10.4), and real data, evidence and device dumps are never committed.
- Real device samples for recovery (`realimages`, plan 3K): `internal/cli/realimages_recovery_test.go` (`//go:build realimages`) runs the recovery commands over examiner-supplied Android and iOS images and databases read from `$MINUTIAE_TEST_IMAGES` (the variable of the APFS, HFS+ and EWF harnesses); unset, every test SKIPs with `MINUTIAE_TEST_IMAGES is not set`. It is an OPERATOR step, never a gate and never part of `tools/check`, which only vets the tag (`realimagesVet`: `go vet -tags realimages ./internal/image/ewf/... ./internal/filesys/apfs/... ./internal/filesys/hfsplus/... ./internal/cli/...`, guard `TestEveryPlanVetsTheRealImagesTag`). Two layouts: `recovery/<name>.<img|img.gz|E01>` with `<name>.expect.json` (a device image: Android `userdata` ext4 or F2FS, or iOS APFS for carving) and `recovery-db/<set>/` with `expect.json`, the database and its optional `-wal` and `-journal` (including `secure_delete` databases). The expect files are decoded strictly (an unknown key is an error), and the layout rules run in the DEFAULT build (`internal/cli/realimages_layout_test.go`): `TestRealImagesRecoveryRootInsideRepoIsRefused` (a root inside the repository fails at once), `TestRealImagesRecoveryLayoutRefusesTypos` (an unknown key, an image without its expect file, an expect file without its image or database, an empty `steps`, a step that declares no min, max or constraint, a stray file: each is an error naming the entry by its position and kind, never its file name and never a silent skip), `TestRealImagesRecoverySHA256CheckedFirst` (the sample's bytes must equal `image_sha256` or `db_sha256` before any command runs) and `TestRxBound`. Per image set the test imports the image, checks `fstype` against `image info`, runs the steps present (recover, use_journal, rollforward, journal, carve, slack, in that order), counts the artifacts each added by a manifest diff and checks them against the expectation's bounds, then `case verify` must exit 0; no command may exit 4, and exit 1 is accepted only with the recover commands' own `undecided N (not recovered` line or "does not support recovery". Per database set it runs `sqlite recover` and checks `written`, per-method rows and `freelist_pages_zeroed`. Subtests are numbered and the logs carry exit codes, counts, methods, classes and types only: never a path, a file name or command output of a sample, which may be personal data. Samples live outside the repository and are never committed. Command: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages ./internal/cli -run TestRealImagesRecovery -v`; the layout and a worked example are in `tools/fixtures/README.md`. No run on a real device is recorded (`docs/limitations/recovery.md`, "Real-device outcomes").
- Recovery acceptance (plan 3K, `tools/recoveryaccept`): `CGO_ENABLED=0 go run ./tools/recoveryaccept` (from the module root; flags `-dir`, `-bin`, `-keep`, `-verbose`) is the hardware-free run of every recovery command. It builds `cmd/minutiae` (or takes `-bin`) and runs it as a subprocess, so the exit codes and outputs are what an examiner sees, over gunzipped copies of seven committed fixtures (`fat16-recover`, `ext4-recover`, `f2fs-recover-nodiscard`, `carve-fat12`, `fat16-slack`, `ext4-journal-crash`, `f2fs-rollforward`) imported into ONE case. Its 21 steps are `case new`, seven imports (each image's hash is compared with its oracle's `image_sha256` first: "fixture and oracle differ"), `image recover --all` on the FAT, ext4 and F2FS images, `image carve` (a new artifact must carry the sha256 of the oracle's deleted, validated `sqlite` object, which then goes through `sqlite recover`: the database input is recovered and its confidence cap is at most 70), `image slack`, `image journal report` and `blocks` and `recover --use-journal stale` on the ext4 journal image, `image journal report` and `recover --rollforward --all` on the F2FS image, `case verify` (exit 0, no `PROBLEM:`) and, after one byte of a recovered artifact is flipped, `case verify` again (exit 4). Each step pins its exit code from the fixture's oracle (a recovery step is 1 only when its oracle has `totals.undecided > 0`, and none of these has) and requires at least one new artifact of the expected kind, class and method. This is smoke and integrity, never oracle equality: that stays with the per-fixture tests. An observed exit code that disagrees with the pin is a finding to report, never a reason to edit the table. Scratch rule: the tool refuses (exit 2, before writing anything) a `-dir` that resolves outside the project or under a `cases` directory, a `-bin` that is not a regular file and a working directory without this module's `go.mod`; it makes `<dir>/accept-<unixnano>-<pid>` (default `<root>/.claude/scratch`) with `os.Mkdir`, never reuses or removes a directory it did not create, and removes that directory (and a parent it had to create) on every exit path: success, a failed step, an interrupt (the child and what it started are killed) and a panic, unless `-keep` prints the path and keeps it (delete it by hand). The gunzipped images (317 MiB) and their copies in the case need about 700 MiB of scratch space. `TestAcceptanceEndToEnd` runs it from `t.TempDir()` in about 11 s and skips under `-short`, so the FAST and RACE forms run it and the AFFECTED form does not. Run it before a release; it needs the Go toolchain on `PATH` and no Docker, hardware or network.
- The `case verify` status line and outcome line (plan 5D, Task 14e) are tested without a console: `renderStatus` and `startStatus` take synthetic `VerifyProgressSnapshot` values, a fixed `now` and a manual tick channel (no clock and no sleeps decide a result), and the CLI tests force the display with `Deps.ErrTerminal` (`TerminalOn` or `TerminalOff`; the zero value `TerminalAuto` detects a console, which no test can fake, so `TestIsTerminalFalseForPipeAndBuffer` covers the negative side and the platform probes are covered by the three cross-builds). The tests compare stdout of a display-on run with a display-off run on a copy of the same case (`os.CopyFS` before either run, because a verify audits itself).
- Parsers have synthetic in-memory builders (`volumetest`, `fstest`) and fuzz targets; fuzz seeds run under `go test`, and the time-boxed runs are `tools/fuzzcampaign` campaigns (see "Fuzz campaigns"). Fuzz seeds must be small (each file at most 64 KB, and a hand-built minimal seed plus a WAL seed where the format has one): every execution of a parser target builds a case, so a seed of hundreds of kilobytes drops the target to under one execution a second and the fuzzer explores nothing (T59); large fixtures stay ordinary tests. Parser targets also fuzz the row mapping on decoded column values directly (`FuzzMapRows` in `internal/parsers/androidmms`).
- Large fuzz seeds (LX-7a, ruling Z60): `FuzzF2FSOpen` and `FuzzExt4Open` are seeded with whole filesystem images, which breaks the 64 KB rule above on purpose: a Linux-made F2FS image has a 16 MiB metadata area before its main area, so its seeds are cut after the last used block (`fuzzSeedMax` 23 MiB each, `fuzzSeedBudget` 84 MiB for F2FS; 4 MiB for the casefold ext4 image, 64 MiB budget for ext4), and the engine panics ("value length larger than shared memory capacity") when the set passes 100 MiB, which `TestFuzzF2FSOpenSeedsFitTheEngine` and `TestFuzzExt4OpenSeedsFitTheEngine` guard. The cost is throughput and mutation quality, measured with `heavy.sh` over 30 s: `FuzzF2FSOpen` 181,492 execs on 85,620,306 bytes of seeds, `FuzzExt4Open` 6,537 execs (it also lists and opens attributes, each hashed whole). A mutation of a mostly-zero 20 MiB input rarely lands on metadata, so these targets are weaker than their size suggests, and run them with `-parallel 2` to `4` (each worker holds seed-sized inputs). The remedy, not yet done, is an edit-list seed: store a small base image and a list of (offset, bytes) edits that the target applies before opening, so the corpus entries stay a few kilobytes and every mutation lands in live metadata.

Five images are empty volumes made by `mkfs.hfsplus` (`hfsplus-empty`, `hfsx-empty`, `hfsplus-journal`, `hfsplus-1k`, `hfsplus-wrapped`; byte-identical on every regeneration). The sixth, `hfsplus-populated` (16 MiB), is filled by the Linux `hfsplus` kernel driver: the Debian bookworm kernel (`linux-image-6.1.0-53-amd64`, module `hfsplus`) is booted under QEMU software emulation (TCG, no `/dev/kvm`, about 20 s per guest run, 65 s for the whole script) because Docker Desktop's own kernel has no `hfsplus` module. Oracles come from a second Python parse, `fsck.hfsplus`, `blkid` and, for the populated image, the source tree, never from Minutiae. The fixture-level HFS+ e2e tests (`internal/examine`) are skipped under `-short` (the populated subtest takes 60-100 s on a loaded machine). The reader's builder images are additionally checked by `fsck.hfsplus` (12 of 15 pass, 3 exempt with recorded reasons: `MINUTIAE_WRITE_BUILDER_IMAGES=<dir> go test -run TestBuilderImagesPassFsck ./internal/filesys/hfsplus`, then `hfsplus.sh check-builder <dir>` in the fixture image). Volumes written by macOS or iOS can be read manually: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages ./internal/filesys/hfsplus` reads `<dir>/hfsplus/*.hfs`, `*.hfsplus` and `*.img` (see `TestRealHFSPlusImages`); see "HFS+ fixtures" in `tools/fixtures/README.md`.

## Fuzz stall findings (LX-8 Task 1, 2026-10-17)
Why `go test -fuzz` of `FuzzSQLiteDB` (and other targets) shows `0/sec` for most of a run. Measured on Windows 11, go1.26.8 windows/amd64, 12 CPUs, 15.4 GB RAM, CGO_ENABLED=0, main c8e5122 (3J merged); Linux in Docker Desktop 29.7.2 (VM 8.0 GB, 12 CPUs), image `golang:1.26.8@sha256:eb36c1664dd974cde625f736e02c204383deebe03977365caaec5bf49f794348` (`go version` there: go1.26.8 linux/amd64), `--cpus 2 --memory 4g --network none`, a `git archive` copy, fresh fuzz corpus (seeds only). Every run was 40 s of `-fuzztime`. What the numbers show:
- During the stall the body keeps running; only the counter is frozen. In the counted `FuzzSQLiteDB` run the reported execs reached 4608 at elapsed 26 s and stayed there (0/sec from 29 s, as in the table) while the sampled body count rose from 9473 (wall 33 s) to 42441 (wall 53 s), about 33000 runs or 1650 per second (wall time includes a build of about 7 s before the engine's clock starts). `FuzzFATOpen` shows the same (15883 reported, 56330 body). With `-fuzzminimizetime 0s` the two agree to within 0.5 percent (7933 against 7970; 47046 against 47126). The engine's counter therefore does not include the work done while the stall lasts. This was measured on Windows only: no body count was taken on Linux, where the same 0/sec is reported but whether the body runs meanwhile is not known.
- The stall ends when minimisation is switched off: `-fuzzminimizetime 0s` restores a normal rate for `FuzzSQLiteDB` on Windows (E3 9289/sec, E4 3615/sec) and on Linux (2888/sec), and it makes "new interesting" grow (E1 0 against E3 374 and Linux 0 against 793). That the extra body runs belong to the minimiser of a newly interesting input is an inference from this flag effect and from the 60 s default `-fuzzminimizetime` outlasting a 40 s run; the minimiser itself was not observed. The control target `FuzzResolveChain` shows short 0/sec windows too, so this is the engine's behaviour, not something particular to the SQLite bodies.
- Linux reproduces it (E5: 56 execs, 0/sec), so it is not Windows-only.
- The `FuzzSQLiteDB` body is cheap per input (seed times above), so its cost is not the cause. The default-flag runs started from a corpus of 860 entries on Windows (54 seeds plus earlier cached inputs; E1 and E2 added none, E3 grew it to 1234, E4 started from 1234, the counted runs from 1277); the Linux runs started from the 54 seeds. Only E1, E2 and E3 share the 860 starting corpus, so the E3 against E4 comparison (and the other Windows rows after E3) and every Windows against Linux comparison are qualified: the corpora differ. The within-run observations (counter frozen, flag restores the rate) do not depend on it.
- The runs overran `-fuzztime 40s`: the Windows and Linux wall times were 49 to 134 s. The build and the baseline phase (up to 57 s) run outside `-fuzztime`, which accounts for the overrun; the runs that stalled and the runs that did not are spread across that range (the unstalled counted `-fuzzminimizetime 0s` run took 126 s, a stalled one 56 s, Linux E5 134 s), so whether minimisation adds time beyond `-fuzztime` is not shown. A campaign's deadlines must allow for the overrun. The rate of the counted `-fuzzminimizetime 0s` run (222/sec, after a 57 s baseline phase that took 16 s in the other counted run) is far below E3 (9289/sec) for a reason not found (machine load or the instrument); it is used only for the body-against-counter agreement, not for any rate claim.

Outcome, by the plan's rules: **D-A holds** (the reported counter is not the work: the body count grows while the rate is 0, on Windows). **D-B holds in its effect and not in its literal test**: `-fuzzminimizetime 0s` restores a non-zero rate, but the body count was not flat, because the work during the stall is the invisible minimisation. **D-E is refuted** (Linux stalls the same way and recovers with `-fuzzminimizetime 0s`). **D-C is refuted for `FuzzSQLiteDB`** (median seed time at most 0.01 s, none above 100 ms, and 2888/sec on Linux without minimisation), so no split of `FuzzSQLiteDB` is called for and LX-4 Task 12 is not triggered. Consequences for the plan: a reported rate of 0 is never read as "ok"; campaigns run the targets with `-fuzzminimizetime 0s` (Task 3). Not decided by these runs: `FuzzRun`. Even with minimisation off its rate is 16 to 20/sec on Windows (12 workers) and 4 to 6/sec on Linux (2 workers), so a per-input cost is suspected for `FuzzRun` in `internal/dbrecover` (a hypothesis: no seed times were measured, so D-C is neither shown nor refuted for it). `FuzzOpen` (`internal/sqlitefile`) was not measured.

## Fuzz campaigns
`tools/fuzzcampaign` (L120, plan LX-8) runs the repository's fuzz targets as a time-boxed, bounded campaign. It is run by hand through `heavy.sh` before a release and is not part of the check. It finds the targets itself (every top-level `Fuzz*` function taking only `*testing.F` in a `*_test.go` file that builds for linux/amd64 without cgo), selects them by profile (`decoders`, `readers`, `parsers`, `all`, optionally narrowed by `-pkg` path prefixes) and runs each as `go test -run=^$ -fuzz=^<Name>$` with the fuzz time, `-parallel`, the minimisation time and a `-timeout` ten minutes above both, in its own process group.
- `FuzzCarve` (`internal/carve`, plan 3E) is in the `readers` profile; its committed seeds under `internal/carve/testdata/fuzz/FuzzCarve` (builder outputs and the real objects, each at most 64 KB, generated from the same corpus as `TestCarveValidatorsBounded`) also run as `TestFuzzCarveSeedsRun` in the ordinary check.
- Subcommands: `plan [-list]` prints the plan and its estimate (or only the selection); `run -out DIR -mode docker|host`; `prepare -image I -out DIR` downloads, with the network and only then, the modules the selected packages compile (`go list -deps -test` piped to `go mod download`), so `-profile parsers` and `-profile readers` each need their own `prepare` run. Host mode is refused on Windows (the exec counter stalls there, see "Fuzz stall findings"); on Windows use docker mode and Windows-form paths (a Git Bash path such as `/c/work` is refused).
- Docker mode: the image is pinned by digest in `tools/fuzzcampaign/Dockerfile` (`FROM golang:<go.mod toolchain>@sha256:<digest>`, tied to go.mod's toolchain by `TestDockerfilePinsTheBaseImage`, so a toolchain bump fails until the digest is bumped in the same commit); the tool checks `go version` inside the image against go.mod before it starts, in a container of its own (`--rm`, a numbers-only name, `--network none`, 1 GiB, one minute, killed by name on the deadline or an interrupt). An `-image` that begins with `-` is refused, since `docker run` has no `--` and the word would be read as an option. The container runs with `--memory 4g --memory-swap 4g --cpus 2 --pids-limit 1024 --network none`, `GOPROXY=off`, no privilege, capability, device, port or extra mount; the source copy and the tool are mounted read-only and the output directory is the only read-write bind. The module and build caches live under `<out>/.cache` (inside that one bind, so nothing large is written into the container or a Docker volume). The tool kills and removes the container by its recorded name (`minutiae-fuzz-<unix seconds>-<pid>`, numbers only) on the deadline, on interrupt and on every exit path.
- What it never touches: it fuzzes a throwaway copy, never the working tree. In a git tree the copy holds only the tracked files (`git ls-files -z`), so an untracked `cases/`, dump or scratch directory never reaches a container; `.git`, `bin`, `cases`, `.superpowers`, `docs/superpowers`, `*.exe` and symlinks are skipped in any case, and a copy over 2 GiB is refused, and so is one of more than 200000 entries (files, symlinks and, in a tree that is not a git tree, directories; its own error) (each file is copied by its checked size; a file that grew or shrank meanwhile is an error). `-out` inside the source, under any `cases` directory or equal to the work copy is a usage error, also when it reaches those through a symlink or junction: the deepest existing ancestor is resolved first, and every existing ancestor of `-out` is also compared by identity (`os.SameFile`, which follows a Windows junction that `EvalSymlinks` does not resolve) with the source root, the work copy and the `cases` directories in and beside the source. On Windows the final path of the deepest existing ancestor is also taken from the OS (`GetFinalPathNameByHandle`, extended prefix removed) and checked by containment, so a junction into a subdirectory of the source is refused too. The repository's own `testdata/fuzz` corpora are never written.
- Caps: fuzz time 10 s to 15 min per target (default 120 s; a stall cannot be seen below about 16 s), minimisation 0 to 60 s (default 10 s; `FuzzSQLiteDB` and `FuzzFATOpen` run with 0, see "Fuzz stall findings"), total 10 to 240 min (default 90), parallel 1 to 4 (default 2), a log of at most 8 MiB per target (lines past it are counted, still parsed for progress, and a `[log truncated]` line closes the file), and the fuzz corpus cache pruned after each target to 2000 files and 64 MiB. A plan whose estimate exceeds the total is refused, never shortened.
- Outcomes and exit codes: `ok`, `failed` (a failing input or a non-zero exit), `stalled` (five or more progress lines with an unchanged non-zero execution count over at least 12 s), `no-progress` (the engine never reported an execution: a reported rate of 0 is never ok), `timeout`, `build-failed`, `skipped` (the campaign deadline). Exit 0 only when every target is `ok`; any other outcome, a finding, a skipped target, the deadline or a docker failure is exit 1; a usage error is 2. A failing input is copied byte for byte to `<out>/findings/<pkg>/<Name>/` with a README holding the re-run command and is not fixed by the campaign. `results.json` and one log per target are written under `<out>`. `results.json` is rewritten atomically after every target, so a container that dies still leaves the finished ones; its temporary file is removed on any write failure, and a write error is exit 1. A plan that selects no target is refused before the run. After an interrupt the targets not yet started are `skipped` with the note `cancelled`. A target that reported new interesting inputs but has no corpus cache directory fails with a note (the cap was not enforced).
- `-out` must be a local directory: a UNC path (`\\host\share\...`, also `\\?\UNC\...`), a path that resolves to one, and a path none of whose ancestors can be resolved to a final path are refused (fail closed), since identity cannot be compared across a share (`TestIsUNC`, `TestOutDirOnAUNCPathOrAnUnresolvableDriveIsRefused`). Residual: a reachable share cannot be tested without admin rights or a real share, so the UNC test uses `\\localhost\C$` and unreachable hosts; `TestIsUNC` pins the lexical refusal on its own.
- One campaign per `-out`: a second `run` into the same `-out` is refused ("copy destination is not empty": `<out>/src`, `<out>/work`, the logs and `results.json` stay, and logs are never overwritten). Use a new `-out` and a new `prepare` (the caches are under `<out>/.cache`), or delete everything in the old `-out` except `.cache` first.
- Docker Desktop is the user's: the tool starts and stops nothing but its own container. To wipe what a campaign left, delete its output directory (the caches are under `<out>/.cache`).

## Release build
```bash
# Default release: pure Go, static, no C dependency, any OS.
CGO_ENABLED=0 go build -ldflags "-X github.com/rbenzing/minutiae/internal/version.Version=v1.0.0 -X github.com/rbenzing/minutiae/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/minutiae.exe ./cmd/minutiae
# cgo-capable build (per OS, needs a C toolchain; only once a cgo capability exists, see the cgo policy (docs/architecture.md)).
CGO_ENABLED=1 go build -ldflags "-X github.com/rbenzing/minutiae/internal/version.Version=v1.0.0 -X github.com/rbenzing/minutiae/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/minutiae-cgo.exe ./cmd/minutiae
```
Run `go run ./tools/check` before a release build: it verifies the generated parser identities (`internal/parsers/identity_gen.go` against `parsers.lock`, `tools/parserhash -check`), which a plain `go build` does not.
