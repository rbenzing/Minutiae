# Testing

## Check forms
Two whole-suite forms (the per-task AFFECTED form follows below): FAST, `CGO_ENABLED=0 go run ./tools/check` (no `-race`; must print `CHECK PASSED`; it uses Go's test cache, so unchanged packages print `(cached)` and the cache invalidates on any source, dependency, environment or opened-file change; for a full uncached fast run use `go clean -testcache` first), and RACE, plain `go run ./tools/check` on a machine with a C toolchain (REQUIRED before a plan merges to main; it runs every test uncached, `-count=1`). The RACE test step is split in three, because `internal/evidence` and `internal/records` exceed the 30 minute per-package timeout under `-race` (modernc sqlite instrumented for the race detector is very slow; no test hangs): (1) `go test -count=1 ./...` without `-race`, so every test runs; (2) `go test -race -timeout 30m` on every other package (listed at run time with `go list`); (3) `go test -race -timeout 30m -run` an explicit anchored list of the concurrency tests of those two packages (`raceConcurrencyTests` in `tools/check/main.go`; the check fails if a listed name matches no test). Both must pass where they apply.

Three ways to run the check, every `go test` step with an explicit `-timeout 30m`:
- Per-task commits: AFFECTED, `CGO_ENABLED=0 go run ./tools/check -affected -base <BASE>` (agents: `bash .superpowers/sdd/check.sh -affected -base <BASE>`, BASE from the brief, so a main merged in counts as changed; without `-base` it is `git merge-base HEAD main`; a base starting with `-` is refused and git gets it after `--end-of-options`). The check fails closed: it may test more than needed, never less, and nothing is dropped silently. The changed set is `git diff --name-only <base>` (committed, staged and unstaged) plus the untracked files that are not ignored; a failing git call is an error, never an empty set. A changed file belongs to its NEAREST ANCESTOR package directory (so `fixtures/`, `schema/` and `testdata/` under a package count for it). The affected packages are those plus every package that reaches one through Imports, TestImports or XTestImports, transitively; they get `go vet` and `golangci-lint run`. The TEST step depends on what changed. If only `.go` files changed: `go test -short` (cached) on the affected packages (the reverse closure). If ANY non-`.go` file changed (testdata, fixtures, docs, `CLAUDE.md`, anything), or a `.go` file under a `testdata/` directory or one that belongs to no package: `go test -short -timeout 30m ./...` with the cache on, in place of the scoped test step. Every run prints "changed files mapped to no package:" and the `-list` output says which test form runs and why. The race detector and `-affected`/`-block` exclude each other (the race gate is always the full form; the per-task check runs with `CGO_ENABLED=0`).
- Data-file changes rely on Go's test cache: it records every file and environment variable a test opens or reads (through the `os` package) and reruns a cached result exactly when one of them changed, so the cached `./...` run reruns only the tests that read the changed file, in whichever package they live (a package reading another package's `testdata/` included), plus the reverse closure of changed Go packages. Limitation: a test that reads a file outside the module, or through a non-`os` API (for example a memory-mapped file opened by another library), is not tracked by the cache. A data change that such a test depends on needs the full form, and the builder must say so in the report.
- Global block, on every `-affected` and `-block` run, so a run can never pass having run nothing: `go mod tidy -diff`, `tools/parserhash -check`, `go build ./...`, the host build of `cmd/minutiae` and the two `CGO_ENABLED=0` cross-builds, and `go test -short` of the packages that check the repository as a whole: `internal/archtest` (repo-wide source scans) and `tools/check` (its test reads this file). The table is `docConsistencyPackages` in `tools/check/plan.go`. The run prints every package it tested.
- Escalation to the full form (the reason is printed): a change to `go.mod`, `go.sum`, `.golangci.yml`, anything under `tools/check/`, a `.go` file whose `//go:build` line or file name names cgo, unix, a GOOS or a GOARCH (a deleted file is read from the base with `git show`), or a deleted package directory.
- Blocks, `-block <name>` (repeatable; plus the global block; an unknown name is an error listing the valid ones): `acquisition` (`internal/android`, `ios`, `device`, `transport`, `protocol`), `image` (`internal/image`, `volume`), `filesys`, `sqlite` (`internal/sqlitefile`, `dbrecover`), `parsers` (`internal/parse`, `parsers`, `decode`, `artparse`, `recordtypes`), `case` (`internal/evidence`, `records`, `examine`, `version`), `cli` (`internal/cli`, `cmd`), `tools` (`internal/archtest`, `tools`); the table is `blocks` in `tools/check/plan.go`, and every package is in exactly one (`TestEveryPackageIsInExactlyOneBlock`).
- `-list` prints the changed files, the files mapped to no package, the affected packages with their blocks and the steps, and exits 0 without running anything. Run it directly, `CGO_ENABLED=0 go run ./tools/check -affected -base <BASE> -list`, not through `check.sh`, which would queue it behind the machine-wide lock for nothing.
- Merge gate: RACE, `check.sh --race`, the whole suite, uncached, never `-short`. The full form (no flag) never passes `-short` either.

### Slow tests skipped under -short
A test that takes more than 60 s starts with `if testing.Short() { t.Skip("slow (> 60 s): runs in the merge gate") }`, so the per-task AFFECTED check skips it and the merge gate runs it.
This table lists every such test with its seconds from the pass and from an isolated run. ## Rules and fixtures
- Check modes: per-task commits use the AFFECTED check (see "Check forms"); the whole-suite FAST check (`CGO_ENABLED=0 go run ./tools/check`, no `-race`) uses the test cache; the RACE check (plain `go run ./tools/check`: all tests without `-race`, then `-race` on all packages but `internal/evidence` and `internal/records`, then `-race` on the named concurrency tests of those two; 30 minute package timeout) is required before a plan merges to main and runs every test uncached (`-count=1`) (CLAUDE.md, Definition of done).
- TDD: write the failing test, see it fail, implement, see it pass.
- Default tests never need hardware: use fakes (fake ADB server, in-memory serial, fake iOS).
- Hardware tests use `//go:build hardware` and are run manually: `go test -tags hardware ./...`.
- Parsers have synthetic in-memory builders (`volumetest`, `fstest`) and fuzz targets; fuzz seeds run under `go test`, `go test -fuzz` is run manually. Fuzz seeds must be small (each file at most 64 KB, and a hand-built minimal seed plus a WAL seed where the format has one): every execution of a parser target builds a case, so a seed of hundreds of kilobytes drops the target to under one execution a second and the fuzzer explores nothing (T59); large fixtures stay ordinary tests. Parser targets also fuzz the row mapping on decoded column values directly (`FuzzMapRows` in `internal/parsers/androidmms`).
- Real-image fixtures (`*.img.gz` plus an independent oracle `*.expect.json`) are committed under each package's `testdata/`. Regenerating them needs Docker (`docker build -t minutiae-fixtures tools/fixtures`, then `gen.sh all` in the container; the exFAT fixture needs `docker run --privileged`, and the F2FS fixtures use it only to try a kernel mount; see `tools/fixtures/README.md`); running the tests never does.
- HFS+/HFSX fixtures (`gen.sh hfsplus`, output in `internal/filesys/hfsplus/testdata/`) are NOT part of `gen.sh all`: `hfsprogs` (`mkfs.hfsplus`, `fsck.hfsplus`) is not installable in the main fixture image, so they use a separate image (`docker build -f tools/fixtures/Dockerfile.hfs -t minutiae-fixtures-hfs tools/fixtures`, then `docker run --rm --shm-size=1g -v "$PWD:/work" -w /work minutiae-fixtures-hfs bash tools/fixtures/gen.sh hfsplus`; no `--privileged`) and the main image and every other fixture stay byte-identical. Five images are empty volumes made by `mkfs.hfsplus` (`hfsplus-empty`, `hfsx-empty`, `hfsplus-journal`, `hfsplus-1k`, `hfsplus-wrapped`; byte-identical on every regeneration). The sixth, `hfsplus-populated` (16 MiB), is filled by the Linux `hfsplus` kernel driver: the Debian bookworm kernel (`linux-image-6.1.0-53-amd64`, module `hfsplus`) is booted under QEMU software emulation (TCG, no `/dev/kvm`, about 20 s per guest run, 65 s for the whole script) because Docker Desktop's own kernel has no `hfsplus` module. Its regeneration is byte-identical in every run tried (15 runs, 12 of them under concurrent host load, after the guest clock is rewound to the fixture time every 0.2 virtual seconds: before that, 3 of 9 runs differed in one byte, the volume header modify date, one second late; the package set is pinned to `snapshot.debian.org` as of 2026-10-03 and exact versions in `Dockerfile.hfs`), but a different host or QEMU could in principle change the timing: regenerate it TOGETHER with its `expect.json`, never one without the other (the test checks the image sha256 against `generator.image_sha256` first, so a different regenerated image passes only with its own oracle). Oracles come from a second Python parse, `fsck.hfsplus`, `blkid` and, for the populated image, the source tree, never from Minutiae. The fixture-level HFS+ e2e tests (`internal/examine`) are skipped under `-short` (the populated subtest takes 60-100 s on a loaded machine). The reader's builder images are additionally checked by `fsck.hfsplus` (12 of 15 pass, 3 exempt with recorded reasons: `MINUTIAE_WRITE_BUILDER_IMAGES=<dir> go test -run TestBuilderImagesPassFsck ./internal/filesys/hfsplus`, then `hfsplus.sh check-builder <dir>` in the fixture image). Volumes written by macOS or iOS can be read manually: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages ./internal/filesys/hfsplus` reads `<dir>/hfsplus/*.hfs`, `*.hfsplus` and `*.img` (see `TestRealHFSPlusImages`); see "HFS+ fixtures" in `tools/fixtures/README.md`.
- EWF/E01 fixtures (`gen.sh ewf`, output in `internal/image/ewf/testdata/`): one 8 MiB GPT raw disk (`ewf-disk.img.gz`, built from the committed ext4 and fat12 fixtures) acquired with `ewfacquire` into four sets: `single-none` (one segment, uncompressed chunks), `single-best` (one segment, compressed plus a few uncompressed chunks), `multi-none` (five segments) and `seed-small` (first MiB only, the fuzz seed), each stored as one `.E0N.gz` per segment, plus `ewf-fixtures.expect.json` (the oracle from the independent Python decoder `ewf_inspect.py`, `ewfverify`, `ewfinfo` and `ewfexport`). Generation is deterministic (frozen clock; the writer emits an all-zero set identifier, and `ewf_normalize.py` pins a non-zero one as a safeguard), checked by generating twice and comparing every sha256. Regenerate with `docker run --rm -v "$PWD:/work" -w /work minutiae-fixtures bash tools/fixtures/gen.sh ewf` (not privileged, about 30 s; regenerate the ext4 and fat12 fixtures first if they ever change). The `error2` section, table base 0 and layouts the real writer does not produce are covered by the `ewftest` builder only. Real images from other acquirers can be checked by hand: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages -run TestEWFRealImages -v ./internal/image/ewf` (needs `*.E01` sets; not run by default). The EWF tests run under `-race` in the race gate (step 2; passed 2026-10-08, 0 data races) and without it in the fast check.
- APFS fixtures (output in `internal/filesys/apfs/testdata/`): three EMPTY containers built by `mkapfs` from `apfsprogs` (`apfs-ci`, `apfs-cs`, `apfs-multichunk`; `gen.sh apfs`, part of `gen.sh all`, in the main fixture image: `apfsprogs` is a last layer of `tools/fixtures/Dockerfile`, so the earlier layers and every other fixture stay byte-identical; no `--privileged`), byte-identical on every regeneration (frozen `faketime`, fixed UUIDs and label, a fresh sparse file per image, generated twice and compared inside the script), with an oracle from `apfs_oracle.py` (an independent decoder) and `apfsck`. The fourth, `apfs-populated` (`gen.sh apfs-populated`), is NOT part of `gen.sh all`: it needs the separate image `minutiae-fixtures-apfs` (`docker build -f tools/fixtures/Dockerfile.apfs -t minutiae-fixtures-apfs tools/fixtures`, then `docker run --rm -v "$PWD:/work" -w /work minutiae-fixtures-apfs bash tools/fixtures/gen.sh apfs-populated`; no `--privileged`, about 1 minute a run, the image build needs network for the pinned git clones and Debian mirrors). It is written by the real `linux-apfs-rw` kernel driver (v0.3.21 built from a pinned commit against the Debian bookworm 6.1 kernel headers) inside a QEMU software-emulation guest (TCG, no `/dev/kvm`) that boots the Debian kernel from a busybox initramfs: the module is loaded only in that guest and NOTHING is ever loaded into the host or the Docker Desktop VM kernel (an earlier attempt to load it into the Docker Desktop VM kernel failed and tainted that kernel until Docker was restarted; that route is ruled out). Its oracle, `apfs_populated_oracle.py`, decodes the finished image alone and compares it with the source tree (never with Minutiae), and `apfsck` must accept the image. The populated image is NOT byte-reproducible (five generations gave five different images: the number and timing of driver transactions under writeback differ even under emulation; the logical content, final xid and record counts were stable), so regenerate the image TOGETHER with its `expect.json`, never one without the other: every test checks the image sha256 against `generator.image_sha256` first, so a regenerated image passes only with its own oracle. A fifth container, a 17 GiB `mkapfs` container with several chunk-info blocks (`tools/fixtures/apfs-big.sh`), is NOT part of `gen.sh all`: its image is sparse, never committed and made outside the repository (the script refuses a path inside it and refuses to start without the free disk it needs), only its oracle `apfs-bigcib.expect.json` is committed, and `TestAPFSBigContainerMatchesOracle` runs on it only when `MINUTIAE_APFS_BIG_IMAGE` names the image (it SKIPS, with the command that makes it, otherwise); the image and the oracle file are regenerated TOGETHER (the test checks the image sha256 first). `go test -short ./internal/filesys/apfs` skips only the 129 MiB `apfs-multichunk` oracle test (the populated fixture still runs, about 3 s), and `TestOpenMutatedNeverPanics` mutates one block in each position instead of four. A real image written by macOS or iOS (compression, encryption, several snapshots) can be checked by hand: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages -run TestRealImages -v ./internal/filesys/apfs` reads `<dir>/apfs/<name>.img[.gz]` with a `<name>.expect.json` beside it (schema in the test file header and `tools/fixtures/README.md`; `apfs_expect.sh` writes such a file on macOS, from memory and never run); see "APFS determinism and limits", "APFS populated fixture" and "Supplying a real APFS image" in `tools/fixtures/README.md`. `apfs-reoracle.sh <outdir>` re-emits the expectation file for the committed image with the current oracle (no QEMU): it refuses an image whose sha256 differs from the old oracle and any change other than the added `xattr_values`.
- Records tests (`internal/records`, `internal/evidence`) use `recordstest` as the fixture: `NewCase`, `AddArtifact`, `AddIncompleteArtifact`, `Records` (a deterministic generator with tied and untimed timestamps, deleted and recovered records, mixed time bases and byte ranges), `Ingest` and `NewV1Case`/`NewV1CaseWithRecord` (a frozen v1 database, tied to the migration code by `TestRecordstestV1DDLMatchesEvidence`). Named-tamper-helper rule: every way a test damages a case lives in `recordstest/tamper.go` (records and database tamper) or `evidencetest/tamper.go` (manifest and artifact-file tamper for tests of `internal/evidence` and above, where `recordstest` would make an import cycle) as a helper named for what it does (`SetRecordSummary`, `DeleteBatch`, `RepointRecord`, `RemoveArtifactEverywhere`, `RewriteArtifactConsistently`, ...), opens the database with `foreign_keys=OFF`, drops the immutability triggers, tampers and RE-CREATES the triggers from the expected DDL, so the problem under test is the only one left. Helpers that deliberately leave damage behind say so in their name (`DropImmutabilityTriggers`, `DropTrigger`, `ReplaceTrigger`, `DropTable`). A tamper test asserts its SPECIFIC problem text (and that no other kind of problem appears), never only "not OK" or exit 4. Raw row inserts for evidence-internal tests live in `internal/evidence` `_test.go` files. `FuzzCursor` and `FuzzValidateRecord` are the records fuzz targets, and `FuzzCheckReadSQL` (the lexical read guard: no panic, an accepted statement starts with SELECT or WITH and compiles to bytecode that opens nothing for writing) and `FuzzDecodeDetails` (audit details of any shape never panic and decode and re-encode to the same value) the evidence ones (`go test -fuzz` is run manually).
- Recovery test fixtures (plan 3A): `fstest` (the MTFS in-memory filesystem, test-only) plants deleted entries with `Deleted` and `Freed` (its blocks count as free for `Unallocated`, as after a real delete) and the stale maps its `Recoverer` returns with `Recover: []RecoverMap{...}` (method, explicit or laid-out runs, claimed size, basis, assumptions, hostile maps that are never validated by the builder). `fstest.RecovererContract` is the kit every filesystem reader must run once it implements `filesys.Recoverer` (3B-3D): every candidate passes `filesys.CheckCandidate`; forged `Entry` fields change nothing; a live entry is `ErrNotDeleted`; a forged id is `ErrNotFound` without a read; a duplicate id is a corrupt-structure error; `Open` of the deleted entry is `ErrDeleted`; at most `MaxCandidatesPerEntry` candidates; repeated calls are equal and returned slices are not aliased. `evidencetest.AddRecovered` writes a recovered artifact with its audit entry and `RecoveredSpec` overrides (kind, class, method, scope, path, runs, data, alloc, `Mutate`), so a tamper test starts from a clean case. Real kernel-written recovery fixtures need the QEMU toolchain of `tools/fixtures/Dockerfile.recover` and `recover_probe.sh` (see "Recovery fixtures: toolchain probe" in `tools/fixtures/README.md`; the kernel modules are loaded only inside the guest, never in the host or the Docker VM). Four exist for FAT and exFAT (plan 3B): `fat12-recover`, `fat16-recover`, `fat32-recover` and `exfat-recover` in `testdata/recover/` of `internal/filesys/fat` and `internal/filesys/exfat`, generated by `gen.sh fat-recover` and `gen.sh exfat-recover` in the `minutiae-recover-fixtures` image (no `--privileged`; not in `gen.sh all`; images are not byte-reproducible, so image and oracle are regenerated together and `generator.image_sha256` is checked first). The kernel driver writes the files and deletes them in four fresh-mount guest boots, one directory per scenario family, with the volume full before every reuse step, so nothing relies on where the allocator places a file; the oracle (`fat_recover_oracle.py`, `exfat_recover_oracle.py`) is an independent Python reader of the finished image checked against the source tree and the filesystem tools, never Minutiae, and the generator exits 1 naming a missing family. The tests are `TestRecoverFixturesHoldWhatTheyClaim` / `TestExfatRecoverFixturesHoldWhatTheyClaim` (self-check), `TestFATRecoverableMatchesOracle` / `TestExfatRecoverableMatchesOracle` (readers), `TestFATRecoverFixtureOutcomes` / `TestExfatRecoverFixtureOutcomes` (examine, skipped under `-short`) and `TestImageRecoverFixturesVerifyClean` (command, with the flipped-byte `case verify` exit 4). (3) Committed fixtures under `internal/sqlitefile/testdata/` (`<name>.db.gz`, optional `.db-wal.gz` and `.db-journal.gz`, `<name>.expect.json`) with oracles that never come from the library: class A (builder-written files and engine-written database-only files) is byte-reproducible, checked by `TestFixtureGeneratorIsDeterministic`; class B (engine-written WAL and journal files, whose salts and nonces come from the engine's PRNG) and class C (the Docker container family: Debian `sqlite3` 3.46.1 in the last layer of `tools/fixtures/Dockerfile`, pinned to `3.46.1-7+deb13u2`, run by `gen.sh sqlite`, including a writer killed with `os._exit` so a WAL or hot journal is left behind with no copy of open files) are NOT byte-reproducible: regenerate image and oracle TOGETHER (every test checks the sha256 of each file against the oracle first, so a stale oracle or image fails before anything else). - Android telephony fixtures (plan 4D, `internal/parsers/androidmms/testdata`, `internal/parsers/androidcalllog/testdata` and `internal/parsers/androidcontacts/testdata`; the call log and contacts families are `telephony_calllog.py` and `telephony_contacts.py`, lone databases whose oracle states the db path for every row): generated by `tools/fixtures/telephony_gen.py` with the host Python's `sqlite3` (no Docker; see `tools/fixtures/README.md`), committed as `*.gz` plus a compact one-line `*.expect.json` oracle (`separators=(",",":")`, `sort_keys`). A fixture, its oracle and its `fixturePins` entry are regenerated together; `TestFixturesArePinnedByHash` and `TestEveryCommittedFixtureIsInTheVariantList` fail on a lone change, `TestBaselineOracleStatesTheSpecRules` holds the oracle's literal facts written from the spec, and `TestTelephonyDDLSnapshotsCiteTheirSourceAndHaveAVerdict` (`internal/archtest`) checks the DDL snapshots against their cross-check record. The comparer (`parsertest.AssertMatchesOracle`) requires a record's `SourcePath` to be the remote path of the file holding its `ArtifactID`; the oracle states it for a row placed in one file and for every row of a db-only variant, and derives it for a row of a WAL or journal variant that may lie in any. `Bundle` refuses an empty remote path (`ErrEmptyRemotePath`). Running these tests needs neither Python nor Docker: the pins are the generated `fixturePins` tables (`pins_test.go`, per parser), the oracle is an independent Python restatement of the spec that reads the stored values back from an engine COPY of the finished files (a WAL or hot journal is applied to the copy and never consumed from the shipped bytes), and the `parsertest` kit supplies `LoadFixture` (hash checked before anything is read), `Bundle`, `AssertMatchesOracle`, `AssertMapperSourceAgnostic` and `FuzzParse`. Each parser has fast fuzz seeds that run under `go test` (`FuzzParseMMSSMS`, `FuzzParseCallLog`, `FuzzParseContacts`, seeds capped at 64 KiB, `TestFuzzSeedsAreSmall`), a deterministic `TestPageLevelMutationsNeverBreakTheContract` (zeroed pages, flipped types, wild counts and offsets, and cells rewritten to another storage class of the same size) and a `FuzzMapRows` (in each parser's package) that feeds decoded cells of any storage class straight to the mapping and checks invented values (the contacts one checks VALUES, not only classes: T64, T80); `go test -fuzz` is run manually, through `heavy.sh` for the agents, and its progress counter can be stale (T65), so a throughput claim is measured another way. The contacts variant `duplicate-keys` carries an empty `-wal` on purpose: Probe then defers to Parse, which is how a database whose `accounts` or `contacts` table has no rowid alias reaches the mapper (T79).
- Race gate: under the RACE form, `internal/evidence` and `internal/records` run under `-race` only through the explicit list `raceConcurrencyTests` in `tools/check/main.go` (every test that starts goroutines, uses `t.Parallel`, or exercises concurrent, queued or nested transactions, live-ingest exclusion, the case lock or concurrent Add), because the whole packages exceed the per-package timeout under the race detector; every test still runs in step 1 without `-race`. A new concurrency test in those packages must be added to the list, and a listed name that matches no test fails the check.


## Fuzz stall findings (LX-8 Task 1, 2026-10-17)
Why `go test -fuzz` of `FuzzSQLiteDB` (and other targets) shows `0/sec` for most of a run. Measured on Windows 11, go1.26.8 windows/amd64, 12 CPUs, 15.4 GB RAM, CGO_ENABLED=0, main c8e5122 (3J merged); Linux in Docker Desktop 29.7.2 (VM 8.0 GB, 12 CPUs), image `golang:1.26.8@sha256:eb36c1664dd974cde625f736e02c204383deebe03977365caaec5bf49f794348` (`go version` there: go1.26.8 linux/amd64), `--cpus 2 --memory 4g --network none`, a `git archive` copy, fresh fuzz corpus (seeds only). Every run was 40 s of `-fuzztime`. "Body" is the number of times the fuzz callback ran, counted by a throwaway file-append instrument (reverted, not committed) that is independent of the engine's counter; it was only applied to `FuzzSQLiteDB` and `FuzzFATOpen` on Windows. `FuzzOpen` (`internal/sqlitefile`) was not instrumented (3J edits that file).

What the numbers show:
- During the stall the body keeps running; only the counter is frozen. In the counted `FuzzSQLiteDB` run the reported execs reached 4608 at elapsed 26 s and stayed there (0/sec from 29 s, as in the table) while the sampled body count rose from 9473 (wall 33 s) to 42441 (wall 53 s), about 33000 runs or 1650 per second (wall time includes a build of about 7 s before the engine's clock starts). `FuzzFATOpen` shows the same (15883 reported, 56330 body). With `-fuzzminimizetime 0s` the two agree to within 0.5 percent (7933 against 7970; 47046 against 47126). The engine's counter therefore does not include the work done while the stall lasts. This was measured on Windows only: no body count was taken on Linux, where the same 0/sec is reported but whether the body runs meanwhile is not known.
- The stall ends when minimisation is switched off: `-fuzzminimizetime 0s` restores a normal rate for `FuzzSQLiteDB` on Windows (E3 9289/sec, E4 3615/sec) and on Linux (2888/sec), and it makes "new interesting" grow (E1 0 against E3 374 and Linux 0 against 793). That the extra body runs belong to the minimiser of a newly interesting input is an inference from this flag effect and from the 60 s default `-fuzzminimizetime` outlasting a 40 s run; the minimiser itself was not observed. The control target `FuzzResolveChain` shows short 0/sec windows too, so this is the engine's behaviour, not something particular to the SQLite bodies.
- Linux reproduces it (E5: 56 execs, 0/sec), so it is not Windows-only.
- The `FuzzSQLiteDB` body is cheap per input (seed times above), so its cost is not the cause. The default-flag runs started from a corpus of 860 entries on Windows (54 seeds plus earlier cached inputs; E1 and E2 added none, E3 grew it to 1234, E4 started from 1234, the counted runs from 1277); the Linux runs started from the 54 seeds. Only E1, E2 and E3 share the 860 starting corpus, so the E3 against E4 comparison (and the other Windows rows after E3) and every Windows against Linux comparison are qualified: the corpora differ. The within-run observations (counter frozen, flag restores the rate) do not depend on it.
- The runs overran `-fuzztime 40s`: the Windows and Linux wall times were 49 to 134 s. The build and the baseline phase (up to 57 s) run outside `-fuzztime`, which accounts for the overrun; the runs that stalled and the runs that did not are spread across that range (the unstalled counted `-fuzzminimizetime 0s` run took 126 s, a stalled one 56 s, Linux E5 134 s), so whether minimisation adds time beyond `-fuzztime` is not shown. A campaign's deadlines must allow for the overrun. The rate of the counted `-fuzzminimizetime 0s` run (222/sec, after a 57 s baseline phase that took 16 s in the other counted run) is far below E3 (9289/sec) for a reason not found (machine load or the instrument); it is used only for the body-against-counter agreement, not for any rate claim.

Outcome, by the plan's rules: **D-A holds** (the reported counter is not the work: the body count grows while the rate is 0, on Windows). **D-B holds in its effect and not in its literal test**: `-fuzzminimizetime 0s` restores a non-zero rate, but the body count was not flat, because the work during the stall is the invisible minimisation. **D-E is refuted** (Linux stalls the same way and recovers with `-fuzzminimizetime 0s`). **D-C is refuted for `FuzzSQLiteDB`** (median seed time at most 0.01 s, none above 100 ms, and 2888/sec on Linux without minimisation), so no split of `FuzzSQLiteDB` is called for and LX-4 Task 12 is not triggered. Consequences for the plan: a reported rate of 0 is never read as "ok"; campaigns run the targets with `-fuzzminimizetime 0s` (Task 3). Not decided by these runs: `FuzzRun`. Even with minimisation off its rate is 16 to 20/sec on Windows (12 workers) and 4 to 6/sec on Linux (2 workers), so a per-input cost is suspected for `FuzzRun` in `internal/dbrecover` (a hypothesis: no seed times were measured, so D-C is neither shown nor refuted for it). `FuzzOpen` (`internal/sqlitefile`) was not measured.

## Release build
```bash
# Default release: pure Go, static, no C dependency, any OS.
CGO_ENABLED=0 go build -ldflags "-X github.com/rbenzing/minutiae/internal/version.Version=v1.0.0 -X github.com/rbenzing/minutiae/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/minutiae.exe ./cmd/minutiae
# cgo-capable build (per OS, needs a C toolchain; only once a cgo capability exists, see the cgo policy (docs/architecture.md)).
CGO_ENABLED=1 go build -ldflags "-X github.com/rbenzing/minutiae/internal/version.Version=v1.0.0 -X github.com/rbenzing/minutiae/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/minutiae-cgo.exe ./cmd/minutiae
```
Run `go run ./tools/check` before a release build: it verifies the generated parser identities (`internal/parsers/identity_gen.go` against `parsers.lock`, `tools/parserhash -check`), which a plain `go build` does not.
