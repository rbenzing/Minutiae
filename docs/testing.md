# Testing

## Check forms
Two forms: FAST, `CGO_ENABLED=0 go run ./tools/check` (no `-race`; used for per-task commits; must print `CHECK PASSED`), and RACE, plain `go run ./tools/check` on a machine with a C toolchain (REQUIRED before a plan merges to main). The RACE test step is split in three, because `internal/evidence` and `internal/records` exceed the 30 minute per-package timeout under `-race` (modernc sqlite instrumented for the race detector is very slow; no test hangs): (1) `go test -count=1 ./...` without `-race`, so every test runs; (2) `go test -race -timeout 30m` on every other package (listed at run time with `go list`); (3) `go test -race -timeout 30m -run` an explicit anchored list of the concurrency tests of those two packages (`raceConcurrencyTests` in `tools/check/main.go`; the check fails if a listed name matches no test). Both must pass where they apply.

## Rules and fixtures
- Check modes: per-task commits use the FAST check (`CGO_ENABLED=0 go run ./tools/check`, no `-race`); the RACE check (plain `go run ./tools/check`: all tests without `-race`, then `-race` on all packages but `internal/evidence` and `internal/records`, then `-race` on the named concurrency tests of those two; 30 minute package timeout) is required before a plan merges to main (CLAUDE.md, Definition of done).
- TDD: write the failing test, see it fail, implement, see it pass.
- Default tests never need hardware: use fakes (fake ADB server, in-memory serial, fake iOS).
- Hardware tests use `//go:build hardware` and are run manually: `go test -tags hardware ./...`.
- Parsers have synthetic in-memory builders (`volumetest`, `fstest`) and fuzz targets; fuzz seeds run under `go test`, `go test -fuzz` is run manually.
- Real-image fixtures (`*.img.gz` plus an independent oracle `*.expect.json`) are committed under each package's `testdata/`. Regenerating them needs Docker (`docker build -t minutiae-fixtures tools/fixtures`, then `gen.sh all` in the container; the exFAT fixture needs `docker run --privileged`, and the F2FS fixtures use it only to try a kernel mount; see `tools/fixtures/README.md`); running the tests never does.
- HFS+/HFSX fixtures (`gen.sh hfsplus`, output in `internal/filesys/hfsplus/testdata/`) are NOT part of `gen.sh all`: `hfsprogs` (`mkfs.hfsplus`, `fsck.hfsplus`) is not installable in the main fixture image, so they use a separate image (`docker build -f tools/fixtures/Dockerfile.hfs -t minutiae-fixtures-hfs tools/fixtures`, then `docker run --rm --shm-size=1g -v "$PWD:/work" -w /work minutiae-fixtures-hfs bash tools/fixtures/gen.sh hfsplus`; no `--privileged`) and the main image and every other fixture stay byte-identical. Five images are empty volumes made by `mkfs.hfsplus` (`hfsplus-empty`, `hfsx-empty`, `hfsplus-journal`, `hfsplus-1k`, `hfsplus-wrapped`; byte-identical on every regeneration). The sixth, `hfsplus-populated` (16 MiB), is filled by the Linux `hfsplus` kernel driver: the Debian bookworm kernel (`linux-image-6.1.0-53-amd64`, module `hfsplus`) is booted under QEMU software emulation (TCG, no `/dev/kvm`, about 20 s per guest run, 65 s for the whole script) because Docker Desktop's own kernel has no `hfsplus` module. Its regeneration is byte-identical in every run tried (15 runs, 12 of them under concurrent host load, after the guest clock is rewound to the fixture time every 0.2 virtual seconds: before that, 3 of 9 runs differed in one byte, the volume header modify date, one second late; the package set is pinned to `snapshot.debian.org` as of 2026-10-03 and exact versions in `Dockerfile.hfs`), but a different host or QEMU could in principle change the timing: regenerate it TOGETHER with its `expect.json`, never one without the other (the test checks the image sha256 against `generator.image_sha256` first, so a different regenerated image passes only with its own oracle). Oracles come from a second Python parse, `fsck.hfsplus`, `blkid` and, for the populated image, the source tree, never from Minutiae. The fixture-level HFS+ e2e tests (`internal/examine`) are skipped under `-short` (the populated subtest takes 60-100 s on a loaded machine). The reader's builder images are additionally checked by `fsck.hfsplus` (12 of 15 pass, 3 exempt with recorded reasons: `MINUTIAE_WRITE_BUILDER_IMAGES=<dir> go test -run TestBuilderImagesPassFsck ./internal/filesys/hfsplus`, then `hfsplus.sh check-builder <dir>` in the fixture image). Volumes written by macOS or iOS can be read manually: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages ./internal/filesys/hfsplus` reads `<dir>/hfsplus/*.hfs`, `*.hfsplus` and `*.img` (see `TestRealHFSPlusImages`); see "HFS+ fixtures" in `tools/fixtures/README.md`.
- EWF/E01 fixtures (`gen.sh ewf`, output in `internal/image/ewf/testdata/`): one 8 MiB GPT raw disk (`ewf-disk.img.gz`, built from the committed ext4 and fat12 fixtures) acquired with `ewfacquire` into four sets: `single-none` (one segment, uncompressed chunks), `single-best` (one segment, compressed plus a few uncompressed chunks), `multi-none` (five segments) and `seed-small` (first MiB only, the fuzz seed), each stored as one `.E0N.gz` per segment, plus `ewf-fixtures.expect.json` (the oracle from the independent Python decoder `ewf_inspect.py`, `ewfverify`, `ewfinfo` and `ewfexport`). Generation is deterministic (frozen clock; the writer emits an all-zero set identifier, and `ewf_normalize.py` pins a non-zero one as a safeguard), checked by generating twice and comparing every sha256. Regenerate with `docker run --rm -v "$PWD:/work" -w /work minutiae-fixtures bash tools/fixtures/gen.sh ewf` (not privileged, about 30 s; regenerate the ext4 and fat12 fixtures first if they ever change). The `error2` section, table base 0 and layouts the real writer does not produce are covered by the `ewftest` builder only. Real images from other acquirers can be checked by hand: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages -run TestEWFRealImages -v ./internal/image/ewf` (needs `*.E01` sets; not run by default). The EWF tests run under `-race` in the race gate (step 2; passed 2026-10-08, 0 data races) and without it in the fast check.
- APFS fixtures (output in `internal/filesys/apfs/testdata/`): three EMPTY containers built by `mkapfs` from `apfsprogs` (`apfs-ci`, `apfs-cs`, `apfs-multichunk`; `gen.sh apfs`, part of `gen.sh all`, in the main fixture image: `apfsprogs` is a last layer of `tools/fixtures/Dockerfile`, so the earlier layers and every other fixture stay byte-identical; no `--privileged`), byte-identical on every regeneration (frozen `faketime`, fixed UUIDs and label, a fresh sparse file per image, generated twice and compared inside the script), with an oracle from `apfs_oracle.py` (an independent decoder) and `apfsck`. The fourth, `apfs-populated` (`gen.sh apfs-populated`), is NOT part of `gen.sh all`: it needs the separate image `minutiae-fixtures-apfs` (`docker build -f tools/fixtures/Dockerfile.apfs -t minutiae-fixtures-apfs tools/fixtures`, then `docker run --rm -v "$PWD:/work" -w /work minutiae-fixtures-apfs bash tools/fixtures/gen.sh apfs-populated`; no `--privileged`, about 1 minute a run, the image build needs network for the pinned git clones and Debian mirrors). It is written by the real `linux-apfs-rw` kernel driver (v0.3.21 built from a pinned commit against the Debian bookworm 6.1 kernel headers) inside a QEMU software-emulation guest (TCG, no `/dev/kvm`) that boots the Debian kernel from a busybox initramfs: the module is loaded only in that guest and NOTHING is ever loaded into the host or the Docker Desktop VM kernel (an earlier attempt to load it into the Docker Desktop VM kernel failed and tainted that kernel until Docker was restarted; that route is ruled out). Its oracle, `apfs_populated_oracle.py`, decodes the finished image alone and compares it with the source tree (never with Minutiae), and `apfsck` must accept the image. The populated image is NOT byte-reproducible (five generations gave five different images: the number and timing of driver transactions under writeback differ even under emulation; the logical content, final xid and record counts were stable), so regenerate the image TOGETHER with its `expect.json`, never one without the other: every test checks the image sha256 against `generator.image_sha256` first, so a regenerated image passes only with its own oracle. `go test -short ./internal/filesys/apfs` skips only the 129 MiB `apfs-multichunk` oracle test (the populated fixture still runs, about 3 s), and `TestOpenMutatedNeverPanics` mutates one block in each position instead of four. A real image written by macOS or iOS (compression, encryption, several snapshots) can be checked by hand: `MINUTIAE_TEST_IMAGES=<dir> go test -tags realimages -run TestRealImages -v ./internal/filesys/apfs` reads `<dir>/apfs/<name>.img[.gz]` with a `<name>.expect.json` beside it (schema in the test file header and `tools/fixtures/README.md`; `apfs_expect.sh` writes such a file on macOS, from memory and never run); see "APFS determinism and limits", "APFS populated fixture" and "Supplying a real APFS image" in `tools/fixtures/README.md`.
- Records tests (`internal/records`, `internal/evidence`) use `recordstest` as the fixture: `NewCase`, `AddArtifact`, `AddIncompleteArtifact`, `Records` (a deterministic generator with tied and untimed timestamps, deleted and recovered records, mixed time bases and byte ranges), `Ingest` and `NewV1Case`/`NewV1CaseWithRecord` (a frozen v1 database, tied to the migration code by `TestRecordstestV1DDLMatchesEvidence`). Named-tamper-helper rule: every way a test damages a case lives in `recordstest/tamper.go` (records and database tamper) or `evidencetest/tamper.go` (manifest and artifact-file tamper for tests of `internal/evidence` and above, where `recordstest` would make an import cycle) as a helper named for what it does (`SetRecordSummary`, `DeleteBatch`, `RepointRecord`, `RemoveArtifactEverywhere`, `RewriteArtifactConsistently`, ...), opens the database with `foreign_keys=OFF`, drops the immutability triggers, tampers and RE-CREATES the triggers from the expected DDL, so the problem under test is the only one left. Helpers that deliberately leave damage behind say so in their name (`DropImmutabilityTriggers`, `DropTrigger`, `ReplaceTrigger`, `DropTable`). A tamper test asserts its SPECIFIC problem text (and that no other kind of problem appears), never only "not OK" or exit 4. Raw row inserts for evidence-internal tests live in `internal/evidence` `_test.go` files. `FuzzCursor` and `FuzzValidateRecord` are the records fuzz targets, and `FuzzCheckReadSQL` (the lexical read guard: no panic, an accepted statement starts with SELECT or WITH and compiles to bytecode that opens nothing for writing) and `FuzzDecodeDetails` (audit details of any shape never panic and decode and re-encode to the same value) the evidence ones (`go test -fuzz` is run manually).
- Recovery test fixtures (plan 3A): `fstest` (the MTFS in-memory filesystem, test-only) plants deleted entries with `Deleted` and `Freed` (its blocks count as free for `Unallocated`, as after a real delete) and the stale maps its `Recoverer` returns with `Recover: []RecoverMap{...}` (method, explicit or laid-out runs, claimed size, basis, assumptions, hostile maps that are never validated by the builder). `fstest.RecovererContract` is the kit every filesystem reader must run once it implements `filesys.Recoverer` (3B-3D): every candidate passes `filesys.CheckCandidate`; forged `Entry` fields change nothing; a live entry is `ErrNotDeleted`; a forged id is `ErrNotFound` without a read; a duplicate id is a corrupt-structure error; `Open` of the deleted entry is `ErrDeleted`; at most `MaxCandidatesPerEntry` candidates; repeated calls are equal and returned slices are not aliased. `evidencetest.AddRecovered` writes a recovered artifact with its audit entry and `RecoveredSpec` overrides (kind, class, method, scope, path, runs, data, alloc, `Mutate`), so a tamper test starts from a clean case. Real kernel-written recovery fixtures (ext4, f2fs, exFAT, FAT deleted files) need the QEMU toolchain of `tools/fixtures/Dockerfile.recover` and `recover_probe.sh` (see "Recovery fixtures: toolchain probe" in `tools/fixtures/README.md`; the kernel modules are loaded only inside the guest, never in the host or the Docker VM).
- Full-text test fixtures (plan 5B): `recordstest.CopyV2Case` copies the committed schema v2 case (`recordstest/testdata/v2case`: one artifact, 12 records in two ingests, written by the 5A code before any v3 change, fixed audit actor); it is history, frozen and never regenerated (`.gitattributes` keeps its bytes exact so the audit chain survives). Every way a test damages the full-text index is a named function in `recordstest/ftstamper.go` and `fts.go` (`HideFromIndex`, `InventIndexText`, `DuplicateIndexRow`, `EmptyFTSIndex`, `EmptyFTSTable`, `SetDocsize`, `CorruptDocsize`, `DeleteDocsize`, `AddDocsize`, `SetFTSTotals`, `SetFTSConfig`, `DeleteFTSIdxRows`, `RepointFTSIdxRow`, `AlterFTSIdxTerm`, `SetFTSNormVersion`, `DeleteFTSNormVersion`, `WreckFTSStructure`), under the same named-tamper rule as the record helpers; tampered text is disjoint from the original because deleting an index row removes a (term, rowid) pair.
- SQLite file library tests (plan 3I, `internal/sqlitefile`): the files under test come from three independent writers, never from the code under test. (1) The `sqlitetest` builder, an independent encoder of databases, WALs and rollback journals, which is itself held to the engine (see docs/invariants.md). (2) The engine oracle, `modernc.org/sqlite` (SQLite 3.53.4 at the pinned module version), used in `_test.go` files only and only on COPIES the tests write to a temporary directory (never on evidence; a copy that meets a sharing violation is retried and logged, `copyFiles`), to answer what the SQLite engine shows for a database, a WAL or a hot journal; a test that had to use such a retry logs it. (3) Committed fixtures under `internal/sqlitefile/testdata/` (`<name>.db.gz`, optional `.db-wal.gz` and `.db-journal.gz`, `<name>.expect.json`) with oracles that never come from the library: class A (builder-written files and engine-written database-only files) is byte-reproducible, checked by `TestFixtureGeneratorIsDeterministic`; class B (engine-written WAL and journal files, whose salts and nonces come from the engine's PRNG) and class C (the Docker container family: Debian `sqlite3` 3.46.1 in the last layer of `tools/fixtures/Dockerfile`, pinned to `3.46.1-7+deb13u2`, run by `gen.sh sqlite`, including a writer killed with `os._exit` so a WAL or hot journal is left behind with no copy of open files) are NOT byte-reproducible: regenerate image and oracle TOGETHER (every test checks the sha256 of each file against the oracle first, so a stale oracle or image fails before anything else). Class A and B regenerate with `MINUTIAE_REGEN_SQLITE_FIXTURES=1 go test ./internal/sqlitefile -run TestGenerateFixtures` (no Docker); only class C needs Docker, running the tests never does. `go test -tags sqlitematrix -p 2 -timeout 40m ./internal/sqlitefile` runs the full engine matrix (45 live scenarios: five page sizes by three encodings by three auto-vacuum modes, and 1448 WAL mutations); the default run has a reduced matrix under a stated time budget. The fuzz targets (`FuzzOpen`, `FuzzWAL`, `FuzzJournal`, `FuzzRecord`, `FuzzCreateParse`) run their seeds under `go test`; `go test -fuzz` is run manually; one corpus seed is committed (`internal/sqlitefile/testdata/fuzz/FuzzCreateParse/d65cbe711e2fe660`, a CREATE INDEX statement kept as a regression input). The `expect.json` oracles are large (up to 1.7 MB each, 8.6 MB in all) because they list every cell. Class C reproducibility is not promised: `sqlite.sh` reports which files differ between two generations and tolerates a difference in the killed-writer family. The single-writer scanner exempts a plain `DROP TABLE` of a non-record table in `_test.go` files of `internal/sqlitefile/` and `internal/decode/` only (engine-oracle tests build throwaway fixture databases and drop tables in them; `TestOracleDropExemptionIsNarrow` proves DROP TRIGGER, DROP INDEX, a record table, a non-constant name, a non-test file and any other directory stay flagged; `internal/decode/` now holds `sqlitedb` (plan 4B), but the proof feeds hand-written violation texts to the predicate, so real-scanner coverage is only that the full rule passes). See "SQLite fixtures" in `tools/fixtures/README.md`.
- SQLite table decoder tests (plan 4B, `internal/decode/sqlitedb`): they use the `sqlitetest` builder, the engine on COPIES (including the engine's own JOIN results) and the committed 3I fixtures. Engine tests are slow on Windows (copy retries are logged). `go test -fuzz FuzzSQLiteDB` is run manually; its seeds run under `go test`.
- A C toolchain (WinLibs GCC, cgo) is installed on this machine since 2026-10-07, and the race gate (`check.sh --race`) passed on 2026-10-08 (0 data races, 0 failures, 0 timeouts, 76 packages ok). The concurrency tests (`TestAddConcurrent`, `TestConcurrentTxQueueAndSucceed`, `TestNestedTxFailsWhileOthersAreQueued`) assert outcomes (every caller succeeds, ids and counters exact) and run under `-race` in the race gate (the records and evidence ones by name, step 3); the fast check runs them without `-race`. `TestNestedTxFailsWhileOthersAreQueued` waits on the gate's counter of queued callers, never on a sleep.
- Parser tests (plan 4A): `internal/parsers/parsertest` is the test-only kit (the strict emitter and an `Input` that behave like the host, the determinism harness, the fakes `Slow`, `Hog`, `Mutator`, `Liar`; every fake that can outlive a test is closed with `Release` and observed on `Done`, never on goroutine counts). `recordstest.ValidPayload(type)` returns a fresh valid payload for each of the six validated record types; test records of those types must use it, because the validators are active in every binary that links `artparse` (the `cli` tests too). Test seams of `artparse` are unexported options reachable only from `artparse/export_test.go`; no `records` hook is exported for them. A test name is unique within its package.
- Race gate: under the RACE form, `internal/evidence` and `internal/records` run under `-race` only through the explicit list `raceConcurrencyTests` in `tools/check/main.go` (every test that starts goroutines, uses `t.Parallel`, or exercises concurrent, queued or nested transactions, live-ingest exclusion, the case lock or concurrent Add), because the whole packages exceed the per-package timeout under the race detector; every test still runs in step 1 without `-race`. A new concurrency test in those packages must be added to the list, and a listed name that matches no test fails the check.


## Release build
```bash
# Default release: pure Go, static, no C dependency, any OS.
CGO_ENABLED=0 go build -ldflags "-X github.com/rbenzing/minutiae/internal/version.Version=v1.0.0 -X github.com/rbenzing/minutiae/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/minutiae.exe ./cmd/minutiae
# cgo-capable build (per OS, needs a C toolchain; only once a cgo capability exists, see the cgo policy (docs/architecture.md)).
CGO_ENABLED=1 go build -ldflags "-X github.com/rbenzing/minutiae/internal/version.Version=v1.0.0 -X github.com/rbenzing/minutiae/internal/version.Commit=$(git rev-parse --short HEAD)" -o bin/minutiae-cgo.exe ./cmd/minutiae
```
Run `go run ./tools/check` before a release build: it verifies the generated parser identities (`internal/parsers/identity_gen.go` against `parsers.lock`, `tools/parserhash -check`), which a plain `go build` does not.
