# Limitations: recovery, carving and slack

What the current build does not do, does approximately, or has validated only on builder data, for deleted-file recovery (`image recover`, each reader's `Recoverer`), carving (`internal/carve`, `image carve`), slack (`image slack`) and the R-series checks of `case verify`. Part of the [known limitations](../limitations.md), which say how to add or close one.

- F2FS deleted-file recovery (plan 3D, `f2fs-node-scan`, `internal/filesys/f2fs/recover*.go`), what it is and is not. (a) From memory and confirmed on the guest kernel `6.1.0-53-amd64` only (probe gates G1 to G6, `tools/fixtures/README.md`): the footer `cp_ver` and its CRC half (only the low 32 bits are compared), the checkpoint's current-segment cursor offsets, the SSA summary layout and `SUM_TYPE_NODE` (a summary block whose footer type is not a node summary is not trusted: a counted warning, and its copies are kept without an SSA confirmation), the SIT segment-type numbers, and the footer `ofs_of_node` starting at bit 3 (`OFFSET_BIT_SHIFT`). Other kernels and vendor F2FS forks are unmeasured. (b) The node index answers "among the scanned node-segment blocks": blocks past a current node cursor and segments now typed data are not scanned (3D-R5, R25). Its cap is 2,097,152 entries (24 bytes each, at most 48 MiB, plus 8 bytes per inode number), past which every lookup is `ErrLimit`; one skipped segment, or an inode number whose copies the per-inode cap of 8 evicted, makes the lookup undecided; both are counted `undecided` skips and the command exits 1. The index pass cannot be cancelled (a cancel takes effect at the next entry, 3D-R15), as for `Unallocated`. (c) A hole (`NULL_ADDR`/`NEW_ADDR`), a missing, foreign or non-node block, a cycle, a tie, an address outside the main area, a repeated address or the end of the node tree (`tree-end`) ends the map as a prefix named in `stale-chain-stop=`, and a repeated address cuts the whole run that contains it; every such map is capped at 20 and there are no declared holes (3D-R6; `TestRecoverF2FSSparseFileIsPrefixCapped`). (d) Inline-data and compressed files are not recovered (`ErrUnsupported`, 3D-R16); the kernel stores a 0-byte file inline, so the `empty` skip occurs only on builder images. (e) The identity binding is (inode number, parent directory, name): a file deleted, recreated with the same name, directory and inode number and deleted again cannot be told apart from its earlier incarnation by structure, and when both dentries are listed the overlap caps them at 30; a renamed file shows both its names, each recovering from the same blocks (30). (f) The older checkpoint pack's NAT journal is not read (3D-R1). (g) Discard: the fixtures show what the 6.1 kernel with QEMU `discard=unmap` leaves (the stale inode and data blocks are zeroed, so every deleted file is "not found", gate G5); devices whose firmware zeroes or keeps trimmed blocks differently are unmeasured. (h) The `renamed`, `nidreuse` and `reuse` families are real-image (gate G6); the tie, evicted, forged, foreign-owner, encrypted, compressed, `uniform` and `cut` cases are builder-only. (i) The F2FS roll-forward node chain (post-checkpoint data) is plan 3H, not recovered here. (j) `offsetBitShift` was 7 in the F2FS reader before plan 3D and the kernel's value is 3 (proven by the flag words `0x9`, `0x11`, `0x19` of kernel-written nodes); it was fixed in plan 3D because recovery depends on it. On the live reader the only effect of the wrong value was one hostile-input edge case: a block whose footer ino equals its own nid with a small tree offset was accepted as an inode, and real kernel-written trees were unaffected (`TestFooterOfsFollowsTheKernelBitLayout`).
- Deleted-data recovery (sub-project 3, plan 3A: the foundation; 3G, 3H and 3K pending, 3B, 3C, 3D, 3E, 3E2, 3F, 3I and 3J done): the model (`evidence.Recovery`, the class table, namespaces), the checks R1 to R7 of `case verify`, the optional `filesys.Recoverer`/`Journaler`/`AllocatedRunner` interfaces, the planner and writer (`examine.Session.PlanRecovery`/`Recover`) and `image recover` exist; FAT12/16/32, exFAT, F2FS and ext4 implement `Recoverer` (3B, 3C, 3D); HFS+ and APFS are out of scope, so on a filesystem without a reader `image recover` reports that the filesystem "does not support recovery" (exit 1, nothing written, only `case.open` audited). `AllocatedRunner` is implemented by ext4, FAT, exFAT and F2FS and consumed by `image slack` (3F); `Journaler` has no consumer yet (3G).
- Carving (plan 3E, done): `image carve` and `internal/carve` carve JPEG, PNG, GIF, WebP, ISO-BMFF (MP4, MOV, 3GP, HEIC/HEIF), SQLite 3, binary plist, ZIP (APK, JAR, OOXML), PDF, gzip, WAV and Ogg objects from unallocated space, volume gaps, raw scopes and case artifacts; each artifact has kind `carve`, class `carved`, a confidence of 70 at most and `case verify` reproduces it from its parent (R6) and rechecks its allocation (R5, R9 and R10 cover the scopes `unallocated`, `volume` and `raw`). The per-format layout bullets follow; this bullet holds what holds for every format. Plan 3E2 extended the built-in set to `minutiae-sigset/2` (BMP, TIFF, ICO, AVIF, CR3, JPEG XL container; see "Carving, image formats (plan 3E2)"); the twelve-family count below is that of the original set. (1) Twelve families, refined types: the ISO-BMFF family refines to `mp4`, `mov`, `3gp`, `heic` or `heif` by brand, ZIP to `apk`, `jar`, `docx`, `xlsx`, `pptx` or plain `zip` by member names, the rest keep their family name. Every layout is written from memory and checked against one encoder's output (the fixtures, produced by real encoders, and an independent builder per format) and never against a second decoder or the standard text; the HEIC fixture is a real `heif-enc` object (no builder-only fallback was needed, ruling 3E-R27). (2) Contiguous objects only: a fragmented file is truncated or rejected, never reported whole, and fragment reassembly is not attempted; the JPEG validator walks the entropy-coded data so a fragment followed by fill is rejected (ruling 3E-C5); the other formats prove structure, so a fragmented PNG, GIF, WebP, ISO-BMFF, SQLite, plist, ZIP, PDF, WAV or Ogg whose pieces happen to leave a consistent structure is accepted as it reads. (3) No de-duplication: the same bytes at two offsets are two artifacts; an identical hash is not merged. (4) A QuickTime file without `ftyp` is not carved. (5) gzip is bounded from its header and never inflated, so it is `carve-bounded` at confidence 25 and hidden by the default floor of 40 (counted `below-min-confidence`, listed by `--list`, written with `--min-confidence 25` or lower); a PDF has no length field and is a `carve-footer` hit (confidence 50) ended by its last `%%EOF`. (6) `case verify` does not check the chain cap of a carve: a carve of a cut chain is held to the class ceiling (70) and its own R2 rules, not to the 3J chain minimum (ruling 3E-R24, as for 3J rows). (7) Alignment: headers are tried at the start of every block, cluster or sector of the scope (the scan unit, counted from each run's start) and `--unaligned` tries every byte, which is slow and finds more false headers; an object that starts at an unaligned offset is invisible without it. (8) A header that no validator accepts is counted by reason (`Stats.Rejected`, shown in the summary), never audited or listed one by one; `--nested` reports objects found inside an already carved object and tries every byte inside it (depth one, `nested-in=<offset>`); only an accepted validated hit nests (spec 7.3.4), so an object inside a footer or bounded hit (a PDF, a gzip member) is reported at top level, without a `nested-in` marker. Every basis or assumption entry is cut by the scanner to `MaxEntryBytes` (200) and ends in `...(cut N bytes)` when it was longer (a gzip file name is escaped first and bounded after escaping), so a hostile header cannot make the case refuse a hit. (9) The validate budget bounds the bytes validators may read (charged for the bytes a validator reaches through the 512-byte-granular, doubling read cache, not for a whole 64 KiB cache per look; a factor of the scope plus a slack, never above `MaxValidateBudget`); once spent every later header is rejected `validate-budget` and the run says so, so a hostile image can cost work but a result is never silently thin. A JPEG walk has its own caps: the refinement-state cap (16 MiB), a work cap (16384 units plus 128 per byte read, an EOB run counting all its blocks) and 128 scans; a frame over any of them is a `carve-footer` hit with `entropy-not-walked=<reason>`, never a rejection or a silent cut. (10) The whole-media scan limit applies to a carve scope only as the default 64 GiB for a container whose size claim its bytes cannot hold: bytes past it are not scanned, a scope note says so and the run is partial; carve has no `--max-scan-bytes` flag of its own, no `--timeout` flag (a cancel is the context) and no `case info` marker for carved artifacts. (11) `--sig-file` adds types from an examiner's JSON file (at most 64 KiB, exact keys, no duplicate or unknown key, a name that collides with a built-in or refined name refused): a type there is only as good as its header, footer and size bounds, is validated only if its `validate` field names a built-in validator id (a refined name colliding with one is refused), otherwise it is a `carve-footer` or `carve-bounded` hit and its digest is recorded in the run (`sig_file_sha256`). (12) The padding assumption of JPEG: an encoder that pads the last byte of a scan with 0 bits instead of 1 bits is accepted with the assumption `jpeg-padding=nonstandard` (ruling 3E-C6), because the block count is already proven. (13) A read failure inside a hit is the case writer's to flag: the readable prefix is kept as an incomplete artifact (`read-failed-after=<n>`), the run goes on and the exit is partial; the scanner clips a hit's window only at unreadable ranges found in the chunk it loaded, so a validator that never reads the body can accept an object that spans a later bad range (it rejects `unreadable` only when it reads those bytes). `scanned_bytes` counts completed scope runs plus the chunks before the one a stop happened in, so a run stopped early reports more `not_scanned_bytes` than strictly unscanned. Carve is not a records source: carved artifacts are parser input only with `--include-recovered` and every record parsed from one is recovered, never live (plan 4G).
- Carving, image formats (plan 3E2): the built-in set is `minutiae-sigset/2` (the 3E set plus BMP, TIFF and BigTIFF with the refined types DNG, CR2, ORF and RW2, ICO and CUR, AVIF, CR3 and the JPEG XL container); the per-format layout bullets that follow hold every layout, and this bullet holds what holds across them. (1) Evidence base: each new format is checked against one set of encoders only (the real-encoder objects of `carve-images`, plus an independent `carvetest` builder); nothing is checked against a second decoder or the standard text. (2) Camera raw (ruling Q3): DNG, CR2, ORF, RW2 and CR3 identity and layout rules are from memory and unchecked against camera output; no real camera or phone sample is part of the fixtures, so they are proven against the builder alone. (3) AVIF is typed by major brand only, maker notes are counted and never followed, TIFF objects above 1 GiB are rejected `truncated`, and an incomplete TIFF walk is `carve-bounded` and hidden at the default floor of 40. (4) An offset-valued tag the TIFF walk does not follow (FreeOffsets and other unlisted tags) can lead past the computed end. (5) The bare JPEG XL codestream (`FF 0A`, no container) is not carved (backlog). (6) Reserved names: `--sig-file` refuses a type whose name is reserved by `minutiae-sigset/2`, which now includes the new families and refined names (`bmp`, `tiff`, `dng`, `cr2`, `orf`, `rw2`, `ico`, `cur`, `avif`, `cr3`, `jxl`); a sig file written for set 1 that used one of them stops working, and the reserved names are not interpreted beyond the refusal. (7) BMP and ICO carry no checksum, so a truncated object followed by other bytes of the window validates at its declared length (see their bullets), and Pillow's trailing zero padding after a TIFF's last strip is not carved.
- Carving fixtures, `carve-ext4` is not reproducible (plan 3E, open carry-over m3; found in plan 3E2 Task 1): regenerating the committed 3E `carve-ext4` image with `gen.sh carve` gives a different file (and so a different oracle `image_sha256`), 35 bytes differing in blocks 34 and 35 of the 8 MiB image. It happens in the unextended 3E image rebuilt from the committed `Dockerfile.carve` as well, and two runs of the extended image agree with each other, so it is not caused by plan 3E2; the probable cause is the lazily initialised ext4 inode table, not confirmed. The committed image and oracle are left as they are and are consistent with each other (the tests check the hash first); the generator is not fixed. Regenerating this one fixture needs its image and oracle replaced together. See "Reproducibility" in `tools/fixtures/README.md`.
- Carving, JPEG XL container from memory (plan 3E2, `internal/carve/validate_jxl_container.go`): the container is the 12-byte signature box (`JXL ` with `0D 0A 87 0A`), an `ftyp` with major brand `jxl `, then top-level boxes of the set `jxll jxli jxlc jxlp jbrd Exif xml  jumb brob free skip`, all written from memory and unchecked against the reference. The codestream must be one `jxlc` or `jxlp` parts, never both; a `jxlp` payload starts with a big-endian u32 index that counts up from 0, and only the last part has the high bit set (anything else is `bad-codestream`, no codestream at all is `missing-codestream`). The `jxlp` index rule is from memory. A size 0 on the `jxlc` or the last `jxlp` gives a `bounded` object to the window end (`box-extends-to-end`); a size 0 on any other box is `unbounded-box`. A `brob` box is walked and never decompressed, and the codestream is never decoded: only its first two bytes are read, which must be `FF 0A` (in the `jxlc` payload, or in the first `jxlp` after its index word), else `bad-codestream`, so an empty `jxlc` or a `jxlp` holding only its index word is refused while a container around a damaged codestream that keeps its magic is validated. The bare codestream (`FF 0A`, no container) is not carved: a 2-byte magic with no length, footer or structure to check has no false-positive control, and it needs an opt-in type selection first (backlog).
- Carving, BMP layout from memory (plan 3E2, `internal/carve/validate_bmp.go`): the file header (`BM`, `bfSize`, `bfOffBits`), the DIB header sizes {12, 40, 52, 56, 64, 108, 124}, the bpp sets (core header 1, 4, 8, 24; longer headers 0, 1, 4, 8, 16, 24, 32), the compression codes (0 RGB, 1 RLE8, 2 RLE4, 3 BITFIELDS, 4 JPEG, 5 PNG, 6 ALPHABITFIELDS), the compression and bpp agreement rules, the OS/2 64-byte header reading of codes 3 (Huffman 1D, bpp 1) and 4 (RLE24, bpp 24), and the rule that a top-down image (negative height) is only RGB or a BITFIELDS form are written from memory and checked only against the independent `carvetest.BMP` builder (and the real-encoder objects of plan 3E2 Task 8), never against a second decoder or the standard text. The length is `bfSize` and nothing else, so a BMP whose `bfSize` is damaged but plausible is cut where it says, and one with `bfSize` 0 (some encoders write it) is rejected `bad-size`, never sized from the pixel array. Pixel data is never read or decompressed: the uncompressed array (row padded to 4 bytes) must fit between `bfOffBits` and `bfSize`, a compressed array needs a non-zero `biSizeImage` that fits, and nothing else about the pixels is checked. Width and height are bounded to 1..65536 in this build. The palette is not measured: `bfOffBits` need only lie at or after the DIB header and before `bfSize`. A BMP with only 2 header bytes (`BM`) plus a plausible DIB is the whole identity, so the validator is weak against data that happens to hold a consistent header. A BMP cut short by overwrite and followed by other bytes of the window validates at its declared `bfSize` and over-reaches into the following bytes (no checksum exists to tell; scanned on a window that ends at the cut it is rejected `truncated`).
- Carving, ICO and CUR layout from memory (plan 3E2, `internal/carve/validate_ico.go`): the directory (reserved `LE16(0)` 0, type `LE16(2)` 1 for ICO or 2 for CUR, count `LE16(4)` in 1..256) and the 16-byte entries (a zero reserved byte at 3, a non-zero size at 8, an offset at 12 that is at least the directory end and puts offset plus size inside the window); the length is the maximum offset plus size of the entries. The width, height, planes and bit-count fields of an entry and the CUR hotspot fields are not judged, since the image header carries the real values. A PNG entry is checked only as far as its signature and an `IHDR` chunk of length 13 with non-zero dimensions (the CRC and every later chunk are not read, so a corrupt PNG entry can still validate); a DIB entry is checked by the BMP header rules (`dibCheck`), and its pixel and mask arrays are never read, so the doubled DIB height is never compared with the entry size. A DIB header larger than its entry is a bad image. An ICO or CUR whose directory and entry headers are plausible but whose pixel data is damaged is carved validated; a truncated ICO or CUR followed by other bytes of the window validates at its declared length and over-reaches into them (scanned on a window that ends at the cut it is rejected `truncated`). The layout is checked against real encoder output (ImageMagick/icoutils objects, plan 3E2 Task 8) for the PNG and DIB entry forms only.
- Carving, TIFF layout from memory (plan 3E2, `internal/carve/validate_tiff.go`): (a) the classic header (`II*\0`, `MM\0*`, IFD0 offset u32 at 4, 12-byte entries, u16 count, u32 next-IFD, inline values up to 4 bytes) and the BigTIFF header (magic 43, offset size 8 at 4, a zero word at 6, IFD0 offset u64 at 8, 20-byte entries, u64 count and next-IFD, inline values up to 8 bytes) and the entry type sizes (types 1..13, plus 16..18 in BigTIFF only; any other type is `bad-entry`) are written from memory of the TIFF 6.0 specification and the BigTIFF proposal, and checked against the independent `carvetest` encoder (the real-encoder objects of plan 3E2 were checked in its Task 8: classic little- and big-endian, BigTIFF, Exif, tiled and multi-page), not against a standard document. (b) The walk follows IFD0 and its next-IFD chain, tag 330 (SubIFDs, every offset), 34665 (Exif), 34853 (GPS) and 40965 (Interoperability, inside Exif), and reads the image data ranges of tags 273/279, 324/325 and 513/514 (the byte count arrays are streamed through two 4 KiB buffers, never allocated from a declared count). The length is the maximum end of the header, every IFD, every out-of-line value and every data range, so it is exact only if the file names all its data through these tags: an offset-valued tag the walk does not follow (for example 288/289 FreeOffsets/FreeByteCounts, or any private tag) can lead past the computed end. The CR2 raw IFD whose offset sits at byte 12 of the header (0 is none) is followed as a main IFD after the next-IFD chain, so its strips count toward the length; a raw pointer of 0 means none, 1..15 is `bad-offset`, and a pointer to a main IFD the chain already holds is that same IFD; a pointer to any other IFD already queued (Exif, GPS, Interoperability, SubIFD) is `ifd-cycle`. (c) The MakerNote (tag 37500) is counted as an out-of-line value but its vendor-private offsets are not followed; every hit whose walked IFDs hold the tag carries the assumption `makernote-private-data-not-followed`, and a preview image a vendor IFD points at may lie past the computed end. (d) Caps: 64 IFDs per object, 1024 entries read per IFD, 1,048,576 values per array tag. A walk that hits one, or meets a strip or tile of byte count 0 (an unresolved strip), is `carve-bounded` (confidence 25) cut at the window, with the counted reason `tiff-walk-capped=ifds|entries|values` or `tiff-zero-bytecount` (`Stats.BoundedBy`, audit key `bounded_by`); at the default floor of 40 it is listed and audited but not written. It keeps the identity the header and the first entries showed; for an IFD0 of more than 1024 entries only the first 1024 are searched for DNGVersion. A cap hit inside IFD0 before tag 50706 is reached (for example more than 64 SubIFD offsets in tag 330) types the bounded hit `tiff`, not `dng`, because the identity is only what the walk saw before it stopped. (e) A TIFF or BigTIFF is carved only up to 1 GiB (the family's `MaxLen`, one for all eight rows): a larger object does not fit its window and is rejected `truncated`, counted. An IFD referenced twice (a cycle, or a shared IFD) is rejected `ifd-cycle`, so a file that shares one IFD between two references is not carved. (f) Camera raw identity is from memory and unchecked against camera output: the ORF magics (`IIRO`, `IIRS`, `MMOR`), the RW2 magic (`II` and 0x0055), the CR2 marker (`CR\x02` at offset 8 of a classic little-endian file) and DNGVersion (tag 50706 in IFD0 of a classic file) are the only identity rules, BigTIFF is never refined, and DNG, CR2, ORF and RW2 are builder-only: no real camera or phone sample is part of the fixtures (ruling Q3), so these types are proven against the `carvetest` encoder alone. A TIFF embedded in a JPEG's Exif segment is found only with `--nested`. (g) An encoder's trailing padding after the structure's maximum end (seen: 4 zero bytes after the last strip of a Pillow multi-page file) is not carved; the carve is the structure-determined length.
- Carving, JPEG layout from memory (plan 3E, `internal/carve/validate_jpeg.go`): the marker grammar (SOI, length-prefixed segments, entropy data with `FF 00` stuffing, `FF D0`-`FF D7` restarts and `FF FF` fill, EOI after at least one scan) is written from memory of ITU-T T.81 and checked only against the Pillow-encoded fixtures and the independent `carvetest.JPEG` builder, never against the standard text or a second decoder. Every scan's entropy-coded data is walked with the frame's Huffman tables (ruling 3E-C5), written from memory as well: baseline and extended sequential blocks, progressive DC and AC first scans, AC refinement scans (the symbol size 1 rule, correction bits for already-nonzero coefficients, the sign bit read before them), EOB runs and RSTn order. The walk decodes code lengths and counts only (no pixel, no coefficient value) and requires the block count to be met exactly, an EOB run to end inside its restart interval; an invalid code, a run past Se, a count mismatch, a restart out of order, a missing table or a DHT that counts more codes of some length than the code space holds (or more than 256 symbols, or a malformed segment) rejects the hit with a counted reason. A DHT is not checked further: an incomplete table and the all-ones code are accepted, as real decoders accept them (a code the data uses that the table lacks is a bad-code rejection). It does not check quantisation tables, component or sampling consistency beyond the geometry, or that a decoded value is plausible, so a JPEG whose coefficients are damaged but whose code stream is well formed is still `validated`. Some encoders pad the last byte of a scan (or of a restart interval) with 0 bits instead of 1 bits: the block count is already proven, so such a hit stays `carve-validated` and carries the assumption `jpeg-padding=nonstandard` (all-1 padding carries none). Progressive frames keep one nonzero bit mask per block (8 bytes) for the refinement scans, grown lazily as the walk reaches blocks (so what is allocated follows the bytes read, never the declared size) and declared at most 16 MiB (about 2 million blocks, checked against the declared dimensions before the walk). The work is bounded too: every block visited or skipped (an EOB run counts all the blocks it covers) costs one unit, and an object may spend 16384 units plus 128 per byte of it read so far; a walk that would exceed that stops, and a frame with more than 128 scans is not walked past the 128th. A frame over the state cap, over the work bound or the scan cap, a frame type the walk does not cover (lossless, hierarchical, arithmetic) and a second SOF are not validated: the object still ends at the first EOI after a scan, but it is a `carve-footer` hit with the assumption `entropy-not-walked=<refinement-state-cap|work-cap|scan-cap|frame-type|multiple-frames>` (the same footer rule for every over-cap case, never a rejection), never a silent cut. A frame with height 0 (a DNL-defined height) is rejected `zero-dimensions`; the object ends at the first EOI after a scan, so a JPEG with an embedded thumbnail is cut correctly only because the thumbnail lives inside a length-skipped APP segment; a multi-picture file (concatenated JPEGs) yields only the first picture; reserved marker codes (0x02-0xBF, 0xC8, 0xCC) are accepted as ordinary length-prefixed segments (a restart marker where the walk expects none ends a walked scan short), so identity rests on the SOI, a consistent SOF and SOS header (length 6+2*Ns), an EOI after a scan, and, for a frame that is not walked, at least one entropy-coded byte per scan; the first frame gives the dimensions.
- Carving, PNG and GIF layouts from memory (plan 3E, `internal/carve/validate_png.go`, `validate_gif.go`): the PNG chunk grammar (signature, IHDR first with a valid colour type and bit depth pair and zero compression, filter and interlace 0 or 1, per-chunk CRC-32, IEND of length 0 after at least one IDAT) and the GIF block grammar (GIF87a or GIF89a, logical screen descriptor, global and local colour tables, image descriptors, extensions, sub-blocks, trailer after at least one image) are written from memory of the PNG specification and the GIF89a specification and are checked only against the Pillow-encoded fixtures and the independent `carvetest.PNG` and `carvetest.GIF` builders, never against the standard texts or a second decoder. The validators prove structure, not decodability: no IDAT is inflated and no LZW stream is decoded, so a file whose compressed data is damaged but whose chunks or sub-blocks are well formed is accepted, and a PNG chunk-order rule beyond IHDR first, one IHDR and IEND last (PLTE before IDAT, consecutive IDATs) is not enforced. Stricter than the pinned grammar: a GIF LZW minimum code size outside 2 to 11 is rejected (`bad-lzw`), and a PNG width or height above 2^31-1 is `bad-ihdr`. A GIF whose logical screen is zero-sized is rejected `zero-dimensions` although some encoders write one. Bytes after the PNG IEND or the GIF trailer are never part of the object.
- Carving, RIFF/WebP layout from memory (plan 3E, `internal/carve/validate_riff.go`): the RIFF header (`RIFF`, little-endian size, form `WEBP`), the chunk grammar (printable fourcc, little-endian size, one pad byte after an odd size, the walk landing exactly on 8 + the RIFF size, which bounds the object so trailing data is excluded), the first chunk `VP8 ` (start code `9D 01 2A`, non-zero 14-bit dimensions), `VP8L` (signature `2F`) or `VP8X` (with a later `VP8 `, `VP8L` or an `ANMF` frame whose first sub-chunk is an image chunk or `ALPH`, each image chunk needing its valid payload header) are written from memory of the WebP container specification and checked only against the builder and two real-encoder files. Image data is never decoded and chunk payloads other than image headers are not read, so a damaged payload or a CRC-less corruption inside a chunk is not detected; a read failure inside unread payload is the scanner and case writer's business (ruling 3E-C1). Odd-sized final chunks without their pad byte are rejected. A VP8X first chunk under 10 bytes is rejected with the reason `bad-vp8x` (not one of the plan's pinned reasons: the pinned grammar gives its payload at least 10 bytes but names no reason for a shorter one).
- Carving, gzip, WAV and Ogg (plan 3E, `internal/carve/validate_gzip.go`, `validate_riff.go`, `validate_ogg.go`): gzip is checked by its header only (magic, method 8, reserved flag bits 5-7 zero, FEXTRA, FNAME, FCOMMENT and FHCRC inside the window, a name or comment terminated within 64 KiB) and the member is never inflated, so no end can be found: every gzip hit is `bounded` to the window end (confidence 25, assumption `length-capped` or `cut-at-run-end`, chosen by the scanner), is hidden by the default floor 40 and is only counted and listed; a gzip carved this way can run far past the real member, and a header-looking byte run that is not a gzip stream is not detected. WAV (form `WAVE`, a first `fmt ` chunk of at least 16 bytes with non-zero audio format, channels, sample rate and block align, a `data` chunk somewhere, the walk landing exactly on 8 + the RIFF size; a file with no chunk is `bad-fmt`) and Ogg (27-byte page header, lacing table, CRC-32 with polynomial 0x04C11DB7, BOS/EOS flags and the end at the page after which every begun stream has ended) are written from memory of their format specifications and checked only against the builders and one real-encoder file each. Sample data and codec packets are never decoded; the Ogg page sequence numbers and granule positions are not checked, a chained second stream after the first group ended is not part of the object, and more than 256 logical streams in one object are rejected `too-many-streams` (a bound of this build, not a format rule).
- `image recover` addressing and coverage: a deleted entry is addressed by `id:<FSID>` or by naming a live directory (every deleted entry below it is considered); a deleted entry cannot be addressed by path. Files inside DELETED directories are not enumerated by 3A (`filesys.Walk` does not descend into them); the FAT and exFAT readers (3B) and the ext4 reader (3C) do not enumerate them either (ruling F2 and plan 3C, see the FAT, exFAT and ext4 recovery items below), and the F2FS reader (3D) owns the same question. In 3A only `image recover` marks recovered artifacts; `records show` marks them (status line first, since 5C) but `case info` does not yet (report work), and `records list|search` filter and show the recovered flag of records. `--list` plans without writing: it reads image bytes (the uniform scan and the allocation lookup) but writes no artifact and appends only the usual `case.open` audit entry.
- FAT and exFAT recovery (plan 3B), what the maps are: (a) FAT recovery is contiguous by assumption. The vfat driver zeroes the whole FAT chain of a deleted file (probe fact P1), so fragmentation cannot be known: a recovered fragmented file is wrong beyond its first fragment and says so (`contiguous-allocation`, confidence at most 55; `TestRecoverFATFragmentedFileIsNotClaimedEqual`). (b) Free is not "unused since deletion": a free cluster may hold the bytes of another deleted file. Overlap is flagged only between LISTED deleted entries, and a file under a deleted directory is not listed, so a hidden overwriter is not named (the `cut-h` fixture case); confidence is ordinal and capped at 55 (75 only for exFAT `NoFatChain`, 65 for a surviving chain). (c) Files under deleted directories are not enumerated (ruling F2): `filesys.Walk` does not descend into them and `Recoverer` has no listing method (`TestRecoverFixtureDeletedDirectoryContentIsNotListed`); a backlog item covers an optional `filesys` interface. (d) Whether the FAT chain of a deleted exFAT file survives was measured only for the kernel `exfat` driver of the pinned guest (kernel 6.1.0-53, probe fact P3): the entries are kept for a chained file and never written for a `NoFatChain` file. Other drivers, other kernel versions and devices that delete differently are unmeasured, and how long the entries survive once their clusters are reallocated is uncharacterized (ruling F26: examine's free-state cut bounds the harm to a prefix capped at 20, it does not cover it). A broken chain yields a prefix capped at 20, never a contiguous guess. (e) The exFAT `NameHash` is verified for listing only (it does not change recovery), and a deleted set with a bad checksum or a damaged set yields no candidate, so its content is not recovered even when intact. (f) The first character of a deleted FAT 8.3 name is lost; `Mode` is synthesized as for live files; FAT times are local with no zone. (g) Cross-linked chains, bad or reserved clusters inside a range, orphan long-name sets, a first cluster outside the volume and an oversize `DataLength` are verified on builder images only (the kernel drivers do not write them). (h) `ValidDataLength` below `DataLength` has no real-image case: the guest tools cannot create it (probe fact P5), so it is covered by builder images only. (i) The fixtures are written by the Linux drivers under QEMU; the behaviour of other firmware (cameras, phones' own stacks) is unvalidated, so run `image recover` on such images by hand before relying on it. (j) A range that leaves the volume, or a truncated image, is skipped as corrupt and never recovered as a clamped prefix (ruling F5). (k) A directory search cut by a cap (FAT `resolveDir`/locate scans, exFAT `resolveDir` directories, the directory record cap) no longer ends the whole run: that entry is skipped as `undecided` with the cap in the audited detail, the other entries are recovered, and the command exits 1 naming the count, so one very deep tree can no longer discard every other recovery but also can never exit 0 with an entry left undecided (the invariant "Typed reader answers are skips").
- FAT and exFAT recovery fixtures (plan 3B), what the real images do not cover: (a) no exFAT fixture record is `exfat-contiguous` (the kernel keeps the chain of every chained file, so the chain-cleared case never occurs); that branch is covered only by hand-built images (`TestRecoverExfatClearedChainIsContiguousAssumption`, `TestExfatStaleChainFirstEntryFreeIsContiguous`) and has no real-image case. (b) The FAT32 fixture has a single FAT copy (`mkfs.fat -f 1`, ruling F100, to stay within the image size budget), so the differing-copies warning is tested on the FAT12 and FAT16 images only. (c) The fixtures are not byte-reproducible: image and oracle are regenerated together and every test checks the image sha256 first. (d) The exFAT oracle's check that a `NoFatChain` file's FAT entries are zero runs at snapshot time only, and fails the generator closed on a NoFatChain file that sits on stale FAT entries; the pinned `dump.exfat` (exfatprogs 1.2.0) has no per-file option, so it is used for geometry and the free-cluster count only.
- ext4 recovery (plan 3C, `image recover` on ext2/3/4), what the maps are: (a) Measured by the probe and the fixtures (`tools/fixtures/README.md`, "ext4 recovery probe (3C)" and "ext4 recovery fixtures (3C)") on Linux 6.1.0-53 and 5.10.223 guests: a kernel `rm` clears the in-inode extent map and zeroes the ext3 block map (GATE-K closed), so a small file deleted by the kernel yields no map (`no-map`) and is recoverable only through the journal (3G, not built); the inode's `i_size` is zeroed for extent files (GATE-S) but kept for inline data; a freed inode number is reused first (GATE-U). A map is intact when the file was deleted with a tool that leaves it (`debugfs rm`): that is `ext-inode-intact`, confidence 80. (b) The leaf method (`ext4-extent-leaf`, GATE-L open but demoted to the clean boundary) finds a free block that holds extents of a deleted inode and binds it by the leaf's 32-bit `metadata_csum` under (inode, generation), a coincidence check: the expected number of false bindings is about (plausible leaves x deleted inodes) / 2^32, stated as an assumption on every candidate, and without `metadata_csum` there is no binding. After a delete in the same mount (same boot) the journal revokes the last version of a freed leaf, so the home block can hold an older, superseded version: such leaves are never assembled into a map, and the result is a correct prefix capped at 20 or undecided. Which of the two a same-boot file yields varies from run to run of the generator (the committed `ext4-recover-sameboot` image keeps the complete chain, the probe's 16 MiB run kept only partial older versions), so the self-check and the oracle tests accept either and refuse a mis-assembled map. (c) With `i_size` zero (GATE-S) the end of the file is unknown: the candidate says `file-end-unknown`, is capped at 20 and its artifact is written Incomplete (3C-C3, 3C-C4); the size from leaf blocks is block-rounded, and a lost LAST leaf is undecidable when `i_size` is zero. (d) Holes and preallocated (uninitialized) extents end a recovery; declared holes are declined because a recovered artifact is the concatenation of its runs with no zero fill (3C-R3; the F2FS reader (3D) may take the question up). (e) Orphan inodes with no directory entry are not enumerated; an inode-table scan is out of scope and is a backlog item. (f) Both deleted names of a hard link overlap at 30. (g) A first-in-block deleted record loses its inode number on the 5.10 kernel (and on 6.1 the whole record), so it is `undecided` (`inode=unknown`). (h) Cost and caps: the deleted-ID search is one more tree pass (at most 1<<18 directories, 1<<21 runs and 1<<22 entries, and a directory no larger than the filesystem; a filesystem with more than 4M live entries makes deleted-ID lookups `ErrLimit`, so those entries are `undecided`), and `PrepareRecovery` reads all free space once, uncached, per recovery run; `--list` does not search for leaves, so leaf-only entries are `undecided` there (3C-R25). (i) The inode-bitmap checksum rule is proven on the committed and kernel images (3C-R18). (j) A group that `Unallocated` skips stops every stale map that crosses it (3C-R4). (k) Other kernels are unmeasured. The 6.1 kernel WIPES a deleted directory entry (inode, name length, type and name are zeroed and the record is merged into its predecessor; a first record keeps only its `rec_len`), so files a kernel of that kind deleted are not found by `image recover` at all: nothing is invented and the orphan-inode scan that would find them is out of scope (3C-C1; the 5.10 line keeps the inode and the name of a merged record, and is expected to match the Android GKI 5.10 kernels, which was not measured on a device). Android devices commonly mount with `discard` or run periodic TRIM, which erases freed blocks, so the fixtures (mounted without `discard`) show the best case, and vendor kernels are unmeasured (3C-R30). (l) An unclean (`needs_recovery`) image is read as found, with every candidate assumed `journal-not-replayed` and capped at 40 (3C-R24). (m) The inode-bitmap checksum's lo-only branch (32-byte descriptors, `metadata_csum` without `64bit`) is from memory and proven on builder images only (`TestInodeBitmapChecksumLoOnlyBranch`, 3C-R26). (n) The ctime/dtime consistency check of spec 6.4 only flags `dtime-before-ctime`; it cannot decide reuse, because the dirent holds no generation (3C-R32). (o) A stale `i_size` larger than the filesystem is an `invalid-map` skip, never clamped (3C-R27). (p) An encrypted inode is recovered as ciphertext and flagged; busybox cannot set an fscrypt policy, so it is covered by builder images only. Inline-data files are `unsupported`, a deleted directory is `not-a-file`, and files under a deleted directory are not enumerated.
- ext4 recovery fixtures (plan 3C), what the real images do not cover: (a) No real image reaches the `map-block-not-free` stop: the ext3 reused case ends as a data-run cut at logical block 12, so only builder tests cover that stop, and a mutation there escapes the oracle test (`TestExt4RecoverableMatchesOracle`). (b) The oracle (`ext4_recover_oracle.py`) re-implements the reader's rules from the spec. It is independent code, but not an independent specification: its true maps, free blocks and bytes come from `debugfs` and `dumpe2fs` and the source files, but a misreading of the spec that both share would pass. (c) The same-boot (`deep-same-boot`) results vary from run to run, see the ext4 recovery item above. (d) The fixtures are not byte-reproducible: image and oracle are regenerated together, every test checks the image sha256 first, regeneration may need re-tuning of the scenario ops (the generator fails closed on a family that does not occur), and the Docker images `minutiae-recover-fixtures` and `minutiae-recover-fixtures-510` are kept for it. (e) Not produced by a real kernel (builder tests only): an unclean image, hostile or damaged stale maps, cross-linked or out-of-range map blocks, a leaf index that overflows, a block-map file with a double-indirect block, encrypted inodes and an inline directory.
- `image ls -r --json` prints each walker finding (a cycle, nesting deeper than the walk limit, a path longer than the walk limit) as an item of the array, `{"path": ..., "warnings": [...]}`, without an `entry` key, so a consumer must test for the key; the exit code stays 0, the finding is printed as a warning on stderr but is not an audit entry (ruling F88, F98, F105).
- Recovery artifacts and kinds: a runs sidecar of a recovered artifact is an ordinary artifact of kind `runs` (empty remote path, no `Recovery`, same directory), not a recovered kind, except that the sidecar of a `slack` artifact is its slack map (`slack.runs.jsonl`, `volume-slack.runs.jsonl`: one strict JSON object per line with `offset`, `length`, `image_offset`, `uniform`, `exported` and, for file slack, `fs_path`, `path_escaped`, `fs_id`, `file_size`; read only under the method its artifact names, and an omitted uniform range of an incomplete artifact is a line with `exported` false that occupies no artifact bytes), and `DerivedRuns` and `CheckedRuns` return the exported lines' image runs. The kind `report` is verified by R1 to R5 and noticed (not reproduced byte for byte) except for the F2FS roll-forward reports that check R12 actually rechecked (`MarkRollForwardRan` takes artifact ids; only existing f2fs-rollforward reports count, once each), until 3G adds the reproduction of the other methods; `recover`, `carve`, `slack` and `journal` (block copies, reproduced by R6) artifacts get the same notice only until R6 runs, which it does in every `case verify` of this build, and a `slack` artifact is also re-derived from the filesystem by R11 (see "case verify limits of the recovery rules"); a verify composed without R11 adds a notice for them. A recovered artifact records ONLY the captured prefix runs (the rest is named in `Excluded`, capped at 256 runs), so the sum of its runs always equals its size; its `Content` is `ok` or `uniform` only (no plausibility or format check yet), and a candidate of size 0 is `empty`, one of size above 0 with no runs `no-runs`. Confidence for `post-checkpoint-file` is required with a ceiling of 60 (3H, coordinator ruling C1; the replay never ran, so such data is never high band) and it takes no journal reference; a journal reference is allowed only for `deleted-file` and `journal-report`. The allocation state `unknown` is decided by presence: a filesystem that has any warning after `Unallocated` counts every unverifiable byte as unknown (conservative, and the same in `--list` and a run).
- Recovered-ness propagates through the derivation chain: extracting files from a carved or recovered partition image yields live-namespace (`extract`) artifacts whose records are still recovered records (R7 walks the chain, at most 16 hops, and requires a recovered flag and a confidence not above the lowest along the chain), so a record cannot launder a recovered artifact by being extracted again.
- Recovery run bounds and cost: `--max-files` and `--max-bytes` (defaults 100000 and 8 GiB) apply to `recover` only (`extract` and `unalloc` have no such cap); the uniform scan is part of admission and its total is capped at 4 x `--max-bytes` (reason `max-scan-bytes`, distinct from `max-bytes`; a uniform verdict is cached per identical run list); a run considers at most 1,000,000 deleted entries and plans at most 1<<19 runs by default (`--max-plan-runs` raises it; planning, the overlap passes included, peaks at about 260 MiB of heap at the default, measured by `TestOverlapPeakHeapAtPlanCapStaysBounded`, and about 2.7 GiB at 1<<22), the rest counted as `limit` with one audited warning (`max-entries`, `max-plan-runs`); at most 1000 walk errors are listed (the rest counted by reason, one further-count note). `not-selected` candidates (without `--all-candidates`) are counted in `skipped_by` and `analysis.end` only. Overlap detection is O(n log n): each entry lists at most 16 overlapping partners (`overlap=<id>`) and the attribute `overlap-other-runs=<n>` counts the further overlapping RUNS of other candidates beyond those partners, not distinct owners (a number never claims more than it counts); the overlap confidence cap of 30 is applied per ENTRY, not per candidate: with `--all-candidates` every alternative of an entry whose chosen runs overlap another entry's gets the overlap assumptions and the cap, even an alternative whose own runs overlap nothing, which under-states its confidence and never over-states it. Overlap is also evaluated over candidates that are later skipped (uniform, below the minimum confidence, past `--max-files`), so a surviving candidate can be capped at 30 and name `overlap=<id>` for an entry that is then not written: again an under-statement. A hostile image with N skippable candidates writes one audited `analysis.warning` per skip (about 1.5 ms each, fsynced) up to 10,000 per analysis, then one "further warnings suppressed" entry; the later ones are only counted (`analysis.end` carries `warnings_suppressed`, the summary counts stay exact; `TestRecoverWarningEntriesAreCapped`). The free-space check is advisory and, on Linux, counts `f_bavail` in `f_frsize` units (`TestStatfsUnitPrefersFragmentSize`).
- `case verify` cost of recovered artifacts: R6 reads, for EVERY recovered or carved artifact, the image bytes at its runs and the artifact itself (1 MiB chunks, one container open per parent), so verify time grows linearly with the recovered bytes (up to the 8 GiB default budget per run, more over several runs); R6 runs the artifacts of each parent on up to 4 workers (the report is identical to one worker's, and a finding made before a cancel is kept, so a cancel never turns exit 4 into exit 1) and reports progress as the phase `checks/reproduce` with a byte counter on the status line; the cost is still linear and is not measured, and there is no skip option and no timeout flag by design (nothing may disable a check; the context cancels it); the prebuilt manifest index keeps it linear instead of quadratic in the artifact count.
- `case verify` limits of the recovery rules: `case verify` recomputes, for every `deleted-file` artifact, that its runs lie in the filesystem's `Unallocated()` as this build's reader reports it (R9, default, composed with the drivers of the command line, no flag; `TestAllocationRecheckFlagsRunsInAllocatedSpace`). Carved artifacts of scope `unallocated`, `volume` and `raw` are rechecked the same way (runs in the free space or the table gaps; a raw carve's allocation counts and region recomputed; `TestAllocationRecheckCarvedRawRecomputesAlloc`), a carve of scope `artifact` has no allocation state. `slack` artifacts are reproduced byte for byte by R6 and re-derived from the filesystem by R11 (`examine.SlackCheck`, default, composed with the drivers of the command line, no flag; `slack_rechecked` counts the artifacts re-derived, 0 together with the notice meaning not re-derived): a complete artifact must equal a re-run of the slack plan (every exported segment and the counters of its Params), an incomplete one is checked segment by segment against the file its `fs_id` names now (`TestVerifySlackRecheckFindsForgedSegments`). R11 limits: the recorded `fs_path` is looked up and must name the regular file the `fs_id` names (another file, a directory or a symlink is a problem), except that a path the walk had to escape (`path_escaped`) cannot be looked up, so its `fs_id` is opened and judged by its runs alone; for an incomplete artifact the shared-unit rule (3F-R17/R18, another live file claiming the same allocation unit) is not re-checked per segment (it needs a walk of the whole live tree), only that omitted ranges and exported segments are disjoint, which also bounds the image bytes scanned by the omitted-range check; the units of directories and metadata are not cross-checked (3F-R9); every complete slack artifact costs one re-run of the plan (two walks of the live tree and the tail reads; one re-run serves the file and the volume artifact of one `include_zero` setting). Residuals: journal artifacts remain held by R5's counts only; a later reader that reports free space differently makes R9 report the artifact (a problem, never a silent pass): after a reader change, `case verify` reports earlier recoveries whose runs the new reader no longer calls free (exit 4) until the examiner judges them; a verify composed without R9 (a library `VerifyWith`) says so in a notice, and the report's `allocation_rechecked` counts the artifacts rechecked (0 together with the notice means not rechecked). Each recovered artifact re-reads its whole runs sidecar (up to 1M lines), so N artifacts sharing a sidecar cost N reads. R6's `OpenContainer` re-reads the manifest per parent group, so the indexed open applies fully only to the `scope=artifact` carve path. The `archtest` scanners of the recovery rules are review aids (they stop mistakes, not a determined author): string conversions of a kind, a function result as a `Kind` and positional `Source` literals are not seen; the real defence is `case verify`. A carve recorded with scope `artifact` (an export, or an imported image carved through `--artifact`, ruling 3E-R9) gets no R9 or R10 recomputation: its allocation is unknown by rule and it carries no gap note. Verify checks that it sits in `carved/raw` and that its parent is not an unallocated export, but a carve of an imported image relabelled `artifact` cannot be told from a legitimate one by manifest data alone, so it loses the allocation recheck (lost information, never a false claim).
- Slack export (plan 3F, `image slack`, `examine.ExportSlack`): file slack is the tail of the last allocation unit of a live regular file, nothing else. Not exported (3F-R2): the exFAT range from `ValidDataLength` to `DataLength` (allocated, but reported as a hole), FAT chain clusters past the size, preallocated or unwritten extents, directories, symlinks, deleted files, encrypted files. Not exported (3F-R8): the unaddressed tail inside the filesystem (FAT sectors after the last whole cluster, F2FS blocks after the main area) and pre-data gaps; the units of directories and metadata are not cross-checked against a file's tail (3F-R9). Caps (3F-R10): at most 1,048,576 segments per run (the cap counts candidates, so a filesystem with more files that have tails ends with `max-segments` even when the tails are zeros), 64 MiB of path text (the paths of the candidates held in pass 1, and the exported labels; either ends the run with `max-path-bytes`), `--max-bytes` exported bytes, and a scan budget of four times that for the tail reads. HFS+ and APFS are refused (`ErrNoSlack`). The cost is two walks of the live tree (no file content read) plus the tail bytes. R11 does not re-derive the shared-unit rule (3F-R9, R17) for an incomplete (narrowed or cut) artifact: a forged sidecar of such an artifact whose segment lies in a unit that another file also allocates is not found (the segment is still a tail of the file its `fs_id` names, and an exported file segment of a COMPLETE artifact is re-planned in full). Unchecked files (3F-C2): a live file that cannot be opened leaves its units unknown, the artifact is incomplete and its artifact carries the assumption `shared-unit-unchecked`. No acquisition-gap note is written. A run map lists at most 1,048,576 omitted ranges; more are counted (`omitted_unlisted`), never silently cut.
- Slack fixture coverage (plan 3F, Task 12): the four kernel-written slack images (`tools/fixtures/README.md`, "Slack fixtures (3F)") do not cover the exFAT trailing hole (`ValidDataLength` below `DataLength`): the kernel exfat driver zero-fills a truncate-extended file, so no such file can be written, and that reader path (3F-R2) is tested only on built images. On FAT and exFAT a truncate-extended file is fully allocated and zero-filled, so only ext4 and F2FS fixtures contain a real hole (`trailing-hole`). ext4 and F2FS leave zero tails (every slack tail there is uniform), so residue that is not uniform is exercised on FAT and exFAT only. FAT32 has no kernel-written slack fixture (the FAT16 image stands for the FAT family; FAT32 is covered by built images only). The images are not byte-reproducible: image and oracle are regenerated together.
- `declared_runs_artifact`: an artifact whose copy was interrupted (cancel, read error) keeps its captured prefix as runs, and the full run list the filesystem declared stays in the case as a `runs` sidecar named by `Recovery.declared_runs_artifact`; it is provenance of what was declared, never of what was captured, and is not used to reproduce bytes. Scope reconciliation: the earlier rule that a carved scope is limited to raw and unallocated is superseded by spec 5.2, which lists `unallocated`, `volume`, `raw` and `artifact`.
- The free-space check is advisory: the output volume can fill after it passes, which is a case-write failure and aborts the run (`analysis.error`, partial artifacts kept and flagged). The check uses the space available to the calling user (Windows: `lpFreeBytesAvailableToCaller`, so quotas count) and saturates at the largest int64 when the OS reports an overflowing value. `case verify` decodes `manifest.jsonl` strictly (unknown, misspelled-case, duplicate and omitted-by-this-build keys are problems naming the line and key, at most 50 listed; a key missing whose zero value matches is tolerated; `TestVerifyManifestStrict`); the open path (`Manifest`, `OpenArtifact`) stays lenient (`TestManifestOpenStaysLenient`).
- Recovery audit anchor: as for the records database, the audit chain has no external anchor unless the examiner took one (`case anchor`, see the records audit anchor line; it covers only the log up to the anchor), so a forger who can append valid, correctly chained audit entries after the last anchor (and rewrite the manifest and the artifact consistently) is not detected by `case verify`; R6 still catches artifact bytes that do not equal the image at the recorded runs, so a forgery must also rewrite the parent image artifact, which changes its hash in every derived record and in the audit.
- Carving, SQLite and binary plist layouts from memory (plan 3E, `internal/carve/validate_sqlite.go`, `validate_bplist.go`): the SQLite 3 database header (page size at 16 with 1 meaning 65536, file format versions, the 64/32/32 payload fractions, change counter and version-valid-for fields, in-header page count, freelist fields, text encoding, schema format) and the page 1 b-tree type byte, and the binary property list trailer (32 bytes: offset size, reference size, object count, top object, offset table offset) and object marker nibbles are written from memory of the SQLite file format and the property list format, and are checked only against the `sqlite3`-produced and Python-encoded fixtures and the independent `carvetest.SQLiteHeader` and `carvetest.BPlist` builders. The validators prove structure, not integrity: no page past page 1 is read and no plist object is parsed, so a database or plist with damaged content but a consistent header or trailer is accepted. A legacy SQLite file without a valid in-header size (page count zero, or change counter different from the version-valid-for field) cannot be sized and is `bounded` to the window end with the assumption `size-from-header-invalid`. A binary plist ends at the first trailer-shaped position that is consistent with its offset table, so a plist nested inside another object's payload may be taken as the outer object's end when the inner trailer is consistent. A plist that is not followed by a consistent trailer inside the window is rejected `no-trailer`.
- Carving, ISO-BMFF layout from memory (plan 3E, `internal/carve/validate_bmff.go`): the brand table (HEIC `heic`/`heix`/`heim`/`heis`/`hevc`/`hevx`, HEIF `mif1`/`msf1`, `qt  `, `3gp*`/`3g2*`, the MP4 family, anything else the generic `isobmff`/`bmff`), the top-level box list the walk continues over (`moov mdat free skip wide uuid meta moof mfra sidx ssix styp pdin prft emsg udta junk pnot`), the `ftyp` size window (16 to 4096, a multiple of 4 after 16), the `moov` child tiling with a required `mvhd` and the `meta` FullBox with the `hdlr` handler type at payload offset 8 are written from memory and checked only against the encoder fixtures. The object ends at the first byte that is not a known top-level box, so a trailing run that happens to start with a known box type is included, and a known-type header whose box does not fit the window rejects the whole hit as `truncated`. A QuickTime file without an `ftyp` is not carved. A last box of size 0 gives a `bounded` object to the window end (`box-extends-to-end`). The `meta` box is judged only for HEIF brands, a non-HEIF `meta` layout is not checked, and only the first `hdlr` of a `meta` counts. Media data and sample tables are never read, so a structurally valid file with damaged samples is validated. Plan 3E2 adds three brands, all from memory: `avif` (types `avif`, needs a picture `meta` like HEIF), `avis` (an AVIF image sequence, types `avif`, needs a `moov` with an `mvhd`) and `crx ` (Canon CR3, types `cr3`, needs a `moov` with an `mvhd`). AVIF is typed by the major brand only: an AVIF whose major brand is `mif1` stays `heif`, which is not wrong but is less specific. CR3 is built only by the independent test encoder: its identity and layout are from memory and have never been checked against camera output. An ftyp-first object whose major brand is `jxl ` is rejected as `jxl-without-signature`: the JPEG XL signature box in front is the true start, and the scanner finds that offset by itself.
- Carving, ZIP and PDF layouts from memory (plan 3E, `internal/carve/validate_zip.go`, `validate_pdf.go`): the ZIP local header, central directory record and end-of-central-directory (EOCD) layouts and the APK, JAR and OOXML identity name rules (`AndroidManifest.xml` with `classes.dex`; `META-INF/MANIFEST.MF`; `[Content_Types].xml` with a `word/`, `xl/` or `ppt/` name) are written from memory, not from a published schema; identity reads only the first 32 bytes of each central-directory name, and no entry data is read or inflated, so a corrupt entry inside a consistent directory is still a validated archive. ZIP64 (a `0xFFFF`/`0xFFFFFFFF` field or a ZIP64 locator before the EOCD) is rejected `zip64` and a non-zero disk field is skipped and counted `multi-disk`, so a ZIP64 or multi-disk archive is never carved; an archive whose EOCD lies outside the hit window or whose directory offsets are off (a spliced or partly overwritten archive) is `no-eocd`. The ZIP search is forward from offset 30 and passes over entry data, so a stored archive inside an entry is skipped only when its own offsets do not hold in the outer archive. The PDF end is found by `startxref`, an end of line, a decimal offset, an end of line and `%%EOF` written contiguously; the offset must lie before that `startxref` and point at `xref` or at `<digits> <digits> obj`, relative to the PDF header, so a PDF with data in front of its header or with other whitespace between the keywords is `no-eof`. The object ends after the LAST counting `%%EOF` before the next `%PDF-` at a multiple of 512 in the window (the window does not carry the scan unit), so a following PDF at an unaligned offset is taken into the length and an embedded uncompressed PDF at an aligned offset ends the outer one; nothing in the body is parsed, so a PDF that is a cut-and-spliced concatenation of revisions is a `footer` hit, never `validated` (confidence 50). When the scan unit (`Align`) is above 512, an embedded `%PDF-` at a multiple of 512 that is not on the scan unit ends the footer search early (the outer PDF is then cut short or rejected `no-eof`). ZIP64 is detected through the `PK\x06\x07` locator at `p-20` (and the `0xFFFF`/`0xFFFFFFFF` EOCD fields); a ZIP64 archive whose locator is missing or damaged and whose EOCD fields are not saturated is not recognised as ZIP64. A stray `PK\x05\x06` with a non-zero disk field is `multi-disk` only when its count, size and offset fields are plausible, otherwise it is skipped. A zero-padded `startxref` offset is read by its significant digits (at most 15).
