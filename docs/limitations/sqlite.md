# Limitations: SQLite library, decoder and record recovery

What the current build does not do, does approximately, or has validated only on builder data, for `internal/sqlitefile`, the table decoder `internal/decode/sqlitedb` (with `cellx`, `rowrun` and `recrun`) and record recovery in `internal/dbrecover` (`sqlite recover`). Part of the [known limitations](../limitations.md), which say how to add or close one.

- SQLite file library (sub-project 3, plan 3I, `internal/sqlitefile`; the typed recovery pass and the generic `db_row` run are done in plan 3J, `internal/dbrecover`, see the 3J item below): the library reads, it never opens an engine, creates a file or writes. `Live()` is the state the SQLite engine would present: the database plus the committed frames of the current WAL generation, and a VALID HOT journal is applied in memory (before-images override database pages, playback stops at the first bad record checksum as the engine does); nothing is written to the evidence or next to it. `AsFound()` is the raw view (the file plus the committed WAL overlay, no rollback); nothing uses it by default. A hot journal that names a super-journal is applied only when the caller says the super-journal file exists (`Options.SuperJournalPresent`), because the library cannot see other files; the engine's behaviour with the file absent is matched. Read-only copies and locks are not modelled: the engine refuses to roll back a journal on a read-only database file and does not treat a journal as hot while a live writer holds a lock, where `Live()` presents the rolled-back state (the `journal-hot` warning is raised either way). A journal whose header declares more records than the file holds is `journal-truncated` (and `JournalInfo.Truncated`, and `truncated` in the `analysis.end` journal facts): the file cannot tell a cut file from a damaged count, the records present are read and the engine plays back the same ones (`TestTruncatedJournalLiveEqualsTheEngine`).
- SQLite file library, deliberate deviations from the engine (each fails closed with a warning, never guesses): a WAL frame or database page that reads past the end of its file is unavailable, never zero-filled (`live-pages-unavailable`, at most one warning per file kind, with counts); a journal initial size above the file size is not zero-filled (`page-count-clamped`); a trailing partial page counts as a page like the engine but its missing bytes are unreadable, never zeros (a cell that reaches past the end is a damaged cell with a warning, and `History` yields the partial page marked `Partial`); a hot journal that is NOT applied (page size differs from the database, or the record or segment limit is reached, so a partial rollback would mix two states) makes `Live()` fail with a typed `LiveUnavailableError` plus a warning, and while `Live()` is unavailable `History`, `Pages` and `Summary` return the same error (no history rows are delivered with an unknown relation to live; `AsFound()` stays available for the raw pages); a WAL whose re-sealed header carries an unsupported version makes `Live()` fail the same way, as the engine refuses such a database; a valid-header WAL is applied whatever its page size (the first database-page-size bytes of each frame are read) and a header-invalid WAL is ignored (`wal-header-invalid`). The journal edge rules (journal page size 0 means the database page size, a zero-length super-journal file is absent, a journal under 512 bytes is not played back while one between 512 and 4096 bytes is, a super-journal name over 1040 bytes is not a trailer, page 0 and the lock-byte page end playback, a page above the initial size is skipped, the last write of a page wins, a hot journal and a WAL are applied rollback first) are those 47 engine probes of `TestEngineJournalRules`; an anomaly the engine does not mind but a reader should (`journal-and-wal`, `journal-duplicate-page`, `journal-page-size-mismatch`) is a warning. Other unmodelled engine behaviour: a WAL beside a rollback-mode header (bytes 18/19) is applied as the engine's probe shows (`wal-mode-mismatch`), the `-shm` file is ignored, and a database whose file is empty but whose WAL is not cannot be `Open`ed (use `ScanWAL` standalone).
- SQLite file library, WAL frames and values: the frames the engine does not apply (uncommitted tail, a broken frame, frames after a break, frames of an older generation) are not live; one `wal-frames-not-applied` warning per scan counts them by class with the first slot of each, and they are History's (`sqlite-wal-uncommitted`, `sqlite-wal-stale`). A live text value over 4 MiB or blob over 64 MiB, a value in a truncated overflow chain, a virtual generated column and a non-literal default are NOT materialized: the value carries `Omitted` (with its true `Len`), every omission is counted in a warning, and the decoding layer must report it as absent; a recovered value over 1 MiB is clipped and marked `Clipped`. Serial types 10 and 11 read as NULL with a `record-reserved-serial` warning (the engine does the same) and the header's text-encoding field is read as the engine reads it. Every allocation is charged to the `Budget` (a nil budget gets an internal 1 GiB one, there is no unbudgeted mode), every count is sized from the physical addressable page limit and never from a declared count, and a limit that is reached ends the work with `limit-reached` and a warning, never silently.
- SQLite file library, schema and lookups: `Table.Get` is `ErrWithoutRowid` for a WITHOUT ROWID table (it has no rowid); `GetByKey` (`Table.GetByKey`, `View.LookupKey`; the decoder's `Table.GetByKey`) finds its row by the primary key under the key's collations, applying the key columns' affinity to each value (text is put in the database encoding), and answers "absent" only on a path proven in order: every page on the path has its entries strictly increasing and inside the range the ancestors' entries give it, and a miss at a side of a leaf that has a bound reads the adjacent leaf's entry next to the bound. Damage on the path is a `CorruptError` ("the row may exist"), a comparison it cannot make (a custom collation, text invalid in its encoding, an unread value, a real against a TEXT key column, whose spelling is the engine's) is `ErrKeyUndecided`, and a key of the wrong length, a NULL or NaN component, a table with rowids or an unparsed definition is `ErrBadKey`. A lookup is bounded like a scan (the visited set, the depth cap, the budget). "Absent" means absent from the path the key's search takes, not from the file: a lookup proves the pages it reads, so an entry placed in another subtree than its key belongs to is not found by its key and the lookup does not report it. The ordered scan does: it compares every entry with the previous one AND with the range its ancestors' separators give its subtree (an index-tree separator is itself an entry; a tie with a bound is damage only where the key is unique), so every entry outside its range is flagged, a misplaced run included, and a row the scan delivers unflagged is never answered absent by a lookup of its key (it is found, or the answer is a `CorruptError` or `ErrKeyUndecided`; `FuzzGetByKey`). A custom collation in a later key column can make every lookup `ErrKeyUndecided`, because the order of stored neighbours that share the earlier columns cannot be proven (fail closed). A miss at the end of a leaf whose sibling lies under another mid-level page reads up to 2 x depth - 1 pages. `Get` reads an overflow chain as the engine does even when another row shares its pages (only a scan or `case verify` of the artifact reports the sharing); an index tree or WITHOUT ROWID table is checked for key order against the engine's comparison (`Table.Rows` of a WITHOUT ROWID table, `Index.Entries`, `View.ScanTreeOrdered`): an entry that does not follow the previous one is delivered flagged (`KeyRangeViolation`, a `btree-order` warning), and so is an entry that repeats the key of the previous one in a unique key (the WITHOUT ROWID primary key, a unique index when no key value is NULL), and so is an entry outside the (lower, upper) range the separators of its ancestors give its subtree (each check flags the entry at fault, never both entries of a pair; the bounds are charged clones, at most two per open level); an entry it cannot compare (a custom collation, text of an expression column, an unread, omitted or clipped value, a short record, an automatic index) is counted in one `key-order-unchecked` warning per scan, never skipped silently and never a violation, and ties of a non-unique index are not judged. A doctored table-tree interior key is flagged by the rowid check. A lookup by key in an index (as opposed to the primary key of a WITHOUT ROWID table) is not implemented. The CREATE parser is tolerant and refuses what the engine refuses (duplicate column names, STRICT types): an unreadable or over-cap definition leaves the table unparsed with a warning (columns unknown), never a failure; views and triggers are listed, not interpreted. Virtual tables are not interpreted. In `sqlitefile` they are listed in `Schema.Objects` (`Virtual`) and `Table()` is `ErrVirtualTable` (never `ErrNotFound`, because the table exists). In the decoder `Tables` excludes them, `VirtualTables` lists their names, and `Table` is an `UnsupportedSchemaError` naming the virtual table that also satisfies `errors.Is(err, sqlitefile.ErrVirtualTable)`; their shadow tables read as ordinary tables. A table whose schema row names a root page that cannot be a b-tree root (0, 1, past the addressable limit) is a warning and `ErrCorrupt`, never `ErrNotFound`; that rule is for the root-page case. In general `Table` and `Index` answer `ErrNotFound` only when the schema was read cleanly (`Schema.Skipped` is 0); after any skipped or contradictory schema row, a name that is not found is an `ErrCorrupt` error ("the schema was read incompletely"), because the object may be among the lost rows (`TestTableAndIndexAreNotAbsentAfterASkippedSchemaRow`). Cells found outside any pointer array (gap, freeblock, orphan page, freelist trunk tail) are plan 3J's: 3I only exports the free-space spans and counts; History ignores interior index cells (counted as `InteriorSkipped`).
- SQLite file library, recovered rows are LEADS with an honest label, never facts (`History()`; spec 3 section 3.3, the confidence rule is `Confidence`): a row's table is named by the schema the IMAGE itself had when it was written (the as-of schema read from the same snapshot; basis `schema`), and only when that schema is unavailable (a stale generation without its schema frame, a damaged as-of schema, a page beyond the as-of state, the state cap reached) does the label come from a fit of the cell shapes (`fit` capped at 60, `guess` at 40, `none` at 30), always with the note `identity-by-fit-only` and the relation `unknown`: a fit is never compared with a live row, so a dropped table is never reported as a modified row of another. Accepted residuals: (1) a dropped table whose shape matches exactly one live table is labelled by that live table (basis `fit`, 60, `unknown`, `identity-by-fit-only`), which can name the wrong table, and the examiner is told by the basis and the note (ruling C46); (2) rows whose as-of owner is unprovable are NOT deduplicated against live rows, so a row equal to a live row can be listed; a row named by the column fit alone that equals a live row of its fitted table byte for byte carries the note `equals-live-row` and nothing else changes (C45, closed in 3J); (3) a label on the schema basis needs every cell of the page to fit the named owner strictly, a page that fits only loosely gets `fit` or `guess`; (4) rows of a WAL generation with no schema frame carry the fit basis and `owner-changed`; (5) the strict fit refuses a record missing a rowid-alias column (ALTER TABLE cannot add one), STRICT tables can be ambiguous, and the fit is bounded by a step cap past which every fit is `limit-reached`; (6) pages the layout cannot attribute because the schema was read incompletely are counted in one `pages-unattributed` warning and NOT listed, because they may be live pages of unread tables; (7) the overflow of a stale cell is followed only under the snapshot rule (the chain as of the image, never from today's pages). `uncommitted` is an ORIGIN fact (`Origin`), not a relation: the relation of EVERY row whose identity the schema does not prove (basis `fit`, `guess` or `none`) is `unknown`, whatever the origin, and only a schema-basis row from an uncommitted origin carries the relation `uncommitted`. Row identity for WITHOUT ROWID history compares numerically across kinds (1 equals 1.0) under BINARY, NOCASE (ASCII folding only) and RTRIM, with the key clause's collation; any other collation or an undecidable key gives `unknown`, never `absent` (rulings C48 and C53). The method token `sqlite-journal-rolledback` (base 45) labels page images the rollback hides; every confidence number has a proving fixture (`TestFitTiersProveConfidenceNumbers`).
- SQLite record recovery (plan 3J, `internal/dbrecover`, `sqlite recover`): (a) `db_row` records values as stored (no `ts`, no interpretation); the rows of tables a parser claims are typed by the parser's own recovery pass (plan 4G), which does interpret time, and `sqlite recover` runs that pass first. (b) The claims exclusion is operator-supplied (`--exclude-table`, claimant `examiner`; narrowing, see (k)) or supplied by a concluded typed pass (`ExcludedTable.Typed` with the typed analysis id; not narrowing, because the typed pass recorded that table's claimed rows; `sqlite recover` wires it in the composed command of plan 4G). A claimed row the typed pass could not map is named to the generic run by `Options.KeepClaimed` (16-byte locator digests, at most `MaxKeepClaimed` = 65,536, else a bad-option refusal) and is written as a `db_row` (`kept_unmapped_claimed`; a digest collision can only keep a row that was not asked for, never drop one). The exclusion applies to table rows of basis `schema` or `fit` whose values fit the LIVE definition of the claimed table strictly (`sqlitefile.ClaimMatch`, one predicate shared with the typed pass): a row named by `guess` or `none`, an index entry, a row carved from page slack, and a schema-basis row that no longer fits today's definition (a dropped and recreated table) are never excluded and stay `db_row` (4G-R3, R22; the parsers spec 12.2 listed `guess`, which is not claimed because identity never comes from a guess). In-page deletions (deleted cells left in the free space of a live page, `secure_delete = OFF`) are recovered only as `db_row`, never typed. A `fit` row is attributed to the claimed table by structure only: a dropped table of the same shape as a claimed table is excluded as if it were that table (`identity-by-fit-only` stays on the rows that are written), and a same-affinity column reordering after a drop and recreate cannot be detected by a fit. (c) Sibling pairing is by name within one acquisition, and a WAL carries no database id, so a same-named WAL of the same acquisition is paired by name only (an ambiguous set is refused, a WAL of another acquisition is not paired); a backup-kind database reports "none found" for siblings: the 4E host step `ResolveBackups` (plan 4E) names backup databases and their `-wal`/`-journal` for the parsers, and `sqlite recover` passes the `-wal`/`-journal` that the same backup's hash-checked Manifest.db names to `dbrecover` as explicit companions (plan 4H, `TestSQLiteRecoverPairsBackupSiblingsByManifest`); an encrypted or unresolvable backup names none and says why (a stdout line and `backup_siblings.reason` in `--json`), a `-wal`/`-journal` the Manifest.db lists but the case does not hold, held backup files that have no logical path (a companion may be among them) and listed companion paths beyond the 4096 kept (a path the Manifest.db lists again under another file ID is kept once and does not spend the cap, `TestReadFilesCompanionsAreDeduplicated`) are each reported as a `backup siblings warning` line and in `backup_siblings.warnings` (never silently absent), two held files listed under one companion path name nothing (ambiguous, exit 1 through the typed pass), and a Manifest.db that fails its hash check is exit 4 before anything runs. (d) `SuperJournalPresent` is not modelled: a hot journal that names a super-journal is not applied, and `analysis.end` records `has_super_journal` and the reason the journal was not applied. (e) The inference of the rollback-journal sector size (512 to 65536 by nonce consensus, `JournalInfo.SectorSize`, `NonceDerived`) is a library inference, not a stated fact: a persist-mode journal with a zeroed header is read on that inference, and the test derives the sector from the journal bytes independently. (f) Slack carving (`sqlite-page-slack`, confidence 25, probe-enabled J5) carves strict cells from free space only: on engine pages the probe recovered 23 of 25 deleted rows and invented none; a freeblock whose first four bytes the engine overwrote is counted in `SlackUnparsedBytes`, not recovered; the free space of index pages is not carved (counted); a page whose carved cells include one stray cell is fitted as a whole and so leaves all its carved cells without a table (J86); the crossed-cell rule can drop a genuine cell that overlaps a later structurally valid cell head (counted as `slack_dropped_crossed` in `analysis.end`, `SlackDroppedCrossed` in `Counts`, J89); the other slack counters are `slack_copies_of_live`, `slack_unparsed_bytes`, `slack_dropped_overlap`, `slack_cross_page_equal`, `slack_work_capped_pages` and `slack_row_capped`; the cost of the clone, the decode and the crossed check of a cell is charged to the page work budget before it is spent (J121), and a check that cannot be paid for leaves the cell undelivered and the page capped; a page whose work cap is reached, or a slack row cap that is reached, narrows the run (k); freelist-trunk tails are carved with the region `freelist-trunk` and identity by fit only. (g) `secure_delete`, iOS and Android databases are unvalidated on real devices: the oracle covers engine-written databases, the manual `realimages` harness (`TestRealImagesRecoveryDatabases`, 3K) exists and no real-device run is recorded. (h) `Live()` unavailable fails closed: a database whose live state cannot be built is refused, never recovered against an assumed live state. (i) Defaults and ceilings: `--max-records` 1,000,000 (ceiling 50,000,000), `--max-bytes` 8 GiB, `--max-fit-equality-rows` 1,048,576 (ceiling 2^29, see (o)), row payload cap 8 MiB (ceiling 12 MiB), row body cap 256 KiB (ceiling 1 MiB), `--timeout` none by default; a limit stops the run cleanly and the run concludes `incomplete`. (j) Mixed or incomplete inputs (a recovered artifact among them, a WAL discovered but unusable, a sibling unused) are flagged on the rows and in `analysis.start`/`analysis.end`; the confidence of a row is capped by the lowest input. A recovered input whose cap cannot be read (labelled recovered with no description, no confidence anywhere on its derivation chain, or a chain that ends at a missing parent, a cycle or the depth bound before one is found) is capped at 25, the lowest base confidence of a 3J method in spec 3.3 (`sqlite-page-slack`), and every row carries the note `recovery-cap-unknown`, counted as `recovery_cap_unknown` in `analysis.end` with one warning; a chain cut after a confidence was found is an unknown cap too, because a lower confidence may lie beyond the cut (`RecoveryTrail.Cut`, `TestDBRecoverCutTrailIsUnknownCap`, J116); residual: the records validator and `records show` still read the confidence found before the cut, and `case verify` reports the cut chain itself (exit 4). The row says how each companion was paired in `sibling_pairing_wal` and `sibling_pairing_journal` (`explicit`, `by-name` or `none`, J119). (k) A narrowed run concludes `incomplete`, keeps the rows it wrote and never supersedes a full run. Narrowing is a filter (`--methods`, `--min-confidence`, `--exclude-table`; an exclusion made by a concluded typed pass is not narrowing), a run limit, or a loss of rows: rows the writer refused (`writer-rejected`), a slack page whose work cap was reached (`slack-work-cap`) and a slack row cap that was reached (`slack-row-cap`). Clipping a payload or a body is not narrowing: each row is flagged and the row set is complete. The summary prints `incomplete: <reasons>` and the top-level JSON `incomplete` follows the ingest outcome (J112, J125); a second run over the same inputs is refused unless `--allow-reingest` is given. (l) The chain test (`TestSQLiteRecoverChainFromDeletedDatabase`) runs on the MTFS stand-in and on a FAT16 builder image deleted the way the vfat driver deletes (`TestSQLiteRecoverChainFromFATImage`, 3K-R4); no kernel-written image holds a deleted database (backlog). (m) B14 is closed (the history comparison of a WITHOUT ROWID row follows `EqualityKey`; the four behaviour changes and the J103 rule are in the invariants) and C45 is closed (a fit-only row equal to a live row is annotated `equals-live-row`). (n) `FuzzRun` runs under `go test` on its seeds only: a `go test -fuzz` run stalls in the worker (8 executions in 30 s, J74) and is a backlog item. `FuzzSQLiteDB` stays one target: the stall seen there is the fuzzer's minimisation and its counter, not the body (LX-8 measured 2888 executions per second on Linux with minimisation off, and a seed median of at most 0.01 s), so it is not split. (o) The fit-only equality (the note `equals-live-row` on rows named by the column fit alone) reads live rows within its own budget (`Limits.MaxFitEqualityRows`, `--max-fit-equality-rows`). Spending it, a fit-mode `MaxDiffRows` hit and a refused memory charge are annotation limits, never run limits: the affected rows get the note `fit-equality-budget` (the equality is unknown, never "not equal"), are counted as `fit_equality_capped`, one audited warning names the cause and the count, and the run, its rows and slack carving continue (J110).
- SQLite file library, validation limits: the library is held to the SQLite engine of `modernc.org/sqlite` (3.53.4) on engine-made files and to the Debian `sqlite3` 3.46.1 on the container family (class C), plus a builder; NO fixture comes from a real application or a real device. Android and iOS behaviours of `secure_delete`, `VACUUM`, journal modes and WAL resets are therefore unvalidated on real devices. Engine-written WAL and journal fixtures are not byte-reproducible (regenerate with their oracle). The tagged matrix (`-tags sqlitematrix`: 45 live scenarios, 1448 WAL mutations) passed with 0 library/engine divergences and no copy-retry fallback in any oracle test at the time of plan close-out and again after the final review fixes (45 live scenarios; 1448 WAL mutations, 1443 equal to the engine's view and 5 refused by the engine); the pinned Docker layer (`sqlite3=3.46.1-7+deb13u2`, a package version that leaves the archive when superseded, so a later rebuild fails loudly) was built and verified on 2026-10-08 (`dpkg-query` shows `sqlite3` and `libsqlite3-0` at 3.46.1-7+deb13u2, `sqlite3 --version` is 3.46.1, the layer's own version tests passed; no fixture was regenerated), and `docker build` of the main fixture image uses an unpinned `debian:stable-slim` base (backlog). The race detector is not part of the per-task check; the coordinator's `check.sh --race` is the merge gate for `sqlitefile`.
- SQLite file library, residuals of the final review (plan 3I): (1) a WAL frame or journal record states its own page number; an impossible one is flagged `invalid-page-number` (closed in the final review, `TestStatedPageNumberMustBePossible`): the number 0, the lock-byte page, a number above `Limits.MaxPages`, and for a journal with an intact, non-zeroed header a number above its initial size; the flag is on the image and its rows (relation `unknown`, one counted warning per file). What is inherent: a WAL frame past the database's end is not impossible (an uncommitted tail may extend it) and is flagged only when committed beyond its commit size. (2) The comparison of a history row with the live row is `unknown` (note `value-unread`) when a scalar of either side was never read; a value that is not stored (a short record's default, a virtual generated column) is not `Unread` and compares equal to its counterpart. (3) A WITHOUT ROWID table with DESC key columns was once measured labelled `owner-changed` with relation `unknown` (38 rows in one scenario of the final review of plan 3I): safe, never wrong, and imprecise. That scenario is not reproduced: engine-written databases with `PRIMARY KEY(y DESC, x DESC)`, `x REAL` holding integers, the key columns declared before or after another column, one or both columns DESC, a rewrite, a delete and a changed key, in the write-ahead log, all give their history rows `BasisSchema`, a decided relation and no `owner-changed` (`TestWithoutRowidDescKeyRowsKeepTheSchemaBasis`, `TestWithoutRowidDescKeyVariantsKeepTheSchemaBasis`). The probe file of that review was not kept and is not available. Further variants (freed-page reuse, no checkpoint, 4096-byte pages with a deeper tree, `ALTER TABLE ADD COLUMN` after the rows were written, a DESC NOCASE text key) also give the schema basis, and a dropped-and-recreated table stays `owner-changed` (`TestWithoutRowidDescKeyMoreVariants`). The refusing check is not named, because no refusal was seen. An unexplained refusal is never labelled `BasisSchema`: the label stays `unknown`, with the note `owner-changed`; if a file shows it again, that file is the reproduction to keep. (4) Closed by `FitCells`: a truncated record, or one with a reserved serial type, cannot support a strict fit, so the page is named at `BasisGuess` at best (`TestFitCellsTruncatedCellNeverFitsStrictly`, `TestHistoryRowOfATruncatedRecordIsNotNamedByAStrictFit`); `FitPage` keeps receiving values only, and a page reachable from the schema is still the table's by reachability, not by shape. Slack carving takes only complete cells without reserved serial types, so its cells never carry the flags (`FitCells` is used there as defence in depth). The trade-off: one truncated or reserved-serial cell denies the strict tier for its whole page, so the other, whole cells of that page are named at `BasisGuess` too (fail closed; a page is named by the shape of all its cells). The history cannot see a cut chain from the record header, so when the fit is reached (a page no schema object owns; never for an owned page) each spilling cell is probed: the last byte of its payload is read through the chain. The probe has a page budget of its own, `Limits.MaxHistoryOverflowPages`, apart from the pages the history follows for the rows, so one `Rows` call reads at most twice that many overflow pages (2 x 16,777,216 by default) in the worst case (the probe charges a page that several cells of a page share once per cell, which is conservative and stays within that bound); when the probe reaches its cap it records `FitProbeOverflowPages` in `LimitsHit` with a `limit-reached` warning, counts the cell it could not probe as truncated and gives the page the note `fit-probe-limit-reached` (`TestFitProbeCapIsCountedAndDenies`, `TestFitProbeDoesNotRunOnAnOwnedPage`). (5) `record-length-mismatch` is a warning at the cell and also marks the row (`Row.LengthMismatch`, the recovered-row note). (6) A repeated column in a primary key list under two collations stays unparsed (the engine keys the index by both); a tree between 21 and 32 levels is read, because it is evidence, with a `btree-depth` warning, and every row it delivers carries `BeyondEngineDepth` (decoder: `FlagBeyondEngineDepth`; index entries are flagged at the `sqlitefile` layer only) because the engine would refuse it. When the schema tree exceeds that depth anywhere the engine refuses the whole file, so every row of every table is flagged (`Schema.BeyondEngineDepth`, `Table.SchemaBeyondEngineDepth` at both layers, `FlagBeyondEngineDepth` on scanned, fetched and recovered rows), `Info.EngineRefuses` says "schema tree deeper than the engine follows", and recovery (`dbrecover`) refuses the database; the same gate now covers every schema-derived reason (name mismatch, orphan index), and a schema that cannot be read at the gate is the same `engine-refuses` refusal (naming the read error; an unavailable live state keeps its `live-unavailable` reason and only a cancelled context is reported as itself), never a pass. (7) The schema-derived reasons in `Info.EngineRefuses` (at most 16, a name or `tbl_name` that disagrees with its statement, an index or trigger on no table) appear only after the schema was read; the name check applies to statements within `MaxSchemaSQLBytes` that the head parser can read, with names compared ASCII case-insensitively. (8) The warning-code set is closed and now has 52 codes (`record-length-mismatch`, `wal-page-invalid` and `hdr-schema-format` were added by the final review; `journal-truncated` and `key-order-unchecked` were added by LX-4).
- SQLite table decoder (plan 4B, `internal/decode/sqlitedb`): (a) the layer inherits the reader's limits; rows the reader skips with a warning are not delivered, and an index built from such a scan is lossy: every miss on it is `ErrKeyUndecidable` naming the loss (never empty) and a hit carries `JoinUndecided` (B76; the loss is the reader's per-scan count of skipped pages and cells, never a warnings delta); the reader de-duplicates and caps warnings, so `Stats.NewWarningsAtLeast` and `Warnings()` are a lower bound, never an exact count; a change to `decode/sqlitedb` or to the `sqlitefile` equality export changes the hash of every parser that imports them. (b) `Files` has no super-journal flag (B8). (c) Bundle completeness is the host's: `Info().WAL == nil` only means none was supplied. (d) Joins use the engine's equality and its affinity rules. INTEGER/REAL/NUMERIC, TEXT (BINARY, NOCASE, RTRIM) and blob keys compare as the engine does, under the TARGET column's collation. A key whose own affinity is weaker than the target column's is converted before the comparison, exactly (D2): a TEXT or no-affinity source column against a numeric target column (the engine applies NUMERIC affinity to both columns), as a literal key is. Two columns of which neither has numeric affinity (a no-affinity source against a TEXT target, which the plan expected to convert, included) are compared as stored by the engine, so the layer converts nothing there. A numeric-looking text that cannot be converted exactly is `ErrKeyUndecidable`, counted in the join report, never an empty answer. The other direction converts the TARGET's values: a numeric source column against a TEXT or no-affinity column meets the target's numeric-looking texts through their numbers (the engine applies NUMERIC affinity to the text), exactly or ErrKeyUndecidable, as above; the index keeps up to one extra entry per numeric-looking value of such a column (counted toward the index limit, charged and released), so an index over a TEXT or no-affinity column reaches ErrIndexLimit earlier, and a numeric-looking text that cannot be converted exactly makes a numeric key's miss ErrKeyUndecidable and its hit JoinUndecided. No TEXT key is rendered against a no-affinity column's numbers (the engine compares them as stored). Every cross-class join is flagged per join with a count of affected keys (`JoinAffinityDiffers`, which means that the classes differ and may be set where the engine converts nothing, as for a no-affinity source against a TEXT target), and so is a differing collation (the engine's own choice follows operand order and `COLLATE` clauses, which the layer does not model: it uses the target's); a custom collation is refused. A miss on a lossy index, or while target rows have undecided keys, is `ErrKeyUndecidable`, not empty; a hit in those cases is returned with `JoinUndecided` because the set of matches may be short (B76, B78). (e) A UTF-16 text value that is not valid UTF-16 is `StateUndecodable` and never decoded. (f) `Row.Locator()` is for live rowid rows only (recovered locators arrive with 4G; WITHOUT ROWID rows and locators over 1024 bytes give `("", false)`). (g) `Index` on a WITHOUT ROWID table is not available (it is refused, A15); it needs a follow-up plan because its result type belongs to `parse.MapContext`. `Table.GetByKey` is available: it finds the row of a WITHOUT ROWID table by its primary key, and a key built from another column (`KeyOf`) is accepted only when its class and collation fit the key column, else `ErrKeyUndecidable` (a numeric 7 against a TEXT key column holding '07' is refused, because the engine reads '07' as 7 and the layer does not model that conversion for a column-sourced key); a literal key takes the key column's affinity as a constant does. (h) No real-device database was used (builder-, engine- and container-made fixtures only; R1 of the spec). (i) `DB`, `Table`, `Index` and `Context` are not safe for concurrent use. (j) A `Row` delivered to a `Scan` callback is valid only inside it (`Clone` to keep). (k) Closed (3J Task 11, B14): `keyDigest` of `internal/sqlitefile` now follows `EqualityKey`, so the four former differences are gone (NaN is `KeyNever`, UTF-16 text under NOCASE/RTRIM has a folded key, invalid UTF-8 under NOCASE/RTRIM and an Unread value are `KeyUnknown`); see the invariants row for the pinned behaviour. (l) `Context.Column` has no error to return, so a failure other than a missing table or column (a cancelled context, an I/O error, a corrupt or unsupported schema) yields -1 and is kept in `Context.Err()` (B77). `rowrun.Run` (plan 4D) runs every telephony mapping and fails the job with `rowrun.ErrContext` when `Err()` is non-nil, after every row and at Close (`TestRunFailsWhenContextErrIsSet`, `TestRunFailsWhenDatabaseIsReleasedMidRun`, `TestCloseChecksContextErr`); a mapper that reads -1 as "this variant lacks the column" is safe only under such a runner.
- SQLite table decoder, out-of-model data (B47): the engine reads a stored NaN REAL as NULL, so NaN never joins and a NaN probe answers empty with no error, as the engine does. Text stored in an INTEGER column is data the engine itself never writes (only a builder can produce it) and on which the engine's own join disagrees with itself; the oracle tests do not cover it and the layer's result for it is not claimed to equal the engine's.
- SQLite table decoder, literal keys: a constant has no affinity, so the target column's affinity is applied to it as the engine does (`'7'` finds the integer 7 in an INTEGER, REAL or NUMERIC column, the integer 7 finds the TEXT `'7'`). A numeric-looking text this reader cannot convert exactly (an integer that does not fit int64, more than 15 significant digits, a decimal exponent shift above 22, longer than 64 bytes after the blanks) and a REAL literal against a TEXT column (the engine's spelling of a real is not reproduced) are `ErrKeyUndecidable`, counted in the join report, never an empty answer (`TestLiteralTextKeyAgainstANumericColumnMatchesTheEngine`, `TestLiteralFloatKeyAgainstATextColumnIsUndecidable`, `TestLiteralTextKeyThatLooksNumericButIsInexactIsUndecidable`). The spellings of infinity and NaN are text (the engine leaves them text) and a NUL ends a text (the engine reads `'7'` then NUL then more bytes as 7). The exactness of a decimal conversion is proven against the reference engine build (a pure-Go engine computing in `float64`, `TestConvertForComparisonMatchesEngine`); a device engine built with extended-precision accumulation may round a decimal that needs a non-zero exponent shift differently in the last bit, which no test here can show.
- Typed recovery (plan 4G, `internal/decode/sqlitedb/recrun`): (1) only the rows `sqlitefile.ClaimMatch` accepts are typed: a table row of a claimed table whose basis is `schema` or a strict `fit` and whose values fit the LIVE definition; `guess`, `none`, slack-carved rows and rows that no longer fit today's definition stay `db_row` for the generic run (a `fit` row keeps its 60 cap and `identity-by-fit-only`: a dropped table of the same shape as a claimed table is attributed to it, the known misattribution `TestFitDecoyIsAttributedToTheClaimedTable` documents, and a same-affinity column reordering after a drop and recreate cannot be detected by a fit); (2) the joins of a recovered row read the LIVE tables of the bundle (note `joins-from-live-view`), so they may describe a later state or another row that reused an id; (3) a claimed row a mapping cannot turn into a record is a counted `Unmapped` call (the host's `analysis.warning`, `unmapped_recovered`) and not a record; standalone `parse recover` leaves it at that (spec 17 Q4 residual), while the composed `sqlite recover` keeps it as a `db_row` beside its warning (`KeepClaimed`, 4G-R21), so in one `sqlite recover` every recovered row is a typed record or a `db_row`, never only a warning; (4) a claimed table the live schema lacks, or lacks a required column of, makes its rows unmapped, never absent (the claim predicate delivers none for a table the live schema lacks: they stay with the generic run and are counted in `History.Skipped`); (5) a row in the database file that a rollback journal hides (origin `db-rolled-back`) states the journal record that hides it, and one a committed WAL frame overlays (origin `db-under-wal`) states that frame when the library knows it (it does not today: the library gives those rows no frame), while the role stays the database; no other database-file row states a companion position; (6) a row whose facts the host would refuse is skipped with a capped warning and counted (`Report.Skipped`), neither typed nor reported as unmapped. Because it is covered by no record, the host (`RecoverTyped`) makes the whole typed job `incomplete` (reason names the count, read from `Report.Skipped` and not from the capped notes, non-zero exit), so the composed command honors none of that job's claims and its generic run records the table as `db_row`; the library never produces such a row today. (7) A mapper panic inside the history walk is turned into a failed-parse error by the library's own guard before the host's: the job is `incomplete` with the panic text in its reason (no `panic` block in `parse.job.end`). (8) The composed `sqlite recover` (4G-R5, R6, R25, R26): the typed pass runs first and a claim is honored only for a job that concluded `complete` (or was skipped because a complete run of the same recover identity covers the bundle); a job that failed, was refused, narrowed, had another bundle (`bundle-differs`, from `--wal` or `--journal`) or overflowed its unmapped-locator list (65,536 digests) honors nothing, so the generic run records its tables too: after a failed typed job a row may exist as a record of the incomplete typed run AND as a `db_row` (never in neither), and the report and the generic `analysis.start` (`typed_not_honored`) say "also recorded as an incomplete typed run". The exit code is the worst of the two runs (integrity 4 wins and starts no generic run; an incomplete or refused typed job gives at least 1; a typed job that is skipped does not raise it). An unparsed claim blocks generic recovery of that database: when a claiming parser cannot decide its claim (a corrupt, encrypted or unreadable database, an unsupported schema, or a probe failure) the claim is undecided, no generic run starts, the command exits 1 and there is no override (recording the tables as if unclaimed would double-cover them once the parser can read the database; an opt-in generic-anyway mode is a backlog item). An already-parsed typed job (skipped because a complete run of the same recover identity covers the bundle) honors its claims, but the rows it could not map in that earlier run were only warnings then and are not recorded as `db_row` now; the report warns of it and `--allow-reingest` redoes both. Companion ids are admitted as recovered input only together with `OnlyPrimary` (`TestAdmitRecoveredCompanionNeedsOnlyPrimary`). Every `parse recover` and `sqlite recover` resolves all iOS backups of the case (one Manifest.db read and hash per backup), so a tampered Manifest.db of any backup ends the run with exit 4 even when the database recovered is elsewhere (`TestRecoverTypedPropagatesAnUnrelatedBackupIntegrityFailure`); `sqlite recover` pairs the `-wal`/`-journal` of a backup database through its Manifest.db before either pass, so the typed and the generic run read the same bundle (`TestSQLiteRecoverPairsBackupSiblingsByManifest`). Typed recovery is unvalidated on real device databases (class C; the `realdata` harness of plan 4H exists and no run is recorded, see "Real-data runs" in [parsers](parsers.md)); every first-set parser claims its tables.
- SQLite column defaults: a column DEFAULT is converted only when the conversion is exact (the rule of the literal keys above: an integer of at most 18 digits, a decimal of at most 15 significant digits with an exponent shift of at most 22, an integer rendered as decimal text). An inexact one (19 or more integer digits, more than 15 significant digits, an exponent shift above 22, an out-of-range exponent, a REAL needed as TEXT, and an expression) is delivered as `StateDefaultUndecided`: not stored, not a value, never a rounded number, with a typed reason (`Row.UndecidedDefault`); `KeyOf` is `ErrKeyUndecidable`, the history comparison of a row holding an expression default is `unknown` (`compare-incomplete`), while a short record whose column has an inexact literal default fits its table only at the loose tier (`guess`, not `fit`) and its history relation is `unknown` with `owner-changed` and `identity-by-fit-only`. A DDL numeric literal that is not exact is not evaluated (`DefaultInexactLiteral`, the source text is kept). The exactness is proven against the reference engine build (a pure-Go engine computing in `float64`); a device engine built with extended-precision accumulation may round a decimal needing a non-zero shift differently in the last bit. The engine cannot ADD COLUMN with an expression default, yet a nullable column with one still counts as addable for the strict fit (unchanged): such a short record is a `fit`, not a `guess` (`TestDefaultsMatchEngineMatrix`, `TestUndecidedDefaultHasItsOwnState`).
- SQLite file library, truncated hot journal (B61): a truncated hot journal stays loud (`journal-hot` shows the applied record count against the header's count, and the b-tree order check fires), and, since LX-4, one `journal-truncated` warning also names the cause (`JournalInfo.Truncated`, the declared and the held record count; `TestTruncatedJournalLiveEqualsTheEngine`). The file cannot tell a cut file from a damaged count, so the warning says both.
