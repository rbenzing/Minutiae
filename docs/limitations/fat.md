# Limitations: FAT and exFAT readers

What the current build does not do, does approximately, or has validated only on builder data, for the FAT12/16/32 reader `internal/filesys/fat`, the exFAT reader `internal/filesys/exfat` and their builders. The rules every reader shares are under [filesystems](filesystems.md); deleted-file recovery is under [recovery](recovery.md). Part of the [known limitations](../limitations.md), which say how to add or close one.

- FAT12/16/32 reader, read-only and as found (`internal/filesys/fat`): deleted entries are listed with `image ls --deleted` and flagged `Deleted`; `extract` never writes their content, which is recovered only by `image recover` (see the FAT and exFAT recovery items in [recovery](recovery.md)). A long name recovered from the slots of a deleted entry is flagged `lfn=recovered`, and `lfn_tail=unterminated` when the name may be cut short because a slot was reused (`TestDeletedLongNameRecoveryMarkers`); an orphaned long-name set is flagged `lfn=orphan`. FAT times are the local time of the system that wrote them with no zone (`Time.ZoneKnown` is false): modified times have 2 s resolution, created times 10 ms, and the access time is a date only (reported as `T00:00:00`). 8.3 short names and the volume label are strings in an OEM code page that the volume does not record: bytes from 0x80 up are decoded as code page 437 (a name written under another page shows other letters), `Entry.RawName` keeps the 11 raw name bytes (`TestShortNameDecodesCodePage437`, and the fixture's 8.3-only `/ÉTÉ.TXT`). Directory entry IDs are canonical decimals only (`TestEntryIDsMustBeCanonical`), and an entry at or past the directory's first end-of-directory (0x00) entry cannot be opened or listed by ID (`TestEntryBeyondEndMarkerIsNotFound`). When the volume has two or more FAT copies, `Unallocated` compares the others with the active one and warns once if they differ (`TestDifferingFATCopiesWarn`). FAT has no Unix permissions, so `Mode` is synthesized: 0644 for files and 0755 for directories, with the write bits cleared when the read-only attribute is set (not evidence of the original owner's permissions). A FAT chain shorter than the file size (it ends early, meets a free or bad cluster, loops or leaves the volume) yields a partial artifact flagged `incomplete` whose provenance records only runs that cover the kept prefix (see the `File.Runs` prefix rule in [filesystems](filesystems.md)) and a warning (`TestFileChainShorterThanSize`, `TestExtractFATShortChainIsIncomplete`). A lookup that finds nothing in a directory the scan did not read to the end (the 65536-entry cap, a directory chain that loops, breaks or leaves the volume before its end marker, a failed read, the read budget spent after the first entry) is an error matching `filesys.ErrIncomplete` (with `ErrLimit` for the cap and the budget; a budget spent before the first entry is a plain corruption error, the directory could not be read at all), never not found, and an entry ID beyond such a cut is not reported as beyond the end of the directory, and `ReadDir` returns the entries it read together with that error, as the exFAT reader does (`TestLookupAfterCapIsAnError`, `TestLookupInDamagedChainIsAnError`, `TestReadDirOfCutDirectoryReturnsEntriesAndError`). Lookup decides over the whole directory, in one order: an exact long or 8.3 name; the `~raw~` form (one spelling per name, standing only for names `ReadDir` shows in that form); the incomplete-scan error; one case-insensitive match (a `~raw~` display name is not case-folded, although the entry's 8.3 name still is); `ErrAmbiguous` for two or more, for two entries with the same name, and for a stored name that is also another entry's `~raw~` form. On a cut scan only an exact name stands: an alias or case-insensitive match could differ from what the unread part would decide, so it is the incomplete error. The volume label of a root listing that was cut before a label entry is undecided and a warning says so (the BPB label is shown as the BPB's). The case-insensitive rule is the reader's convention, Unicode simple case folding of the long or 8.3 name: the volume records no rule, and the OS that wrote it may fold differently (`TestLookupFoldAmbiguousIsAnError`, `TestLookupStoredNameThatIsAnotherRecordsAliasIsAmbiguous`, `TestCutLookupReturnsOnlyAnExactMatch`, `TestRootLabelWarnsWhenTheRootListingIsCut`). Unlike the exFAT reader, FAT has no undecided result for a long name that was lost: an entry whose long-name set is orphaned or broken (`lfn=orphan`, or a checksum mismatch) is matched by its 8.3 name only, so a lookup by the lost long name is not found.
- exFAT reader, read-only and as found (`internal/filesys/exfat`): deleted entry sets are names only, as for FAT (`TestExfatDeletedSetFlagged`). The `NameHash` is verified with the volume's up-case table: a mismatch is a warning and `name_hash=bad` (the entry is still listed and opened), and without a usable table or a full name it is `name_hash=unverified` (`TestExfatNameHashMismatchFlagsTheEntry`, `TestExfatNameHashVerifiesOnRealFixtures`); the entry-set checksum is, and a set that fails it is still listed, flagged `checksum=bad` (`TestExfatSetChecksumBadFlagged`); a set with no Stream Extension or too many secondaries is flagged `set=damaged` and cannot be opened. On a TexFAT volume (two FATs) the FAT and bitmap that `ActiveFat` names are read, the inactive copies are compared and a difference is a warning, a missing active bitmap means no free space is reported, never the other one; this is checked on builder images only (no tool in the pinned fixture images writes TexFAT) (`TestExfatTexFATSecondActiveIsRead`). The TexFAT layout (VolumeFlags `ActiveFat`, `NumberOfFats`, the Allocation Bitmap entry `BitmapFlags` bit 0) was read from a summary of the published specification and is not byte-verified against the document, and no real TexFAT image checks it. Bytes between `ValidDataLength` and `DataLength` read as zeros and are recorded as a hole run, as the format defines. exFAT has no Unix permissions either: `Mode` is 0. A name that is "." or ".." (or holds '/' or NUL) is shown in the `~raw~` form (`TestExfatDotNamesUseRawForm`). The `~raw~` form is the shared one (one spelling per name; it stands only for names shown that way). Lookup decides over the whole directory: exact name, `~raw~` form, the incomplete-scan error (a directory chain that loops or breaks before its end marker and the 256 MiB limit are cuts too, besides the cap, the budget and an unreadable chunk; `ReadDir` returns the entries read with the same error), `ErrUndecided` when a live entry set's name cannot be read in full, one match through the volume's up-case table, `ErrAmbiguous` for two or more (and for two exact or alias records, or a stored name that is another record's form). Without a usable up-case table nothing is folded: a miss is `ErrUndecided` when a stored name has the query's length, else not found (`TestExfatLookupWithoutUpcaseTableIsUndecided`). An entry set at or past a directory's first end-of-directory entry cannot be opened by ID (`TestExfatEntryBeyondEndMarkerIsNotFound`). `Unallocated` never reports the allocation bitmap, the up-case table, the root directory or the clusters the FAT marks bad as free, even if the bitmap says they are, and reports at most 1<<24 runs (a warning says when the rest is cut off; `TestExfatUnallocatedExcludesSystemAndBadClusters`, `TestExfatUnallocatedRunCap`). At most 1<<18 entry sets are read per directory (`TestExfatDirRecordCapDefault`), and at most 1M distinct directories are remembered by first cluster (past that, a warning says the rest cannot be reached by id).
- FAT and exFAT directory read budgets: each filesystem instance reads at most 1 GiB of directory data in total (exFAT) or at most 4M directory entries, 128 MiB (FAT, which counts entries), so a hostile volume whose chains overlap cannot cost unbounded time. Once the budget is spent, directories are no longer read (a directory read after that is an error; one being read when it ran out returns the entries read together with an `ErrIncomplete` error) and the filesystem reports a single budget warning (`TestDirectoryReadBudget`, `TestExfatDirectoryReadBudget`, `TestExfatBudgetExhaustedBeforeFirstEntryIsAnError`). A FAT directory also holds at most 65536 entries, an exFAT directory at most 256 MiB. The budgets are never reset within an instance, so one huge but legitimate volume can reach them. A directory that cannot be read because the budget is spent is an error, never an empty listing: `image ls -r` and `image extract` report it and do not treat the directory as empty. The budgets belong to the filesystem instance, and every `image` command (`ls`, `unalloc`, `extract`) opens its own session and so its own instance: the budgets start over with each command (this holds for the F2FS and HFS+ budgets too).
