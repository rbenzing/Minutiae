# Known limitations

What the current build does not do, does approximately, or has validated only on builder data. A change that closes or adds a limitation edits its line here.

- Android sync v1: `LIST` of an unreadable directory returns `DONE` with no entries (indistinguishable from an empty directory, so no `acquire.warning` is possible), and `LIST`/`STAT` report sizes and mtimes as 32-bit values (sizes of files ≥ 4 GiB are truncated in listings and in `source.remote_size`; `RECV` still transfers every byte).
- Android hostile device: a malicious or faulty device can stream an unbounded number of `LIST` entries, unbounded directory depth, and arbitrarily large files (`RECV` size is inherent to evidence, so it is not capped). The examiner can stop an acquisition with Ctrl-C: partial artifacts are kept and flagged incomplete.
- iOS backup: the sync-lock / `notification_proxy` step is not performed, and `Info.plist` is not generated; the lockdown values are saved as `device/lockdown.json`.
- iOS backup transfer: a `0x0b` (remote error) block that follows file data is treated as the normal end of that file, mirroring libimobiledevice, so a device-side read failure in the middle of a file can look like a complete file. Files cut off by a transport failure or cancellation are kept and flagged `incomplete`.
- iOS encrypted backups (a backup password set on the device) are captured as-is; decryption belongs to roadmap sub-project 10.
- iOS AFC (`ios ls`/`ios pull`) parsing robustness depends on go-ios: its panics are converted to errors and a pull whose byte count differs from the AFC-reported size is flagged `incomplete`, but malformed AFC responses are otherwise not validated by Minutiae.
- iOS lockdown/service setup: plists the device returns during lockdown `GetValue` and `StartService` (used by `ios info`, `ios ls/pull` and `ios backup` setup) are decoded inside go-ios without Minutiae's bplist validator or panic recovery, so a hostile device could crash the process at that stage (before any artifact is written).
- Image analysis (sub-project 2, complete with the APFS reader): APFS, F2FS, ext2/3/4, FAT12/16/32, exFAT and HFS+/HFSX are recognized (`detect.Drivers` holds the apfs, f2fs, ext4, exFAT, HFS+ and FAT drivers, in that probe order, followed by the last-resort `f2fs-backup` driver; see below), so `image info` shows their filesystem and `image ls`/`stat`/`extract`/`unalloc -p` work on them. A partition whose filesystem no driver recognizes is listed, but `image ls`/`stat`/`extract` and `unalloc -p` report that no filesystem is recognized. Raw and split-raw images, E01 images (EWF v1, see below), MBR/EBR and GPT partition tables, and `image unalloc --volume` (gaps outside partitions) work.
- F2FS detection: `f2fs` matches only a valid primary superblock. An F2FS volume whose primary superblock is destroyed is found only by the last-resort `f2fs-backup` driver, which runs after every other driver, so a destroyed primary on a volume that also carries another filesystem signature opens as that other filesystem; and a stale or forged F2FS backup signature never hides another filesystem. A matching driver that fails to open with a corrupt-structure error falls through to the remaining matching drivers (the failure is kept as a note); `image info` shows that note in the partition error column.
- EWF/E01 images (`internal/image/ewf`, EWF version 1, one or more segment files `.E01`, `.E02`, ...) are opened read-only and can be verified. `image import` takes the segments in order like any split image, any one of them opens the set, and the media is the logical disk (`image info`, partitions, filesystems, `extract`, `unalloc` work as on a raw image; recorded runs are in media coordinates). An E01 that declares 512-byte sectors is probed for both 512 and 4096 (acquirers write 512 for 4096-byte disks as well). Not supported: EWF2 (Ex01) and logical evidence files (L01) stay `image.ErrUnsupportedContainer`; so do volume or `disk` sections of a layout other than the 1128-byte one (legacy short layouts), and encrypted EWF. The format was implemented from the public format notes and validated against `ewfacquire` 20140816 output (one writer, one version; other acquirers' layouts are covered by the `ewftest` builder only, and `TestEWFRealImages` under `-tags realimages` checks real E01 sets by hand) and against an independent decoder.
- E01 incomplete and damaged sets are opened, not refused, and never guessed: a set whose last segment has no `done` section, whose last segment is missing, or whose last segment is truncated mid-section opens with an "E01 set incomplete" warning (the sections walked before a truncation are kept) and every chunk the walked sections do not cover fails with `ErrChunkCorrupt` on read; a missing or out-of-order MIDDLE segment, a truncated non-last segment and a bad section descriptor checksum fail the open. Note the two levels: the case's import record only knows the files given (a 2-of-3 import is a complete import of two files), while the E01 `done` section is what reveals the missing third segment. A chunk table is trusted only if it directly follows its sectors section, its first entry is the sectors payload start, its entries strictly increase and lie inside that section; `table2` is the fallback; if both copies fail, every chunk from that group onward is unreadable (`ErrChunkCorrupt`) with a warning naming the rule, and the image still opens (a damaged table never makes the image unopenable, the part before it stays readable). A corrupt chunk (bad zlib stream, wrong Adler-32, wrong length) is an error on read, never zeros, and `ReadAt` returns the bytes before it. Only libewf-written layouts have been tested against the table rules: an acquirer that pads between the sectors descriptor and the first chunk would open but read no chunk (the same unreadable-chunk error as damage). A bad chunk inside a structure read at open time (the primary or backup GPT) makes `image info` fail at the partition step, while `image info --verify` still runs and audits it (see below).
- E01 acquisition errors: `error2` ranges (sectors the acquirer could not read from the device; the acquirer wrote zeros there and the tables cover them) are reported as warnings and are part of the media, as the acquirer stored it. Acquirer-supplied metadata (case number, examiner, notes, dates, acquirer version) is shown as claimed, size-capped and escaped on output; it is not evidence of anything the acquirer did not record.
- `image info --verify` (E01 only): recomputes MD5 and SHA-1 of the whole media and compares them with the hashes stored in the image; one hash-chained `image.verify` audit entry is always written, also for a mismatch, an unreadable chunk, a cancel or a panic. It proves that the container's media matches what the acquirer stored, not that the acquirer's read of the device was faithful (an `error2` range is zero-filled before it is hashed), and it covers only the hashes the container stores (MD5 and SHA-1; no SHA-256). `absent` (no hash section at all) is not a failure, but a stored-hash section that is present and damaged (checksum mismatch, or too small to parse) is never `absent`: that hash is `unverified` with a `reason` (also in `--json` and the audit entry), the open warning says "stored hash section damaged", and the exit code is 1; a hash that another valid section (hash or digest) still stores is verified normally. Exit codes: `match`/`absent` 0, `mismatch` 4, `unverified` (an unreadable chunk, a damaged stored-hash section or a partial run), cancel, panic and a failed audit append 1; a mismatch whose audit append fails still exits 4. Verification does not need a readable partition table. Raw and split-raw images carry no stored hashes: `--verify` prints a note and writes no audit entry (`case verify` re-hashes their artifacts regardless).
- E01 `extract`: a file that reaches an unreadable chunk keeps the readable bytes before it as an artifact flagged `incomplete` (the prefix is found by bisecting the failing read, so only error-free bytes are written; its provenance records only the runs covering them) with an `analysis.warning`, and extraction continues. A real I/O error of the segment source is not a chunk error: it keeps the old behaviour and ends the analysis (`analysis.error`) rather than producing an incomplete artifact (`TestExtractIOErrorIsNotDowngradedToIncompleteFile`). When the prefix needs a runs sidecar (more than `MaxInlineRuns` runs), it is written under the first free of `<file>.incomplete.runs.jsonl`, `<file>.incomplete~2.runs.jsonl` ... `~16` (a taken name is not a case failure), and the full run list sidecar written before the read stays in the case as an unreferenced runs artifact (an ordinary hashed artifact: `case verify` passes, but nothing references it); the partial artifact's error, and so the `analysis.warning`, names that orphan (`complete run list of the file: runs artifact <id>`). When all 16 names are taken, the partial artifact carries no runs at all and its error says "the runs of the kept bytes are not recorded": incomplete provenance, never wrong provenance (`TestExtractPrefixSidecarNamesExhaustedRecordsNoRuns`). `image unalloc` is different: its runs sidecar always lists every run, so after an unreadable chunk it can be longer than the truncated, `incomplete` `unallocated.bin`.
- E01 size claims: the logical size is the volume section's sector count times the sector size, and must agree with the chunk count (at most 2^26 chunks of at most 16 MiB), so a hostile image can claim up to a petabyte of media with few real bytes; a read stops at the first chunk the tables do not cover and `Verify` stops at the first unreadable chunk, but a whole-media loop over a claimed-huge image is bounded only by cancellation or the caller's budget. The chunk reference table costs 8 bytes per entry (up to 512 MiB at the limit, and only when the file really holds that many table entries).
- E01 chunk-table trust is structural, not a proof of contiguity (parked review finding): the rules above do not prove that a table covers its whole sectors payload without gaps or overlaps, so only a checksum-consistent forgery of the table, `table2` and the section descriptor could make chunks read from the wrong place without a warning. `image info --verify` catches such a forgery unless the stored MD5 and SHA-1 are forged too, and `case verify` still protects the image artifact itself.
- The EWF concurrency tests (`TestEWFConcurrentReadAt`, the chunk cache) run under `-race` in the race gate (step 2); the gate passed on 2026-10-08 with 0 data races. The fast check runs them without `-race`.
- One `image import` call imports exactly one image (its files are segments 1..N in the order given; nothing is sorted). A partially imported image cannot be opened: re-import it.
- Deleted filesystem entries are listed (`image ls --deleted`) and flagged, but not recovered or extracted; recovery is sub-project 3. HFS+ and APFS keep no deletion marker, so they list none (see the HFS+ and APFS items below).
- `image ls`/`stat`/`extract` check the parent artifact's size only (`OpenArtifact`), not its hash: a same-size content swap of the parent is not caught at open time, but `case verify` detects it (derived artifacts record the parent's SHA-256, and the parent is re-hashed).
- Sparse-expansion guard: `extract` skips a file whose hole bytes (sum of `Offset -1` runs, or the whole size when the filesystem reports no runs) exceed the partition length, with an `analysis.warning` ("sparse size exceeds partition length; not extracted"). A sparse file within the partition length is still expanded to its full size, and overlapping data runs are not bounded by this guard.
- Encrypted filesystem content is extracted as ciphertext (flagged `Derived.Encrypted`; on HFS+ per entry, from the `cprotect` attribute; on APFS per file, from any crypto id, while a whole encrypted APFS volume is not read at all, see the APFS items below); decryption belongs to roadmap sub-project 10.
- ext4 (ext2/3/4) reader, read-only and as found: the journal is not replayed, so an image that needs recovery is read as it lies on disk (the reader warns that the filesystem may be inconsistent); journal analysis belongs to sub-project 3. `bigalloc`, an external journal device and unknown incompatible features are refused as unsupported.
- ext4 deleted entries are names only: a deleted directory record is listed and flagged (`image ls --deleted`) with what the on-disk record still holds, but its content is not recovered or extracted (sub-project 3). A stale copy of a live record left behind by an htree leaf split stays listed with attribute `stale_copy=true`.
- ext4 names: encrypted (FBE) directory names are shown as `~enc~<base64url of the raw name>` and their file content is extracted as ciphertext (decryption is sub-project 10); names that are not valid UTF-8 are shown as `~raw~<base64url>`. Path lookup accepts both displayed forms.
- ext4 casefold directories: name lookup is approximate (`strings.EqualFold` on valid UTF-8 names, not the kernel's casefold table), so a path may resolve differently than on a live system; directory listing is unaffected.
- ext4 directory record cap: at most 262144 records are read per directory (live and deleted). A lookup beyond the cap, or in a damaged region of a directory, returns not found with a warning, not an error. Extended attributes are read from the inode and the xattr block, but xattr block checksums are not verified and values held in an EA inode (`ea_inode`) are not read.
- ext4 unallocated export: a block group whose bitmap fails its checksum (or cannot be read) is omitted from the export and reported as a filesystem warning (`analysis.warning`); its blocks are neither exported nor claimed as free. Any group whose descriptor checksum is wrong is skipped whatever its flags (`TestBadDescriptorChecksumGroupIsSkippedWhateverItsFlags`), and when the descriptor table is truncated the `BLOCK_UNINIT` groups are skipped too (`TestUnreadableDescriptorsSkipBlockUninitGroups`), each with a warning. The scan for deleted names in directory slack is capped at 16 MiB of slack per directory (`TestSlackScanCap`); past the cap the reader warns and stops searching, so a hostile directory cannot cost unbounded time.
- Analysis warning ordering: a filesystem warning is written to the audit log as `analysis.warning` after the artifact whose processing triggered it (never before): the reader notices an anomaly only while doing that work. Warnings about directories met while walking are attributed through the `after` field, which names the last extracted path, not the directory itself. Warnings the filesystem already had when the analysis began are written once as `source: filesystem-open`; later ones as `source: filesystem` and counted in the summary (`fs_warnings`) apart from skips.
- Filesystem readers keep at most 1000 distinct warnings (de-duplicated by text; every reader, F2FS, ext4, FAT, exFAT, HFS+ and APFS, then adds one "further warnings suppressed" note), so the audit log is not an exhaustive list of every anomaly in a hostile image. `image ls`/`stat` print the warnings a command raised (escaped, at most 20 lines) on stderr; `image stat --json` carries them in a top-level `warnings` field.
- ext4 hard links: every directory path to a multiply-linked inode is a separate entry, so `extract` writes one copy per path (the entries share the filesystem id, so provenance shows they are the same inode). Directory entries stored beyond a directory's `i_size` are listed as deleted entries with attribute `beyond_isize=true` (`TestEntriesBeyondISizeAreDeletedNotLive`). A live directory entry whose inode has `links_count` 0 and a `dtime` gets attribute `inode_freed=true` and a warning (`TestLiveEntryOfFreedInode`).
- A file whose extents run past the end of a truncated image cannot be read in full: `extract` skips it with an `analysis.warning` rather than extracting a prefix (readers that report a trusted prefix, FAT, F2FS, HFS+ and APFS, yield an `incomplete` artifact instead, see the prefix rule below). Local artifact names are capped at 200 bytes per path component (cut on a rune boundary, then `~` plus the first 8 hex digits of the SHA-256 of the original name, so distinct long names stay distinct; this applies to `image extract` and `android logical` alike); the original path is kept in `Source.RemotePath` and `Derived.FSPath`. An OS path-syntax or name-too-long error creating one artifact becomes a per-file `analysis.warning` and a skip.
- FAT12/16/32 reader, read-only and as found (`internal/filesys/fat`): deleted entries are names only (listed with `image ls --deleted`, flagged `Deleted`; their content is never recovered or extracted, sub-project 3). A long name recovered from the slots of a deleted entry is flagged `lfn=recovered`, and `lfn_tail=unterminated` when the name may be cut short because a slot was reused (`TestDeletedLongNameRecoveryMarkers`); an orphaned long-name set is flagged `lfn=orphan`. FAT times are the local time of the system that wrote them with no zone (`Time.ZoneKnown` is false): modified times have 2 s resolution, created times 10 ms, and the access time is a date only (reported as `T00:00:00`). 8.3 short names and the volume label are strings in an OEM code page that the volume does not record: bytes from 0x80 up are decoded as code page 437 (a name written under another page shows other letters), `Entry.RawName` keeps the 11 raw name bytes (`TestShortNameDecodesCodePage437`, and the fixture's 8.3-only `/ÉTÉ.TXT`). Directory entry IDs are canonical decimals only (`TestEntryIDsMustBeCanonical`), and an entry at or past the directory's first end-of-directory (0x00) entry cannot be opened or listed by ID (`TestEntryBeyondEndMarkerIsNotFound`). When the volume has two or more FAT copies, `Unallocated` compares the others with the active one and warns once if they differ (`TestDifferingFATCopiesWarn`). FAT has no Unix permissions, so `Mode` is synthesized: 0644 for files and 0755 for directories, with the write bits cleared when the read-only attribute is set (not evidence of the original owner's permissions). A FAT chain shorter than the file size (it ends early, meets a free or bad cluster, loops or leaves the volume) yields a partial artifact flagged `incomplete` whose provenance records only runs that cover the kept prefix (see the `File.Runs` prefix rule below) and a warning (`TestFileChainShorterThanSize`, `TestExtractFATShortChainIsIncomplete`).
- exFAT reader, read-only and as found (`internal/filesys/exfat`): deleted entry sets are names only, as for FAT (`TestExfatDeletedSetFlagged`). The File entry's `NameHash` is not verified; the entry-set checksum is, and a set that fails it is still listed, flagged `checksum=bad` (`TestExfatSetChecksumBadFlagged`); a set with no Stream Extension or too many secondaries is flagged `set=damaged` and cannot be opened. TexFAT (a second FAT and allocation bitmap) is ignored: the first FAT and the first bitmap are read. Bytes between `ValidDataLength` and `DataLength` read as zeros and are recorded as a hole run, as the format defines. exFAT has no Unix permissions either: `Mode` is 0. A name that is "." or ".." (or holds '/' or NUL) is shown in the `~raw~` form (`TestExfatDotNamesUseRawForm`), and an entry set at or past a directory's first end-of-directory entry cannot be opened by ID (`TestExfatEntryBeyondEndMarkerIsNotFound`). `Unallocated` never reports the allocation bitmap, the up-case table, the root directory or the clusters the FAT marks bad as free, even if the bitmap says they are, and reports at most 1<<24 runs (a warning says when the rest is cut off; `TestExfatUnallocatedExcludesSystemAndBadClusters`, `TestExfatUnallocatedRunCap`). At most 1<<18 entry sets are read per directory (`TestExfatDirRecordCapDefault`), and at most 1M distinct directories are remembered by first cluster (past that, a warning says the rest cannot be reached by id).
- F2FS reader, read-only and as found (`internal/filesys/f2fs`): the image is read as of its last checkpoint. Roll-forward recovery (the fsync'd node chains written after the last checkpoint, which the kernel replays at mount) is not applied, so later data may exist in such a chain yet is not shown; when the last checkpoint is not an unmount checkpoint the reader warns "last checkpoint is not an unmount checkpoint (data written after it is not reflected)" (`TestUncleanCheckpointWarns`). Analysing that node chain belongs to sub-project 3. Only single-device, non-zoned volumes are supported: the superblock's device table is not read and zoned (`blkzoned`) volumes are not interpreted.
- F2FS compressed files (`F2FS_COMPR_FL`) are unsupported: `Open` of one fails with `ErrUnsupported` ("compressed file") and `extract` skips it with an `analysis.warning`; the listing still shows the entry, with attribute `compressed=true` (`TestCompressedFileUnsupported`).
- F2FS deleted dentries are names only: a deleted entry is listed and flagged (`image ls --deleted`) with what its inode still says while the NAT maps it (type, size, attribute `inode`; `inode_reused=true` when the inode now belongs to another directory, `inode_unreadable=true` when it cannot be read), but its content is neither recovered nor extracted, and F2FS records no deletion time (sub-project 3; `TestReadDirFlagsDeletedEntries`).
- F2FS names and content: encrypted (FBE) names are shown as `~enc~<base64url of the raw name>`, names that are not valid UTF-8 as `~raw~<base64url>`, and path lookup accepts both displayed forms; encrypted file content is extracted as ciphertext (flagged `Derived.Encrypted`), and decryption is sub-project 10 (`TestEncryptedDentryNames`, `TestRawEncryptedContent`). In casefold directories name lookup is approximate (`strings.EqualFold` on valid UTF-8 names, not the kernel's casefold table), so a path may resolve differently than on a live system; `.` and `..` are never matched by casefold, and listing is unaffected (`TestLookupCasefoldNeverFindsDots`).
- F2FS inline data whose `DATA_EXIST` flag is clear (the kernel reads such a file as empty) is returned as stored, with attribute `data_exist=false` on the entry and a warning (`TestInlineDataWithoutDataExist`).
- F2FS free space: `Unallocated` is built from the SIT, with the journal in the checkpoint applied over the SIT blocks. A SIT journal whose entry count exceeds its block makes the export empty, with a warning (no free space is reported rather than guessed); a SIT block that cannot be read, or a segment whose entry is inconsistent, is not reported as free; the segments the current logs write into are not excluded, because the SIT is authoritative; at most 1<<24 runs are reported (a warning says when the rest is cut off). A NAT journal whose entry count exceeds its block is ignored, with a warning that file locations may be stale: inodes then resolve through the NAT blocks only (`TestSITJournalHostile`, `TestNATJournalFullAndOverfull`, `TestUnallocatedIgnoresCurrentSegmentCursor`, `TestUnallocatedBoundsAndCap`).
- F2FS caps: a directory is read up to 64 MiB and 262144 entries (deleted entries at most half of that, so live ones come first), a file maps at most 1<<20 runs and node blocks, and one filesystem instance reads at most 1 GiB of directory data in total; past a cap the reader warns and stops, and a directory that cannot be read because the budget is spent is an error, never an empty listing. Every `image` command (`ls`, `unalloc`, `extract`) opens its own instance, so these budgets, like the FAT and exFAT ones, start over with each command (`TestDirectoryReadBudget`, `TestDirEntryCapPrefersLiveEntries`, `TestRunCapIsCorrupt`).
- F2FS real-image coverage: the committed fixtures (`f2fs-extra-attr`, `f2fs-default`) have no deleted entries (F2FS keeps no deletion time and `sload.f2fs` cannot delete; deleting needs a kernel mount, and the Docker Desktop kernel has no f2fs module), no holes (`sload.f2fs` writes holes out as zero blocks), no indirect or double-indirect node (`sload.f2fs` cannot place a single 7 MiB file) and no inline-dentry directory. Those paths are covered by the `f2fstest` builder tests only and have never been validated against an image written by a real kernel. The generator tries the kernel mount and the removals when it runs where f2fs is available (`tools/fixtures/README.md`).
- HFS+ and HFSX reader, read-only and as found (`internal/filesys/hfsplus`; HFSX reports type `hfsx`, plain HFS+ `hfsplus`): the journal is not replayed, so a volume with pending transactions is read as it lies on disk (a warning at open) and `Unallocated` REFUSES it with an error wrapping `ErrUnsupported`, because the bitmap on disk may lag the journal (`TestJournalStateWarnings`, `TestUnallocatedPendingJournalRefused`, `TestUnallocatedUnknownJournalRefused`); replay and journal analysis belong to sub-project 3. A volume that was not cleanly unmounted, or whose header says inconsistent, only warns. The journal-header layout (magic, endian marker, start/end) is from memory and was never validated against an initialised journal (the only real journaled fixture is `mkfs.hfsplus -J`, whose journal is flagged need-init and all zero, which the reader treats as clean); a layout that deviates reads as "unknown", which refuses `Unallocated` rather than guessing. A classic HFS volume with no embedded HFS+ volume is `ErrUnsupported`, and an Apple Partition Map is not parsed.
- HFS+ wrapped volumes, truncated images and detection: a classic HFS wrapper (master directory block `BD`) is followed to the embedded volume (validated against a real `mkfs.hfsplus -w` image, volume at byte 45056), the volume is clamped to the wrapper's embedded extent with a warning (the wrapper's own area is never part of the volume and never reported free; `TestWrappedVolumeIsBoundedByTheWrapperExtent`), and an HFSX volume inside a wrapper is accepted although Apple never writes one. A truncated image (also a truncated wrapped one) opens clamped to what it holds with a warning, not as corrupt: a file reaching past the end keeps its trusted prefix (`incomplete` artifact, see the prefix rule below) and `Unallocated` is clipped to the whole blocks the image holds, with one warning when free blocks were dropped (`TestTruncatedImageEndsTrustedPrefix`, `TestUnallocatedRunsStayInsideTruncatedImage`). `hfsplus.Probe` matches a valid PRIMARY volume header only (the embedded one for a wrapper), so a volume with a destroyed primary header is not claimed by `detect` although `Open` of the reader could use the alternate header (consistent with the F2FS ruling). `Probe` is independent of FAT: a stale or planted HFS+ header in a FAT image whose catalog is held by the image and is not a B-tree header node fails the HFS+ `Open` and detection falls through to FAT with a note (one whose catalog lies beyond the end of the image is accepted as a truncated HFS+ volume, and the `also matched by: fat` note is the only signal), and a stale FAT boot sector in the boot blocks of a real HFS+ volume does not hide it. When several drivers' signatures match one partition the result carries the note `also matched by: <drivers> (ambiguous signatures)` (shown in `image info`), the signal that a signature is stale or forged. Probe order: apfs, f2fs, ext4, exFAT, HFS+, FAT, then the last-resort `f2fs-backup` (never reported as an ambiguous claimant). `Open` requires the first node of the catalog file to be a B-tree header node (kind 1, height 0, 3 records, no backward link); a volume where it is damaged cannot be opened at all (no listing, no unallocated export) and is reported as a corrupt volume, "failed to open" in `image info`, even though its bitmap may be intact; recovering such a volume belongs to sub-project 3 (`TestOpenChecksTheCatalogHeaderNode`). Only a catalog cut off by a truncated image still opens (with a warning).
- HFS+ deleted entries: none are listed (the catalog keeps no deletion marker; a deleted record's bytes survive only as stale slack in a node, in the journal or in unused nodes). The reader never reads slack, so nothing is flagged `Deleted`; finding such records belongs to sub-project 3 (`TestStaleNodeSlackIsNotListed`).
- HFS+ names and case: names are shown as stored (decomposed Unicode, no normalization), so a composed (NFC) path does not find a name stored decomposed; the entry is reachable through its listed ID (`TestUnicodeNamesDecomposedAsStored`). The on-disk `:` is not translated to `/` (a stored `/` or NUL, an empty name, `.` or `..` and invalid UTF-16 are shown as `~raw~<base64url>`, and `Lookup` accepts both forms). Lookup prefers an exact spelling to the `~raw~` alias to a case-fold match (`TestLookupPrefersExactOverFolded`). Case: HFSX with catalog `keyCompareType` 0xBC is case-sensitive and exact; plain HFS+ and case-folding HFSX are case-insensitive, and that fold is an APPROXIMATION: Go's per-unit lower-casing, with Apple's published table not embedded and the list of ignorable code units (U+200C-200F, U+202A-202E, U+206A-206F, U+FEFF) from memory and not validated against a real image, so a path may resolve differently than on a live system for exotic letters (the exact-first order limits the effect). Folding NUL to 0xFFFF (it sorts after every other unit, so the hard-link private folder is the last child of the root) is the one ordering rule CONFIRMED on a kernel-written image (`TestRealPrivateFolderSortsLastAndIsFoundByDescent`).
- HFS+ compressed (decmpfs) files: zlib types 3 (data in the attribute) and 4 (blocks in the resource fork) are decompressed on read, with `Size` the uncompressed size, `File.Runs` nil and attribute `compressed=zlib`; every other type (LZVN, LZFSE, ...) and any `UF_COMPRESSED` file whose header cannot be read is `ErrUnsupported` (attribute `compressed=<type>` or `unknown`) and `extract` skips it with an `analysis.warning`; it is never returned as an empty file (`TestDecmpfsZlibInline`, `TestDecmpfsZlibResourceFork`, `TestOtherTypesAreUnsupported`, `TestCompressedFileUnsupportedNotEmpty`). The decmpfs layouts (header, the type-4 block table: a big-endian 0x100 header word, the little-endian block count and (offset, size) pairs, stored-block marker) are from memory and validated by builder images only: no real compressed file exists in any fixture (compression is written by macOS, not by the Linux driver), and a real file that deviates fails as `ErrCorrupt` or `ErrUnsupported`, never as guessed bytes. A decmpfs attribute on a file without `UF_COMPRESSED` is ignored, as the OS does (attribute `decmpfs_ignored=true`, a warning, the data fork is the content; `TestDecmpfsAttributeWithoutFlagIsIgnored`). A decompressed file's artifact records no image runs (its bytes are decoded, not copied) and nothing in the provenance says so; the entry attribute does. A type-4 file whose resource fork is incomplete fails `Open` instead of offering a prefix. Resource forks of ordinary files are shown in attributes only (`rsrc_size`, `rsrc_blocks`); `Open` returns the data fork.
- HFS+ hard links, threads and attributes: file hard links are resolved through the private folder's `iNode<N>` record and listed once per path (the entries share the inode in attribute `hardlink_inode`, so `extract` writes one copy per path), directory hard links are listed (type `other`) and not followed, and a link whose inode is missing is flagged `hardlink=dangling` and is a corrupt-volume error on `Open` (`TestHardLinkResolvesToIndirectNode`, `TestDirectoryHardLinkIsNotFollowed`, `TestHardLinkDanglingIsFlagged`). The file hard-link layout (private folder name, `iNode<N>`, `hlnk`/`hfs+`, the link count) was validated against the kernel-written fixture (a three-link group, its link count and the private folder); the directory-link markers (`fldr`/`MACS`) are from memory and builder-only; a link record's own dates are not shown (the inode's win, as on macOS). The private folder is listed and flagged `private_metadata` (only the folder: a root-level folder with the private name); its iNode files are listed unflagged under the private folder's path, never hidden. A file with no thread record is listed with `thread=missing` but cannot be opened by ID (the ID scheme is `cnid:<n>` and the catalog cannot be searched by CNID without a thread), so `extract` skips it with an `analysis.warning` and counts it as skipped: such a file is NOT extracted (`TestMissingThreadIsFlagged`, `TestOpenFileWithoutThreadIsNotFound`). At most 4096 attribute records are read per file; an attribute past that cap (for example `cprotect`) is not seen: the entry shows `attributes=unreadable` and a warning says so (a compressed file still fails closed through its flag); at most 32 attribute names are listed (`xattr_more` says how many more). The attributes-file layouts are builder-only: the Linux driver cannot write attributes, so the populated fixture's attributes file is empty (`TestAttributesTreeXattrs`, `TestAttributesHostile`). A catalog record whose id has no matching thread (a shared id: see docs/invariants.md, `TestDuplicateCNIDEntryIsConflictAndNeverOpens`) is flagged `cnid_conflict=true` and has an unresolvable `conflict:...` ID, so `Open`, `ReadDir` and `Lookup` through it are corrupt-volume errors and `extract` skips it with an `analysis.warning`; the record the thread names is unaffected, and the children of a duplicated folder id (keyed by that id alone) may appear under both folders.
- HFS+ data protection: an entry with a `cprotect` attribute is flagged `Encrypted` (per entry, attribute `cprotect=present`) and its content is extracted as ciphertext (flagged `Derived.Encrypted`), while `Info.Encrypted` stays false because protection is per file; the volume's content-protection attribute bit only appears as a feature. The `cprotect` attribute layout is builder-only. Decryption belongs to roadmap sub-project 10 (`TestCProtectMarksEncrypted`).
- HFS+ free space: `Unallocated` is exact against the real fixtures (`TestUnallocatedMatchesOracle`) and conservative elsewhere: bitmap bits at or past `totalBlocks` are ignored whatever they hold (real images have them clear; an early format note said set, which was wrong, and the reader does not depend on either); a system file whose extents cannot be fully resolved, or an unreadable or invalid bad-block record, makes it return nothing with a warning (a damaged catalog volume reports no free space) instead of an incomplete protected set (`TestUnallocatedIncompleteSystemFileReportsNothing`); the bad-block file's extents are only searched in the extents-overflow tree when that tree is non-empty, and no real image holds a bad-block record, so that path is builder-only. At most 1<<24 runs are reported (a warning says when the rest is cut off).
- HFS+ caps and budgets: one filesystem instance reads at most 1 GiB of catalog leaf nodes in total for directory listings and fallback scans (single-name descents are not charged); a directory lists at most 262144 entries (thread records count) and examines at most 1<<20 records; a file maps at most 1<<20 extents (past that a trusted prefix and a warning); `Unallocated` reports at most 1<<24 runs and examines at most 1<<16 bad-block records; a directory that cannot be read because the budget is spent is an error, never an empty listing. Like the FAT, exFAT and F2FS budgets, these belong to the instance and start over with every `image` command (`ls`, `unalloc`, `extract` each open their own) (`TestDirectoryReadBudget`, `TestDirectoryEntryCap`, `TestDirRecordCapCountsThreadRecords`, `TestRunCapKeepsPrefix`, `TestUnallocatedRunCap`). A B-tree read that falls short of its fork is a corrupt-structure error, not an I/O error.
- HFS+ real-image coverage and the format reference: the committed fixtures are five empty `mkfs.hfsplus` volumes and one kernel-written populated volume (see docs/invariants.md and `tools/fixtures/README.md`); populated behaviour that the Linux driver cannot write (extended attributes, resource forks, decmpfs, data protection, HFSX with content, a journal with transactions, deleted-record slack, non-BMP names) is verified on builder images only, checked by `fsck.hfsplus` (12 of 15 pass, three exempt with recorded reasons) and never against a volume written by macOS or iOS: run `TestRealHFSPlusImages` (`-tags realimages`, `MINUTIAE_TEST_IMAGES`) by hand on such volumes before relying on those paths. Items of the format reference that real images settled: allocation-bitmap bits past `totalBlocks` are CLEAR (the reference said set), an HFS+ catalog's `keyCompareType` is 0xCF (not 0; HFSX binary is 0xBC), folder records carry flags 0, `mkfs.hfsplus -J` leaves the journal uninitialised, `mkfs.hfsplus -s` omits the folder-count flag that `fsck.hfsplus` then reports, and NUL folds last. Still unverified against any real image: the initialised journal header, the volume-attribute bits for an inconsistent boot volume, reused CNIDs and a software lock, the ignorable-unit list and the rest of Apple's fold table, the decmpfs formats, the directory-link markers, the attributes-file records (inline, fork-data and extents) and the `cprotect` layout.
- APFS reader, read-only and as found (`internal/filesys/apfs`, type `apfs`): `Info.Label` is empty (a container has no label; the volume names are in `Info.Volumes`, the per-volume feature lines and the root listing, one entry per volume). Only the NEWEST valid checkpoint is read: older checkpoints, the free queues, unreferenced blocks and deleted data are not interpreted (sub-project 3; `TestCheckpointPicksHighestValidXid`), and APFS keeps no deleted directory entries, so `image ls --deleted` shows none (`TestReadDirLiveEntries`). Fusion containers, version-1 containers and a non-contiguous checkpoint-descriptor area are `ErrUnsupported` (`TestFusionAndVersion1AreUnsupported`, `TestNonContiguousAreaIsUnsupported`); unknown incompatible volume features (the known set is the six bits of the format reference, 0x3f), a sealed volume and a pending revert only warn, and the hashes of a sealed volume are not verified. A time of 0 is shown as the epoch (present); only a value beyond the signed 64-bit range is invalid (`time_ns=invalid`). Extended attributes: their names are listed (at most 32 per entry, `xattr_count` says how many), their values and resource forks are not extracted, and a symlink whose target is stream-stored is `ErrUnsupported` when opened and is listed with attribute `symlink=unreadable` (`TestXattrNamesInAttrs`, `TestSymlinkTarget`, `TestSymlinkOpenReturnsTarget`). A damaged container object map makes `Open` fail with a `CorruptError` for the whole container, so no volume is listed at all (a damaged volume, by contrast, is warned about as unreadable and the others are still listed; `TestOmapPhysHostile`, `TestUnreadableVolumeIsListed`).
- APFS encryption: a volume flagged encrypted is reported (`Info.Encrypted`, `ErrEncrypted` on every read of it; `extract` skips it with an `analysis.warning` and extracts the other volumes) and its blocks are never read; decryption is sub-project 10 (`TestEncryptedVolumeIsErrEncrypted`, `TestExtractAPFSEncryptedVolumeIsSkipped`). On an unencrypted volume a file whose dstream crypto id OR any of its extents' crypto ids is not 0 or 4 is read as stored ciphertext and `extract` flags the artifact `Derived.Encrypted`; the listing flag `Entry.Encrypted` comes from the dstream crypto id only (listings do not scan extents), so a file keyed only in its extents is flagged when opened, not when listed (`TestOpenedFileReportsPerFileEncryption`, `TestPerFileCryptoIDAnomaly`, `TestExtractFlagsFileThatReportsItselfEncrypted`). The crypto id `~0` (unassigned) may mean "no key" in the format, but the reader treats it as a key, so it can over-flag `Encrypted` (unverified; the bytes are the stored ones either way). No committed real image holds an encrypted file or volume.
- APFS compressed files (the compressed inode flag) are unsupported: `Open` fails with `ErrUnsupported` ("decmpfs-compressed file"), the listing shows the entry with attribute `compressed=<type>` (named from the decmpfs header's type number, or its decimal number, or `unknown`) and `extract` skips it with an `analysis.warning`, never an empty file. This differs from F2FS (`compressed=true`) and HFS+ (zlib types are decoded); sharing HFS+'s decoder would need a package `internal/filesys/decmpfs`, because readers may not import each other. The type numbers are from memory of Apple's decmpfs header: 3/4 (zlib), 7/8 (lzvn) and 11/12 (lzfse) were re-derived by the review, but 9/10 (`uncompressed-*`) and 1, 2, 5, 6 (not named, printed as decimals) are UNVERIFIED, and no committed image holds a compressed file (`TestCompressedFileUnsupported`, `TestCompressedAttrNamesTheDecmpfsType`).
- APFS snapshots: each volume lists a synthetic `.snapshots` directory and every snapshot is a read-only view of the volume at its xid (`image ls --snapshot`, `image extract --snapshot`, or a path below `.snapshots`; see docs/invariants.md). RECURSIVE operations do not descend into `.snapshots` (`extract -r`, `image ls -r`), so a snapshot-heavy volume is not multiplied in the output, and they say so: one `analysis.warning` (source `examine`, not a skipped file) names the skipped `.snapshots` when the volume has snapshots. Other walkers of `filesys.Walk` (the fuzz targets) and `Session.Lookup("id:...")` DO follow snapshots. The snapshot-metadata layouts (record offsets, the snapshot name record, the object-map snapshot tree, which block holds the volume-superblock copy) are validated against ONE snapshot written by the Linux driver (`snap1` in `apfs-populated`, read with no warning) and a reviewer's re-derivation from the format reference (0 disagreements), never against a snapshot written by Apple software; several snapshots, deleted or reverted ones, duplicate names and a missing object-map record are builder-only. Two assumptions stay UNVERIFIED: that the volume-superblock copy of a snapshot carries its own block address as header oid (a mismatch is only a warning and the copy is used; the one real driver-written copy satisfied it) and the exact object-map xid boundary for records written in the snapshot's own transaction. `apfs_num_snapshots` is not compared with the records found. `--snapshot` needs a path that names a volume (`filesys.ErrNeedsVolume` is a usage error), and a bare reference that matches more than one snapshot is refused (use `xid:` or `name:`) rather than guessed (`TestSnapshotPathSharedNameIsAmbiguous`, `TestSnapshotFlagRefusesAmbiguousReference`).
- APFS names: a directory record's name hash is verified for every name that is valid UTF-8 and made only of code points assigned in Unicode 9.0 (that cutoff, from memory of how APFS freezes its tables, is unverified: a wrong cutoff only widens or narrows the set of names that are skipped, and it produced no false mismatch on any real fixture); a mismatch is flagged `name_hash=bad` with a warning and never hides the entry. On a normalization-insensitive volume lookup matches NFC and NFD spellings and, on a case-insensitive one, case-folded ones, using `golang.org/x/text` tables of Unicode 15.0: for a code point that exists in 9.0 the result is stable by policy, but a path may still resolve differently than on a live system for characters whose folding changed after 9.0; listing is unaffected. An exactly spelled hashed lookup reads only the records of one hash (a name matched only insensitively costs a scan, which looks for an exact name stored under a wrong hash first), so it can find an entry beyond the 262144-entry directory listing cap that a listing never shows. A case-sensitive volume that is normalization-insensitive (`0x8` only) matches NFD-equal names without case folding, as its hash does; no committed real image has that flag combination (builder-only, `TestLookupNormalizationInsensitiveOnlyVolume`). A name that is `.`, `..`, holds `/` or NUL or is not valid UTF-8 is shown as `~raw~<base64url>` with `RawName` set, and a duplicate volume name gets a `~<slot>` suffix (`TestNameHashNonASCIIMatchesRealImage`, `TestLookupNormalizationInsensitiveRealImage`, `TestVolumeNameEdgeCases`).
- APFS free space and the space manager: `Unallocated` comes from the space manager's chunk bitmaps and is exact against all four real fixtures (`TestAPFSMatchesOracle`), including a chunk with no bitmap block. A damaged structure is skipped with a warning or yields no runs, never guessed free space (see docs/invariants.md), and block 0, the checkpoint areas, the internal pool and the metadata blocks are removed even if a bitmap calls them free. The multi-CIB and CAB (chunk-info address block) layouts exist only in the builder (a real CAB needs a container of more than 126 chunks, 16 GiB): the real fixtures have one CIB. At most 1<<24 runs are reported (`TestUnallocatedBoundsAndCap`). Blocks that a snapshot still holds are allocated, so they are not in the export.
- APFS caps and detection limits: a B-tree is read to a depth of 16, with a per-scan node budget (`min(1<<20, blocks)`, tightened by `bt_node_count`) and a cumulative per-filesystem one (`max(1<<20, 4 x blocks)`); a directory is read up to 262144 entries and one filesystem instance reads at most 1 GiB of directory data in total (past that a warning and a partial listing, or an error when nothing was read, never an empty listing); a file maps at most 1<<20 runs and 1<<22 extent records; a volume lists at most 65536 snapshots. Like the other readers' budgets these belong to the instance and start over with every `image` command (`TestBTreeDepthCapIsCorrupt`, `TestBTreeCumulativeNodeBudget`, `TestDirectoryReadBudget`, `TestDirEntryCap`, `TestRunCapIsCorrupt`). The budgets can be reached by one huge or dense but legitimate volume: the cumulative node budget has a floor of 1 Mi node reads, about 9 reads per entry for a walk that also opens every file on a shallow tree on the populated fixture, so very roughly 50k to 100k small files before an `extract -r` ends with "node read budget exhausted" skips (loud, never a silent hole; deeper trees cost more), and a session that resolves many explicit paths in a very large directory spends the directory budget by scans (about 40 scans of a 262144-entry directory; a normalization-sensitive volume has no hash to search by, so every path component is a scan until the exact match). Not detected: an extent record erased from the middle of a file whose neighbours stay in order reads as a hole there, because APFS cannot tell a sparse range from a missing record (a sparse range has no record at all). The dstream `alloced_size` is deliberately not cross-checked against the extents: on the populated fixture it equals the mapped bytes for 1282 of 1290 ordinary files, but the four real sparse files report `alloced_size == size` (holes counted), so such a check would flag real sparse files (`TestWellOrderedSparseFileStaysHoles`, `TestSizeLargerThanExtentsIsAHoleTail`); a larger-id record at the very end of a leaf with the file's extent in the next leaf behind a hostile index key is not found, and two files whose extents overlap physically are not reported (clones legitimately share extents).
- APFS detection: the `apfs` driver probes block 0 only and is first in `detect.Drivers`. An NXSB signature planted at byte 0 of an ext4, F2FS, HFS+ or HFSX image (the boot area those filesystems leave free: their superblock or volume header is at byte 1024) is therefore claimed by `apfs` first; its `Open` fails with a corrupt-structure error and detection falls through to the real driver with the note `driver apfs matched but failed to open ...; opened as ...`, so the type the image opens as is unchanged; a signature anywhere else is never seen (`TestStaleAPFSSuperblockDoesNotHideOtherFilesystems`). A damaged container whose block 0 still carries the signature is claimed and opened through the checkpoint ring (block 0 supplies the geometry only).
- APFS real-image coverage: since the populated fixture the earlier "empty containers only" limitation is largely lifted. Validated against real bytes: the container, checkpoint ring, object maps, space manager and its bitmaps, the volume superblock, both directory-record key forms, inodes and their extended fields, directory records and name hashes (all 678 of the populated image), extents (fragmented files of 121 and 124 runs, sparse files with a hole first, last, between and all-hole), clones, symlinks, a hard-link group, extended attributes (embedded and stream), one snapshot, free queues and four checkpoints, written by `mkapfs` and by the `linux-apfs-rw` kernel driver (so conventions particular to that driver are what was seen: symlink mode 0755, and the `osx.` attribute prefix the driver adds on Linux). Still builder-only, never validated against any real image: encrypted volumes and per-file keys, decmpfs-compressed files, sealed volumes, Fusion, a second volume in one container, several, deleted or reverted snapshots and the object-map snapshot flags, the CAB and multi-CIB space-manager layouts, a checkpoint ring that wraps or has to fall back to an older checkpoint, volume roles other than none, a case-sensitive normalization-insensitive volume, hard-link records beyond the one real group, names with code points newer than Unicode 9.0, 64 KiB blocks, and anything written by macOS or iOS. Run `TestRealImages` (`-tags realimages`, `MINUTIAE_TEST_IMAGES`) by hand on such an image before relying on those paths; `tools/fixtures/apfs_expect.sh`, which writes the expectation file on macOS, was written from memory and never run.
- The populated APFS fixture is not byte-reproducible: five generations under QEMU gave five different images (the number and timing of driver transactions vary), so `apfs-populated.img.gz` and `apfs-populated.expect.json` must be regenerated together (`gen.sh apfs-populated` in the `minutiae-fixtures-apfs` image); every test pins the image sha256 to the oracle first. Regenerating changes the committed binary and the roughly 436 KB oracle.
- FAT and exFAT directory read budgets: each filesystem instance reads at most 1 GiB of directory data in total (exFAT) or at most 4M directory entries, 128 MiB (FAT, which counts entries), so a hostile volume whose chains overlap cannot cost unbounded time. Once the budget is spent, directories are no longer read (a directory read after that is an error, one being read when it ran out is cut short) and the filesystem reports a single budget warning (`TestDirectoryReadBudget`, `TestExfatDirectoryReadBudget`, `TestExfatBudgetExhaustedBeforeFirstEntryIsAnError`). A FAT directory also holds at most 65536 entries, an exFAT directory at most 256 MiB. The budgets are never reset within an instance, so one huge but legitimate volume can reach them. A directory that cannot be read because the budget is spent is an error, never an empty listing: `image ls -r` and `image extract` report it and do not treat the directory as empty. The budgets belong to the filesystem instance, and every `image` command (`ls`, `unalloc`, `extract`) opens its own session and so its own instance: the budgets start over with each command (this holds for the F2FS and HFS+ budgets too).
- `File.Runs` prefix rule: normally the runs cover exactly `[0, Size())`. A file whose allocation is truncated or corrupt (a FAT chain that ends, loops or leaves the volume; an HFS+ fork with a missing overflow record or an extent past the end of a truncated image; an APFS file whose extent records are out of order or invalid) may report only a leading prefix of it; every read at or beyond the end of that prefix fails with `ErrCorrupt`, never zeros, so the covered bytes can be told from the missing ones (`filesys.CheckRunsPrefix`, `TestCheckRunsPrefix`, `TestImageRunsAcceptsOnlyAValidPrefix`).
- Regenerating the real-image fixtures needs Docker; running the tests never does. The exFAT fixture additionally needs `docker run --privileged` (a loop device plus the FUSE driver `exfat-fuse`, because no exFAT image tool copies files into an image and the Docker Desktop kernel has no exfat driver); without it only that fixture cannot be regenerated, the committed `exfat.img.gz` and the builder-based `exfattest` tests still run. The HFS+ fixtures are not part of `gen.sh all` and need the separate `minutiae-fixtures-hfs` image (`tools/fixtures/Dockerfile.hfs`; no `--privileged`, the populated one is written by the Linux `hfsplus` driver under QEMU software emulation); the populated image is byte-identical on most regenerations (8 of 9) but not guaranteed, so it is regenerated together with its `expect.json`. The three empty APFS fixtures are part of `gen.sh all`, but `apfs-populated` needs the separate `minutiae-fixtures-apfs` image (`tools/fixtures/Dockerfile.apfs`; no `--privileged`, the Linux `linux-apfs-rw` driver runs only inside a QEMU guest, never in the host or Docker Desktop kernel) and is not byte-reproducible, so it is always regenerated together with its `expect.json`.
- Records database (sub-project 5, plan 5A: schema, writer, verify, reader, `records list|show|stats`; 5C added the provenance chain and image offsets to `show`; plan 5D remains; 5B added full-text search, see the full-text bullets below): the schema is v3 (v2 cases are upgraded by `case upgrade` then `records reindex`); a v1 case opens as v1 and works for everything else, but every `records` command refuses it (exit 2, `case upgrade` named) because a case is migrated only by the explicit, audited `case upgrade` (never on open). A corrupt `artifacts.db` is an integrity error (exit 4) and is never recreated. `records show` prints the columns, the artifact (id, path, sha256, source), the parser, the batch (digest, audit sequence), the run, `superseded by` and, since 5C, the checked provenance chain with image-relative offsets.
- Records audit anchor: the audit chain has no external anchor, so someone with file access who can append valid, correctly chained audit entries could forge a `records.ingest.recover` entry. A recover entry's `batch_nos` and `by_ingest_id` are not cross-checked against the ingest's audited batches, so for an interrupted ingest a forged `unfinished` recover that names a trailing batch (together with erasing that batch) leaves only a notice; for a concluded ingest the totals check defeats it. Anchoring the audit head outside the case is not planned yet.
- Records supersession and runs: only a complete run supersedes an older run of the same parser name for an artifact, so an incomplete (failed, cancelled or interrupted) run is shown beside the older complete run until a complete run supersedes both. `case verify` lists at most 50 problems per kind, then one "N further <kind> problems are not listed" line (`TestVerifyListsAtMostFiftyProblemsPerKind`). `Overview.Runs` is case-wide (not filtered); `Overview.Deleted` includes recovered records while `Stats` by `deleted` puts them in a `recovered` group. `Reader.Count(limit)` is exact up to `limit`, `capped` is true only when more than `limit` records exist (n is then `limit`) and a limit of 0 means no cap (`Page.Limit` 0 means 100).
- Records reads are not verification: `records list|show|stats` read `artifacts.db` as it is and never run the `case verify` row checks, so what they print is only as trustworthy as the last `case verify` (the exception is `show`, which since 5C checks the provenance chain, its audit binding and the sidecar hashes, and still not row digests) (a repointed `artifact_id` shows another artifact's provenance, an edited summary is shown as edited). The one check they make is the cheap comparison of the schema objects (`ReadRecordsTx`): a database whose tables, indexes, triggers or views differ from the schema this build defines is refused with exit 4 (a redefined index or view could otherwise shape every answer silently). A forged row or an injected `record_superseded` pair is not seen by the reader. Run `case verify` before relying on a listing.
- Record provenance in `records show` (sub-project 5, plan 5C): `show` resolves and checks the chain, the audit binding of each hop and the runs sidecar hashes, but it still does not recompute row digests or re-verify the audit chain itself (`case verify` does; exit 4 from `show` means a provenance problem, not that the log is intact). `extract` and `unalloc` runs are claims recorded at extraction time: `show` checks they are self-consistent and translates through them but does not prove they reproduce the image (`case verify` R6 does that for recovered artifacts only). Offsets are logical media offsets (E01 shows media coordinates, labelled); a decompressed artifact (decmpfs) has no runs and so no image offset. Translation is not linear in the runs: each hop re-scans the runs for each of up to 256 pieces (256 x runs per hop, times up to 16 hops), so a hostile sidecar of 1M runs makes `show` slow (still bounded; no algorithm change). The unallocated run map has its own strict reader (`ReadUnallocRunMap`); carving (3E) relies on it.
- Verify gap (owed to 5D): `show` flags a COMPLETE non-recovered artifact whose runs sum differs from its size (`runs cover <n> bytes but the artifact has <m>`), but no `case verify` rule checks it, so verify can be clean for a case where `show` reports a problem. A verify rule is in the backlog.
- Raw terminal-display risk in `--json`: bidi controls and NEL (for example U+202E, U+0085) are left raw in JSON strings (controls below 0x20 are escaped, the decoded JSON values equal the stored strings), so a JSON line viewed raw in a terminal can be visually reordered. A CLI-wide terminal-safe JSON encoder (`\uXXXX` for every non-graphic rune, values unchanged) is in the backlog.
- The default `records list` hides superseded records through the STORED `record_superseded` table (`Filter.compile`), not through a recomputation from the runs. `case verify` (P14) proves that table equal, in both directions, to the recomputation from the one shared definition `evidence.SupersededPairsSQL`, so a forged or deleted pair changes a listing only until the next verify.
- Records write-time limits (a record outside them is refused with a typed error; nothing is buffered or audited; `TestPrepareValidationMatrix`): summary 512 bytes, body 4 MiB, payload 16 MiB of canonical JSON and 64 levels of nesting, locator 1024 bytes and a scheme `[a-z][a-z0-9]{1,15}:`, source path 4096 bytes, at most 16 secondary times per record with kinds `[a-z][a-z0-9_]{1,31}`, registered record type names `[a-z][a-z0-9_]{1,31}`, recovery method `[a-z][a-z0-9-]{1,31}`, 20,000 rows per batch (default 5000), parser name and version `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, parser hash empty (stored NULL, never "") or `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`; NUL and invalid UTF-8 in text are refused, and a timestamp outside 1970 to 2100 is accepted only with a non-empty payload `ts_note`. Warnings written through `Writer.Warn` are bounded (path 4096 bytes, reason 1024) and capped at 10,000 per ingest.
- Records ingest counts: `rejected` counts records refused by `Add` (validation) and `Writer.Reject` calls. Every one is audited as an `analysis.warning` entry marked `rejected=true`, sharing the 10,000-entry cap with `Writer.Warn`; past the cap nothing is written per entry and the single suppression note, written right before `records.ingest.end`/`.error`, carries the numbers of suppressed warnings and suppressed rejections. `case verify` therefore checks equality: `warnings` = entries, `warnings_suppressed` = the note's two numbers summed, `rejected` = rejection entries + the note's suppressed rejections. Recovery of an unconcluded ingest derives the same numbers from the log. The writer also appends a "suppression began" marker note (`suppression_began=true`, no numbers) the first time the cap keeps an entry out of the log. Limit: an ingest that dies before it writes the conclusion note (a crash or kill before `End`/`Abort`) leaves no proof of how much was suppressed; its recovery sets `suppression_unknown=true` (with the placeholders `warnings_suppressed` 0 and `rejected` counting only the rejection entries, both lower bounds), never a silent 0, and verify accepts that flag only on such a recovered ingest. A concluded ingest (an end/error entry, or a run-missing recover) that has a began note but no conclusion note is a verify problem, so an end entry appended for a crashed, suppressing ingest cannot pass as "0 suppressed"; a repeated began note (an audit append that failed after its entry reached the log, then retried) is tolerated. After the note is written the writer refuses further `Warn`/`Reject`/refused `Add` calls (`ErrWriterClosed`), so the note is never stale.
- Records audit entries are decoded strictly (`evidence.DecodeDetails` refuses an unknown field): a later build that adds a field to a `records.*` audit entry makes an older build report `case verify` problems for the newer log. That is acceptable only while the schema is unreleased (see the "no compatibility path" bullet); the layouts must be versioned before the first release that has to add a field.
- `case verify` reports a derived-artifact cycle of N artifacts once per artifact (N problems, at most 50 listed per kind; `TestDerivedChainWalk`), and a parent chain longer than 16 hops as one problem.
- Records time and text: timestamps are stored as Unix microseconds (a sub-microsecond remainder is truncated; the raw value is the parser's to keep in the payload); a time outside 1970 to 2100 needs a non-empty `ts_note` in the payload; `local-unknown` is a wall clock stored as if UTC; `TimeEnd` must share its `Time`'s basis and offset; NUL is rejected in every record string and payload string. `records list|show` display a local time with a known offset as its wall clock plus `~local+HH:MM`, and a local time of unknown zone as `~local` (stored instants in `stats` time ranges are shown as UTC).
- Records cursors are stable only across an unchanged database (a record ingested between two pages is not seen by a cursor taken before it, and ids are never reused); the fingerprint a cursor carries is a guard against using it with the wrong filter, order, direction or case, not a defence against a forger, who learns nothing from reusing one.
- Full-text search (sub-project 5, plan 5B: schema v3, `records search`, `records reindex`, P11): the index (`records_fts` word table, `records_fts_sub` trigram table) is DERIVED data over the summary and body of each record, never evidence, and `case verify` P11 proves it by recomputation: it normalizes every record, rebuilds the expected index in a scratch database and compares documents, sizes, totals, config, vocab and per-term MATCH reachability. Verify time and temporary space therefore grow with the indexed text. P11 has no skip flag and its cost is unmeasured until plan 5D (the per-term reachability pass included). Payload values are NOT indexed (summary and body only), there is no `prefix` index (a prefix needs at least 2 letters or digits on its last token and its speed is untuned), and search plans are untuned until 5D (only the use of the index for MATCH is pinned).
- Full-text version rule: the index is valid only for the pipeline version it was built with (`FTSNormVersion`: normalization, the `golang.org/x/text` version, Go's Unicode version and the driver). A normalization or driver version bump therefore requires `records reindex` BEFORE any ingest: until then `records search` and `Writer.Start` refuse (exit 2 for search, `ErrIndexNotCurrent`), a batch cannot be written and `case verify` reports a notice. A v2 case needs `case upgrade` (which leaves a case with records "index not built") and then `records reindex`. An attacker with file access can force "index not current" (edit or delete `fts_norm_version`): that denies search and writing and can never produce a wrong hit; `case verify` does not trust the value either: it derives the expected state from the audit log (the last `records.reindex.done` and the `norm_version` of the later `records.ingest.start` entries), reports a different value as a PROBLEM and compares the index content whenever the derived version is this build's. A state the audit log explains but P11 cannot check (never built after an upgrade, built by another pipeline version, a reindex announced and not concluded) is a NOTICE: `case verify` exits 0 and the index content is not compared until `records reindex` runs.
- Full-text schema comparison: the FTS5 shadow tables (4 per index) are verified by DDL text like every other schema object (P12 and the reader's check). A future SQLite that changes the DDL FTS5 writes for its shadow tables makes older v3 cases fail that comparison (exit 4 on `records` commands, a P12 problem); the weakening of the comparison is refused, the remedy (a version-aware expected schema) is for 5D or later.
- Full-text temporary files: `PRAGMA temp_store_directory` is process-wide state. `case verify` sets it to `<case>/tmp/verify-<runid>/` for the P11 work and resets it in a defer (even on panic), so evidence-derived text never spills outside the case; the CLI runs one command per process, a library caller running other SQLite work in the same process during a verify shares that setting. The scratch database and spill files are removed when verify ends. A leftover `<case>/tmp/verify-*` directory (an interrupted verify) is a `case verify` problem on the next run, as is `<case>/tmp` when it is a symlink, junction or any non-directory (checked with `Lstat`; nothing is created or listed through it); at most 50 leftover entries are listed, then one "further entries are not listed" line (`TestCheckTmpListsAtMostFiftyEntries`, `TestCheckTmpAloneRefusesANonDirectory`), and verify removes only what it created: its run directory, and `<case>/tmp` only when this run created it (`TestVerifyKeepsAPreExistingEmptyTmp`). The P11 scratch database is a deliberate exception to "reads go through `ReadHandle`": it is a private temporary database that `case verify` creates and fills itself (never the case database), under `<case>/tmp`. Every read transaction on the case database sets `temp_store = MEMORY` (a connection setting of the transaction, undone when it ends), so a search or stats sorter never spills outside the case; the rank statement ends in `LIMIT ?`, which bounds its sorter. Two caveats: a symlink or junction `tmp` is tested only with a regular file on Windows (the symlink subtest skips without the privilege), and a `--timeout` below the clock resolution (1 ns on Windows) is not guaranteed to have passed when the first statement starts (a test hands the command a past deadline instead).
- Full-text index residuals: rows in the FTS5 shadow tables (`_data`, `_idx`) that no structure record references are inert and pass `case verify`: they are a hiding place inside `artifacts.db` of the same class as SQLite's free pages and are not detected (backlog: parse the structure record and flag unreferenced segments). The query grammar scan runs after the 4096-byte cap on the raw query text and is bounded by it. A search hit shown without a marked snippet on one column means that column did not match (`--in any`); a stored text that literally holds the six characters of an escaped marker looks the same as an escaped marker on screen (harmless). The scanner of the single-writer rule now also flags `sqlite_master` writes and `writable_schema`; a comment marker inside an SQL string literal remains the residual below.
- Full-text query limits and grammar: the grammar is closed (words ANDed, `AND` optional, upper-case `OR`, `"phrases"`, `prefix*`, `-negation`); everything else is text and is tokenized like the stored text, so punctuation separates tokens. Terms with nothing to search for are refused with a usage error, never answered empty: a term with no letter or digit (emoji-only, private-use characters, symbols), a prefix with fewer than 2 letters or digits on the token its star attaches to, a `--substring` needle under 3 characters after the tokenizer's mark folding (`ab` plus a combining mark is 2), a term over 256 bytes, a query over 4096 bytes or 64 terms. Behaviours: `--foo` is the negation of `-foo`, and a group of only negations is refused; `c++` searches the token `c` (it also finds `c#` and `c`); `+1` searches the token `1`; `a-b` is the phrase `a b` (the two tokens adjacent, so it also finds `a b` and `a.b`); a query that starts with `-` is read by the command line as a flag, so write `minutiae records search --case C -- -x`. Use `--substring` for punctuation-exact needles.
- Full-text tokenization limits: a run of CJK characters is ONE token (a word search finds it only as that whole run, `--substring` finds parts of it from 3 characters), and emoji are not word tokens (a word query cannot find them, and an emoji-only term is refused for `--substring` as well; variation selectors are dropped so `❤` and `❤️` meet inside a longer text). U+200B is a separator, U+200C/U+200D and U+2060 are dropped (they join within words). These misses are pinned by `TestNormalizeKnownSilentMisses`, not fixed.
- Full-text ranking and snippets: `--rank` returns the best 1000 hits at most, without a cursor and without `--substring`; its order uses bm25 with the totals P11 verifies, which mean little for trigram text and for short summaries. Snippets are cut from the stored text and highlighted with an approximate tokenization (the query's needles folded like the index, not the FTS5 tokenizer itself), so a hit the index found may show a head snippet with no highlight. A snippet line without a marker means that column did not match (the head of the column is shown), and with `--in summary` or `--in body` the other column gets no snippet. `--json` spans carry the text as stored and a `match` flag. A search that runs past `--timeout` (default 30 s) ends with `ErrSearchTimeout` (exit 1); a cancel stays a cancel.
- Records performance is not yet measured: `case verify` re-reads every row (streamed in chunks of 5000 rows or 64 MiB, the byte cut untested), also runs `PRAGMA integrity_check` (a full scan of every table and index) and selects `typeof()` of every column read (`Writer.Start` and every batch read `max(id)` and the counter, and every reader call compares `sqlite_master`; their cost at scale is unmeasured), `Writer.Start` reads the audit log twice, `Reader.Get` and every no-op `case upgrade` read the whole audit log, and a list filtered by several types, artifacts or parsers, by path prefix or by confidence cannot be served in order by an index (only unfiltered, single-type and deleted-only plans are pinned); `Stats` does not cap the number of groups. Ingest throughput, 10-million-record scale and the p95 targets belong to plan 5D.
- Records concurrency: one `Writer` per `Case` at a time (a second `Start` is `ErrIngestActive`; another process is excluded by the case lock). Nested `StoreTx`/`ReadTx` calls are detected by goroutine identity (parsed from `runtime.Stack`): a nested call from the same goroutine fails with `ErrNestedTx`, other goroutines queue; a function that hands its transaction to another goroutine and waits for it is not detected (it queues behind itself). `ReadHandle` refuses non-read SQL lexically before running it; SQLite cannot stop a query from switching `query_only` off inside the open transaction, so that second layer detects and rolls it back (`ErrReadTxModified`, connection discarded) instead of preventing it. The concurrency tests run under `-race` in the race gate (the records and evidence ones by name, step 3; passed 2026-10-08, 0 data races); the fast check runs them without `-race`.
- Single-writer scanner residual: the scan of Go files for SQL that writes the record tables strips comments from a normalized SQL string, so a comment marker inside an SQL string literal (`'--'`, `'/*'`) in a deliberately built multi-statement string can hide a following write from the scanner. The immutability triggers and `case verify` still catch the write; the scanner stops mistakes, not a determined author.
- Records schema history: no compatibility path exists for audit logs written before `created` was added to `records.batch` (the schema is unreleased); a `case.upgrade` announced and then dropped by a later announced upgrade is not reported (latent until schema v3).
- Deleted-data recovery (sub-project 3, plan 3A: the foundation; 3B to 3K pending): the model (`evidence.Recovery`, the class table, namespaces), the checks R1 to R7 of `case verify`, the optional `filesys.Recoverer`/`Journaler`/`AllocatedRunner` interfaces, the planner and writer (`examine.Session.PlanRecovery`/`Recover`) and `image recover` exist, but NO filesystem reader implements `Recoverer` yet (ext4, FAT, exFAT, F2FS and HFS+ readers are 3B to 3D), so on a real image `image recover` reports that the filesystem "does not support recovery" (exit 1, nothing written, only `case.open` audited) and is exercised end to end only on the in-memory MTFS test filesystem. `Journaler` and `AllocatedRunner` have no consumer in 3A (interfaces only; their users are 3F/3G and the carving plans).
- `image recover` addressing and coverage: a deleted entry is addressed by `id:<FSID>` or by naming a live directory (every deleted entry below it is considered); a deleted entry cannot be addressed by path. Files inside DELETED directories are not enumerated by 3A (`filesys.Walk` does not descend into them); the owners are the 3B to 3D readers (enumeration inside the `Recoverer`). In 3A only `image recover` marks recovered artifacts; `records show` marks them (status line first, since 5C) but `case info` does not yet (report work), and `records list|search` filter and show the recovered flag of records. `--list` plans without writing: it reads image bytes (the uniform scan and the allocation lookup) but writes no artifact and appends only the usual `case.open` audit entry.
- Recovery artifacts and kinds: a runs sidecar of a recovered artifact is an ordinary artifact of kind `runs` (empty remote path, no `Recovery`, same directory), not a recovered kind. The kinds `slack`, `journal` and `report` are verified by R1 to R5 only and noticed (not reproduced byte for byte) until 3F/3G add their reproduction; `recover` and `carve` artifacts get the same notice only until R6 runs, which it does in every `case verify` of this build. A recovered artifact records ONLY the captured prefix runs (the rest is named in `Excluded`, capped at 256 runs), so the sum of its runs always equals its size; its `Content` is `ok` or `uniform` only (no plausibility or format check yet), and a candidate of size 0 is `empty`, one of size above 0 with no runs `no-runs`. Confidence for `post-checkpoint-file` is required and its journal reference rules may change in 3H; a journal reference is allowed only for `deleted-file` and `journal-report`. The allocation state `unknown` is decided by presence: a filesystem that has any warning after `Unallocated` counts every unverifiable byte as unknown (conservative, and the same in `--list` and a run).
- Recovered-ness propagates through the derivation chain: extracting files from a carved or recovered partition image yields live-namespace (`extract`) artifacts whose records are still recovered records (R7 walks the chain, at most 16 hops, and requires a recovered flag and a confidence not above the lowest along the chain), so a record cannot launder a recovered artifact by being extracted again.
- Recovery run bounds and cost: `--max-files` and `--max-bytes` (defaults 100000 and 8 GiB) apply to `recover` only (`extract` and `unalloc` have no such cap); the uniform scan is part of admission and its total is capped at 4 x `--max-bytes` (reason `max-scan-bytes`, distinct from `max-bytes`; a uniform verdict is cached per identical run list); a run considers at most 1,000,000 deleted entries and plans at most 1<<19 runs by default (`--max-plan-runs` raises it; planning, the overlap passes included, peaks at about 260 MiB of heap at the default, measured by `TestOverlapPeakHeapAtPlanCapStaysBounded`, and about 2.7 GiB at 1<<22), the rest counted as `limit` with one audited warning (`max-entries`, `max-plan-runs`); at most 1000 walk errors are listed (the rest counted by reason, one further-count note). `not-selected` candidates (without `--all-candidates`) are counted in `skipped_by` and `analysis.end` only. Overlap detection is O(n log n): each entry lists at most 16 overlapping partners (`overlap=<id>`) and the attribute `overlap-other-runs=<n>` counts the further overlapping RUNS of other candidates beyond those partners, not distinct owners (a number never claims more than it counts); the overlap confidence cap of 30 is applied per ENTRY, not per candidate: with `--all-candidates` every alternative of an entry whose chosen runs overlap another entry's gets the overlap assumptions and the cap, even an alternative whose own runs overlap nothing, which under-states its confidence and never over-states it. Overlap is also evaluated over candidates that are later skipped (uniform, below the minimum confidence, past `--max-files`), so a surviving candidate can be capped at 30 and name `overlap=<id>` for an entry that is then not written: again an under-statement. A hostile image with N skippable candidates writes one audited `analysis.warning` per skip (about 1.5 ms each, fsynced) up to 10,000 per analysis, then one "further warnings suppressed" entry; the later ones are only counted (`analysis.end` carries `warnings_suppressed`, the summary counts stay exact; `TestRecoverWarningEntriesAreCapped`). The free-space check is advisory and, on Linux, counts `f_bavail` in `f_frsize` units (`TestStatfsUnitPrefersFragmentSize`).
- `case verify` cost of recovered artifacts: R6 reads, for EVERY recovered or carved artifact, the image bytes at its runs and the artifact itself (1 MiB chunks, one container open per parent), so verify time grows linearly with the recovered bytes (up to the 8 GiB default budget per run, more over several runs); there is no skip option and no timeout flag (the context cancels it) and the cost is not measured; the prebuilt manifest index keeps it linear instead of quadratic in the artifact count. A flag to skip or report progress belongs to a later plan.
- `case verify` limits of the recovery rules: verify cannot check that the runs of a `deleted-file` lie inside the filesystem's `Unallocated()` (R5 checks only the writer's own `Alloc` claim, R6 reproduces bytes, not allocation state; spec 3.2.3 is enforced at write time by `examine` only). Each recovered artifact re-reads its whole runs sidecar (up to 1M lines), so N artifacts sharing a sidecar cost N reads. R6's `OpenContainer` re-reads the manifest per parent group, so the indexed open applies fully only to the `scope=artifact` carve path. The `archtest` scanners of the recovery rules are review aids (they stop mistakes, not a determined author): string conversions of a kind, a function result as a `Kind` and positional `Source` literals are not seen; the real defence is `case verify`.
- `declared_runs_artifact`: an artifact whose copy was interrupted (cancel, read error) keeps its captured prefix as runs, and the full run list the filesystem declared stays in the case as a `runs` sidecar named by `Recovery.declared_runs_artifact`; it is provenance of what was declared, never of what was captured, and is not used to reproduce bytes. Scope reconciliation: the earlier rule that a carved scope is limited to raw and unallocated is superseded by spec 5.2, which lists `unallocated`, `volume`, `raw` and `artifact`.
- The free-space check is advisory: the output volume can fill after it passes, which is a case-write failure and aborts the run (`analysis.error`, partial artifacts kept and flagged). The check uses the space available to the calling user (Windows: `lpFreeBytesAvailableToCaller`, so quotas count) and saturates at the largest int64 when the OS reports an overflowing value. A manifest line with an unknown field is dropped by the non-strict decode of `manifest.jsonl` (pre-existing; the hash-chained `artifact.create` entry still carries the full `Source` and `case verify` compares it field by field).
- Recovery audit anchor: as for the records database, the audit chain has no external anchor, so a forger who can append valid, correctly chained audit entries (and rewrite the manifest and the artifact consistently) is not detected by `case verify`; R6 still catches artifact bytes that do not equal the image at the recorded runs, so a forgery must also rewrite the parent image artifact, which changes its hash in every derived record and in the audit.
- SQLite file library (sub-project 3, plan 3I, `internal/sqlitefile`; the typed recovery pass and the generic `db_row` run are plans 3J and later): the library reads, it never opens an engine, creates a file or writes. `Live()` is the state the SQLite engine would present: the database plus the committed frames of the current WAL generation, and a VALID HOT journal is applied in memory (before-images override database pages, playback stops at the first bad record checksum as the engine does); nothing is written to the evidence or next to it. `AsFound()` is the raw view (the file plus the committed WAL overlay, no rollback); nothing uses it by default. A hot journal that names a super-journal is applied only when the caller says the super-journal file exists (`Options.SuperJournalPresent`), because the library cannot see other files; the engine's behaviour with the file absent is matched. Read-only copies and locks are not modelled: the engine refuses to roll back a journal on a read-only database file and does not treat a journal as hot while a live writer holds a lock, where `Live()` presents the rolled-back state (the `journal-hot` warning is raised either way).
- SQLite file library, deliberate deviations from the engine (each fails closed with a warning, never guesses): a WAL frame or database page that reads past the end of its file is unavailable, never zero-filled (`live-pages-unavailable`, at most one warning per file kind, with counts); a journal initial size above the file size is not zero-filled (`page-count-clamped`); a trailing partial page counts as a page like the engine but its missing bytes are unreadable, never zeros (a cell that reaches past the end is a damaged cell with a warning, and `History` yields the partial page marked `Partial`); a hot journal that is NOT applied (page size differs from the database, or the record or segment limit is reached, so a partial rollback would mix two states) makes `Live()` fail with a typed `LiveUnavailableError` plus a warning, and while `Live()` is unavailable `History`, `Pages` and `Summary` return the same error (no history rows are delivered with an unknown relation to live; `AsFound()` stays available for the raw pages); a WAL whose re-sealed header carries an unsupported version makes `Live()` fail the same way, as the engine refuses such a database; a valid-header WAL is applied whatever its page size (the first database-page-size bytes of each frame are read) and a header-invalid WAL is ignored (`wal-header-invalid`). The journal edge rules (journal page size 0 means the database page size, a zero-length super-journal file is absent, a journal under 512 bytes is not played back while one between 512 and 4096 bytes is, a super-journal name over 1040 bytes is not a trailer, page 0 and the lock-byte page end playback, a page above the initial size is skipped, the last write of a page wins, a hot journal and a WAL are applied rollback first) are those 47 engine probes of `TestEngineJournalRules`; an anomaly the engine does not mind but a reader should (`journal-and-wal`, `journal-duplicate-page`, `journal-page-size-mismatch`) is a warning. Other unmodelled engine behaviour: a WAL beside a rollback-mode header (bytes 18/19) is applied as the engine's probe shows (`wal-mode-mismatch`), the `-shm` file is ignored, and a database whose file is empty but whose WAL is not cannot be `Open`ed (use `ScanWAL` standalone).
- SQLite file library, WAL frames and values: the frames the engine does not apply (uncommitted tail, a broken frame, frames after a break, frames of an older generation) are not live; one `wal-frames-not-applied` warning per scan counts them by class with the first slot of each, and they are History's (`sqlite-wal-uncommitted`, `sqlite-wal-stale`). A live text value over 4 MiB or blob over 64 MiB, a value in a truncated overflow chain, a virtual generated column and a non-literal default are NOT materialized: the value carries `Omitted` (with its true `Len`), every omission is counted in a warning, and the decoding layer must report it as absent; a recovered value over 1 MiB is clipped and marked `Clipped`. Serial types 10 and 11 read as NULL with a `record-reserved-serial` warning (the engine does the same) and the header's text-encoding field is read as the engine reads it. Every allocation is charged to the `Budget` (a nil budget gets an internal 1 GiB one, there is no unbudgeted mode), every count is sized from the physical addressable page limit and never from a declared count, and a limit that is reached ends the work with `limit-reached` and a warning, never silently.
- SQLite file library, schema and lookups: no `Get` by rowid for a WITHOUT ROWID table (`ErrWithoutRowid`); `Get` reads an overflow chain as the engine does even when another row shares its pages (only a scan or `case verify` of the artifact reports the sharing); an index tree is scanned without a key-range check (it needs collations; a doctored table-tree interior key is flagged); collation-aware comparison is NOT implemented for scans or lookups. The CREATE parser is tolerant and refuses what the engine refuses (duplicate column names, STRICT types): an unreadable or over-cap definition leaves the table unparsed with a warning (columns unknown), never a failure; views and triggers are listed, not interpreted. Virtual tables are listed and not interpreted (`Table()` is `ErrNotFound`), and their shadow tables read as ordinary tables. A table whose schema row names a root page that cannot be a b-tree root (0, 1, past the addressable limit) is a warning and `ErrCorrupt`, never `ErrNotFound`; that rule is for the root-page case. In general `Table` and `Index` answer `ErrNotFound` only when the schema was read cleanly (`Schema.Skipped` is 0); after any skipped or contradictory schema row, a name that is not found is an `ErrCorrupt` error ("the schema was read incompletely"), because the object may be among the lost rows (`TestTableAndIndexAreNotAbsentAfterASkippedSchemaRow`). Cells found outside any pointer array (gap, freeblock, orphan page, freelist trunk tail) are plan 3J's: 3I only exports the free-space spans and counts; History ignores interior index cells (counted as `InteriorSkipped`).
- SQLite file library, recovered rows are LEADS with an honest label, never facts (`History()`; spec 3 section 3.3, the confidence rule is `Confidence`): a row's table is named by the schema the IMAGE itself had when it was written (the as-of schema read from the same snapshot; basis `schema`), and only when that schema is unavailable (a stale generation without its schema frame, a damaged as-of schema, a page beyond the as-of state, the state cap reached) does the label come from a fit of the cell shapes (`fit` capped at 60, `guess` at 40, `none` at 30), always with the note `identity-by-fit-only` and the relation `unknown`: a fit is never compared with a live row, so a dropped table is never reported as a modified row of another. Accepted residuals: (1) a dropped table whose shape matches exactly one live table is labelled by that live table (basis `fit`, 60, `unknown`, `identity-by-fit-only`), which can name the wrong table, and the examiner is told by the basis and the note (ruling C46); (2) rows whose as-of owner is unprovable are NOT deduplicated against live rows, so a row equal to a live row can be listed (no "equals a live row" annotation; ruling C45); (3) a label on the schema basis needs every cell of the page to fit the named owner strictly, a page that fits only loosely gets `fit` or `guess`; (4) rows of a WAL generation with no schema frame carry the fit basis and `owner-changed`; (5) the strict fit refuses a record missing a rowid-alias column (ALTER TABLE cannot add one), STRICT tables can be ambiguous, and the fit is bounded by a step cap past which every fit is `limit-reached`; (6) pages the layout cannot attribute because the schema was read incompletely are counted in one `pages-unattributed` warning and NOT listed, because they may be live pages of unread tables; (7) the overflow of a stale cell is followed only under the snapshot rule (the chain as of the image, never from today's pages). `uncommitted` is an ORIGIN fact (`Origin`), not a relation: the relation of EVERY row whose identity the schema does not prove (basis `fit`, `guess` or `none`) is `unknown`, whatever the origin, and only a schema-basis row from an uncommitted origin carries the relation `uncommitted`. Row identity for WITHOUT ROWID history compares numerically across kinds (1 equals 1.0) under BINARY, NOCASE (ASCII folding only) and RTRIM, with the key clause's collation; any other collation or an undecidable key gives `unknown`, never `absent` (rulings C48 and C53). The method token `sqlite-journal-rolledback` (base 45) labels page images the rollback hides; every confidence number has a proving fixture (`TestFitTiersProveConfidenceNumbers`).
- SQLite file library, validation limits: the library is held to the SQLite engine of `modernc.org/sqlite` (3.53.4) on engine-made files and to the Debian `sqlite3` 3.46.1 on the container family (class C), plus a builder; NO fixture comes from a real application or a real device. Android and iOS behaviours of `secure_delete`, `VACUUM`, journal modes and WAL resets are therefore unvalidated on real devices. Engine-written WAL and journal fixtures are not byte-reproducible (regenerate with their oracle). The tagged matrix (`-tags sqlitematrix`: 45 live scenarios, 1448 WAL mutations) passed with 0 library/engine divergences and no copy-retry fallback in any oracle test at the time of plan close-out and again after the final review fixes (45 live scenarios; 1448 WAL mutations, 1443 equal to the engine's view and 5 refused by the engine); the pinned Docker layer (`sqlite3=3.46.1-7+deb13u2`, a package version that leaves the archive when superseded, so a later rebuild fails loudly) was built and verified on 2026-10-08 (`dpkg-query` shows `sqlite3` and `libsqlite3-0` at 3.46.1-7+deb13u2, `sqlite3 --version` is 3.46.1, the layer's own version tests passed; no fixture was regenerated), and `docker build` of the main fixture image uses an unpinned `debian:stable-slim` base (backlog). The race detector is not part of the per-task check; the coordinator's `check.sh --race` is the merge gate for `sqlitefile`.
- SQLite file library, residuals of the final review (plan 3I): (1) a WAL frame or journal record states its own page number and that number is not checked against the pages the database can address: an impossible one (0, the lock-byte page, above `Limits.MaxPages`, and for a journal with an intact, non-zeroed header above its initial size) is flagged `invalid-page-number` on the image and its rows (relation `unknown`, one counted warning per file), but a WAL frame past the database's end is not impossible (an uncommitted tail may extend it) and is flagged only when committed beyond its commit size. (2) The comparison of a history row with the live row is `unknown` (note `value-unread`) when a scalar of either side was never read; a value that is not stored (a short record's default, a virtual generated column) is not `Unread` and compares equal to its counterpart. (3) A row whose strict fit or as-of owner check refuses a legal image of a table with DESC key columns is labelled `owner-changed` with relation `unknown` (38 rows in one measured scenario): safe, never wrong, and imprecise (backlog). (4) `FitPage` receives the values of a cell only: whether the record was `Truncated` or held reserved serial types is not visible to the fit. (5) `record-length-mismatch` is a warning at the cell and also marks the row (`Row.LengthMismatch`, the recovered-row note). (6) A repeated column in a primary key list under two collations stays unparsed (the engine keys the index by both); a tree between 21 and 32 levels is read with a `btree-depth` warning although the engine calls it corrupt. (7) The schema-derived reasons in `Info.EngineRefuses` (at most 16, a name or `tbl_name` that disagrees with its statement, an index or trigger on no table) appear only after the schema was read; the name check applies to statements within `MaxSchemaSQLBytes` that the head parser can read, with names compared ASCII case-insensitively. (8) The warning-code set is closed and now has 50 codes (`record-length-mismatch`, `wal-page-invalid` and `hdr-schema-format` were added by the final review).
- Artifact parsers (sub-project 4, plan 4A: contract, host, registry, `parse list|plan|run`). No real parser exists yet (plans 4D to 4F add them): the registry is empty, `parse run` plans zero jobs and the parser tests that range over the registry are vacuous until then and rely on their self-test tables (`TestRegistryWellFormed`, `TestClaimsEqualMappings` over the registry, `TestClaimedTablesEmptyWithoutClaims`, `TestRepositoryIdentitiesAreCurrent`). `--include-recovered`, `parse recover`, `parse plan --scan` and the `ios-backup` namer are later plans; snapshot-derived artifacts are parsed only with `--include-snapshots`; a parser can emit only types that have a payload contract; the validators are active in every binary that links `artparse`.
- Parser isolation is in-process. A stack overflow or an out-of-memory kills the process (`debug.SetMemoryLimit`, set to twice the memory budget for the run and restored, is a soft GC limit only). The threat model is hostile DATA, not a malicious parser author. A parser that ignores cancellation is ABANDONED: it is sealed, its accepted records are flushed, its ingest is concluded as error and the whole run stops (exit 1, "restart recommended"); the spinning goroutine keeps a core and the memory its inputs pin until the process exits. Flush and Abort wait at most the grace period behind a stuck writer call, then the job is abandoned with that reason. The run summary `Stopped` is `abandoned`, `cancelled`, `audit-failure`, `abort-failure` or `run-error` (any other run-level failure such as `ErrIngestActive` or a failed `Start`).
  A conclusion detached from an abandoned job can finish after the host stopped waiting for it; if the case closes first it can lose its run row, and the next Start recovers it (backlog: a bounded join in the CLI before Close).
- Parse outcomes: an integrity failure while opening a job's inputs makes the job `refused` with `Integrity` true (not `unparsed`), the run goes on and the final exit is 4, also next to a cancel (integrity wins); a plain I/O error opening inputs leaves the job `unparsed` and the exit at least 1. A job whose writer refused records (`CheckRefusals`) concludes `incomplete` with reason `records-refused`, so it cannot supersede an older complete run; the cost is a re-run to supersede. `warnings` and `rejected` are in `records.ingest.end` only (not in `records stats`), and an interrupted ingest's recovery derives its counts from the audit log (`suppression_unknown` when the cap was hit before the conclusion note was written). A re-hash of the inputs that times out (its own 5 minute budget, apart from the conclusion's) concludes the job `incomplete` with reason `recheck-timeout`: an error, exit 1, never an integrity verdict. A record of the run's snapshot that is missing from the manifest, or a manifest that cannot be read, when a job opens its inputs is an integrity failure (exit 4). A bundle that gained a companion artifact since an earlier run is `unparsed` as `stale-bundle` unless `--reparse` is given (`TestParseExitCodes`).
- Parse input trust window. Large inputs (over 256 MiB) are pre-hashed and re-hashed after the job, not continuously, and a streamed input is served only through a section of the verified size (it never grows past it). An input changed during the job and restored before the re-hash (ABA) is NOT detected for a streamed input (`job.end` marks it `streamed: true`); an input changed and not restored is caught by the re-hash (exit 4, the run is `incomplete` with `integrity: true`, batches committed during that job stay, and `case verify` flags the artifact). The exclusive case lock is the defence against another process. The manifest is read once per run, but decoded again per opened artifact (O(artifacts x manifest) until an open-by-record function exists; 5D backlog), and `parse plan` reads every candidate artifact once. Discovery trusts the manifest's `Source` fields (the CLI prints a note: run `case verify` first). The platform of a `file` artifact is known only from device evidence in the case (an `ios pull` with no `ios backup` or `ios info` evidence has none, so only `--artifact` names it); the iOS extract path mapping covers only `/private/var/mobile/`.
- Artifact files on Windows: `OpenArtifact` (image analysis and parse alike) refuses an artifact file, or a directory on its path, that is a symlink or junction, and, since Go reports every reparse point that is not a link as irregular, also a non-link reparse point such as a cloud-sync placeholder, as an integrity error (exit 4, fail closed; not reproduced here, no such volume was available). Keep cases off cloud-synchronised folders.
- Parser handles: the `Budget` and `Lookup` of an `Input` are pointers shared with the host, so a parser can overwrite its own accounting (`*in.Budget = parse.BudgetView{}`); the host's limits do not depend on it, and the threat model (trusted parsers) leaves it documented, not defended. A read in flight when the host seals a parser's reader returns `ErrSealed` with no byte count but may already have filled the parser's buffer; the host never reads that buffer.
- Parser metadata: `InputSpec.Companions` applies to every role, not only the primary (a role is filled by the primary's path plus the suffix), and a title is at most 200 bytes of valid UTF-8 without control characters.
- Parser identity: the hash covers layout-, comment- and import-grouping-insensitive syntax, so any other change, including a formatter's `0777` to `0o777` and `a string, b string` to `a, b string` rewrites, needs a version bump; a Go release that adds AST fields can change a dump only for source that uses them. `internal/parse` and `internal/records` (the parsers use their constants and data types) are not in the hash scope: a change there is a change of the build, not of a parser version. A parser package that embeds a file keeps it raw. `parsers.lock` is append-only and has no external anchor: someone with file access can edit it, the writer still refuses a conflicting identity per case. `Start` runs the full schema-object comparison once per job (measure with hundreds of jobs). The CLI prints at most one stderr status line per job in text mode and no job progress; `--json` emits `job.progress` throttled by the emitter.
- Hardware: as of v1.0.0 the device backends (ADB, iOS, serial) have NOT been validated on real hardware, only against fakes. Before relying on them in casework, run the hardware acceptance steps with authorized/trusted devices attached and confirm `case verify` reports OK:
  ```bash
  go test -tags hardware ./... -v
  ./bin/minutiae.exe case new --dir ./cases --id HW1 --examiner "<name>"
  ./bin/minutiae.exe android logical --serial <s> --case ./cases/HW1
  ./bin/minutiae.exe ios backup --udid <u> --case ./cases/HW1
  ./bin/minutiae.exe serial console --port <p> --baud <n> --case ./cases/HW1
  ./bin/minutiae.exe case verify --case ./cases/HW1
  ```
