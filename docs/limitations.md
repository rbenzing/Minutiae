# Known limitations

What the current build does not do, does approximately, or has validated only on builder data. A change that closes or adds a limitation edits its line here.

- Android sync: sync v2 (64-bit sizes) is negotiated when the device advertises both ls_v2 and stat_v2 and is then used for listings, `source.remote_size` and `android ls`; on the v1 fallback LIST/STAT sizes and mtimes are 32-bit (sizes of files of 4 GiB or more are truncated in listings), so `android logical` records no `source.remote_size` for a file listed over v1 (unknown, not a possibly truncated number), and records the fallback as an `acquire.warning` (reason `sync-v1`) and in `acquire.stats` (`sync_v1`, `sync_fallback`). An unknown modification time is not recorded (`source.remote_mtime` omitted); `android ls` prints it as `unknown` (the shared `ls` does the same for an iOS entry without a time) and `--json` gives `mod_time: null`, never 0001-01-01. An unreadable directory, an entry the device could not stat and an empty answer are never an empty directory: `android logical` audits them as `acquire.warning` (`op: list` with reason `list-errno` or `list-unknown`, `op: stat` with reason `entry-errno`, at most 1000 per directory and then one summary), in v1 and v2 (v1 detects only a LIST with no entry at all; a listing cut after its first entries cannot be detected); `android ls` fails on an unreadable directory (text and JSON) and prints the readable entries of a partial listing before failing with a partial-listing error. Under v2 the declared size is compared with the received bytes: a difference keeps the artifact flagged `incomplete` with a `size-mismatch` warning (a file that changed during the acquisition is flagged too). A walk that fails after pulling files writes `acquire.stats` with `incomplete: true` and the error before `acquire.error`. Validated against test doubles; hardware acceptance pending (the v2 wire is from memory, including the errno in the DONE frame of a v2 listing).
- Android hostile device: a faulty or malicious device can still stream arbitrarily large files (`RECV` size is inherent to evidence, so it is never capped). The entries per directory (default 1,000,000; and 64 MiB of names per listing), the entries per acquisition (10,000,000), the path text seen (512 MiB) and the directory depth (128) are capped: a hit is an audited `acquire.warning` with `op: limit` and a typed `reason` (`entries-per-dir`, `entries-total`, `path-bytes`, `depth`), `acquire.stats` carries `incomplete: true` and `limit_hits`, and the acquisition ends with `ErrAcquisitionLimited` after keeping every file already pulled (the entries read before a per-directory cap are still pulled; nothing past a cap is). The sync client's own `LIST` bound returns `ErrListLimit` with partial entries and leaves the session unusable. The limits have no command-line flags yet. The examiner can also stop an acquisition with Ctrl-C: partial artifacts are kept and flagged incomplete. `Device.List` and `android ls` honour `SetWalkLimits` (a cut listing returns the entries read plus a partial-listing error).
- iOS backup: the sync-lock / `notification_proxy` step is not performed, and `Info.plist` is not generated; the lockdown values are saved as `device/lockdown.json`.
- iOS backup device-requested changes: when the device moves, copies over, removes or re-sends a file already received, Minutiae counts it (`Result.RemovedFileCount`, `RemovedBytes`, uncapped, beside the capped detail) but does not retain the replaced bytes: device-requested removals are counted; their bytes are not retained. A move whose source and destination are the same path is a no-op, and a move between nested paths is refused and recorded (`RefusedMoves`). The per-request scan of the recorded device error ends is O(marks x requests): a bounded cost (both are finite within a session), not a loop. `RemoteEnd.Message` holds raw, bounded device bytes and must be quoted (`%q`) on display.
- iOS backup transfer: a `0x0b` (remote error) block that follows file data is where libimobiledevice, the reference implementation, ends a file, so it cannot tell a device-side read failure from a normal end; a zero length after data with no terminal block is likewise not a normal end. Minutiae records every such file (code, message, received byte count; `acquire.stats` `end_confirmed`, `end_mismatch`, `end_unconfirmed`, `end_samples`; the message detail is capped at 1000 files, `end_detail_omitted` counts the rest, and every such file is still flagged) and promotes it as an artifact flagged `incomplete` unless the backup's own `Manifest.db` positively confirms its size ("confirmed" means consistent with the device's own `Manifest.db`, shown to the examiner as "consistent with the backup's Manifest.db" (`end_confirmed_basis`); it is not independently verified, and a device that truncates a file and declares the truncated size confirms it; the declared `Size` of the file's keyed archive, matched by file ID and read only when such a file exists; a manifest that is absent, encrypted, damaged, too large, or itself cut off confirms nothing, and a proven size mismatch also fails the acquisition). The `Manifest.db` layout is from memory of iOS 10+ backups and validated only against builder-made databases. The mark follows the file through the device's move and copy requests, and the mark of a file the device then removed or replaced is kept in the audit record (`end_removed`). An unconfirmed file adds one audited `acquire.warning` (`reason: end-unconfirmed`) and does not fail the acquisition. Whether real devices send that marker after files that are complete is from memory of libimobiledevice and unverified on hardware: if they do, those files are flagged `incomplete` although they may be whole (a flag, never a drop). Files cut off by a transport failure or cancellation are kept and flagged `incomplete` as before.
- iOS encrypted backups (a backup password set on the device) are captured as-is; decryption belongs to roadmap sub-project 10.
- iOS AFC (`ios ls`/`ios pull`): Minutiae's own client (`internal/ios/afc`) validates every reply (lengths against fixed caps, no allocation from a declared size, names, `st_size`, read lengths) and sends only read operations; go-ios is used only to open the `com.apple.afc` service (see the lockdown/StartService bullet). A pull whose byte count differs from the AFC-reported size is flagged `incomplete`, and a stream past the declared size is cut one byte beyond it. An entry whose `st_ifmt` is none of regular file, directory or link is listed as irregular and is never pulled (the artifact is flagged `incomplete` with the type named, and no read is sent). Names and paths are kept exactly as the device sent them; only the host path inside the case is sanitised. Every AFC session is closed when its context ends, which unblocks a silent device, and opening the service (lockdown and go-ios `StartService`) runs in a guarded goroutine so a cancelled context returns at once and a late connection is closed; the residual is that this goroutine waits until go-ios returns. Pull reads only an entry the device positively reported as a regular file: directories, links (open would follow them), unknown types and a missing type are refused before any open. `ios ls` fails whole when the `Stat` of one entry fails (loudly, never with a partial listing); an empty directory path is refused. The wire format is from memory and is cross-checked only against the go-ios client reading the same fake device (`TestGoIOSClientReadsOurFakeAFC`); it has not run against a real device (validated against test doubles; hardware acceptance pending). A directory reply with no entry at all (not even `.` and `..`) is a protocol error, not an empty directory, and a device that really answers that way would make `ios ls` fail on that directory.
- iOS lockdown/service setup: the plists the device returns during lockdown `GetValue` and `StartService`, and usbmuxd's device list (used by `ios info`, `ios ls/pull` and `ios backup` setup), are still decoded inside go-ios, without Minutiae's plist validator. Every such call (`List`, `Values`, `OpenAFC`, `OpenBackup` and the device lookup they share) runs under a panic guard, so a decoder panic on the calling goroutine is returned as an error and no artifact is written at that stage (`TestGoIOSLockdownValuesPanicIsAnError`, `TestGoIOSStartServicePanicIsAnError`, `TestGoIOSUsbmuxdListPanicIsAnError`). Residual: go-ios code that runs on its own goroutines is not covered and a panic there still ends the process, and go-ios may allocate from a size a plist declares before it returns. A half-open service connection leaks when go-ios panics after opening it, until the process exits.
- Image analysis (sub-project 2, complete with the APFS reader): APFS, F2FS, ext2/3/4, FAT12/16/32, exFAT and HFS+/HFSX are recognized (`detect.Drivers` holds the apfs, f2fs, ext4, exFAT, HFS+ and FAT drivers, in that probe order, followed by the last-resort `f2fs-backup` driver; see below), so `image info` shows their filesystem and `image ls`/`stat`/`extract`/`unalloc -p` work on them. A partition whose filesystem no driver recognizes is listed, but `image ls`/`stat`/`extract` and `unalloc -p` report that no filesystem is recognized. Raw and split-raw images, E01 images (EWF v1, see below), MBR/EBR and GPT partition tables, and `image unalloc --volume` (gaps outside partitions) work.
- F2FS detection: `f2fs` matches only a valid primary superblock. An F2FS volume whose primary superblock is destroyed is found only by the last-resort `f2fs-backup` driver, which runs after every other driver, so a destroyed primary on a volume that also carries another filesystem signature opens as that other filesystem; and a stale or forged F2FS backup signature never hides another filesystem. A matching driver that fails to open with a corrupt-structure error falls through to the remaining matching drivers (the failure is kept as a note); `image info` shows that note in the partition error column.
- EWF/E01 images (`internal/image/ewf`, EWF version 1, one or more segment files `.E01`, `.E02`, ...) are opened read-only and can be verified. `image import` takes the segments in order like any split image, any one of them opens the set, and the media is the logical disk (`image info`, partitions, filesystems, `extract`, `unalloc` work as on a raw image; recorded runs are in media coordinates, and an artifact whose runs touch an acquirer-declared error range carries a gap note, see the acquisition-errors bullet). An E01 that declares 512-byte sectors is probed for both 512 and 4096 (acquirers write 512 for 4096-byte disks as well). Not supported: EWF2 (Ex01) and logical evidence files (L01) stay `image.ErrUnsupportedContainer`; so do volume or `disk` sections of a layout other than the 1128-byte one (legacy short layouts), and encrypted EWF. The format was implemented from the public format notes and validated against `ewfacquire` 20140816 output (one writer, one version; other acquirers' layouts are covered by the `ewftest` builder only, and `TestEWFRealImages` under `-tags realimages` checks real E01 sets by hand) and against an independent decoder.
- E01 incomplete and damaged sets are opened, not refused, and never guessed: a set whose last segment has no `done` section, whose last segment is missing, or whose last segment is truncated mid-section opens with an "E01 set incomplete" warning (the sections walked before a truncation are kept) and every chunk the walked sections do not cover fails with `ErrChunkCorrupt` on read; a missing or out-of-order MIDDLE segment, a truncated non-last segment and a bad section descriptor checksum fail the open. Note the two levels: the case's import record only knows the files given (a 2-of-3 import is a complete import of two files), while the E01 `done` section is what reveals the missing third segment. A chunk table is trusted only if it directly follows its sectors section, its first entry is the sectors payload start, its entries strictly increase and lie inside that section; `table2` is the fallback; if both copies fail, every chunk from that group onward is unreadable (`ErrChunkCorrupt`) with a warning naming the rule, and the image still opens (a damaged table never makes the image unopenable, the part before it stays readable). A corrupt chunk (bad zlib stream, wrong Adler-32, wrong length) is an error on read, never zeros, and `ReadAt` returns the bytes before it. Only libewf-written layouts have been tested against the table rules: an acquirer that pads between the sectors descriptor and the first chunk would open but read no chunk (the same unreadable-chunk error as damage). A bad chunk inside a structure read at open time (the primary or backup GPT) makes `image info` fail at the partition step, while `image info --verify` still runs and audits it (see below).
- E01 acquisition errors: `error2` ranges (sectors the acquirer could not read from the device; the acquirer declares it wrote fill there and the tables cover them; the open warning states that declaration, not a fact about the bytes) are reported as warnings and are part of the media, as the acquirer stored it. Acquirer-supplied metadata (case number, examiner, notes, dates, acquirer version) is shown as claimed, size-capped and escaped on output; it is not evidence of anything the acquirer did not record. The ranges are also available in media byte coordinates (clipped, merged; ranges beyond the media, empty ranges and ranges beyond the 65536 kept are counted, never dropped silently) and `image info` prints them as the acquirer's declaration (`Acq. errors`, JSON `acquisition_gaps`). Raw and split-raw images carry no acquisition-error record (the format has none): `Acq. errors` and `acquisition_gaps` are omitted for them, and that omission is not evidence of no gaps (it is not the `absent` or `empty` state of an E01). Three states are kept distinct, in text and JSON, for E01: no error2 section (`absent`), an intact empty section (`empty`), and a section that is damaged, too small or skipped by a bound (`damaged`: the gaps are UNKNOWN, never read as none; a warning says why). The sector-to-byte factor is the volume section's bytes per sector. Every `extract` or `unalloc` artifact whose recorded runs touch the declared ranges carries `Derived.acquisition_gaps` (exact overlap bytes and range count, the first 8 overlaps, and `unknown` when the overlap cannot be decided: runs not recorded, content stored inline in filesystem metadata, a truncated range list, more than 4,194,304 run/gap pairs, or a damaged error2 section, in which case every non-empty artifact of that image carries `unknown`, never "none"); the extract summary prints a note. Residual: the note is a claim about the parent container, shape-checked by `case verify` but NOT recomputed from the container yet (verify trusts it; recomputing the overlap from the container's error2 list and the artifact's runs is carried to LX-5, after plan 5D); runs that overlap each other are detected explicitly (sorted and compared): the overlap is counted once over their union and the note is marked `unknown`, never a double-counted exact figure, and an exact `bytes` is also capped at the artifact size and marked `unknown` when it would exceed it; the shape rule of `case verify` is symmetric (`bytes` and `ranges` are both zero or both positive, both zero only when `unknown`); the note of an incomplete `unallocated.bin` covers its whole offset map, not only the kept prefix (an incomplete extract's note is recomputed over the kept prefix); recovered and carved artifacts carry no note; a zero byte in such an artifact that does not overlap a declared range is still an ordinary zero.

- `image info --verify` (E01 only): recomputes MD5 and SHA-1 of the whole media and compares them with the hashes stored in the image; one hash-chained `image.verify` audit entry is always written, also for a mismatch, an unreadable chunk, a cancel or a panic. It proves that the container's media matches what the acquirer stored, not that the acquirer's read of the device was faithful (an `error2` range is zero-filled before it is hashed), and it covers only the hashes the container stores (MD5 and SHA-1; no SHA-256). `absent` (no hash section at all) is not a failure, but a stored-hash section that is present and damaged (checksum mismatch, or too small to parse) is never `absent`: that hash is `unverified` with a `reason` (also in `--json` and the audit entry), the open warning says "stored hash section damaged", and the exit code is 1; a hash that another valid section (hash or digest) still stores is verified normally. Exit codes: `match`/`absent` 0, `mismatch` 4, `unverified` (an unreadable chunk, a damaged stored-hash section or a partial run), `scan-budget` (the `--max-scan-bytes` limit or the implausible-size default stopped the scan, see the size-claims bullet), cancel, panic and a failed audit append 1; a mismatch whose audit append fails still exits 4. Verification does not need a readable partition table. Raw and split-raw images carry no stored hashes: `--verify` prints a note and writes no audit entry (`case verify` re-hashes their artifacts regardless).
- E01 `extract`: a file that reaches an unreadable chunk keeps the readable bytes before it as an artifact flagged `incomplete` (the prefix is found by bisecting the failing read, so only error-free bytes are written; its provenance records only the runs covering them) with an `analysis.warning`, and extraction continues. A real I/O error of the segment source is not a chunk error: it keeps the old behaviour and ends the analysis (`analysis.error`) rather than producing an incomplete artifact (`TestExtractIOErrorIsNotDowngradedToIncompleteFile`). When the prefix needs a runs sidecar (more than `MaxInlineRuns` runs), it is written under the first free of `<file>.incomplete.runs.jsonl`, `<file>.incomplete~2.runs.jsonl` ... `~16` (a taken name is not a case failure), and the full run list sidecar written before the read stays in the case, referenced by the partial artifact as `Derived.declared_runs_artifact` (provenance of what the filesystem declared, never of what was captured; `case verify` requires an incomplete `extract`, a `runs` sidecar of the same parent and directory, different from the captured-runs sidecar and named by exactly one artifact); the partial artifact's error, and so the `analysis.warning`, also names it (`complete run list of the file: runs artifact <id>`). When all 16 names are taken, the partial artifact carries no captured runs and its error says "the runs of the kept bytes are not recorded", while the declared link remains: incomplete provenance, never wrong provenance (`TestExtractPrefixSidecarNamesExhaustedRecordsNoRuns`, `TestExtractIncompleteArtifactReferencesFullRunList`). A case written before this build holds such a sidecar unreferenced (an ordinary hashed artifact; `case verify` passes). `case verify` also recomputes that the artifact's captured runs are an in-order prefix of the declared list (the last run may be a shorter cut). `image unalloc` is different: its runs sidecar is the offset map of the export, so after an unreadable chunk it lists every run while the truncated, `incomplete` `unallocated.bin` holds only a prefix; the map stays valid as a lookup for the kept prefix (a map is not a claim that every byte was captured) and the artifact's `incomplete` flag says the rest was not captured.
- E01 size claims: the logical size is the volume section's sector count times the sector size, and must agree with the chunk count (at most 2^26 chunks of at most 16 MiB), so a hostile image can claim up to a petabyte of media with few real bytes. A claim larger than the segment files could hold at deflate's best ratio (1032:1) is flagged: an open warning stating both numbers (`implausible size`), `Size claim` in `image info` and `implausible_size` in its JSON; an all-zero honest image stays below the line (about 1000:1). A read stops at the first chunk the tables do not cover and `Verify` stops at the first unreadable chunk; whole-media verification takes `--max-scan-bytes N` (0 = no limit; it requires `--verify` and is a usage error without it; the budget is checked once per chunk, so a stop can overshoot it by up to one chunk, 16 MiB), and when the claim is implausible and no flag is given it runs under a 64 GiB default; a budget stop is its own audited result (`scan-budget`, exit 1), never `match` or `absent`. Residual: an image that is plausible but huge (an honest multi-terabyte disk) has no default limit, and a hostile image that is plausible by ratio can still cost up to 1032 bytes of decoding per stored byte; `image unalloc` has no scan budget. The chunk reference table costs 8 bytes per entry (up to 512 MiB at the limit, and only when the file really holds that many table entries).
- E01 chunk-table trust is structural, not a proof of contiguity (parked review finding): the rules above do not prove that a table covers its whole sectors payload without gaps or overlaps, so only a checksum-consistent forgery of the table, `table2` and the section descriptor could make chunks read from the wrong place without a warning. A contiguity rule at open was tried and dropped: it refused the existing hostile-table fixtures that pin the per-entry handling of differing copies (chunks of 1 and 11 bytes), so the check is left to read time. Mitigated at read time: a compressed chunk followed inside its span by what parses as another zlib stream is an `ErrChunkCorrupt` read, so a forgery that drops a compressed chunk is found at the chunk before the drop; an uncompressed one is found only by `image info --verify`, which catches it unless the stored MD5 and SHA-1 are forged too, and `case verify` still protects the image artifact itself. A legitimate chunk whose padding happens to form a valid zlib header is reported corrupt (a second zlib stream header follows the chunk's stream), never silently accepted; no writer is known to pad that way.
- The EWF concurrency tests (`TestEWFConcurrentReadAt`, the chunk cache) run under `-race` in the race gate (step 2). The fast check runs them without `-race`.
- One `image import` call imports exactly one image (its files are segments 1..N in the order given; nothing is sorted). A partially imported image cannot be opened: re-import it.
- Deleted filesystem entries are listed (`image ls --deleted`) and flagged, but not recovered or extracted; recovery is sub-project 3. HFS+ and APFS keep no deletion marker, so they list none (see the HFS+ and APFS items below).
- `image info`/`ls`/`stat`/`extract`/`unalloc` open the parent artifact with the cheap size check by default (`OpenArtifact`): a same-size content swap of the parent is not caught at open time, but `case verify` detects it (derived artifacts record the parent's SHA-256, and the parent is re-hashed). `--verify-parent` re-hashes every segment of the parent (SHA-256, MD5, size) against the manifest at open and fails with the integrity error (exit 4) on a difference; it remembers nothing (no stamp, no mtime, no cache: each open hashes again), costs one full read of the image, and is not offered on `image recover`. `case verify` remains the authority.
- Extract output guards: `extract` skips a file whose hole bytes (sum of `Offset -1` runs, or the whole size when the filesystem reports no runs) exceed the partition length ("sparse size exceeds partition length; not extracted"), and a file whose data runs total more than the partition length, which only overlapping runs can ("data runs exceed partition length; not extracted"); both are an `analysis.warning`. A run is also bounded in aggregate: `--max-files` (default 100,000) and `--max-bytes` (default 8 GiB, counting a sparse file's full expanded size) stop the run at the first file that does not fit, with one `analysis.warning`, `limit_reached` in `analysis.end`, `output_limit` in the JSON summary, a printed notice and exit 1; files already written are complete and nothing is cut mid-file, `max_files` and `max_bytes` in `analysis.start` record the limits enforced (so `limit_reached` absent from `analysis.end` means not reached), the files after the refused one are neither visited nor counted as skipped, bytes admitted for a file that then could not be written or read are given back, and re-running with higher limits is the way on (a legitimate extraction above 8 GiB needs `--max-bytes`). Residual: a sparse file within the partition length and the limits is still expanded to its full size, and `image unalloc` has no output limit (a deliberate choice: exporting the free space of a large disk is legitimate; ruling X5).
- Encrypted filesystem content is extracted as ciphertext (flagged `Derived.Encrypted`; on HFS+ per entry, from the `cprotect` attribute; on APFS per file, from any crypto id, while a whole encrypted APFS volume is not read at all, see the APFS items below); decryption belongs to roadmap sub-project 10.
- ext4 (ext2/3/4) reader, read-only and as found: the journal is not replayed, so an image that needs recovery is read as it lies on disk (the reader warns that the filesystem may be inconsistent); journal analysis belongs to sub-project 3. `bigalloc`, an external journal device and unknown incompatible features are refused as unsupported. No plan owns lifting these refusals. `bigalloc` is readable in pure Go (cluster mapping in `internal/filesys/ext4`, a `mke2fs -O bigalloc` fixture, a spec amendment) but is unscheduled; an external journal device cannot be read from the data image alone (it needs the separate journal device image, which is inherent to the input), so that volume stays refused.
- ext4 deleted entries are names only: a deleted directory record is listed and flagged (`image ls --deleted`) with what the on-disk record still holds, but its content is not recovered or extracted (sub-project 3). A stale copy of a live record left behind by an htree leaf split stays listed with attribute `stale_copy=true`.
- ext4 names: encrypted (FBE) directory names are shown as `~enc~<base64url of the raw name>` and their file content is extracted as ciphertext (decryption is sub-project 10); names that are not valid UTF-8 are shown as `~raw~<base64url>`. Path lookup accepts both displayed forms, each in its one canonical spelling (`filesys.DecodeRawNameAlias`), and in a plain directory the `~raw~` form stands only for names `ReadDir` shows that way (`TestLookupAliasRejectsNonCanonicalSpelling`, `TestLookupAliasNeverStandsForAPlainName`). A name that is stored as the display form of another record is ambiguous, never the stored name (`TestLookupStoredNameThatIsAnotherRecordsAliasIsAmbiguous`); APFS and HFS+ had the same pattern (the stored name or the first record met won) and give the same answer (`TestLookupStoredNameThatIsAnotherRecordsAliasIsAmbiguous` in each); the APFS and HFS+ alias of a plain name stays a lower-preference fallback.
- ext4 casefold directories: after an exact byte match and the `~raw~` alias, `Lookup` compares names with the kernel's rules for encoding `utf8-12.1.0` (canonical decomposition, full case folding, default-ignorable code points removed; `internal/filesys/utf8fold`, generated from the Unicode 12.1.0 data files and replayed against 15988 names a real kernel resolved: `TestKernelVectors`, `TestCasefoldLookupMatchesKernel`). A stored name that is not valid UTF-8 follows the measured rule (a stray continuation byte after the first byte is text; a leading stray byte or a listed invalid tail makes the name compared byte for byte); a code point assigned after Unicode 12.1 has no case mapping. The whole directory is scanned and the answer is decided in one order: exact, alias, the incomplete-scan error, exactly one fold hit, `ErrAmbiguous` for two or more (naming the first two and counting the rest), `ErrUndecided` when a stored name has a shape the comparison was not measured for and nothing above decided (never "not found"), not found. One stored name of an unmeasured shape therefore turns every lookup in its directory that finds no exact, alias or single fold match into an `ErrUndecided` error. The strict-encoding flag is read but not applied: the kernel refuses to look up an invalid name on a strict volume, this reader still finds the on-disk bytes. On a volume whose `s_encoding` is not `utf8-12.1.0` or whose `s_encoding_flags` has a bit other than strict, a miss in a casefold directory is `ErrUnsupported`, never "not found" (`TestCasefoldUnknownEncodingIsUnsupported`); an exact or alias hit still resolves. `.` and `..` are never folded and an encrypted directory is exact-only. Listing is unaffected. Cost: a lookup that is not an exact or alias hit reads the whole directory (at most 64 MiB and 262,144 records per scan); ext4 keeps no cumulative per-filesystem read budget, so repeated lookups are never cut off, they only cost time. A fold decision (one hit, ambiguous, undecided) is made only from a complete scan: when the scan was cut (see the directory record cap item) and no exact or alias hit was read, the answer is the incomplete-scan error, never the fold hit (`TestCasefoldIncompleteScanBeatsFoldDecision`, `TestCasefoldExactAndAliasAfterTheCutStillWin`).
- `internal/filesys/utf8fold` (the casefold comparison of the ext4 and F2FS readers): it reproduces the Linux utf8-12.1.0 comparison for the 15988 names of the kernel vectors and decides only the shapes of name that some vector row shows, as whole combinations: the text before an invalid tail, where the stray bytes sit and the tail form are ONE label, and only the labels a vector name has are decided (`TestEveryDecidedShapeIsShownByAVector`; a wide-text prefix with a stray byte and an `F8 88 80 80 80` tail, for example, is undecided because no vector shows it). A name that is not valid UTF-8 follows the measured rule (a stray continuation byte after the first byte is text; one or two stray bytes first, or an invalid tail at the end of a name, make the name compared byte for byte). Every other shape is `Unknown`: the empty name, a name over 255 bytes, an invalid byte followed by text, an unshown invalid tail, a leading stray byte with a later stray byte or an ignorable, and a stray byte anywhere in a name that also has a default-ignorable character. `Equal` returns a tri-state `Verdict` (`Same`, `Different`, `Unknown`) and a caller must never read `Unknown` as different or as "not found" (`TestClassifyMatchesTheMeasuredRule`, `TestHostileUnmeasuredShapeIsUndecided`, `TestEqualBothOrdersForEveryKindPairing`). The one measured extension is an opaque name against itself plus a lowercase `z`; an upper-case `Z` or another letter is `Unknown`. Trade-off: one stored name of an unmeasured shape makes every lookup in its directory that finds no exact, alias or single fold match an undecided error, never "not found", because the reader cannot show that the name does not fold to the query. The command line reports such a lookup (`image ls`, `stat`, `extract` and the like) with the message and a note saying it is neither found nor absent, and exits 1 (`ExitError`), never 0; a batch path (`extract`, `recover`) ends with the typed error and never skips the entry as "not found" or as a content problem (`TestImageUndecidedLookupExitsNonZeroWithAClearMessage`, `TestExtractOfAnUndecidedLookupFailsTyped`, `TestExtractOfAnUndecidedOpenIsNotSkipped`). Two records whose bytes are the same `~raw~` alias, with no exact match, are `ErrAmbiguous` too (`TestCasefoldTwoAliasRecordsAreAmbiguous`). An `extract` whose path does not resolve (undecided or not found) ends before its analysis, so it writes an `analysis.start` and an `analysis.error` that name the path (`path`, `reason` `undecided`, `not-found` or `ambiguous`) with nothing extracted; a `recover` plans inside its analysis and is audited the same way, and the read-only dry run (`recover --list`) writes nothing (`TestExtractPathLookupFailureIsAudited`, `TestRecoverPathLookupFailureIsAudited`). The kernel's stream-safe limit for runs of combining marks is not modelled (runs of up to 40 marks were measured and are ordered completely). The only disagreement with `golang.org/x/text` is the 86 Cherokee capitals U+13A0-U+13F5, which `cases.Fold` maps to the small letters while Unicode 12.1.0 `CaseFolding.txt` and the kernel leave them (`TestCrossCheckAgainstXText`).
- ext4 directory record cap: at most 262144 records are read per directory (live and deleted). A lookup that finds nothing in a directory the scan did not finish (cap reached, damaged or unreadable block, damaged block map, sparse hole, `i_size` above the 64 MiB read limit, a record whose name does not fit) is an error, never 'not found': `filesys.ErrLimit` for the cap, otherwise a corruption error that also matches `filesys.ErrIncomplete` (`TestLookupAfterCapIsAnError`, `TestLookupInDamagedBlockIsAnError`, `TestLookupInOversizeDirectoryIsAnError`); a block whose checksum is wrong is still searched and is not a cut (`TestLookupBadChecksumBlockIsStillSearched`). `ReadDir` still returns the entries it read with the warning and a nil error (it does not return `ErrLimit` as the exFAT listing does). A command-line or batch path that hits the incomplete error is audited (`analysis.error`, reason `incomplete`) and exits non-zero (`TestExtractPathLookupFailureIsAudited`, `TestExitCodeOfAnIncompleteLookup`). Extended attributes are read from the inode and the xattr block. An xattr block's checksum is verified under `metadata_csum` (crc32c); a mismatch is a warning and the attribute names are still listed and the values returned, and the entry carries `xattr_csum=bad` (`TestXattrBlockChecksumMismatchWarns`); with another checksum type no verdict is made. A value held in an EA inode is read as a streaming file of its real image runs (the EA inode is read without its own attributes, so a loop of them cannot recurse; the EA-inode flag, regular type, an i_size equal to the entry's declared size and a fully mapped value are required, at most 16 MiB, anything else is corrupt for that value alone; the crc32c of the value, seeded with the filesystem seed, is compared with the EA inode's `i_atime` and a mismatch is a warning with the bytes still returned; `TestEAInodeValueIsRead`, confirmed against the libext2fs-written `ext4-xattr` fixture); a `system.data` value (inline file content) held in an EA inode is reported unsupported (`filesys.ErrUnsupported`, a warning, `system_data=unsupported` on the entry), not decoded (`TestSystemDataInEAInodeIsUnsupported`). The attributes are reachable through the ext4 `XattrReader` (`TestXattrReaderListsAllStorages`: names, sizes, storage kinds and values equal the `ea_list` oracle; `filesys.Xattr.Integrity` is `value_hash_ok` on an EA-inode value that was hashed and matches, `value_hash_bad` on the attribute whose EA-inode value fails its hash, and on no other, `TestXattrReaderHashBadMarksOnlyThatAttribute`; an empty `Integrity` means this reader did not check the value, never that it verified it, so an inline or xattr-block value, which has no hash of its own, is empty). The hash verdict (including "the value cannot be read", which lists the attribute with size -1 and fails it with `ErrCorrupt`) is computed once per EA inode and kept (at most 65536 inodes), so a failed read is charged to the bound once and never drains it again (`TestXattrReaderUnreadableValueIsChargedOnce`), and any number of attributes naming one EA inode read its value once (`TestXattrReaderManyEntriesOnOneEAInodeReadItOnce`), and the value bytes hashed per filesystem are bounded to 512 MiB: past that a value is listed `value_hash_unchecked` with size -1 and `OpenXattr` fails with `ErrLimit`, never passing it unverified (`TestXattrReaderHashWorkIsBounded`). Listing the attributes of an entry therefore reads and hashes its EA-inode values (up to 16 MiB each, once). Which attributes are marked `value_hash_unchecked` once the bound is spent depends on the order in which the entries are listed (the bound is shared, first come first served), so the unchecked mark is a statement about this run, not about the attribute. A size of -1 means unknown: a printer of these attributes (none exists yet) must render it as unknown, never as 0, and must show `Integrity`; the test belongs with that printer. The EA-inode back-reference (parent inode number and generation) and the entry `e_hash` are not checked, so a value that passes its hash may not belong to this parent. The `ext4-xattr` EA-inode value is 1024 bytes because `debugfs ea_set -f` reads at most one block.
- ext4 unallocated export: a block group whose bitmap fails its checksum (or cannot be read) is omitted from the export and reported as a filesystem warning (`analysis.warning`); its blocks are neither exported nor claimed as free. Any group whose descriptor checksum is wrong is skipped whatever its flags (`TestBadDescriptorChecksumGroupIsSkippedWhateverItsFlags`), and when the descriptor table is truncated the `BLOCK_UNINIT` groups are skipped too (`TestUnreadableDescriptorsSkipBlockUninitGroups`), each with a warning. The scan for deleted names in directory slack is capped at 16 MiB of slack per directory (`TestSlackScanCap`); past the cap the reader warns and stops searching, so a hostile directory cannot cost unbounded time.
- Analysis warning ordering: a filesystem warning is written to the audit log as `analysis.warning` after the artifact whose processing triggered it (never before): the reader notices an anomaly only while doing that work. Warnings about directories met while walking are attributed through the `after` field, which names the last extracted path, not the directory itself. Warnings the filesystem already had when the analysis began are written once as `source: filesystem-open`; later ones as `source: filesystem` and counted in the summary (`fs_warnings`) apart from skips. The `image recover --list` dry run lists a grown suppression note as one warning in `fs_warnings`, and reports how many warnings were dropped while planning as `filesystem warnings suppressed while planning: N` (text) and `fs_warnings_suppressed` (JSON, omitted when 0) (`TestPlanRecoveryReportsWarningsSuppressedDuringPlanning`, `TestRecoverListShowsWarningsSuppressedDuringPlanning`).
- Filesystem readers keep at most 1000 distinct warnings (de-duplicated by text; every reader, F2FS, ext4, FAT, exFAT, HFS+ and APFS, then ends the list with one note, `further warnings suppressed: N occurrences not recorded`, where N counts every dropped `Add` (a repeat of a dropped message counts again; N saturates at the largest uint64), and `analysis.end` and `analysis.error` carry the final N as `fs_warnings_suppressed`; `image ls`/`stat` print the note once, when the list first fills), so the audit log is not an exhaustive list of every anomaly in a hostile image, but it states how many were not recorded. `image ls`/`stat` print the warnings a command raised (escaped, at most 20 lines) on stderr; `image stat --json` carries them in a top-level `warnings` field.
- ext4 hard links: every directory path to a multiply-linked inode is a separate entry, so `extract` writes one copy per path (the entries share the filesystem id, so provenance shows they are the same inode). Directory entries stored beyond a directory's `i_size` are listed as deleted entries with attribute `beyond_isize=true` (`TestEntriesBeyondISizeAreDeletedNotLive`). A live directory entry whose inode has `links_count` 0 and a `dtime` gets attribute `inode_freed=true` and a warning (`TestLiveEntryOfFreedInode`).
- A file whose extents run past the end of a truncated image yields its trusted prefix as an `incomplete` artifact (ext4, FAT, exFAT, F2FS, HFS+ and APFS; see the prefix rule below); only the leading bytes are extracted, so extents that follow the cut but lie inside the image are not, and the warning states at least how many bytes that is, counted in the cut extent's own tree node only (when the cut lies under an index node it says that other nodes were not examined and the count may be incomplete, and in any node kind it says when the count stopped at a damaged entry; `TestTruncatedImageWarningNamesTheLoss`, `TestTruncatedWarningUnderIndexNodeSaysCountMayBeIncomplete`, `TestTruncatedWarningCountStopsAtADamagedEntry`). An ext4 file whose extent tree or block map is damaged for any other reason (a bad node, a loop, an extent outside the declared filesystem) still fails to open with `ErrCorrupt` (`TestExtentBeyondDeclaredFilesystemStaysCorrupt`, `TestOtherDamagedMapsStillFailToOpen`); only the cut by the end of the image yields a prefix, unlike F2FS, which yields one for any damaged map. Local artifact names are capped at 200 bytes per path component (cut on a rune boundary, then `~` plus the first 8 hex digits of the SHA-256 of the original name, so distinct long names stay distinct; this applies to `image extract` and `android logical` alike); the original path is kept in `Source.RemotePath` and `Derived.FSPath`. An OS path-syntax or name-too-long error creating one artifact becomes a per-file `analysis.warning` and a skip.
- FAT12/16/32 reader, read-only and as found (`internal/filesys/fat`): deleted entries are listed with `image ls --deleted` and flagged `Deleted`; `extract` never writes their content, which is recovered only by `image recover` (see the FAT and exFAT recovery items below). A long name recovered from the slots of a deleted entry is flagged `lfn=recovered`, and `lfn_tail=unterminated` when the name may be cut short because a slot was reused (`TestDeletedLongNameRecoveryMarkers`); an orphaned long-name set is flagged `lfn=orphan`. FAT times are the local time of the system that wrote them with no zone (`Time.ZoneKnown` is false): modified times have 2 s resolution, created times 10 ms, and the access time is a date only (reported as `T00:00:00`). 8.3 short names and the volume label are strings in an OEM code page that the volume does not record: bytes from 0x80 up are decoded as code page 437 (a name written under another page shows other letters), `Entry.RawName` keeps the 11 raw name bytes (`TestShortNameDecodesCodePage437`, and the fixture's 8.3-only `/ÉTÉ.TXT`). Directory entry IDs are canonical decimals only (`TestEntryIDsMustBeCanonical`), and an entry at or past the directory's first end-of-directory (0x00) entry cannot be opened or listed by ID (`TestEntryBeyondEndMarkerIsNotFound`). When the volume has two or more FAT copies, `Unallocated` compares the others with the active one and warns once if they differ (`TestDifferingFATCopiesWarn`). FAT has no Unix permissions, so `Mode` is synthesized: 0644 for files and 0755 for directories, with the write bits cleared when the read-only attribute is set (not evidence of the original owner's permissions). A FAT chain shorter than the file size (it ends early, meets a free or bad cluster, loops or leaves the volume) yields a partial artifact flagged `incomplete` whose provenance records only runs that cover the kept prefix (see the `File.Runs` prefix rule below) and a warning (`TestFileChainShorterThanSize`, `TestExtractFATShortChainIsIncomplete`).
- exFAT reader, read-only and as found (`internal/filesys/exfat`): deleted entry sets are names only, as for FAT (`TestExfatDeletedSetFlagged`). The `NameHash` is verified with the volume's up-case table: a mismatch is a warning and `name_hash=bad` (the entry is still listed and opened), and without a usable table or a full name it is `name_hash=unverified` (`TestExfatNameHashMismatchFlagsTheEntry`, `TestExfatNameHashVerifiesOnRealFixtures`); the entry-set checksum is, and a set that fails it is still listed, flagged `checksum=bad` (`TestExfatSetChecksumBadFlagged`); a set with no Stream Extension or too many secondaries is flagged `set=damaged` and cannot be opened. TexFAT (a second FAT and allocation bitmap) is ignored: the first FAT and the first bitmap are read. Bytes between `ValidDataLength` and `DataLength` read as zeros and are recorded as a hole run, as the format defines. exFAT has no Unix permissions either: `Mode` is 0. A name that is "." or ".." (or holds '/' or NUL) is shown in the `~raw~` form (`TestExfatDotNamesUseRawForm`). The `~raw~` form is the shared one (one spelling per name; it stands only for names shown that way). Lookup decides over the whole directory: exact name, `~raw~` form, the incomplete-scan error (a directory chain that loops or breaks before its end marker and the 256 MiB limit are cuts too, besides the cap, the budget and an unreadable chunk; `ReadDir` returns the entries read with the same error), `ErrUndecided` when a live entry set's name cannot be read in full, one match through the volume's up-case table, `ErrAmbiguous` for two or more (and for two exact or alias records, or a stored name that is another record's form). Without a usable up-case table nothing is folded: a miss is `ErrUndecided` when a stored name has the query's length, else not found (`TestExfatLookupWithoutUpcaseTableIsUndecided`). An entry set at or past a directory's first end-of-directory entry cannot be opened by ID (`TestExfatEntryBeyondEndMarkerIsNotFound`). `Unallocated` never reports the allocation bitmap, the up-case table, the root directory or the clusters the FAT marks bad as free, even if the bitmap says they are, and reports at most 1<<24 runs (a warning says when the rest is cut off; `TestExfatUnallocatedExcludesSystemAndBadClusters`, `TestExfatUnallocatedRunCap`). At most 1<<18 entry sets are read per directory (`TestExfatDirRecordCapDefault`), and at most 1M distinct directories are remembered by first cluster (past that, a warning says the rest cannot be reached by id).
- F2FS reader, read-only and as found (`internal/filesys/f2fs`): the image is read as of its last checkpoint. Roll-forward recovery (the fsync'd node chains written after the last checkpoint, which the kernel replays at mount) is not applied, so later data may exist in such a chain yet is not shown; when the last checkpoint is not an unmount checkpoint the reader warns "last checkpoint is not an unmount checkpoint (data written after it is not reflected)" (`TestUncleanCheckpointWarns`). Analysing that node chain belongs to sub-project 3. Only single-device, non-zoned volumes are supported: the superblock's device table is not read and zoned (`blkzoned`) volumes are not interpreted. No plan owns either: the device table is a documented on-disk structure that a later filesystem plan could read (with a spec amendment); a zoned volume needs a zoned-device guest to build a fixture. Both are unscheduled.
- F2FS compressed files (`F2FS_COMPR_FL`) are unsupported: `Open` of one fails with `ErrUnsupported` ("compressed file") and `extract` skips it with an `analysis.warning`; the listing still shows the entry, with attribute `compressed=true` (`TestCompressedFileUnsupported`). No plan owns decompression; it would need pure-Go LZO, LZ4 and zstd decoders (new `go.mod` dependencies, no cgo) and a spec amendment, and until then the file is refused, never decoded by guess.
- F2FS deleted dentries are names only: a deleted entry is listed and flagged (`image ls --deleted`) with what its inode still says while the NAT maps it (type, size, attribute `inode`; `inode_reused=true` when the inode now belongs to another directory, `inode_unreadable=true` when it cannot be read), but its content is neither recovered nor extracted, and F2FS records no deletion time (sub-project 3; `TestReadDirFlagsDeletedEntries`).
- F2FS names and content: encrypted (FBE) names are shown as `~enc~<base64url of the raw name>`, names that are not valid UTF-8 as `~raw~<base64url>`, and path lookup accepts both displayed forms; encrypted file content is extracted as ciphertext (flagged `Derived.Encrypted`), and decryption is sub-project 10 (`TestEncryptedDentryNames`, `TestRawEncryptedContent`). In casefold directories name lookup uses the kernel's utf8-12.1.0 rules (`internal/filesys/utf8fold`), in the same order as the ext4 reader's: exact, alias (two records with the alias bytes are `ErrAmbiguous`), exactly one fold hit, `ErrAmbiguous` for two or more, `ErrUndecided` when a stored name has a shape the comparison was not measured for and nothing above decided, never "not found" (`TestCasefoldLookupMatchesKernel` replays all 15988 kernel rows against the committed `f2fs-casefold` image, `TestCasefoldUnknownShapeIsUndecidedNotNotFound`, `TestCasefoldTwoAliasRecordsAreAmbiguous`); on a volume whose `s_encoding` (superblock offset 2758) is not `utf8-12.1.0` or whose `s_encoding_flags` (2760) has a bit other than strict, a miss in a casefold directory is `ErrUnsupported` (strict itself is read, not applied; `TestCasefoldUnknownEncodingIsUnsupported`); a lookup that finds nothing in a directory the scan did not read to the end is an error, never "not found", in every F2FS directory (see the F2FS caps bullet), and that check comes BEFORE any fold decision (`TestCasefoldIncompleteScanBeatsFoldDecision`, `TestCasefoldEveryCutBeatsFoldDecision`). Cost: a lookup in a casefold directory that is not an exact or alias hit reads the whole directory, and every such read is charged to the per-filesystem directory read budget of 1 GiB (`maxDirBudget`, 1<<30 bytes of dentry blocks); so about 1 GiB divided by the directory's size such lookups fit in one command (a 5000-name directory of about 150 KiB: roughly 7000), and beyond that they fail with the typed budget error, never "not found" (`TestCasefoldLookupMatchesKernel` reopens the image every 2000 rows for this reason); `.` and `..` are never matched by casefold, and listing is unaffected (`TestLookupCasefoldNeverFindsDots`).
- F2FS inline data whose `DATA_EXIST` flag is clear (the kernel reads such a file as empty) is returned as stored, with attribute `data_exist=false` on the entry and a warning (`TestInlineDataWithoutDataExist`).
- F2FS free space: `Unallocated` is built from the SIT, with the journal in the checkpoint applied over the SIT blocks. A SIT journal whose entry count exceeds its block makes the export empty, with a warning (no free space is reported rather than guessed); a SIT block that cannot be read, or a segment whose entry is inconsistent, is not reported as free; the segments the current logs write into are not excluded, because the SIT is authoritative; at most 1<<24 runs are reported (a warning says when the rest is cut off). A NAT journal whose entry count exceeds its block is ignored, with a warning that file locations may be stale: inodes then resolve through the NAT blocks only (`TestSITJournalHostile`, `TestNATJournalFullAndOverfull`, `TestUnallocatedIgnoresCurrentSegmentCursor`, `TestUnallocatedBoundsAndCap`).
- F2FS caps: a directory is read up to 64 MiB and 262144 entries (deleted entries at most half of that, so live ones come first), a file maps at most 1<<20 runs and node blocks, and one filesystem instance reads at most 1 GiB of directory data in total; past a cap the reader warns and stops, and a directory that cannot be read because the budget is spent is an error, never an empty listing. A lookup that finds nothing in a directory the scan did not finish (the entry cap, a damaged block map, a dentry block that another directory owns or this directory maps twice, damaged dentry slots, an unreadable block, `i_size` above the 64 MiB read limit, or the read budget running out after the first block) is an error, never "not found": `filesys.ErrLimit` for the entry cap, otherwise a corruption error, both matching `filesys.ErrIncomplete`, and `extract`/`recover` audit it with the reason `incomplete`; `ReadDir` still returns the entries it read with the warning and a nil error. A hole in the block map is not a cut (the directory is a sparse hash table), and a name an earlier or later block holds exactly (or as the alias) still resolves (`TestLookupAfterCapIsAnError`, `TestLookupInDamagedBlockMapIsAnError`, `TestLookupSkipsSharedDentryBlockAndSaysSo`, `TestLookupWithDamagedDentrySlotsIsAnError`, `TestLookupInOversizeDirectoryIsAnError`, `TestLookupAfterUnreadableBlockIsAnError`, `TestLookupBudgetCutKeepsItsError`, `TestImageCutDirectoryExitsNonZeroAndIsAudited`). Every `image` command (`ls`, `unalloc`, `extract`) opens its own instance, so these budgets, like the FAT and exFAT ones, start over with each command (`TestDirectoryReadBudget`, `TestDirEntryCapPrefersLiveEntries`, `TestRunCapIsCorrupt`).
- F2FS real-image coverage: the committed fixtures (`f2fs-extra-attr`, `f2fs-default`) have no deleted entries (F2FS keeps no deletion time and `sload.f2fs` cannot delete; deleting needs a kernel mount, and the Docker Desktop kernel has no f2fs module), no holes (`sload.f2fs` writes holes out as zero blocks), no indirect or double-indirect node (`sload.f2fs` cannot place a single 7 MiB file) and no inline-dentry directory. Those paths are covered by the `f2fstest` builder tests only and have never been validated against an image written by a real kernel. The generator tries the kernel mount and the removals when it runs where f2fs is available (`tools/fixtures/README.md`).
- HFS+ and HFSX reader, read-only and as found (`internal/filesys/hfsplus`; HFSX reports type `hfsx`, plain HFS+ `hfsplus`): the journal is not replayed, so a volume with pending transactions is read as it lies on disk (a warning at open) and `Unallocated` REFUSES it with an error wrapping `ErrUnsupported`, because the bitmap on disk may lag the journal (`TestJournalStateWarnings`, `TestUnallocatedPendingJournalRefused`, `TestUnallocatedUnknownJournalRefused`); replay and journal analysis belong to sub-project 3. A volume that was not cleanly unmounted, or whose header says inconsistent, only warns. The journal-header layout (magic, endian marker, start/end) is from memory and was never validated against an initialised journal (the only real journaled fixture is `mkfs.hfsplus -J`, whose journal is flagged need-init and all zero, which the reader treats as clean); a layout that deviates reads as "unknown", which refuses `Unallocated` rather than guessing. A classic HFS volume with no embedded HFS+ volume is `ErrUnsupported`, and an Apple Partition Map is not parsed.
- HFS+ wrapped volumes, truncated images and detection: a classic HFS wrapper (master directory block `BD`) is followed to the embedded volume (validated against a real `mkfs.hfsplus -w` image, volume at byte 45056), the volume is clamped to the wrapper's embedded extent with a warning (the wrapper's own area is never part of the volume and never reported free; `TestWrappedVolumeIsBoundedByTheWrapperExtent`), and an HFSX volume inside a wrapper is accepted although Apple never writes one. A truncated image (also a truncated wrapped one) opens clamped to what it holds with a warning, not as corrupt: a file reaching past the end keeps its trusted prefix (`incomplete` artifact, see the prefix rule below) and `Unallocated` is clipped to the whole blocks the image holds, with one warning when free blocks were dropped (`TestTruncatedImageEndsTrustedPrefix`, `TestUnallocatedRunsStayInsideTruncatedImage`). `hfsplus.Probe` matches a valid PRIMARY volume header only (the embedded one for a wrapper), so a volume with a destroyed primary header is not claimed by `detect` although `Open` of the reader could use the alternate header (consistent with the F2FS ruling). `Probe` is independent of FAT: a stale or planted HFS+ header in a FAT image whose catalog is held by the image and is not a B-tree header node fails the HFS+ `Open` and detection falls through to FAT with a note (one whose catalog lies beyond the end of the image is accepted as a truncated HFS+ volume, and the `also matched by: fat` note is the only signal), and a stale FAT boot sector in the boot blocks of a real HFS+ volume does not hide it. When several drivers' signatures match one partition the result carries the note `also matched by: <drivers> (ambiguous signatures)` (shown in `image info`), the signal that a signature is stale or forged. Probe order: apfs, f2fs, ext4, exFAT, HFS+, FAT, then the last-resort `f2fs-backup` (never reported as an ambiguous claimant). `Open` requires the first node of the catalog file to be a B-tree header node (kind 1, height 0, 3 records, no backward link); a volume where it is damaged cannot be opened at all (no listing, no unallocated export) and is reported as a corrupt volume, "failed to open" in `image info`, even though its bitmap may be intact; recovering such a volume belongs to sub-project 3 (`TestOpenChecksTheCatalogHeaderNode`). Only a catalog cut off by a truncated image still opens (with a warning).
- HFS+ deleted entries: none are listed (the catalog keeps no deletion marker; a deleted record's bytes survive only as stale slack in a node, in the journal or in unused nodes). The reader never reads slack, so nothing is flagged `Deleted`; finding such records belongs to sub-project 3 (`TestStaleNodeSlackIsNotListed`).
- HFS+ names and case: names are shown as stored (decomposed Unicode, no normalization), so a composed (NFC) path does not find a name stored decomposed; the entry is reachable through its listed ID (`TestUnicodeNamesDecomposedAsStored`). The on-disk `:` is not translated to `/` (a stored `/` or NUL, an empty name, `.` or `..` and invalid UTF-16 are shown as `~raw~<base64url>`, and `Lookup` accepts both forms). Lookup prefers an exact spelling to the `~raw~` alias to a case-fold match (`TestLookupPrefersExactOverFolded`). Case: HFSX with catalog `keyCompareType` 0xBC is case-sensitive and exact; plain HFS+ and case-folding HFSX are case-insensitive, and that fold is an APPROXIMATION: Go's per-unit lower-casing, with Apple's published table not embedded and the list of ignorable code units (U+200C-200F, U+202A-202E, U+206A-206F, U+FEFF) from memory and not validated against a real image, so a path may resolve differently than on a live system for exotic letters (the exact-first order limits the effect). Folding NUL to 0xFFFF (it sorts after every other unit, so the hard-link private folder is the last child of the root) is the one ordering rule CONFIRMED on a kernel-written image (`TestRealPrivateFolderSortsLastAndIsFoundByDescent`).
- HFS+ compressed (decmpfs) files: zlib types 3 (data in the attribute) and 4 (blocks in the resource fork) are decompressed on read, with `Size` the uncompressed size, `File.Runs` nil and attribute `compressed=zlib`; every other type (LZVN, LZFSE, ...) and any `UF_COMPRESSED` file whose header cannot be read is `ErrUnsupported` (attribute `compressed=<type>` or `unknown`) and `extract` skips it with an `analysis.warning`; it is never returned as an empty file (`TestDecmpfsZlibInline`, `TestDecmpfsZlibResourceFork`, `TestOtherTypesAreUnsupported`, `TestCompressedFileUnsupportedNotEmpty`). The decoder lives in the shared package `internal/filesys/decmpfs` (also for APFS); a type it does not decode is a typed `*decmpfs.UnsupportedError` (`errors.As`), and the compressed bytes stay reachable: `filesys.XattrReader` returns the raw `com.apple.decmpfs` attribute and the resource fork (`com.apple.ResourceFork`, with its image runs) byte for byte (`TestUnsupportedCompressionKeepsRawBytesReachable`). In that decoder an inline (type 3) file whose header declares more than 16 MiB is `ErrCorrupt`: type 3 is meant for tiny files and a larger one is type 4, whose blocks are 64 KiB. The zlib type 3 and 4 layouts (header, the type-4 block table: a big-endian 0x100 header word, the little-endian block count and (offset, size) pairs, stored-block marker) are implemented from the format description and are UNVALIDATED: no file written by an Apple system is available, so only builder images exercise them (no real compressed file exists in any fixture: compression is written by macOS, not by the Linux driver); no other type is decoded and no layout is guessed, so a real file that deviates fails as `ErrCorrupt` or `ErrUnsupported`, never as guessed bytes. A decmpfs attribute on a file without `UF_COMPRESSED` is ignored, as the OS does (attribute `decmpfs_ignored=true`, a warning, the data fork is the content; `TestDecmpfsAttributeWithoutFlagIsIgnored`). A decompressed file's artifact records no image runs (its bytes are decoded, not copied) and nothing in the provenance says so; the entry attribute does. A type-4 file whose resource fork is incomplete fails `Open` instead of offering a prefix. Resource forks of ordinary files are shown in attributes (`rsrc_size`, `rsrc_blocks`) and are readable through `OpenXattr("com.apple.ResourceFork")`; `Open` still returns the data fork.
- HFS+ hard links, threads and attributes: file hard links are resolved through the private folder's `iNode<N>` record and listed once per path (the entries share the inode in attribute `hardlink_inode`, so `extract` writes one copy per path), directory hard links are listed (type `other`) and not followed, and a link whose inode is missing is flagged `hardlink=dangling` and is a corrupt-volume error on `Open` (`TestHardLinkResolvesToIndirectNode`, `TestDirectoryHardLinkIsNotFollowed`, `TestHardLinkDanglingIsFlagged`). The file hard-link layout (private folder name, `iNode<N>`, `hlnk`/`hfs+`, the link count) was validated against the kernel-written fixture (a three-link group, its link count and the private folder); the directory-link markers (`fldr`/`MACS`) are from memory and builder-only; a link record's own dates are not shown (the inode's win, as on macOS). The private folder is listed and flagged `private_metadata` (only the folder: a root-level folder with the private name); its iNode files are listed unflagged under the private folder's path, never hidden. A file with no thread record is listed with `thread=missing` but IS opened: the catalog leaves are scanned for its id, charged to an id-scan budget of its own (256 MiB per filesystem, separate from the directory read budget; `TestOpenFileWithoutThreadByCatalogScan`), only for an id below the volume's next catalog id, and never for a file that has a thread (`TestThreadPresentNeverScans`, `TestNoThreadIDBeyondNextCNIDDoesNotScan`). The id must be provably unique: a second file or folder record with it, a catalog record that cannot be decoded or has an unknown type (its id is unreadable; only the unknown-type record keyed (the opened id, empty name), that id's own thread position, is skipped), or a budget or the record cap that ends the scan first is a corrupt-volume error, nothing is opened, and a spent budget is counted and warned about per refused open (`TestNoThreadDuplicateIDIsConflict`, `TestNoThreadDamagedRecordMakesTheIDUnprovable`, `TestNoThreadUnknownRecordTypeMakesTheIDUnprovable`, `TestNoThreadForeignEmptyNameUnknownRecordFailsClosed`, `TestNoThreadOwnParentNonEmptyNameUnknownRecordFailsClosed`, `TestNoThreadScanBudget`, `TestNoThreadScanRecordCap`, `TestNoThreadEmptyCatalogIsNotFound`); a thread-less folder id is `ErrUnsupported` (`TestNoThreadFolderIDIsNotAFile`) and a folder without a thread still cannot be listed by id (`TestMissingThreadIsFlagged`). A thread position holding an unknown-type record is unreadable, not missing: `thread=unreadable` with a warning, a `CorruptError` for listing by id, an open only when the scan proves the id unique, and every unknown-type record a thread lookup passes is warned about (`TestReadDirUnreadableThreadIsCorrupt`, `TestReadDirByIDWarnsOnPassedUnknownRecord`, `TestEntryUnreadableThreadIsNotMissing`, `TestEntryWarnsOnPassedUnknownRecord`, `TestOpenFoldsLookupWarningIntoUnprovable`, `TestOpenOwnUnreadableThreadOpensWhenScanProvesUnique`, `TestNoThreadFileOwnParentNonEmptyNameUnknownRecordFailsClosed`). The thread-less path is also proven on the kernel-written populated volume: one file's thread record is made unreadable in place and the file's bytes equal the independent oracle's SHA-256 (`TestOpenNoThreadFileOnRealImage`); the real driver never writes a thread-less volume, so the missing-thread layout is damage, not a legacy volume, there. Extracting a damaged volume with many thread-less files costs one catalog scan each until the budget is spent. At most 4096 attribute records are read per file (an attribute past that cap is not seen: `attributes=unreadable`, with a warning; a compressed file still fails closed through its flag); the attributes-file layouts and the directory-link markers (`fldr`/`MACS`) stay builder-only. At most 32 attribute names are listed (`xattr_more` says how many more). The Linux driver cannot write attributes, so the populated fixture's attributes file is empty (`TestAttributesTreeXattrs`, `TestAttributesHostile`). A catalog record whose id has no matching thread (a shared id: see docs/invariants.md, `TestDuplicateCNIDEntryIsConflictAndNeverOpens`) is flagged `cnid_conflict=true` and has an unresolvable `conflict:...` ID, so `Open`, `ReadDir` and `Lookup` through it are corrupt-volume errors and `extract` skips it with an `analysis.warning`; the record the thread names is unaffected, and the children of a duplicated folder id (keyed by that id alone) may appear under both folders.
- HFS+ data protection: an entry with a `cprotect` attribute is flagged `Encrypted` (per entry, attribute `cprotect=present`) and its content is extracted as ciphertext (flagged `Derived.Encrypted`), while `Info.Encrypted` stays false because protection is per file; the volume's content-protection attribute bit only appears as a feature. The `cprotect` attribute layout is builder-only. Decryption belongs to roadmap sub-project 10 (`TestCProtectMarksEncrypted`).
- HFS+ free space: `Unallocated` is exact against the real fixtures (`TestUnallocatedMatchesOracle`) and conservative elsewhere: bitmap bits at or past `totalBlocks` are ignored whatever they hold (real images have them clear; an early format note said set, which was wrong, and the reader does not depend on either); a system file whose extents cannot be fully resolved, or an unreadable or invalid bad-block record, makes it return nothing with a warning (a damaged catalog volume reports no free space) instead of an incomplete protected set (`TestUnallocatedIncompleteSystemFileReportsNothing`); the bad-block file's extents are only searched in the extents-overflow tree when that tree is non-empty, and no real image holds a bad-block record, so that path is builder-only. At most 1<<24 runs are reported (a warning says when the rest is cut off).
- HFS+ caps and budgets: one filesystem instance reads at most 1 GiB of catalog leaf nodes in total for directory listings and fallback scans (single-name descents are not charged); a directory lists at most 262144 entries (thread records count) and examines at most 1<<20 records; a file maps at most 1<<20 extents (past that a trusted prefix and a warning); `Unallocated` reports at most 1<<24 runs and examines at most 1<<16 bad-block records; a directory that cannot be read because the budget is spent is an error, never an empty listing. Like the FAT, exFAT and F2FS budgets, these belong to the instance and start over with every `image` command (`ls`, `unalloc`, `extract` each open their own) (`TestDirectoryReadBudget`, `TestDirectoryEntryCap`, `TestDirRecordCapCountsThreadRecords`, `TestRunCapKeepsPrefix`, `TestUnallocatedRunCap`). A B-tree read that falls short of its fork is a corrupt-structure error, not an I/O error.
- HFS+ real-image coverage and the format reference: the committed fixtures are five empty `mkfs.hfsplus` volumes and one kernel-written populated volume (see docs/invariants.md and `tools/fixtures/README.md`); populated behaviour that the Linux driver cannot write (extended attributes, resource forks, decmpfs, data protection, HFSX with content, a journal with transactions, deleted-record slack, non-BMP names) is verified on builder images only, checked by `fsck.hfsplus` (12 of 15 pass, three exempt with recorded reasons) and never against a volume written by macOS or iOS: run `TestRealHFSPlusImages` (`-tags realimages`, `MINUTIAE_TEST_IMAGES`) by hand on such volumes before relying on those paths. Items of the format reference that real images settled: allocation-bitmap bits past `totalBlocks` are CLEAR (the reference said set), an HFS+ catalog's `keyCompareType` is 0xCF (not 0; HFSX binary is 0xBC), folder records carry flags 0, `mkfs.hfsplus -J` leaves the journal uninitialised, `mkfs.hfsplus -s` omits the folder-count flag that `fsck.hfsplus` then reports, and NUL folds last. Still unverified against any real image: the initialised journal header, the volume-attribute bits for an inconsistent boot volume, reused CNIDs and a software lock, the ignorable-unit list and the rest of Apple's fold table, the decmpfs formats, the directory-link markers, the attributes-file records (inline, fork-data and extents) and the `cprotect` layout.
- APFS reader, read-only and as found (`internal/filesys/apfs`, type `apfs`): `Info.Label` is empty (a container has no label; the volume names are in `Info.Volumes`, the per-volume feature lines and the root listing, one entry per volume). Only the NEWEST valid checkpoint is read: older checkpoints, the free queues, unreferenced blocks and deleted data are not interpreted (sub-project 3; `TestCheckpointPicksHighestValidXid`), and APFS keeps no deleted directory entries, so `image ls --deleted` shows none (`TestReadDirLiveEntries`). Fusion containers, version-1 containers and a non-contiguous checkpoint-descriptor area are `ErrUnsupported` (`TestFusionAndVersion1AreUnsupported`, `TestNonContiguousAreaIsUnsupported`); unknown incompatible volume features (the known set is the six bits of the format reference, 0x3f), a sealed volume and a pending revert only warn, and the hashes of a sealed volume are not verified. A time of 0 is shown as the epoch (present); only a value beyond the signed 64-bit range is invalid (`time_ns=invalid`). Extended attributes: their names are listed in the entry attributes (at most 32 per entry, `xattr_count` says how many) and their VALUES are read through `filesys.XattrReader` (`Xattrs`, `OpenXattr`; embedded values come from the record, stream-stored values through their own extents with real image runs; a stream larger than the container, with a hole or a damaged extent map, a record with both or neither storage flag, and a value that does not fit its record are `ErrCorrupt` and never a prefix or zeros; more than 4096 xattr records on one object is `ErrXattrCap`; `TestXattrsListNamesSizesAndStorage`, `TestOpenXattrReturnsValues`, `TestOpenXattrStreamHostile`, `TestXattrRecordCap`). No command extracts xattr values as artifacts yet; a resource fork is the xattr `com.apple.ResourceFork`. A symlink whose target is stream-stored is read like an embedded one (up to 65536 bytes, at most 64 MiB of such targets per filesystem in total; a spent budget and an oversize target are reported as `symlink=unreadable` with a warning; `Open` reports the stream's image runs; a hole, missing extents or an empty target is `ErrCorrupt`; `TestSymlinkStreamTarget`, `TestSymlinkStreamHostile`, `TestSymlinkStreamBudgetIsCumulativeAndReported`, `TestSymlinkTarget`, `TestSymlinkOpenReturnsTarget`). Xattr values are validated against the real populated fixture: every value (embedded, empty, binary, the 6000-byte stream-stored one and a directory xattr, in the live view) equals the SHA-256 and size the independent oracle computed (`TestPopulatedXattrValuesMatchOracle`, `TestAPFSMatchesOracle`); the snapshot view of the values is NOT told apart by the real oracle (the fixture's snapshot xattrs equal the live ones) and is pinned by the builder test `TestXattrsReadFromTheSnapshotView`. Stream-stored symlink TARGETS are validated on builder images only: the populated real fixture holds none (its longest target is 203 bytes); the stream-reading code itself is the path the real 6000-byte xattr stream proves. A damaged container object map makes `Open` fail with a `CorruptError` for the whole container, so no volume is listed at all (a damaged volume, by contrast, is warned about as unreadable and the others are still listed; `TestOmapPhysHostile`, `TestUnreadableVolumeIsListed`).
- APFS encryption: a volume flagged encrypted is reported (`Info.Encrypted`, `ErrEncrypted` on every read of it; `extract` skips it with an `analysis.warning` and extracts the other volumes) and its blocks are never read; decryption is sub-project 10 (`TestEncryptedVolumeIsErrEncrypted`, `TestExtractAPFSEncryptedVolumeIsSkipped`). On an unencrypted volume a file whose dstream crypto id OR any of its extents' crypto ids is not 0 or 4 is read as stored ciphertext and `extract` flags the artifact `Derived.Encrypted`; the listing flag `Entry.Encrypted` comes from the dstream crypto id only (listings do not scan extents), so a file keyed only in its extents is flagged when opened, not when listed (`TestOpenedFileReportsPerFileEncryption`, `TestPerFileCryptoIDAnomaly`, `TestExtractFlagsFileThatReportsItselfEncrypted`). The crypto id `~0` (unassigned) may mean "no key" in the format, but the reader treats it as a key, so it can over-flag `Encrypted` (unverified; the bytes are the stored ones either way). No committed real image holds an encrypted file or volume.
- APFS compressed files (the compressed inode flag) are unsupported: `Open` fails with `ErrUnsupported` ("decmpfs-compressed file"), the listing shows the entry with attribute `compressed=<type>` (named from the decmpfs header's type number, or its decimal number, or `unknown`) and `extract` skips it with an `analysis.warning`, never an empty file. This differs from F2FS (`compressed=true`) and HFS+ (zlib types are decoded); sharing HFS+'s decoder would need a package `internal/filesys/decmpfs`, because readers may not import each other. The type numbers are from memory of Apple's decmpfs header: 3/4 (zlib), 7/8 (lzvn) and 11/12 (lzfse) were re-derived by the review, but 9/10 (`uncompressed-*`) and 1, 2, 5, 6 (not named, printed as decimals) are UNVERIFIED, and no committed image holds a compressed file (`TestCompressedFileUnsupported`, `TestCompressedAttrNamesTheDecmpfsType`).
- APFS snapshots: each volume lists a synthetic `.snapshots` directory and every snapshot is a read-only view of the volume at its xid (`image ls --snapshot`, `image extract --snapshot`, or a path below `.snapshots`; see docs/invariants.md). RECURSIVE operations do not descend into `.snapshots` by default (`extract -r`, `image ls -r`), so a snapshot-heavy volume is not multiplied in the output, and they say so: one `analysis.warning` (source `examine`, not a skipped file) names the skipped `.snapshots` when the volume has snapshots. `--include-snapshots` (with `-r`; refused with `--snapshot`) opts in (library: `examine.ExtractOptions.IncludeSnapshots`): the run then descends, writes no skip warning, records `include_snapshots` in the `analysis.start` details of `extract` and keeps each snapshot artifact's snapshot provenance; `image ls -r --include-snapshots` marks every entry below `.snapshots` as snapshot data (`[snapshot <name>]` in the text, a `snapshot` field in the JSON) and writes no audit entry (a listing has no `analysis.start`), and is bounded only by the walk's own caps (`extract` is subject to `--max-files`/`--max-bytes`) (`TestImageLsRecursiveIncludeSnapshots`, `TestImageLsIncludeSnapshotsMarksSnapshotData`, `TestImageExtractRecursiveIncludeSnapshots`, `TestExtractRecursiveIncludeSnapshots`, `TestExtractRecursiveDefaultStillSkipsSnapshots`, `TestExtractAPFSIncludeSnapshotsProvenance`); the output then multiplies by the number of snapshots, which is why it is opt-in. Other walkers of `filesys.Walk` (the fuzz targets) and `Session.Lookup("id:...")` DO follow snapshots. The snapshot-metadata layouts (record offsets, the snapshot name record, the object-map snapshot tree, which block holds the volume-superblock copy) are validated against ONE snapshot written by the Linux driver (`snap1` in `apfs-populated`, read with no warning) and a reviewer's re-derivation from the format reference (0 disagreements), never against a snapshot written by Apple software; several snapshots, deleted or reverted ones, duplicate names and a missing object-map record are builder-only. Two assumptions stay UNVERIFIED: that the volume-superblock copy of a snapshot carries its own block address as header oid (a mismatch is only a warning and the copy is used; the one real driver-written copy satisfied it) and the exact object-map xid boundary for records written in the snapshot's own transaction. `apfs_num_snapshots` is not compared with the records found. `--snapshot` needs a path that names a volume (`filesys.ErrNeedsVolume` is a usage error), and a bare reference that matches more than one snapshot is refused (use `xid:` or `name:`) rather than guessed (`TestSnapshotPathSharedNameIsAmbiguous`, `TestSnapshotFlagRefusesAmbiguousReference`).
- APFS names: a directory record's name hash is verified for every name that is valid UTF-8 and made only of code points assigned in Unicode 9.0 (that cutoff, from memory of how APFS freezes its tables, is unverified: a wrong cutoff only widens or narrows the set of names that are skipped, and it produced no false mismatch on any real fixture); a mismatch is flagged `name_hash=bad` with a warning and never hides the entry. On a normalization-insensitive volume lookup matches NFC and NFD spellings and, on a case-insensitive one, case-folded ones, using `golang.org/x/text` tables of Unicode 15.0: for a code point that exists in 9.0 the result is stable by policy, but a path may still resolve differently than on a live system for characters whose folding changed after 9.0; listing is unaffected. An exactly spelled hashed lookup reads only the records of one hash (a name matched only insensitively costs a scan, which looks for an exact name stored under a wrong hash first), so it can find an entry beyond the 262144-entry directory listing cap that a listing never shows. A case-sensitive volume that is normalization-insensitive (`0x8` only) matches NFD-equal names without case folding, as its hash does; no committed real image has that flag combination (builder-only, `TestLookupNormalizationInsensitiveOnlyVolume`). A name that is `.`, `..`, holds `/` or NUL or is not valid UTF-8 is shown as `~raw~<base64url>` with `RawName` set, and a duplicate volume name gets a `~<slot>` suffix (`TestNameHashNonASCIIMatchesRealImage`, `TestLookupNormalizationInsensitiveRealImage`, `TestVolumeNameEdgeCases`).
- APFS free space and the space manager: `Unallocated` comes from the space manager's chunk bitmaps and is exact against all four real fixtures (`TestAPFSMatchesOracle`), including a chunk with no bitmap block. A damaged structure is skipped with a warning or yields no runs, never guessed free space (see docs/invariants.md), and block 0, the checkpoint areas, the internal pool and the metadata blocks are removed even if a bitmap calls them free. The multi-CIB layout is validated on a real `mkapfs` container of 17 GiB (136 chunks, 2 CIBs of 126 and 10 chunk-info records; sparse, never committed, regenerated by `tools/fixtures/apfs-big.sh` together with `apfs-bigcib.expect.json`; `TestAPFSBigContainerMatchesOracle` needs `MINUTIAE_APFS_BIG_IMAGE` and SKIPS without it): `Unallocated` equals the independent oracle exactly, with zero warnings and the reader's CIB and CAB counts equal to the oracle's. The CAB (chunk-info address block) layout is still builder-only: a real CAB needs more than `sm_cibs_per_cab` = 507 CIBs, that is more than 63,882 chunks, about 8 TiB, and the other real fixtures have one CIB. At most 1<<24 runs are reported (`TestUnallocatedBoundsAndCap`). Blocks that a snapshot still holds are allocated, so they are not in the export.
- APFS caps and detection limits: a B-tree is read to a depth of 16, with a per-scan node budget (`min(1<<20, blocks)`, tightened by `bt_node_count`) and a cumulative per-filesystem one (`max(1<<20, 4 x blocks)`); a directory is read up to 262144 entries and one filesystem instance reads at most 1 GiB of directory data in total (past that a warning and a partial listing, or an error when nothing was read, never an empty listing); a file maps at most 1<<20 runs and 1<<22 extent records; a volume lists at most 65536 snapshots. Like the other readers' budgets these belong to the instance and start over with every `image` command (`TestBTreeDepthCapIsCorrupt`, `TestBTreeCumulativeNodeBudget`, `TestDirectoryReadBudget`, `TestDirEntryCap`, `TestRunCapIsCorrupt`). The budgets can be reached by one huge or dense but legitimate volume: the cumulative node budget has a floor of 1 Mi node reads, about 9 reads per entry for a walk that also opens every file on a shallow tree on the populated fixture, so very roughly 50k to 100k small files before an `extract -r` ends with "node read budget exhausted" skips (loud, never a silent hole; deeper trees cost more), and a session that resolves many explicit paths in a very large directory spends the directory budget by scans (about 40 scans of a 262144-entry directory; a normalization-sensitive volume has no hash to search by, so every path component is a scan until the exact match). Not detected: an extent record erased from the middle of a file whose neighbours stay in order reads as a hole there, because APFS cannot tell a sparse range from a missing record (a sparse range has no record at all). The dstream `alloced_size` is deliberately not cross-checked against the extents: on the populated fixture it equals the mapped bytes for 1282 of 1290 ordinary files, but the four real sparse files report `alloced_size == size` (holes counted), so such a check would flag real sparse files (`TestWellOrderedSparseFileStaysHoles`, `TestSizeLargerThanExtentsIsAHoleTail`); a larger-id record at the very end of a leaf with the file's extent in the next leaf behind a hostile index key is not found, and two files whose extents overlap physically are not reported (clones legitimately share extents).
- APFS detection: the `apfs` driver probes block 0 only and is first in `detect.Drivers`. An NXSB signature planted at byte 0 of an ext4, F2FS, HFS+ or HFSX image (the boot area those filesystems leave free: their superblock or volume header is at byte 1024) is therefore claimed by `apfs` first; its `Open` fails with a corrupt-structure error and detection falls through to the real driver with the note `driver apfs matched but failed to open ...; opened as ...`, so the type the image opens as is unchanged; a signature anywhere else is never seen (`TestStaleAPFSSuperblockDoesNotHideOtherFilesystems`). A damaged container whose block 0 still carries the signature is claimed and opened through the checkpoint ring (block 0 supplies the geometry only).
- APFS real-image coverage: since the populated fixture the earlier "empty containers only" limitation is largely lifted. Validated against real bytes: the container, checkpoint ring, object maps, space manager and its bitmaps, the volume superblock, both directory-record key forms, inodes and their extended fields, directory records and name hashes (all 678 of the populated image), extents (fragmented files of 121 and 124 runs, sparse files with a hole first, last, between and all-hole), clones, symlinks, a hard-link group, extended attributes (names, and the values of embedded, empty, binary and stream xattrs by SHA-256), one snapshot, free queues and four checkpoints, written by `mkapfs` and by the `linux-apfs-rw` kernel driver (so conventions particular to that driver are what was seen: symlink mode 0755, and the `osx.` attribute prefix the driver adds on Linux). Still builder-only, never validated against any real image: encrypted volumes and per-file keys, decmpfs-compressed files, sealed volumes, Fusion, a second volume in one container, several, deleted or reverted snapshots and the object-map snapshot flags, the CAB space-manager layout, a checkpoint ring that wraps or has to fall back to an older checkpoint, volume roles other than none, a case-sensitive normalization-insensitive volume, hard-link records beyond the one real group, names with code points newer than Unicode 9.0, 64 KiB blocks, and anything written by macOS or iOS. Run `TestRealImages` (`-tags realimages`, `MINUTIAE_TEST_IMAGES`) by hand on such an image before relying on those paths; `tools/fixtures/apfs_expect.sh`, which writes the expectation file on macOS, was written from memory and never run.
- The populated APFS fixture is not byte-reproducible: five generations under QEMU gave five different images (the number and timing of driver transactions vary), so `apfs-populated.img.gz` and `apfs-populated.expect.json` must be regenerated together (`gen.sh apfs-populated` in the `minutiae-fixtures-apfs` image); every test pins the image sha256 to the oracle first. Regenerating changes the committed binary and the roughly 436 KB oracle.
- FAT and exFAT directory read budgets: each filesystem instance reads at most 1 GiB of directory data in total (exFAT) or at most 4M directory entries, 128 MiB (FAT, which counts entries), so a hostile volume whose chains overlap cannot cost unbounded time. Once the budget is spent, directories are no longer read (a directory read after that is an error, one being read when it ran out is cut short) and the filesystem reports a single budget warning (`TestDirectoryReadBudget`, `TestExfatDirectoryReadBudget`, `TestExfatBudgetExhaustedBeforeFirstEntryIsAnError`). A FAT directory also holds at most 65536 entries, an exFAT directory at most 256 MiB. The budgets are never reset within an instance, so one huge but legitimate volume can reach them. A directory that cannot be read because the budget is spent is an error, never an empty listing: `image ls -r` and `image extract` report it and do not treat the directory as empty. The budgets belong to the filesystem instance, and every `image` command (`ls`, `unalloc`, `extract`) opens its own session and so its own instance: the budgets start over with each command (this holds for the F2FS and HFS+ budgets too).
- `File.Runs` prefix rule: normally the runs cover exactly `[0, Size())`. A file whose allocation is truncated or corrupt (a FAT chain that ends, loops or leaves the volume; an exFAT chain that ends, loops, meets a free, reserved or bad cluster, or runs past the end of a truncated image, where a first cluster outside the declared heap, or a `DataLength` the declared heap cannot hold, still fails to open and the zeros after `ValidDataLength` are shown only when the chain covers all of `DataLength`; an ext4 file whose extents run past the end of a truncated image; an HFS+ fork with a missing overflow record or an extent past the end of a truncated image; an F2FS file whose block map is damaged, which reports the blocks mapped before the damage; an APFS file whose extent records are out of order or invalid) may report only a leading prefix of it; every read at or beyond the end of that prefix fails with `ErrCorrupt`, never zeros, so the covered bytes can be told from the missing ones (`filesys.CheckRunsPrefix`, `TestCheckRunsPrefix`, `TestImageRunsAcceptsOnlyAValidPrefix`).
- Regenerating the real-image fixtures needs Docker; running the tests never does. The exFAT fixture additionally needs `docker run --privileged` (a loop device plus the FUSE driver `exfat-fuse`, because no exFAT image tool copies files into an image and the Docker Desktop kernel has no exfat driver); without it only that fixture cannot be regenerated, the committed `exfat.img.gz` and the builder-based `exfattest` tests still run. The HFS+ fixtures are not part of `gen.sh all` and need the separate `minutiae-fixtures-hfs` image (`tools/fixtures/Dockerfile.hfs`; no `--privileged`, the populated one is written by the Linux `hfsplus` driver under QEMU software emulation); the populated image is byte-identical on most regenerations (8 of 9) but not guaranteed, so it is regenerated together with its `expect.json`. The three empty APFS fixtures are part of `gen.sh all`, but `apfs-populated` needs the separate `minutiae-fixtures-apfs` image (`tools/fixtures/Dockerfile.apfs`; no `--privileged`, the Linux `linux-apfs-rw` driver runs only inside a QEMU guest, never in the host or Docker Desktop kernel) and is not byte-reproducible, so it is always regenerated together with its `expect.json`.
- Records database (sub-project 5, plan 5A: schema, writer, verify, reader, `records list|show|stats`; 5C added the provenance chain and image offsets to `show`; 5D added the scale work, see the 5D bullets below; 5B added full-text search, see the full-text bullets below): the schema is v3 (v2 cases are upgraded by `case upgrade` then `records reindex`); a v1 case opens as v1 and works for everything else, but every `records` command refuses it (exit 2, `case upgrade` named) because a case is migrated only by the explicit, audited `case upgrade` (never on open). A corrupt `artifacts.db` is an integrity error (exit 4) and is never recreated. `records show` prints the columns, the artifact (id, path, sha256, source), the parser, the batch (digest, audit sequence), the run, `superseded by` and, since 5C, the checked provenance chain with image-relative offsets.
- Records audit anchor: the audit chain has no external anchor, so someone with file access who can append valid, correctly chained audit entries could forge a `records.ingest.recover` entry. A recover entry's `batch_nos` and `by_ingest_id` are not cross-checked against the ingest's audited batches, so for an interrupted ingest a forged `unfinished` recover that names a trailing batch (together with erasing that batch) leaves only a notice; for a concluded ingest the totals check defeats it. Anchoring the audit head outside the case is not planned yet.
- Records supersession and runs: only a complete run supersedes an older run of the same parser name for an artifact, so an incomplete (failed, cancelled or interrupted) run is shown beside the older complete run until a complete run supersedes both. `case verify` lists at most 50 problems per kind, then one "N further <kind> problems are not listed" line (`TestVerifyListsAtMostFiftyProblemsPerKind`). `Overview.Runs` is case-wide (not filtered); `Overview.Deleted` includes recovered records while `Stats` by `deleted` puts them in a `recovered` group. `Reader.Count(limit)` is exact up to `limit`, `capped` is true only when more than `limit` records exist (n is then `limit`) and a limit of 0 means no cap (`Page.Limit` 0 means 100).
- Records reads are not verification: `records list|show|stats` read `artifacts.db` as it is and never run the `case verify` row checks, so what they print is only as trustworthy as the last `case verify` (the exception is `show`, which since 5C checks the provenance chain, its audit binding and the sidecar hashes, and still not row digests) (a repointed `artifact_id` shows another artifact's provenance, an edited summary is shown as edited). The one check they make is the cheap comparison of the schema objects (`ReadRecordsTx`): a database whose tables, indexes, triggers or views differ from the schema this build defines is refused with exit 4 (a redefined index or view could otherwise shape every answer silently). A forged row or an injected `record_superseded` pair is not seen by the reader. Run `case verify` before relying on a listing.
- Record provenance in `records show` (sub-project 5, plan 5C): `show` resolves and checks the chain, the audit binding of each hop and the runs sidecar hashes, but it still does not recompute row digests or re-verify the audit chain itself (`case verify` does; exit 4 from `show` means a provenance problem, not that the log is intact). `extract` and `unalloc` runs are claims recorded at extraction time: `show` checks they are self-consistent and translates through them but does not prove they reproduce the image (`case verify` R6 does that for recovered artifacts only). Offsets are logical media offsets (E01 shows media coordinates, labelled); a decompressed artifact (decmpfs) has no runs and so no image offset. Translation is not linear in the runs: each hop re-scans the runs for each of up to 256 pieces (256 x runs per hop, times up to 16 hops), so a hostile sidecar of 1M runs makes `show` slow (still bounded; no algorithm change). The unallocated run map has its own strict reader (`ReadUnallocRunMap`); carving (3E) relies on it.
- Raw terminal-display risk in `--json`: bidi controls and NEL (for example U+202E, U+0085) are left raw in JSON strings (controls below 0x20 are escaped, the decoded JSON values equal the stored strings), so a JSON line viewed raw in a terminal can be visually reordered. A CLI-wide terminal-safe JSON encoder (`\uXXXX` for every non-graphic rune, values unchanged) is in the backlog.
- The default `records list` hides superseded records through the STORED `record_superseded` table (`Filter.compile`), not through a recomputation from the runs. `case verify` (P14) proves that table equal, in both directions, to the recomputation from the one shared definition `evidence.SupersededPairsSQL`, so a forged or deleted pair changes a listing only until the next verify.
- Records write-time limits (a record outside them is refused with a typed error; nothing is buffered or audited; `TestPrepareValidationMatrix`): summary 512 bytes, body 4 MiB, payload 16 MiB of canonical JSON and 64 levels of nesting, locator 1024 bytes and a scheme `[a-z][a-z0-9]{1,15}:`, source path 4096 bytes, at most 16 secondary times per record with kinds `[a-z][a-z0-9_]{1,31}`, registered record type names `[a-z][a-z0-9_]{1,31}`, recovery method `[a-z][a-z0-9-]{1,31}`, 20,000 rows per batch (default 5000), parser name and version `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, parser hash empty (stored NULL, never "") or `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`; NUL and invalid UTF-8 in text are refused, and a timestamp outside 1970 to 2100 is accepted only with a non-empty payload `ts_note`. Warnings written through `Writer.Warn` are bounded (path 4096 bytes, reason 1024) and capped at 10,000 per ingest.
- Records ingest counts: `rejected` counts records refused by `Add` (validation) and `Writer.Reject` calls. Every one is audited as an `analysis.warning` entry marked `rejected=true`, sharing the 10,000-entry cap with `Writer.Warn`; past the cap nothing is written per entry and the single suppression note, written right before `records.ingest.end`/`.error`, carries the numbers of suppressed warnings and suppressed rejections. `case verify` therefore checks equality: `warnings` = entries, `warnings_suppressed` = the note's two numbers summed, `rejected` = rejection entries + the note's suppressed rejections. Recovery of an unconcluded ingest derives the same numbers from the log. The writer also appends a "suppression began" marker note (`suppression_began=true`, no numbers) the first time the cap keeps an entry out of the log. Limit: an ingest that dies before it writes the conclusion note (a crash or kill before `End`/`Abort`) leaves no proof of how much was suppressed; its recovery sets `suppression_unknown=true` (with the placeholders `warnings_suppressed` 0 and `rejected` counting only the rejection entries, both lower bounds), never a silent 0, and verify accepts that flag only on such a recovered ingest. A concluded ingest (an end/error entry, or a run-missing recover) that has a began note but no conclusion note is a verify problem, so an end entry appended for a crashed, suppressing ingest cannot pass as "0 suppressed"; a repeated began note (an audit append that failed after its entry reached the log, then retried) is tolerated. After the note is written the writer refuses further `Warn`/`Reject`/refused `Add` calls (`ErrWriterClosed`), so the note is never stale.
- Records audit entries are decoded strictly (`evidence.DecodeDetails` refuses an unknown field): a later build that adds a field to a `records.*` audit entry makes an older build report `case verify` problems for the newer log. That is acceptable only while the schema is unreleased (see the "no compatibility path" bullet); the layouts must be versioned before the first release that has to add a field.
- `case verify` reports a derived-artifact cycle of N artifacts once per artifact (N problems, at most 50 listed per kind; `TestDerivedChainWalk`), and a parent chain longer than 16 hops as one problem.
- Records time and text: timestamps are stored as Unix microseconds (a sub-microsecond remainder is truncated; the raw value is the parser's to keep in the payload); a time outside 1970 to 2100 needs a non-empty `ts_note` in the payload; `local-unknown` is a wall clock stored as if UTC; `TimeEnd` must share its `Time`'s basis and offset; NUL is rejected in every record string and payload string. `records list|show` display a local time with a known offset as its wall clock plus `~local+HH:MM`, and a local time of unknown zone as `~local` (stored instants in `stats` time ranges are shown as UTC).
- Records cursors are stable only across an unchanged database (a record ingested between two pages is not seen by a cursor taken before it, and ids are never reused); the fingerprint a cursor carries is a guard against using it with the wrong filter, order, direction or case, not a defence against a forger, who learns nothing from reusing one.
- Full-text search (sub-project 5, plan 5B: schema v3, `records search`, `records reindex`, P11): the index (`records_fts` word table, `records_fts_sub` trigram table) is DERIVED data over the summary and body of each record, never evidence, and `case verify` P11 proves it by recomputation: it normalizes every record and recomputes the postings (a digest per audited batch), the document sizes and the totals inside the record stream, decodes the leaf pages strictly and compares them with it, and checks `_config`; it recomputes the `_idx` rows and the doclist indexes from the leaf pages (a split key may be the whole first term of its page, which an incremental-merge step writes; the `_idx` and doclist-index rows left over below the first page of a trimmed segment of an unfinished merge, and the rows of a drained segment, are never used by a search and are not compared; the key of the row of the first remaining page of a trimmed segment cannot be recomputed and only its page and flag are compared), and a clean verify creates no scratch area. Only the failing buckets are rebuilt with SQLite's own tokenizer (plan 5D Task 14k): at most 64 batches, in rounds of 4,000,000 expected postings with at most 8,000,000 found rows each, so the scratch is bounded by the round budget and not by the indexed text; the failing batches past the bound are named in one line per table and are not listed entry by entry (the examiner sees which batches to look at, and a re-run after a repair lists the next ones). A table with a segment that does not decode is not localized, because what its pages hold is not known (its failing batches are named with that reason). P11 has no skip flag, no sampling and no shortcut: every posting of every record is digested at every verify. Its cost with the digest was measured by plan 5D Task 14m: a clean verify of 2,000,000 records takes 681 s (2,935 records/s) and of 10,000,000 records 4,633 s (2,158 records/s), of which `fts.index` 1,182 s and the expected side of `records.stream` 723 s (`docs/performance.md`). Payload values are NOT indexed (summary and body only), there is no `prefix` index (a prefix needs at least 2 letters or digits on its last token and a prefix with a type filter measured 77.5 ms at p95 at 10,000,000 records after the plan shapes), and search plans are chosen by bounded probes (see the search plan shapes bullet).
- Full-text version rule: the index is valid only for the pipeline version it was built with (`FTSNormVersion`: normalization, the `golang.org/x/text` version, Go's Unicode version and the driver). A normalization or driver version bump therefore requires `records reindex` BEFORE any ingest: until then `records search` and `Writer.Start` refuse (exit 2 for search, `ErrIndexNotCurrent`), a batch cannot be written and `case verify` reports a notice. A v2 case needs `case upgrade` (which leaves a case with records "index not built") and then `records reindex`. An attacker with file access can force "index not current" (edit or delete `fts_norm_version`): that denies search and writing and can never produce a wrong hit; `case verify` does not trust the value either: it derives the expected state from the audit log (the last `records.reindex.done` and the `norm_version` of the later `records.ingest.start` entries), reports a different value as a PROBLEM and compares the index content whenever the derived version is this build's. A state the audit log explains but P11 cannot check (never built after an upgrade, built by another pipeline version, a reindex announced and not concluded) is a NOTICE: `case verify` exits 0 and the index content is not compared until `records reindex` runs.
- Full-text schema comparison: the FTS5 shadow tables (4 per index) are verified by DDL text like every other schema object (P12 and the reader's check). A future SQLite that changes the DDL FTS5 writes for its shadow tables makes older v3 cases fail that comparison (exit 4 on `records` commands, a P12 problem); the weakening of the comparison is refused, the remedy (a version-aware expected schema) is for 5D or later.
- Full-text temporary files: `PRAGMA temp_store_directory` is process-wide state. `case verify` sets it to `<case>/tmp/verify-<runid>/` for the P11 work and resets it in a defer (even on panic), so evidence-derived text never spills outside the case; the CLI runs one command per process, a library caller running other SQLite work in the same process during a verify shares that setting. A clean verify creates no scratch area; the two scratch databases and the spill files of a localization are removed when verify ends. A leftover `<case>/tmp/verify-*` directory (an interrupted verify) is a `case verify` problem on the next run, as is `<case>/tmp` when it is a symlink, junction or any non-directory (checked with `Lstat`; nothing is created or listed through it); at most 50 leftover entries are listed, then one "further entries are not listed" line (`TestCheckTmpListsAtMostFiftyEntries`, `TestCheckTmpAloneRefusesANonDirectory`), and verify removes only what it created: its run directory, and `<case>/tmp` only when this run created it (`TestVerifyKeepsAPreExistingEmptyTmp`). The two scratch databases of the localization (the rebuild by SQLite and the postings the pages hold) are a deliberate exception to "reads go through `ReadHandle`": they are private temporary databases that `case verify` creates and fills itself (never the case database), under `<case>/tmp`, only when a bucket fails. Every connection to the case database runs with `temp_store = MEMORY` (set when it opens, re-set after each read transaction and before each write transaction), so the statements outside `ReadTx` (ingest batches and their statement journals, the supersede conclusion, migrations, `records reindex`) never create a SQLite temp file in the OS temp directory (`TestIngestAndReindexLeaveNoSQLiteTempFileOutsideTheCase`, with the control `TestTempSpillWatcherSeesASpill`); their sorters and statement journals therefore live in memory (their cost at 10 million records is measured in plan 5D). Only verify uses the process-wide `temp_store_directory` (one case per process, above). A search or stats sorter inside a read transaction therefore never spills outside the case either; the rank statement ends in `LIMIT ?`, which bounds its sorter. Two caveats: a symlink or junction `tmp` is tested only with a regular file on Windows (the symlink subtest skips without the privilege), and a `--timeout` below the clock resolution (1 ns on Windows) is not guaranteed to have passed when the first statement starts (a test hands the command a past deadline instead).
- Scale measurements of temporary files are samples (plan 5D, rulings D46, D50, D52, D57): the OS temp directory is compared before and after each phase, `<case>/tmp/verify-*` is read every 500 ms, and neither sees a file created and removed between two looks, an unlinked file, or a file kept open and deleted. A recorded 0 therefore means "none seen", not "none written", and is never evidence that nothing spilled. The method and its blind spots are in `docs/performance.md` ("Verify spill and the OS temp directory"). Open handles and the cleanup time of `verify-*` are not measured (not scheduled).
- Full-text index residuals: rows in the FTS5 shadow tables (`_data`, `_idx`) that no structure record references are inert to search but are flagged by `case verify` (P11, plan 5D Task 13: the structure record is decoded and every `_data` row and `_idx` segment must belong to a segment it names). A leaf row of a listed segment outside its pages First..Last is reported by the strict decoder as an invalid leaf (D157), a height row (an interior page) of a listed segment is reported as a row a genuine index never holds (D156), and a segment id that no data row id can hold is one problem for that segment while the other segments are still read (D158). Not covered: a stale `_idx` or doclist-index row below the first page of a trimmed segment of an unfinished incremental merge (a genuine index leaves such rows, and they cannot be told from a tampered low-page row; no search reads them, D156), and a "version 2" structure record, which only a table created with `contentless_delete=1` writes and which no Minutiae table uses (it is reported as unreadable). The query grammar scan runs after the 4096-byte cap on the raw query text and is bounded by it. A search hit shown without a marked snippet on one column means that column did not match (`--in any`); a stored text that literally holds the six characters of an escaped marker looks the same as an escaped marker on screen (harmless). The scanner of the single-writer rule now also flags `sqlite_master` writes and `writable_schema`; a comment marker inside an SQL string literal remains the residual below.
- FTS5 page decoder (plan 5D Task 14h, `internal/evidence/fts5seg.go`; P11 reads the leaf pages with it since Task 14i): it follows the FTS5 leaf and segment format of the pinned SQLite only (modernc.org/sqlite v1.60.1, SQLite 3.53.4). It is strict on purpose, so a page layout another SQLite version writes differently is refused with a typed error rather than read, and a driver upgrade must fail the pin tests of Task 14g (`TestFTS5ReplicaPinMatchesDriver`, `TestFTS5TokenTablesAreCurrent`) before it can reach the decoder. Its rowid-delta bound assumes positive rowids, as Minutiae's are, and on any error the caller must discard everything that segment contributed through the sink. It knows two columns (`summary`, `body`) and the main index only (no prefix indexes, no `contentless_delete` tombstones). It does not merge segments: the postings of every segment are reported as stored and a delete marker is reported, not applied. Those are left to the caller (the segment age is `ftsSegmentAge`, newest first by level and position), and a record that was deleted and re-added shows its old postings in an older segment.
- P11 postings digest (plan 5D Task 14i): the leaf pages are compared with the records by a keyed digest per audited batch (`verify_ftsdigest.go`), not entry by entry. A forged index that has the same 128-bit sum and posting count as the genuine postings of a batch would need a collision of AES-128 CBC-MAC under a key that is new for every run and never stored; the bound is the PRF advantage of AES-128 CBC-MAC over prefix-free messages, about q^2/2^128 over all the postings q hashed under one key (q is about 2^32 at 10 million records, so about 2^-63), and forging a chosen different multiset of postings with the same sum and count is about 2^-128. This is not sampling: every posting of every record is hashed and every leaf page is decoded; the residual is the collision bound alone, per run. The adversary cannot query the PRF: the key is drawn from `crypto/rand` for each run (`TestStartFTSDrawsADifferentNonZeroKeyEachRun`), exists only in the memory of that run and is never stored or logged, and the case is written before the key exists. The distinct "outside" id blocks (ids no audited batch holds, 2^16 ids each) are capped at 1,000,000 per table, per set of delete-marker buckets and per set of failing buckets; the blocks past the cap are counted together in one overflow bucket, which is always a PROBLEM ("too many unaudited id blocks") and is never localized (D150, `TestVerifyFTSHostileRowidsKeepMemoryBounded`). A failing bucket is localized with SQLite's own tokenizer (Task 14k, `verify_ftslocal.go`); a failing bucket whose localization finds nothing (the index equals SQLite's rebuild but not the replica) is a PROBLEM that names the batch and says the replica does not match this SQLite, so it fails closed. The leftover `_data` leaf rows of a segment that the structure record lists with pages 0 to 0 (an emptied segment of an incremental merge, D143) are not decoded (D149): no search reaches them, so they cannot cause a hidden or an invented hit, `checkUnreferenced` accepts them because their segment is listed, and their content is unverified. A delete marker in any segment is a problem and marks its batch as failing, whatever the sums say. The tokenizer self-test (about 0.35 s) runs once per process, at the first verify with a current index (a failure is kept for the life of the process, a cancel is not, `TestFTSSelfTestMemoKeepsAFailure`), and reads fresh `_config` rows from a private in-memory database, so a verify needs a working SQLite in memory beside the case; if it cannot be built, the postings, sizes and totals of the index are reported as not verified and the verify fails.
- Full-text query limits and grammar: the grammar is closed (words ANDed, `AND` optional, upper-case `OR`, `"phrases"`, `prefix*`, `-negation`); everything else is text and is tokenized like the stored text, so punctuation separates tokens. Terms with nothing to search for are refused with a usage error, never answered empty: a term with no letter or digit (emoji-only, private-use characters, symbols), a prefix with fewer than 2 letters or digits on the token its star attaches to, a `--substring` needle under 3 characters after the tokenizer's mark folding (`ab` plus a combining mark is 2), a term over 256 bytes, a query over 4096 bytes or 64 terms. Behaviours: `--foo` is the negation of `-foo`, and a group of only negations is refused; `c++` searches the token `c` (it also finds `c#` and `c`); `+1` searches the token `1`; `a-b` is the phrase `a b` (the two tokens adjacent, so it also finds `a b` and `a.b`); a query that starts with `-` is read by the command line as a flag, so write `minutiae records search --case C -- -x`. Use `--substring` for punctuation-exact needles.
- Full-text tokenization limits: a run of CJK characters is ONE token (a word search finds it only as that whole run, `--substring` finds parts of it from 3 characters), and emoji are not word tokens (a word query cannot find them, and an emoji-only term is refused for `--substring` as well; variation selectors are dropped so `❤` and `❤️` meet inside a longer text). U+200B is a separator, U+200C/U+200D and U+2060 are dropped (they join within words). These misses are pinned by `TestNormalizeKnownSilentMisses`, not fixed.
- Full-text ranking and snippets: `--rank` returns the best 1000 hits at most, without a cursor and without `--substring`; its order uses bm25 with the totals P11 verifies, which mean little for trigram text and for short summaries. Snippets are cut from the stored text and highlighted with an approximate tokenization (the query's needles folded like the index, not the FTS5 tokenizer itself), so a hit the index found may show a head snippet with no highlight. A snippet line without a marker means that column did not match (the head of the column is shown), and with `--in summary` or `--in body` the other column gets no snippet. `--json` spans carry the text as stored and a `match` flag. A search that runs past `--timeout` (default 30 s) ends with `ErrSearchTimeout` (exit 1); a cancel stays a cancel.

Ingest 1,630 records/s against >= 40,000 (a miss: FTS5 maintenance and fsync dominate; `WriterOptions.RelaxedSync` / `parse run --fast-sync` is available and off by default, see the relaxed sync bullet) and `artifacts.db` 3.90 times the row data plus 64 bytes per row against <= 1.6 (a miss, no change made). List p95 19.6 ms against <= 50 over the filter combinations that hit a time-ordered index (pass). Search: word and prefix p95 121.4 ms against <= 300 and substring 128.3 ms against <= 1000 (both pass after Task 14n). Stats by type 42.8 s against <= 3 (a miss, see the stats bullet). Verify 3,094.4 s, 3,231.6 records/s, against >= 3,700 (amendment A10): a miss at 87.3% of the target, caused by `PRAGMA integrity_check` (P10), which cannot be split (see the scale bullet). `OpenArtifact` with 10,000 manifest lines 0.209 ms against <= 1 (benchmark). Nothing was relaxed to reach a number and no skip flag exists. Residuals the plan leaves: filters on artifacts, parsers, path prefixes and `IncludeUntimed` ranges are not served in time order by an index, so those lists sort their whole match set (artifact, artifacts3, path+artifact and parser cells took 81 to 308 s at 10M with 1 to 2 samples each, `time+untimed` 825 ms); a filter list of more than 32 values is one `IN` query that may sort every match; with a superseded run present every list, count and stats statement joins `record_batches` and probes `record_superseded` per row (`matrix.list.super.*` and `stats.super_s` were not run at 10M); `Writer.Start` and `Reader.Get` read the whole audit log (`start_s` 0.06 to 0.09 s and `get_p95_ms` 172 to 274 ms at the sizes measured, `Reader.Get` above the 50 ms plan threshold); the P11 scratch figure `verify_tmp_bytes` is a sampled lower bound (every 500 ms) and reads "not measured" when the sampler saw nothing; the timing assertions that plan 5C left in default tests on main (`records/get_provenance_test.go`, `provenance_chain_test.go`, `provenance_hostile_test.go`, `evidence/ftsnorm_test.go`) are a pre-existing limit, with a backlog item to convert them to work counters. `Stats` is capped (`MaxStatGroups`, `StatsTop`, `records stats --max-groups`), never silently cut.
- Records concurrency: one `Writer` per `Case` at a time (a second `Start` is `ErrIngestActive`; another process is excluded by the case lock). Nested `StoreTx`/`ReadTx` calls are detected by goroutine identity (parsed from `runtime.Stack`): a nested call from the same goroutine fails with `ErrNestedTx`, other goroutines queue; a function that hands its transaction to another goroutine and waits for it is not detected (it queues behind itself). `ReadHandle` refuses non-read SQL lexically before running it; SQLite cannot stop a query from switching `query_only` off inside the open transaction, so that second layer detects and rolls it back (`ErrReadTxModified`, connection discarded) instead of preventing it. The concurrency tests run under `-race` in the race gate (the records and evidence ones by name, step 3; passed 2026-10-08, 0 data races); the fast check runs them without `-race`.
- Single-writer scanner residual: the scan of Go files for SQL that writes the record tables strips comments from a normalized SQL string, so a comment marker inside an SQL string literal (`'--'`, `'/*'`) in a deliberately built multi-statement string can hide a following write from the scanner. The immutability triggers and `case verify` still catch the write; the scanner stops mistakes, not a determined author.
- Records schema history: no compatibility path exists for audit logs written before `created` was added to `records.batch` (the schema is unreleased); a `case.upgrade` announced and then dropped by a later announced upgrade is not reported (latent until schema v3).
- Deleted-data recovery (sub-project 3, plan 3A: the foundation; 3C-3H and 3K pending, 3B, 3I and 3J done): the model (`evidence.Recovery`, the class table, namespaces), the checks R1 to R7 of `case verify`, the optional `filesys.Recoverer`/`Journaler`/`AllocatedRunner` interfaces, the planner and writer (`examine.Session.PlanRecovery`/`Recover`) and `image recover` exist; FAT12/16/32 and exFAT implement `Recoverer` (3B); ext4 and F2FS follow (3C, 3D); HFS+ and APFS are out of scope, so on a filesystem without a reader `image recover` reports that the filesystem "does not support recovery" (exit 1, nothing written, only `case.open` audited). `Journaler` and `AllocatedRunner` have no consumer in 3A (interfaces only; their users are 3F/3G and the carving plans).
- `image recover` addressing and coverage: a deleted entry is addressed by `id:<FSID>` or by naming a live directory (every deleted entry below it is considered); a deleted entry cannot be addressed by path. Files inside DELETED directories are not enumerated by 3A (`filesys.Walk` does not descend into them); the FAT and exFAT readers (3B) do not enumerate them either (ruling F2, see the FAT and exFAT recovery items below), and the ext4 and F2FS readers (3C, 3D) own the same question. In 3A only `image recover` marks recovered artifacts; `records show` marks them (status line first, since 5C) but `case info` does not yet (report work), and `records list|search` filter and show the recovered flag of records. `--list` plans without writing: it reads image bytes (the uniform scan and the allocation lookup) but writes no artifact and appends only the usual `case.open` audit entry.
- FAT and exFAT recovery (plan 3B), what the maps are: (a) FAT recovery is contiguous by assumption. The vfat driver zeroes the whole FAT chain of a deleted file (probe fact P1), so fragmentation cannot be known: a recovered fragmented file is wrong beyond its first fragment and says so (`contiguous-allocation`, confidence at most 55; `TestRecoverFATFragmentedFileIsNotClaimedEqual`). (b) Free is not "unused since deletion": a free cluster may hold the bytes of another deleted file. Overlap is flagged only between LISTED deleted entries, and a file under a deleted directory is not listed, so a hidden overwriter is not named (the `cut-h` fixture case); confidence is ordinal and capped at 55 (75 only for exFAT `NoFatChain`, 65 for a surviving chain). (c) Files under deleted directories are not enumerated (ruling F2): `filesys.Walk` does not descend into them and `Recoverer` has no listing method (`TestRecoverFixtureDeletedDirectoryContentIsNotListed`); a backlog item covers an optional `filesys` interface. (d) Whether the FAT chain of a deleted exFAT file survives was measured only for the kernel `exfat` driver of the pinned guest (kernel 6.1.0-53, probe fact P3): the entries are kept for a chained file and never written for a `NoFatChain` file. Other drivers, other kernel versions and devices that delete differently are unmeasured, and how long the entries survive once their clusters are reallocated is uncharacterized (ruling F26: examine's free-state cut bounds the harm to a prefix capped at 20, it does not cover it). A broken chain yields a prefix capped at 20, never a contiguous guess. (e) The exFAT `NameHash` is verified for listing only (it does not change recovery), and a deleted set with a bad checksum or a damaged set yields no candidate, so its content is not recovered even when intact. (f) The first character of a deleted FAT 8.3 name is lost; `Mode` is synthesized as for live files; FAT times are local with no zone. (g) Cross-linked chains, bad or reserved clusters inside a range, orphan long-name sets, a first cluster outside the volume and an oversize `DataLength` are verified on builder images only (the kernel drivers do not write them). (h) `ValidDataLength` below `DataLength` has no real-image case: the guest tools cannot create it (probe fact P5), so it is covered by builder images only. (i) The fixtures are written by the Linux drivers under QEMU; the behaviour of other firmware (cameras, phones' own stacks) is unvalidated, so run `image recover` on such images by hand before relying on it. (j) A range that leaves the volume, or a truncated image, is skipped as corrupt and never recovered as a clamped prefix (ruling F5).
- FAT and exFAT recovery fixtures (plan 3B), what the real images do not cover: (a) no exFAT fixture record is `exfat-contiguous` (the kernel keeps the chain of every chained file, so the chain-cleared case never occurs); that branch is covered only by hand-built images (`TestRecoverExfatClearedChainIsContiguousAssumption`, `TestExfatStaleChainFirstEntryFreeIsContiguous`) and has no real-image case. (b) The FAT32 fixture has a single FAT copy (`mkfs.fat -f 1`, ruling F100, to stay within the image size budget), so the differing-copies warning is tested on the FAT12 and FAT16 images only. (c) The fixtures are not byte-reproducible: image and oracle are regenerated together and every test checks the image sha256 first. (d) The exFAT oracle's check that a `NoFatChain` file's FAT entries are zero runs at snapshot time only, and fails the generator closed on a NoFatChain file that sits on stale FAT entries; the pinned `dump.exfat` (exfatprogs 1.2.0) has no per-file option, so it is used for geometry and the free-cluster count only.
- `image ls -r --json` prints each walker finding (a cycle, nesting deeper than the walk limit, a path longer than the walk limit) as an item of the array, `{"path": ..., "warnings": [...]}`, without an `entry` key, so a consumer must test for the key; the exit code stays 0, the finding is printed as a warning on stderr but is not an audit entry (ruling F88, F98, F105).
- Recovery artifacts and kinds: a runs sidecar of a recovered artifact is an ordinary artifact of kind `runs` (empty remote path, no `Recovery`, same directory), not a recovered kind. The kinds `slack`, `journal` and `report` are verified by R1 to R5 only and noticed (not reproduced byte for byte) until 3F/3G add their reproduction; `recover` and `carve` artifacts get the same notice only until R6 runs, which it does in every `case verify` of this build. A recovered artifact records ONLY the captured prefix runs (the rest is named in `Excluded`, capped at 256 runs), so the sum of its runs always equals its size; its `Content` is `ok` or `uniform` only (no plausibility or format check yet), and a candidate of size 0 is `empty`, one of size above 0 with no runs `no-runs`. Confidence for `post-checkpoint-file` is required and its journal reference rules may change in 3H; a journal reference is allowed only for `deleted-file` and `journal-report`. The allocation state `unknown` is decided by presence: a filesystem that has any warning after `Unallocated` counts every unverifiable byte as unknown (conservative, and the same in `--list` and a run).
- Recovered-ness propagates through the derivation chain: extracting files from a carved or recovered partition image yields live-namespace (`extract`) artifacts whose records are still recovered records (R7 walks the chain, at most 16 hops, and requires a recovered flag and a confidence not above the lowest along the chain), so a record cannot launder a recovered artifact by being extracted again.
- Recovery run bounds and cost: `--max-files` and `--max-bytes` (defaults 100000 and 8 GiB) apply to `recover` only (`extract` and `unalloc` have no such cap); the uniform scan is part of admission and its total is capped at 4 x `--max-bytes` (reason `max-scan-bytes`, distinct from `max-bytes`; a uniform verdict is cached per identical run list); a run considers at most 1,000,000 deleted entries and plans at most 1<<19 runs by default (`--max-plan-runs` raises it; planning, the overlap passes included, peaks at about 260 MiB of heap at the default, measured by `TestOverlapPeakHeapAtPlanCapStaysBounded`, and about 2.7 GiB at 1<<22), the rest counted as `limit` with one audited warning (`max-entries`, `max-plan-runs`); at most 1000 walk errors are listed (the rest counted by reason, one further-count note). `not-selected` candidates (without `--all-candidates`) are counted in `skipped_by` and `analysis.end` only. Overlap detection is O(n log n): each entry lists at most 16 overlapping partners (`overlap=<id>`) and the attribute `overlap-other-runs=<n>` counts the further overlapping RUNS of other candidates beyond those partners, not distinct owners (a number never claims more than it counts); the overlap confidence cap of 30 is applied per ENTRY, not per candidate: with `--all-candidates` every alternative of an entry whose chosen runs overlap another entry's gets the overlap assumptions and the cap, even an alternative whose own runs overlap nothing, which under-states its confidence and never over-states it. Overlap is also evaluated over candidates that are later skipped (uniform, below the minimum confidence, past `--max-files`), so a surviving candidate can be capped at 30 and name `overlap=<id>` for an entry that is then not written: again an under-statement. A hostile image with N skippable candidates writes one audited `analysis.warning` per skip (about 1.5 ms each, fsynced) up to 10,000 per analysis, then one "further warnings suppressed" entry; the later ones are only counted (`analysis.end` carries `warnings_suppressed`, the summary counts stay exact; `TestRecoverWarningEntriesAreCapped`). The free-space check is advisory and, on Linux, counts `f_bavail` in `f_frsize` units (`TestStatfsUnitPrefersFragmentSize`).
- `case verify` cost of recovered artifacts: R6 reads, for EVERY recovered or carved artifact, the image bytes at its runs and the artifact itself (1 MiB chunks, one container open per parent), so verify time grows linearly with the recovered bytes (up to the 8 GiB default budget per run, more over several runs); there is no skip option and no timeout flag (the context cancels it) and the cost is not measured; the prebuilt manifest index keeps it linear instead of quadratic in the artifact count. A flag to skip or report progress belongs to a later plan.
- `case verify` limits of the recovery rules: verify cannot check that the runs of a `deleted-file` lie inside the filesystem's `Unallocated()` (R5 checks only the writer's own `Alloc` claim, R6 reproduces bytes, not allocation state; spec 3.2.3 is enforced at write time by `examine` only). Each recovered artifact re-reads its whole runs sidecar (up to 1M lines), so N artifacts sharing a sidecar cost N reads. R6's `OpenContainer` re-reads the manifest per parent group, so the indexed open applies fully only to the `scope=artifact` carve path. The `archtest` scanners of the recovery rules are review aids (they stop mistakes, not a determined author): string conversions of a kind, a function result as a `Kind` and positional `Source` literals are not seen; the real defence is `case verify`.
- `declared_runs_artifact`: an artifact whose copy was interrupted (cancel, read error) keeps its captured prefix as runs, and the full run list the filesystem declared stays in the case as a `runs` sidecar named by `Recovery.declared_runs_artifact`; it is provenance of what was declared, never of what was captured, and is not used to reproduce bytes. Scope reconciliation: the earlier rule that a carved scope is limited to raw and unallocated is superseded by spec 5.2, which lists `unallocated`, `volume`, `raw` and `artifact`.
- The free-space check is advisory: the output volume can fill after it passes, which is a case-write failure and aborts the run (`analysis.error`, partial artifacts kept and flagged). The check uses the space available to the calling user (Windows: `lpFreeBytesAvailableToCaller`, so quotas count) and saturates at the largest int64 when the OS reports an overflowing value. A manifest line with an unknown field is dropped by the non-strict decode of `manifest.jsonl` (pre-existing; the hash-chained `artifact.create` entry still carries the full `Source` and `case verify` compares it field by field).
- Recovery audit anchor: as for the records database, the audit chain has no external anchor, so a forger who can append valid, correctly chained audit entries (and rewrite the manifest and the artifact consistently) is not detected by `case verify`; R6 still catches artifact bytes that do not equal the image at the recorded runs, so a forgery must also rewrite the parent image artifact, which changes its hash in every derived record and in the audit.
- SQLite file library (sub-project 3, plan 3I, `internal/sqlitefile`; the typed recovery pass and the generic `db_row` run are done in plan 3J, `internal/dbrecover`, see the 3J item below): the library reads, it never opens an engine, creates a file or writes. `Live()` is the state the SQLite engine would present: the database plus the committed frames of the current WAL generation, and a VALID HOT journal is applied in memory (before-images override database pages, playback stops at the first bad record checksum as the engine does); nothing is written to the evidence or next to it. `AsFound()` is the raw view (the file plus the committed WAL overlay, no rollback); nothing uses it by default. A hot journal that names a super-journal is applied only when the caller says the super-journal file exists (`Options.SuperJournalPresent`), because the library cannot see other files; the engine's behaviour with the file absent is matched. Read-only copies and locks are not modelled: the engine refuses to roll back a journal on a read-only database file and does not treat a journal as hot while a live writer holds a lock, where `Live()` presents the rolled-back state (the `journal-hot` warning is raised either way). A journal whose header declares more records than the file holds is `journal-truncated` (and `JournalInfo.Truncated`, and `truncated` in the `analysis.end` journal facts): the file cannot tell a cut file from a damaged count, the records present are read and the engine plays back the same ones (`TestTruncatedJournalLiveEqualsTheEngine`).
- SQLite file library, deliberate deviations from the engine (each fails closed with a warning, never guesses): a WAL frame or database page that reads past the end of its file is unavailable, never zero-filled (`live-pages-unavailable`, at most one warning per file kind, with counts); a journal initial size above the file size is not zero-filled (`page-count-clamped`); a trailing partial page counts as a page like the engine but its missing bytes are unreadable, never zeros (a cell that reaches past the end is a damaged cell with a warning, and `History` yields the partial page marked `Partial`); a hot journal that is NOT applied (page size differs from the database, or the record or segment limit is reached, so a partial rollback would mix two states) makes `Live()` fail with a typed `LiveUnavailableError` plus a warning, and while `Live()` is unavailable `History`, `Pages` and `Summary` return the same error (no history rows are delivered with an unknown relation to live; `AsFound()` stays available for the raw pages); a WAL whose re-sealed header carries an unsupported version makes `Live()` fail the same way, as the engine refuses such a database; a valid-header WAL is applied whatever its page size (the first database-page-size bytes of each frame are read) and a header-invalid WAL is ignored (`wal-header-invalid`). The journal edge rules (journal page size 0 means the database page size, a zero-length super-journal file is absent, a journal under 512 bytes is not played back while one between 512 and 4096 bytes is, a super-journal name over 1040 bytes is not a trailer, page 0 and the lock-byte page end playback, a page above the initial size is skipped, the last write of a page wins, a hot journal and a WAL are applied rollback first) are those 47 engine probes of `TestEngineJournalRules`; an anomaly the engine does not mind but a reader should (`journal-and-wal`, `journal-duplicate-page`, `journal-page-size-mismatch`) is a warning. Other unmodelled engine behaviour: a WAL beside a rollback-mode header (bytes 18/19) is applied as the engine's probe shows (`wal-mode-mismatch`), the `-shm` file is ignored, and a database whose file is empty but whose WAL is not cannot be `Open`ed (use `ScanWAL` standalone).
- SQLite file library, WAL frames and values: the frames the engine does not apply (uncommitted tail, a broken frame, frames after a break, frames of an older generation) are not live; one `wal-frames-not-applied` warning per scan counts them by class with the first slot of each, and they are History's (`sqlite-wal-uncommitted`, `sqlite-wal-stale`). A live text value over 4 MiB or blob over 64 MiB, a value in a truncated overflow chain, a virtual generated column and a non-literal default are NOT materialized: the value carries `Omitted` (with its true `Len`), every omission is counted in a warning, and the decoding layer must report it as absent; a recovered value over 1 MiB is clipped and marked `Clipped`. Serial types 10 and 11 read as NULL with a `record-reserved-serial` warning (the engine does the same) and the header's text-encoding field is read as the engine reads it. Every allocation is charged to the `Budget` (a nil budget gets an internal 1 GiB one, there is no unbudgeted mode), every count is sized from the physical addressable page limit and never from a declared count, and a limit that is reached ends the work with `limit-reached` and a warning, never silently.
- SQLite file library, schema and lookups: `Table.Get` is `ErrWithoutRowid` for a WITHOUT ROWID table (it has no rowid); `GetByKey` (`Table.GetByKey`, `View.LookupKey`; the decoder's `Table.GetByKey`) finds its row by the primary key under the key's collations, applying the key columns' affinity to each value (text is put in the database encoding), and answers "absent" only on a path proven in order: every page on the path has its entries strictly increasing and inside the range the ancestors' entries give it, and a miss at a side of a leaf that has a bound reads the adjacent leaf's entry next to the bound. Damage on the path is a `CorruptError` ("the row may exist"), a comparison it cannot make (a custom collation, text invalid in its encoding, an unread value, a real against a TEXT key column, whose spelling is the engine's) is `ErrKeyUndecided`, and a key of the wrong length, a NULL or NaN component, a table with rowids or an unparsed definition is `ErrBadKey`. A lookup is bounded like a scan (the visited set, the depth cap, the budget). "Absent" means absent from the path the key's search takes, not from the file: a lookup proves the pages it reads, so an entry placed in another subtree than its key belongs to is not found by its key and the lookup does not report it. The ordered scan does: it compares every entry with the previous one AND with the range its ancestors' separators give its subtree (an index-tree separator is itself an entry; a tie with a bound is damage only where the key is unique), so every entry outside its range is flagged, a misplaced run included, and a row the scan delivers unflagged is never answered absent by a lookup of its key (it is found, or the answer is a `CorruptError` or `ErrKeyUndecided`; `FuzzGetByKey`). A custom collation in a later key column can make every lookup `ErrKeyUndecided`, because the order of stored neighbours that share the earlier columns cannot be proven (fail closed). A miss at the end of a leaf whose sibling lies under another mid-level page reads up to 2 x depth - 1 pages. `Get` reads an overflow chain as the engine does even when another row shares its pages (only a scan or `case verify` of the artifact reports the sharing); an index tree or WITHOUT ROWID table is checked for key order against the engine's comparison (`Table.Rows` of a WITHOUT ROWID table, `Index.Entries`, `View.ScanTreeOrdered`): an entry that does not follow the previous one is delivered flagged (`KeyRangeViolation`, a `btree-order` warning), and so is an entry that repeats the key of the previous one in a unique key (the WITHOUT ROWID primary key, a unique index when no key value is NULL), and so is an entry outside the (lower, upper) range the separators of its ancestors give its subtree (each check flags the entry at fault, never both entries of a pair; the bounds are charged clones, at most two per open level); an entry it cannot compare (a custom collation, text of an expression column, an unread, omitted or clipped value, a short record, an automatic index) is counted in one `key-order-unchecked` warning per scan, never skipped silently and never a violation, and ties of a non-unique index are not judged. A doctored table-tree interior key is flagged by the rowid check. A lookup by key in an index (as opposed to the primary key of a WITHOUT ROWID table) is not implemented. The CREATE parser is tolerant and refuses what the engine refuses (duplicate column names, STRICT types): an unreadable or over-cap definition leaves the table unparsed with a warning (columns unknown), never a failure; views and triggers are listed, not interpreted. Virtual tables are not interpreted. In `sqlitefile` they are listed in `Schema.Objects` (`Virtual`) and `Table()` is `ErrVirtualTable` (never `ErrNotFound`, because the table exists). In the decoder `Tables` excludes them, `VirtualTables` lists their names, and `Table` is an `UnsupportedSchemaError` naming the virtual table that also satisfies `errors.Is(err, sqlitefile.ErrVirtualTable)`; their shadow tables read as ordinary tables. A table whose schema row names a root page that cannot be a b-tree root (0, 1, past the addressable limit) is a warning and `ErrCorrupt`, never `ErrNotFound`; that rule is for the root-page case. In general `Table` and `Index` answer `ErrNotFound` only when the schema was read cleanly (`Schema.Skipped` is 0); after any skipped or contradictory schema row, a name that is not found is an `ErrCorrupt` error ("the schema was read incompletely"), because the object may be among the lost rows (`TestTableAndIndexAreNotAbsentAfterASkippedSchemaRow`). Cells found outside any pointer array (gap, freeblock, orphan page, freelist trunk tail) are plan 3J's: 3I only exports the free-space spans and counts; History ignores interior index cells (counted as `InteriorSkipped`).
- SQLite file library, recovered rows are LEADS with an honest label, never facts (`History()`; spec 3 section 3.3, the confidence rule is `Confidence`): a row's table is named by the schema the IMAGE itself had when it was written (the as-of schema read from the same snapshot; basis `schema`), and only when that schema is unavailable (a stale generation without its schema frame, a damaged as-of schema, a page beyond the as-of state, the state cap reached) does the label come from a fit of the cell shapes (`fit` capped at 60, `guess` at 40, `none` at 30), always with the note `identity-by-fit-only` and the relation `unknown`: a fit is never compared with a live row, so a dropped table is never reported as a modified row of another. Accepted residuals: (1) a dropped table whose shape matches exactly one live table is labelled by that live table (basis `fit`, 60, `unknown`, `identity-by-fit-only`), which can name the wrong table, and the examiner is told by the basis and the note (ruling C46); (2) rows whose as-of owner is unprovable are NOT deduplicated against live rows, so a row equal to a live row can be listed; a row named by the column fit alone that equals a live row of its fitted table byte for byte carries the note `equals-live-row` and nothing else changes (C45, closed in 3J); (3) a label on the schema basis needs every cell of the page to fit the named owner strictly, a page that fits only loosely gets `fit` or `guess`; (4) rows of a WAL generation with no schema frame carry the fit basis and `owner-changed`; (5) the strict fit refuses a record missing a rowid-alias column (ALTER TABLE cannot add one), STRICT tables can be ambiguous, and the fit is bounded by a step cap past which every fit is `limit-reached`; (6) pages the layout cannot attribute because the schema was read incompletely are counted in one `pages-unattributed` warning and NOT listed, because they may be live pages of unread tables; (7) the overflow of a stale cell is followed only under the snapshot rule (the chain as of the image, never from today's pages). `uncommitted` is an ORIGIN fact (`Origin`), not a relation: the relation of EVERY row whose identity the schema does not prove (basis `fit`, `guess` or `none`) is `unknown`, whatever the origin, and only a schema-basis row from an uncommitted origin carries the relation `uncommitted`. Row identity for WITHOUT ROWID history compares numerically across kinds (1 equals 1.0) under BINARY, NOCASE (ASCII folding only) and RTRIM, with the key clause's collation; any other collation or an undecidable key gives `unknown`, never `absent` (rulings C48 and C53). The method token `sqlite-journal-rolledback` (base 45) labels page images the rollback hides; every confidence number has a proving fixture (`TestFitTiersProveConfidenceNumbers`).

- Artifact parsers (sub-project 4, plan 4A: contract, host, registry, `parse list|plan|run`). The registry holds the three Android telephony parsers of plan 4D (`android.mmssms`, `android.calllog`, `android.contacts`; plans 4E and 4F add more); none declares claims, so the tests that range over claims (`TestClaimsEqualMappings`, `TestClaimedTablesEmptyWithoutClaims`) still rely on their self-test tables for the claiming case, while `TestRegistryWellFormed`, `TestRepositoryIdentitiesAreCurrent` and `TestTelephonyParsersMakeNoClaimsAndAreRowMappers` range over the real registry. `--include-recovered`, `parse recover`, `parse plan --scan` and the `ios-backup` namer are later plans; snapshot-derived artifacts are parsed only with `--include-snapshots`; a parser can emit only types that have a payload contract; the validators are active in every binary that links `artparse`.
- Parser isolation is in-process. A stack overflow or an out-of-memory kills the process (`debug.SetMemoryLimit`, set to twice the memory budget for the run and restored, is a soft GC limit only). The threat model is hostile DATA, not a malicious parser author. A parser that ignores cancellation is ABANDONED: it is sealed, its accepted records are flushed, its ingest is concluded as error and the whole run stops (exit 1, "restart recommended"); the spinning goroutine keeps a core and the memory its inputs pin until the process exits. Flush and Abort wait at most the grace period behind a stuck writer call, then the job is abandoned with that reason. The run summary `Stopped` is `abandoned`, `cancelled`, `audit-failure`, `abort-failure` or `run-error` (any other run-level failure such as `ErrIngestActive` or a failed `Start`).
  The conclusion of an abandoned job runs detached from the caller's context and `Run` joins it (at most `ConcludeTimeout`) before it audits its end and returns. A conclusion still pending then (a stuck writer) makes `Run` return `ErrConclusionPending`; the job stays reported incomplete and the next Start recovers the unconcluded ingest.
- Verify cancel: `case verify` stops the artifact re-hash, the record checks, the full-text index pass and the localization of failing full-text buckets when its context ends (Ctrl-C), reports one `verification cancelled` problem and lists nothing the cancel itself caused. A cancel with no other finding exits 1, like a cancelled parse run; any other problem found before the cancel still exits 4 (integrity wins). A cancelled verify is never a pass and covered only part of the case, so its absence of problems proves nothing about the unchecked part. The audit read, the derived and cross-checks and the staging checks do not take the context (they are fast) and always run to the end.
- Parse outcomes: an integrity failure while opening a job's inputs makes the job `refused` with `Integrity` true (not `unparsed`), the run goes on and the final exit is 4, also next to a cancel (integrity wins); a plain I/O error opening inputs leaves the job `unparsed` and the exit at least 1. A job whose writer refused records (`CheckRefusals`) concludes `incomplete` with reason `records-refused`, so it cannot supersede an older complete run; the cost is a re-run to supersede. `warnings` and `rejected` are in `records.ingest.end` only (not in `records stats`), and an interrupted ingest's recovery derives its counts from the audit log (`suppression_unknown` when the cap was hit before the conclusion note was written). A re-hash of the inputs that times out (its own 5 minute budget, apart from the conclusion's) concludes the job `incomplete` with reason `recheck-timeout`: an error, exit 1, never an integrity verdict. A record of the run's snapshot that is missing from the manifest, or a manifest that cannot be read, when a job opens its inputs is an integrity failure (exit 4). A bundle that gained a companion artifact since an earlier run is `unparsed` as `stale-bundle` unless `--reparse` is given (`TestParseExitCodes`).
- Parse input trust window. Large inputs (over 256 MiB) are pre-hashed and re-hashed after the job, not continuously, and a streamed input is served only through a section of the verified size (it never grows past it). An input changed during the job and restored before the re-hash (ABA) is NOT detected for a streamed input (`job.end` marks it `streamed: true`); an input changed and not restored is caught by the re-hash (exit 4, the run is `incomplete` with `integrity: true`, batches committed during that job stay, and `case verify` flags the artifact). The exclusive case lock is the defence against another process. The manifest is read once per run, but decoded again per opened artifact (O(artifacts x manifest) until an open-by-record function exists; 5D backlog), and `parse plan` reads every candidate artifact once. Discovery trusts the manifest's `Source` fields (the CLI prints a note: run `case verify` first). The platform of a `file` artifact is known only from device evidence in the case (an `ios pull` with no `ios backup` or `ios info` evidence has none, so only `--artifact` names it); the iOS extract path mapping covers only `/private/var/mobile/`.
- Artifact files on Windows: `OpenArtifact` (image analysis and parse alike) refuses an artifact file, or a directory on its path, that is a symlink or junction, and, since Go reports every reparse point that is not a link as irregular, also a non-link reparse point such as a cloud-sync placeholder, as an integrity error (exit 4, fail closed; not reproduced here, no such volume was available). Keep cases off cloud-synchronised folders.
- Manifest cache of `OpenArtifact` (plan 5D, Task 12): the decoded manifest is reused while `manifest.jsonl` is the same file with the same size and modification time. An external edit that rewrites the manifest in place and then restores the same size and modification time (the file identity is unchanged by an in-place write) is served stale to `OpenArtifact`, in the same process, until the manifest next changes. This affects `OpenArtifact` and the code that takes its record: `parse run` (through `artparse`: `loadSource` and `hashNow`, the size and hash it compares with the record) and the image opens of `examine` (`session.go`, every segment of an image), which would work from the stale record. It never reaches `case verify`: it never uses the cache, recomputes the manifest, and detects such an edit (exit 4; `TestCaseVerifyCatchesAManifestEditTheOpenCacheCannotSee`). The artifact file's own size and link checks still run on every open.
- Parser handles: a parser receives its own `BudgetView` handle onto the invocation's accounting (`Input.Clone`), so overwriting it (`*in.Budget = parse.BudgetView{}`) stops only that handle's further allocations (they fail closed with `ErrBudget`). That is all it protects: the host keeps no handle of its own and settles nothing at the end of a job, its limits do not depend on the view, and `parse.NewBudget` is exported, so the budget is cooperative accounting for the decoders a trusted parser hands it to, not a boundary against a parser author. `Input.Lookup` is an interface whose only implementation is unexported. The threat model is hostile DATA with trusted parser code (the purity rules forbid `reflect` and `unsafe`). A read in flight when the host seals a parser's reader returns `ErrSealed` with no byte count but may already have filled the parser's buffer; the host never reads that buffer.
- Parser metadata: `InputSpec.Companions` fills a NON-primary role from the primary's path plus the suffix; the primary declares none, a suffix names at most one role, and a role that can never be filled is refused by `ValidateMeta` (`TestValidateMetaRefusesCompanionsOnThePrimaryRole` and its siblings); the host does not check that the primary is a SQLite database, and a title is at most 200 bytes of valid UTF-8 without control characters.
- Parser identity: the hash covers layout-, comment- and import-grouping-insensitive syntax, so any other change, including a formatter's `0777` to `0o777` and `a string, b string` to `a, b string` rewrites, needs a version bump; a Go release that adds AST fields can change a dump only for source that uses them. `internal/parse` and `internal/records` (the parsers use their constants and data types) are not in the hash scope: a change there is a change of the build, not of a parser version. A parser package that embeds a file keeps it raw. `parsers.lock` is append-only and has no external anchor: someone with file access can edit it, the writer still refuses a conflicting identity per case. `Start` runs the full schema-object comparison once per job (measure with hundreds of jobs). The CLI prints at most one stderr status line per job in text mode and no job progress; `--json` emits `job.progress` throttled by the emitter.
- SQLite table decoder (plan 4B, `internal/decode/sqlitedb`): (a) the layer inherits the reader's limits; rows the reader skips with a warning are not delivered, and an index built from such a scan is lossy: every miss on it is `ErrKeyUndecidable` naming the loss (never empty) and a hit carries `JoinUndecided` (B76; the loss is the reader's per-scan count of skipped pages and cells, never a warnings delta); the reader de-duplicates and caps warnings, so `Stats.NewWarningsAtLeast` and `Warnings()` are a lower bound, never an exact count; a change to `decode/sqlitedb` or to the `sqlitefile` equality export changes the hash of every parser that imports them. (b) `Files` has no super-journal flag (B8). (c) Bundle completeness is the host's: `Info().WAL == nil` only means none was supplied. (d) Joins use the engine's equality and its affinity rules. INTEGER/REAL/NUMERIC, TEXT (BINARY, NOCASE, RTRIM) and blob keys compare as the engine does, under the TARGET column's collation. A key whose own affinity is weaker than the target column's is converted before the comparison, exactly (D2): a TEXT or no-affinity source column against a numeric target column (the engine applies NUMERIC affinity to both columns), as a literal key is. Two columns of which neither has numeric affinity (a no-affinity source against a TEXT target, which the plan expected to convert, included) are compared as stored by the engine, so the layer converts nothing there. A numeric-looking text that cannot be converted exactly is `ErrKeyUndecidable`, counted in the join report, never an empty answer. The other direction converts the TARGET's values: a numeric source column against a TEXT or no-affinity column meets the target's numeric-looking texts through their numbers (the engine applies NUMERIC affinity to the text), exactly or ErrKeyUndecidable, as above; the index keeps up to one extra entry per numeric-looking value of such a column (counted toward the index limit, charged and released), so an index over a TEXT or no-affinity column reaches ErrIndexLimit earlier, and a numeric-looking text that cannot be converted exactly makes a numeric key's miss ErrKeyUndecidable and its hit JoinUndecided. No TEXT key is rendered against a no-affinity column's numbers (the engine compares them as stored). Every cross-class join is flagged per join with a count of affected keys (`JoinAffinityDiffers`, which means that the classes differ and may be set where the engine converts nothing, as for a no-affinity source against a TEXT target), and so is a differing collation (the engine's own choice follows operand order and `COLLATE` clauses, which the layer does not model: it uses the target's); a custom collation is refused. A miss on a lossy index, or while target rows have undecided keys, is `ErrKeyUndecidable`, not empty; a hit in those cases is returned with `JoinUndecided` because the set of matches may be short (B76, B78). (e) A UTF-16 text value that is not valid UTF-16 is `StateUndecodable` and never decoded. (f) `Row.Locator()` is for live rowid rows only (recovered locators arrive with 4G; WITHOUT ROWID rows and locators over 1024 bytes give `("", false)`). (g) `Index` on a WITHOUT ROWID table is not available (it is refused, A15); it needs a follow-up plan because its result type belongs to `parse.MapContext`. `Table.GetByKey` is available: it finds the row of a WITHOUT ROWID table by its primary key, and a key built from another column (`KeyOf`) is accepted only when its class and collation fit the key column, else `ErrKeyUndecidable` (a numeric 7 against a TEXT key column holding '07' is refused, because the engine reads '07' as 7 and the layer does not model that conversion for a column-sourced key); a literal key takes the key column's affinity as a constant does. (h) No real-device database was used (builder-, engine- and container-made fixtures only; R1 of the spec). (i) `DB`, `Table`, `Index` and `Context` are not safe for concurrent use. (j) A `Row` delivered to a `Scan` callback is valid only inside it (`Clone` to keep). (k) Closed (3J Task 11, B14): `keyDigest` of `internal/sqlitefile` now follows `EqualityKey`, so the four former differences are gone (NaN is `KeyNever`, UTF-16 text under NOCASE/RTRIM has a folded key, invalid UTF-8 under NOCASE/RTRIM and an Unread value are `KeyUnknown`); see the invariants row for the pinned behaviour. (l) `Context.Column` has no error to return, so a failure other than a missing table or column (a cancelled context, an I/O error, a corrupt or unsupported schema) yields -1 and is kept in `Context.Err()` (B77). `rowrun.Run` (plan 4D) runs every telephony mapping and fails the job with `rowrun.ErrContext` when `Err()` is non-nil, after every row and at Close (`TestRunFailsWhenContextErrIsSet`, `TestRunFailsWhenDatabaseIsReleasedMidRun`, `TestCloseChecksContextErr`); a mapper that reads -1 as "this variant lacks the column" is safe only under such a runner.
- SQLite table decoder, out-of-model data (B47): the engine reads a stored NaN REAL as NULL, so NaN never joins and a NaN probe answers empty with no error, as the engine does. Text stored in an INTEGER column is data the engine itself never writes (only a builder can produce it) and on which the engine's own join disagrees with itself; the oracle tests do not cover it and the layer's result for it is not claimed to equal the engine's.
- SQLite table decoder, literal keys: a constant has no affinity, so the target column's affinity is applied to it as the engine does (`'7'` finds the integer 7 in an INTEGER, REAL or NUMERIC column, the integer 7 finds the TEXT `'7'`). A numeric-looking text this reader cannot convert exactly (an integer that does not fit int64, more than 15 significant digits, a decimal exponent shift above 22, longer than 64 bytes after the blanks) and a REAL literal against a TEXT column (the engine's spelling of a real is not reproduced) are `ErrKeyUndecidable`, counted in the join report, never an empty answer (`TestLiteralTextKeyAgainstANumericColumnMatchesTheEngine`, `TestLiteralFloatKeyAgainstATextColumnIsUndecidable`, `TestLiteralTextKeyThatLooksNumericButIsInexactIsUndecidable`). The spellings of infinity and NaN are text (the engine leaves them text) and a NUL ends a text (the engine reads `'7'` then NUL then more bytes as 7). The exactness of a decimal conversion is proven against the reference engine build (a pure-Go engine computing in `float64`, `TestConvertForComparisonMatchesEngine`); a device engine built with extended-precision accumulation may round a decimal that needs a non-zero exponent shift differently in the last bit, which no test here can show.
- SQLite column defaults: a column DEFAULT is converted only when the conversion is exact (the rule of the literal keys above: an integer of at most 18 digits, a decimal of at most 15 significant digits with an exponent shift of at most 22, an integer rendered as decimal text). An inexact one (19 or more integer digits, more than 15 significant digits, an exponent shift above 22, an out-of-range exponent, a REAL needed as TEXT, and an expression) is delivered as `StateDefaultUndecided`: not stored, not a value, never a rounded number, with a typed reason (`Row.UndecidedDefault`); `KeyOf` is `ErrKeyUndecidable`, the history comparison of a row holding an expression default is `unknown` (`compare-incomplete`), while a short record whose column has an inexact literal default fits its table only at the loose tier (`guess`, not `fit`) and its history relation is `unknown` with `owner-changed` and `identity-by-fit-only`. A DDL numeric literal that is not exact is not evaluated (`DefaultInexactLiteral`, the source text is kept). The exactness is proven against the reference engine build (a pure-Go engine computing in `float64`); a device engine built with extended-precision accumulation may round a decimal needing a non-zero shift differently in the last bit. The engine cannot ADD COLUMN with an expression default, yet a nullable column with one still counts as addable for the strict fit (unchanged): such a short record is a `fit`, not a `guess` (`TestDefaultsMatchEngineMatrix`, `TestUndecidedDefaultHasItsOwnState`).

  9. The runner ends a database of another kind as a clean, audited "not applicable at parse time" (one `analysis.warning`, note `not_applicable`, no records) because the host has no distinct job outcome for it yet (D13).

- Decoders (sub-project 4, plan 4C: `internal/decode/{ts,plist,typedstream}`): the typedstream layout is from memory of the legacy format, not from a specification or a real blob (the header tag, the `01 2B` type-encoding search, the integer tags and the class name preceded by its length byte); it is validated by builder streams and an independent second reader of the same rules only, and no real `attributedBody` value exists in the repo (4E must obtain one before relying on it). The text is returned verbatim and must go through `CleanText`; the first-match rule can pick a wrong string if an earlier object carries the class marker; "no string object" is a claim only about the `MaxScan` (64 KiB) window after the header, and a short complete stream without a string is `ErrTruncated`, not "no string".
- plist decoding losses and refusals: `Decode` returns plain values; `Unarchive` knows the listed classes only and turns any other class into a map. A duplicate key in a dict keeps the last value, as the format libraries do, and is counted: `DecodeReport` returns it in `Report.DuplicateKeys` (per occurrence in the expanded tree, and not inside an entry that a later entry has already replaced; binary and XML documents, and `NSDictionary` in `Unarchive`, where it is counted once per resolved object (`UnarchiveReport`; the strict `Unarchive` refuses such an archive with the same `*LossError`, after the whole archive resolved); for XML every `<key>` of the document is counted, also inside an entry a later entry replaced, so the XML count can exceed the binary one for the same tree, and it is still a lower bound) and the strict `Decode` refuses such a document with a `*LossError` wrapping `ErrUnsupported`; the XML duplicate check holds one set of key texts per open dictionary and is charged up front (`chargePerXMLNode` per node, which also covers the library's own per-element allocation; see the memory charge below). Two consecutive XML `<key>` elements are `ErrMalformed`, an archived `NSSet`/`NSMutableSet` is a `Set` and an ordered set a `Set{Ordered: true}` (items in archive order, uniqueness not checked), while a binary set tag and a binary null are `ErrMalformed` (the decoding library refuses them; they are never read as something else). `Unarchive` keeps `NS.time` as stored (float64 for a stored real, int64 or uint64 for a stored integer), and the raw seconds are never turned into a time (that is `decode/ts`). A binary date within one float step of the 0001 or 10000 edge is judged on the stored double but may come back from the library rounded, so its `Seconds` can differ by one step from the stored value there; an XML out-of-range date's `Seconds` is computed from the text; a dict key that is not valid text is `ErrUnsupported` (a non-string `NSDictionary` key too). The XML pre-scan is conservative and may refuse exotic but valid plists (UTF-16 XML, a DOCTYPE with an internal subset); OpenStep and GNUstep text plists are refused. `uint64` appears only from XML or a 16-byte positive integer (an 8-byte value with the top bit set is an int64 by the format rule), integers or UIDs beyond 64 bits are `ErrUnsupported` and a negative `CF$UID` is `ErrMalformed`. The memory charge (`len(b)*8 + nodes*478 + payload*2`, plus `nodes*1621` for an XML document, so an XML node is charged 2099 B; each total per node carries a 25 percent margin over the worst measured cost under `-race`, 382.4 B binary and 1678.6 B XML) is a model held to a measurement: `TestChargeCoversMeasuredAllocation` requires it to be at least the bytes allocated while decoding 28 shapes in binary and XML (52 shape and format pairs: flat, many small maps, one large map, empty and small dictionaries, dictionaries of 9 and 17 keys, empty arrays, nesting of 30 and 60 levels, booleans, dates, reals, wide integers, UIDs, short and long strings, UTF-16, non-ASCII and emoji strings, long keys, data, XML attribute strings, comments and whitespace-only text), also under `-race`, with the measured worst case at 0.79 of the charge (0.82 under `-race`). Shapes the decoder refuses (a binary set, an XML processing instruction) have no measurement because nothing is allocated for them beyond the validation. `Unarchive` is charged per resolved object, `1195 + payload bytes + 36 per map entry and list slot` of its fields (`TestUnarchiveChargeCoversMeasuredAllocation`, 12 archive shapes, none allocating more than 0.80 of its charge, also under `-race`), so under the default 1 GiB budget an archive of more than about 898,000 objects (about 780,000 with 5 map entries or slots each) is refused with `ErrNoBudget`. The objects are charged one by one: an over-cap archive is refused only after objects up to the budget have been built and dropped, so peak memory reaches the budget but never exceeds it; the charge is freed and nothing is returned. A shape it was not measured on and the process's peak outside a decode are not covered. Because the charge is that large, the default 1 GiB memory budget refuses the biggest documents the caps admit (`MaxInput` 64 MiB, `MaxNodes` 1 Mi): an XML document must satisfy `8*len + 2099*nodes + 2*payload <= 1 GiB`, so it has at most 511,549 nodes even if it were empty (about 475,000 at 20 bytes per node); a binary document must satisfy `8*len + 478*nodes + 2*payload <= 1 GiB`, so a 1 Mi-node binary document fits only while `8*len + 2*payload` stays within 546 MiB (a 64 MiB document then leaves room for 17 MiB of string and data payload). A larger document is refused with `ErrNoBudget` before anything is allocated (`TestMaxDocumentChargeIsRefusedNotCut`), never decoded in part or cut; a host that must decode them raises the memory budget. No production caller decodes plists today (`internal/ios/mb2` uses only `PrescanXML` and `Check`).
- Timestamps (`internal/decode/ts`): there are three statuses (valid, sentinel, invalid); `ts` guards 1970 to 2100 only, and plausibility floors (for example an SMS date below 1e11 ms) belong to the parsers. `CocoaAuto` reads a genuine nanosecond count below about 3.1e9 (a device clock within three seconds of the 2001 default) as seconds, which gives a plausible but wrong time (2e9 ns reads as the year 2064); 3.1e9 to 1e11 is refused, and a float64 has 53 bits of mantissa, so a nanosecond count of 7e17 is only exact to about 100 ns (read an INTEGER column with `CocoaNanos`, not through a float).

- Relaxed sync (`parse run --fast-sync`, ruling D89): a power loss, OS crash or disk failure during such an ingest can lose the last committed batches of the running ingest although their `records.batch` entries were fsynced to the audit log first; with the default full sync nothing is lost. The loss window is the batches committed since the last FULL commit or checkpoint (up to everything committed since the ingest started, bounded by the write-ahead log; the SQLite file itself stays consistent). Evidence is never silently shortened: the ingest has no completion record, `case verify` reports it interrupted with the absent batches named, and `records stats` and `records show` mark it INCOMPLETE. A re-run is needed to get those records (the lost ids are not reused). A crash that is not a power loss (the process dies) loses nothing: the log is replayed at the next open. The flag exists on `parse run` only; `sqlite recover` and other record writers stay on full sync. While a relaxed ingest runs, `artifacts.db-wal` and `artifacts.db-shm` sit next to `artifacts.db`; `Writer.End` removes them, and the next open of a case left that way converts it back to the rollback journal.
- Verify progress display (plan 5D, Task 14e): the status line exists only when stderr is a console and the mode is not `--json`, so redirected output never contains it; a console that is not UTF-8 (a Windows code page other than 65001, or a locale without UTF-8) gets ASCII glyphs and `cancelling...`. Each frame is cut to the console width minus one column (79 columns when the console cannot say), so a long phase name is shortened rather than wrapped. "no progress for N" states only what was observed (no counter or phase change for 60 s in a counted phase, 10 min in a phase without a counter), never that the run is hung or healthy. The ETA is the rate since the phase started, so a phase that speeds up or slows down shows an ETA that lags. A stall is under-reported by up to one refresh interval, and a verify that ends within the first interval still shows its first frame but no stall text. The localization phase counts batches against its bound (at most 64, or the number of failing batches when smaller), not against the number of failing batches there may be, and it exists only when a bucket fails. A counted phase whose total is unknown shows no ETA, and a phase that counts past its audited total shows the counts as observed with no ETA.
- Search plan shapes (plan 5D, Task 14n, replaces the single threshold of D98): a text search page runs one of three bands by full-text hits, plus a no-hint shape for a tiny filter; every shape selects the same records in the same order, and the plan is chosen by bounded probes in the page's read transaction (never ANALYZE or a stored count). The probes run in stages: a text probe up to 4096 hits first. Under 4096 hits: IN set, planner free. At 4096 or more, the filter is asked first: when every condition of the filter is served by an index (type, artifact, a ts range, deleted) a probe of at most 4096 records decides a tiny filter, which always drops the hint, whatever the query (a plain word runs `EXISTS` driven by the filter's own index; a prefix, a phrase of several tokens, a negation, an AND or an OR runs the unhinted IN, since with the hint the time-index walk would cover nearly every record to find the few the filter selects). A prefix or multi-term query that is not tiny is the hinted IN with no further probe; it never takes `EXISTS`, since a prefix is re-expanded on every record (15 ms per record at 10M). A filter with any other condition (a path prefix, parsers, confidence, recovered, an ingest id) is never probed and keeps the hint, because the probe itself could scan the table. Only a plain word with no tiny filter runs the large text probe (262145 hits): up to 262144 hits is the hinted IN, more is `EXISTS` per record. What stays: a selective filter that is not served by an index (a path prefix, parsers, an ingest id) combined with a common word keeps the hint and may still walk the time index (ruling S13: a path prefix with a common word costs 1,043 ms at p95 at 10M, the one search cell over 300 ms), and with a superseded run in the case the filter probe joins `record_batches` and was not measured (S14: no superseded 10M case exists); the bands are constants measured at 10M on one laptop, not tuned per case; the large probe costs 15 ms on a common word and 23 ms on a prefix at 10M (warm, Task 14m), the filter probe under 0.3 ms; a filter that is large but much rarer than the query's hits is not recognised, and a common word with a mid-sized filter (above 4096 records) keeps the per-record cost of its band. At 10M the word and substring rows pass (121 ms and 128 ms at p95). The tables of results are in `docs/performance.md`.
