# Minutiae — project rules for Claude

Minutiae is a mobile-device forensics tool (Go). Evidence integrity is the
product: a convenient change that weakens it is a bug.

## 1. Before any work
1. Read `docs/ROADMAP.md`. Identify the one sub-project the work belongs to.
   If it fits none, stop and ask — do not start unplanned subsystems.
2. Read that sub-project's spec and plan in `docs/superpowers/` (local only,
   gitignored). If they do not exist yet, brainstorm → spec → plan first.

## 2. Setup (idempotent — safe to rerun any time)
```bash
go version            # must report go1.26.x (go.mod toolchain auto-downloads it)
go mod download
go tool golangci-lint version   # pinned in go.mod as a tool; nothing to install globally
```

## 3. Definition of done (empirical)
Run `go run ./tools/check` and observe `CHECK PASSED` in the output.
It runs: `go mod tidy -diff`, `go vet`, `golangci-lint` (incl. gofumpt/goimports),
`go build ./cmd/minutiae`, `CGO_ENABLED=0` cross-builds for linux/amd64 and
darwin/arm64 (binaries discarded), `go test ./...` (with `-race` when cgo is available).
Never claim work is complete, fixed or passing without that output from the
current code. Auto-fix formatting with `go tool golangci-lint fmt`.

## 5. Architecture rule (enforced by `TestArchitectureDependencyRule`)
- `internal/evidence` and `internal/version` import no other Minutiae package except `evidence → version`.
- `internal/device` imports only `evidence`, `version`.
- Backends (`transport/serial`, `protocol`, `android`, `ios`) import only `device`, `evidence`, `version` and their own sub-packages; never `cli`, never each other.
- `internal/android/adb` imports no Minutiae package.
- `cmd/minutiae` imports only `internal/cli`.
- Parser packages `internal/image`, `internal/volume` and `internal/filesys` import no Minutiae package (the one exception: `internal/image` may import its own sub-package `internal/image/ewf`): they work on `io.ReaderAt` and can never write to a case, so they never import `evidence`.
- `internal/image/ewf` (the EWF/E01 reader) and its test builder `internal/image/ewf/ewftest` import no Minutiae package at all (`ewftest` does not even import `ewf`, so the builder is an independent oracle for the reader); the reader works on `[]ewf.Segment` (an `io.ReaderAt` plus a size), so it can never write to a case and tests and fuzzers feed it in-memory bytes.
- Parser test helpers (`volume/volumetest`, `filesys/fstest`) import only their parent package; `internal/filesys/detect` imports only `filesys` and the filesystem packages it probes (today `filesys/f2fs`, `filesys/ext4`, `filesys/exfat` and `filesys/fat`); each of those imports only `filesys`, and its test builder (`f2fs/f2fstest`, `ext4/ext4test`, `exfat/exfattest`, `fat/fattest`) only `filesys` and its parent package.
- `internal/examine` is the only bridge between the parsers and the case: it imports `evidence`, `version`, `device`, `image`, `volume`, `filesys` and `filesys/detect`.
- `internal/cli` may import anything.

## 9. Known limitations
- Android sync v1: `LIST` of an unreadable directory returns `DONE` with no entries (indistinguishable from an empty directory, so no `acquire.warning` is possible), and `LIST`/`STAT` report sizes and mtimes as 32-bit values (sizes of files ≥ 4 GiB are truncated in listings and in `source.remote_size`; `RECV` still transfers every byte).
- Android hostile device: a malicious or faulty device can stream an unbounded number of `LIST` entries, unbounded directory depth, and arbitrarily large files (`RECV` size is inherent to evidence, so it is not capped). The examiner can stop an acquisition with Ctrl-C: partial artifacts are kept and flagged incomplete.
- iOS backup: the sync-lock / `notification_proxy` step is not performed, and `Info.plist` is not generated; the lockdown values are saved as `device/lockdown.json`.
- iOS backup transfer: a `0x0b` (remote error) block that follows file data is treated as the normal end of that file, mirroring libimobiledevice, so a device-side read failure in the middle of a file can look like a complete file. Files cut off by a transport failure or cancellation are kept and flagged `incomplete`.
- iOS encrypted backups (a backup password set on the device) are captured as-is; decryption belongs to roadmap sub-project 10.
- iOS AFC (`ios ls`/`ios pull`) parsing robustness depends on go-ios: its panics are converted to errors and a pull whose byte count differs from the AFC-reported size is flagged `incomplete`, but malformed AFC responses are otherwise not validated by Minutiae.
- iOS lockdown/service setup: plists the device returns during lockdown `GetValue` and `StartService` (used by `ios info`, `ios ls/pull` and `ios backup` setup) are decoded inside go-ios without Minutiae's bplist validator or panic recovery, so a hostile device could crash the process at that stage (before any artifact is written).
- Image analysis (sub-project 2, in progress): F2FS, ext2/3/4, FAT12/16/32 and exFAT are recognized (`detect.Drivers` holds the f2fs, ext4, exFAT and FAT drivers, in that probe order, followed by the last-resort `f2fs-backup` driver; see below), so `image info` shows their filesystem and `image ls`/`stat`/`extract`/`unalloc -p` work on them. APFS and HFS+ are still to come; until they land, those partitions are listed but `image ls`/`stat`/`extract` and `unalloc -p` report that no filesystem is recognized. Raw and split-raw images, E01 images (EWF v1, see below), MBR/EBR and GPT partition tables, and `image unalloc --volume` (gaps outside partitions) work.
- F2FS detection: `f2fs` matches only a valid primary superblock. An F2FS volume whose primary superblock is destroyed is found only by the last-resort `f2fs-backup` driver, which runs after every other driver, so a destroyed primary on a volume that also carries another filesystem signature opens as that other filesystem; and a stale or forged F2FS backup signature never hides another filesystem. A matching driver that fails to open with a corrupt-structure error falls through to the remaining matching drivers (the failure is kept as a note); `image info` shows that note in the partition error column.
- EWF/E01 images (`internal/image/ewf`, EWF version 1, one or more segment files `.E01`, `.E02`, ...) are opened read-only and can be verified. `image import` takes the segments in order like any split image, any one of them opens the set, and the media is the logical disk (`image info`, partitions, filesystems, `extract`, `unalloc` work as on a raw image; recorded runs are in media coordinates). An E01 that declares 512-byte sectors is probed for both 512 and 4096 (acquirers write 512 for 4096-byte disks as well). Not supported: EWF2 (Ex01) and logical evidence files (L01) stay `image.ErrUnsupportedContainer`; so do volume or `disk` sections of a layout other than the 1128-byte one (legacy short layouts), and encrypted EWF. The format was implemented from the public format notes and validated against `ewfacquire` 20140816 output (one writer, one version; other acquirers' layouts are covered by the `ewftest` builder only, and `TestEWFRealImages` under `-tags realimages` checks real E01 sets by hand) and against an independent decoder.
- E01 incomplete and damaged sets are opened, not refused, and never guessed: a set whose last segment has no `done` section, whose last segment is missing, or whose last segment is truncated mid-section opens with an "E01 set incomplete" warning (the sections walked before a truncation are kept) and every chunk the walked sections do not cover fails with `ErrChunkCorrupt` on read; a missing or out-of-order MIDDLE segment, a truncated non-last segment and a bad section descriptor checksum fail the open. Note the two levels: the case's import record only knows the files given (a 2-of-3 import is a complete import of two files), while the E01 `done` section is what reveals the missing third segment. A chunk table is trusted only if it directly follows its sectors section, its first entry is the sectors payload start, its entries strictly increase and lie inside that section; `table2` is the fallback; if both copies fail, every chunk from that group onward is unreadable (`ErrChunkCorrupt`) with a warning naming the rule, and the image still opens (a damaged table never makes the image unopenable, the part before it stays readable). A corrupt chunk (bad zlib stream, wrong Adler-32, wrong length) is an error on read, never zeros, and `ReadAt` returns the bytes before it. Only libewf-written layouts have been tested against the table rules: an acquirer that pads between the sectors descriptor and the first chunk would open but read no chunk (the same unreadable-chunk error as damage). A bad chunk inside a structure read at open time (the primary or backup GPT) makes `image info` fail at the partition step, while `image info --verify` still runs and audits it (see below).
- E01 acquisition errors: `error2` ranges (sectors the acquirer could not read from the device; the acquirer wrote zeros there and the tables cover them) are reported as warnings and are part of the media, as the acquirer stored it. Acquirer-supplied metadata (case number, examiner, notes, dates, acquirer version) is shown as claimed, size-capped and escaped on output; it is not evidence of anything the acquirer did not record.
- `image info --verify` (E01 only): recomputes MD5 and SHA-1 of the whole media and compares them with the hashes stored in the image; one hash-chained `image.verify` audit entry is always written, also for a mismatch, an unreadable chunk, a cancel or a panic. It proves that the container's media matches what the acquirer stored, not that the acquirer's read of the device was faithful (an `error2` range is zero-filled before it is hashed), and it covers only the hashes the container stores (MD5 and SHA-1; no SHA-256). `absent` (no hash section at all) is not a failure, but a stored-hash section that is present and damaged (checksum mismatch, or too small to parse) is never `absent`: that hash is `unverified` with a `reason` (also in `--json` and the audit entry), the open warning says "stored hash section damaged", and the exit code is 1; a hash that another valid section (hash or digest) still stores is verified normally. Exit codes: `match`/`absent` 0, `mismatch` 4, `unverified` (an unreadable chunk, a damaged stored-hash section or a partial run), cancel, panic and a failed audit append 1; a mismatch whose audit append fails still exits 4. Verification does not need a readable partition table. Raw and split-raw images carry no stored hashes: `--verify` prints a note and writes no audit entry (`case verify` re-hashes their artifacts regardless).
- E01 `extract`: a file that reaches an unreadable chunk keeps the readable bytes before it as an artifact flagged `incomplete` (the prefix is found by bisecting the failing read, so only error-free bytes are written; its provenance records only the runs covering them) with an `analysis.warning`, and extraction continues. A real I/O error of the segment source is not a chunk error: it keeps the old behaviour and ends the analysis (`analysis.error`) rather than producing an incomplete artifact (`TestExtractIOErrorIsNotDowngradedToIncompleteFile`). When the prefix needs a runs sidecar (more than `MaxInlineRuns` runs), it is written under the first free of `<file>.incomplete.runs.jsonl`, `<file>.incomplete~2.runs.jsonl` ... `~16` (a taken name is not a case failure), and the full run list sidecar written before the read stays in the case as an unreferenced runs artifact (an ordinary hashed artifact: `case verify` passes, but nothing references it); the partial artifact's error, and so the `analysis.warning`, names that orphan (`complete run list of the file: runs artifact <id>`). When all 16 names are taken, the partial artifact carries no runs at all and its error says "the runs of the kept bytes are not recorded": incomplete provenance, never wrong provenance (`TestExtractPrefixSidecarNamesExhaustedRecordsNoRuns`). `image unalloc` is different: its runs sidecar always lists every run, so after an unreadable chunk it can be longer than the truncated, `incomplete` `unallocated.bin`.
- E01 size claims: the logical size is the volume section's sector count times the sector size, and must agree with the chunk count (at most 2^26 chunks of at most 16 MiB), so a hostile image can claim up to a petabyte of media with few real bytes; a read stops at the first chunk the tables do not cover and `Verify` stops at the first unreadable chunk, but a whole-media loop over a claimed-huge image is bounded only by cancellation or the caller's budget. The chunk reference table costs 8 bytes per entry (up to 512 MiB at the limit, and only when the file really holds that many table entries).
- E01 chunk-table trust is structural, not a proof of contiguity (parked review finding): the rules above do not prove that a table covers its whole sectors payload without gaps or overlaps, so only a checksum-consistent forgery of the table, `table2` and the section descriptor could make chunks read from the wrong place without a warning. `image info --verify` catches such a forgery unless the stored MD5 and SHA-1 are forged too, and `case verify` still protects the image artifact itself.
- The Go race detector needs cgo, which is not available on this machine, so the EWF concurrency tests (`TestEWFConcurrentReadAt`, the chunk cache) have run without `-race` only; run `go test -race ./internal/image/...` once on a machine with a C toolchain.
- One `image import` call imports exactly one image (its files are segments 1..N in the order given; nothing is sorted). A partially imported image cannot be opened: re-import it.
- Deleted filesystem entries are listed (`image ls --deleted`) and flagged, but not recovered or extracted; recovery is sub-project 3.
- `image ls`/`stat`/`extract` check the parent artifact's size only (`OpenArtifact`), not its hash: a same-size content swap of the parent is not caught at open time, but `case verify` detects it (derived artifacts record the parent's SHA-256, and the parent is re-hashed).
- Sparse-expansion guard: `extract` skips a file whose hole bytes (sum of `Offset -1` runs, or the whole size when the filesystem reports no runs) exceed the partition length, with an `analysis.warning` ("sparse size exceeds partition length; not extracted"). A sparse file within the partition length is still expanded to its full size, and overlapping data runs are not bounded by this guard.
- Encrypted filesystem content is extracted as ciphertext (flagged `Derived.Encrypted`); decryption belongs to roadmap sub-project 10.
- ext4 (ext2/3/4) reader, read-only and as found: the journal is not replayed, so an image that needs recovery is read as it lies on disk (the reader warns that the filesystem may be inconsistent); journal analysis belongs to sub-project 3. `bigalloc`, an external journal device and unknown incompatible features are refused as unsupported.
- ext4 deleted entries are names only: a deleted directory record is listed and flagged (`image ls --deleted`) with what the on-disk record still holds, but its content is not recovered or extracted (sub-project 3). A stale copy of a live record left behind by an htree leaf split stays listed with attribute `stale_copy=true`.
- ext4 names: encrypted (FBE) directory names are shown as `~enc~<base64url of the raw name>` and their file content is extracted as ciphertext (decryption is sub-project 10); names that are not valid UTF-8 are shown as `~raw~<base64url>`. Path lookup accepts both displayed forms.
- ext4 casefold directories: name lookup is approximate (`strings.EqualFold` on valid UTF-8 names, not the kernel's casefold table), so a path may resolve differently than on a live system; directory listing is unaffected.
- ext4 directory record cap: at most 262144 records are read per directory (live and deleted). A lookup beyond the cap, or in a damaged region of a directory, returns not found with a warning, not an error. Extended attributes are read from the inode and the xattr block, but xattr block checksums are not verified and values held in an EA inode (`ea_inode`) are not read.
- ext4 unallocated export: a block group whose bitmap fails its checksum (or cannot be read) is omitted from the export and reported as a filesystem warning (`analysis.warning`); its blocks are neither exported nor claimed as free. Any group whose descriptor checksum is wrong is skipped whatever its flags (`TestBadDescriptorChecksumGroupIsSkippedWhateverItsFlags`), and when the descriptor table is truncated the `BLOCK_UNINIT` groups are skipped too (`TestUnreadableDescriptorsSkipBlockUninitGroups`), each with a warning. The scan for deleted names in directory slack is capped at 16 MiB of slack per directory (`TestSlackScanCap`); past the cap the reader warns and stops searching, so a hostile directory cannot cost unbounded time.
- Analysis warning ordering: a filesystem warning is written to the audit log as `analysis.warning` after the artifact whose processing triggered it (never before): the reader notices an anomaly only while doing that work. Warnings about directories met while walking are attributed through the `after` field, which names the last extracted path, not the directory itself. Warnings the filesystem already had when the analysis began are written once as `source: filesystem-open`; later ones as `source: filesystem` and counted in the summary (`fs_warnings`) apart from skips.
- Filesystem readers keep at most 1000 distinct warnings (de-duplicated by text; every reader, F2FS, ext4, FAT and exFAT, then adds one "further warnings suppressed" note), so the audit log is not an exhaustive list of every anomaly in a hostile image. `image ls`/`stat` print the warnings a command raised (escaped, at most 20 lines) on stderr; `image stat --json` carries them in a top-level `warnings` field.
- ext4 hard links: every directory path to a multiply-linked inode is a separate entry, so `extract` writes one copy per path (the entries share the filesystem id, so provenance shows they are the same inode). Directory entries stored beyond a directory's `i_size` are listed as deleted entries with attribute `beyond_isize=true` (`TestEntriesBeyondISizeAreDeletedNotLive`). A live directory entry whose inode has `links_count` 0 and a `dtime` gets attribute `inode_freed=true` and a warning (`TestLiveEntryOfFreedInode`).
- A file whose extents run past the end of a truncated image cannot be read in full: `extract` skips it with an `analysis.warning` rather than extracting a prefix. Local artifact names are capped at 200 bytes per path component (cut on a rune boundary, then `~` plus the first 8 hex digits of the SHA-256 of the original name, so distinct long names stay distinct; this applies to `image extract` and `android logical` alike); the original path is kept in `Source.RemotePath` and `Derived.FSPath`. An OS path-syntax or name-too-long error creating one artifact becomes a per-file `analysis.warning` and a skip.
- FAT12/16/32 reader, read-only and as found (`internal/filesys/fat`): deleted entries are names only (listed with `image ls --deleted`, flagged `Deleted`; their content is never recovered or extracted, sub-project 3). A long name recovered from the slots of a deleted entry is flagged `lfn=recovered`, and `lfn_tail=unterminated` when the name may be cut short because a slot was reused (`TestDeletedLongNameRecoveryMarkers`); an orphaned long-name set is flagged `lfn=orphan`. FAT times are the local time of the system that wrote them with no zone (`Time.ZoneKnown` is false): modified times have 2 s resolution, created times 10 ms, and the access time is a date only (reported as `T00:00:00`). 8.3 short names and the volume label are strings in an OEM code page that the volume does not record: bytes from 0x80 up are decoded as code page 437 (a name written under another page shows other letters), `Entry.RawName` keeps the 11 raw name bytes (`TestShortNameDecodesCodePage437`, and the fixture's 8.3-only `/ÉTÉ.TXT`). Directory entry IDs are canonical decimals only (`TestEntryIDsMustBeCanonical`), and an entry at or past the directory's first end-of-directory (0x00) entry cannot be opened or listed by ID (`TestEntryBeyondEndMarkerIsNotFound`). When the volume has two or more FAT copies, `Unallocated` compares the others with the active one and warns once if they differ (`TestDifferingFATCopiesWarn`). FAT has no Unix permissions, so `Mode` is synthesized: 0644 for files and 0755 for directories, with the write bits cleared when the read-only attribute is set (not evidence of the original owner's permissions). A FAT chain shorter than the file size (it ends early, meets a free or bad cluster, loops or leaves the volume) yields a partial artifact flagged `incomplete` whose provenance records only runs that cover the kept prefix (see the `File.Runs` prefix rule below) and a warning (`TestFileChainShorterThanSize`, `TestExtractFATShortChainIsIncomplete`).
- exFAT reader, read-only and as found (`internal/filesys/exfat`): deleted entry sets are names only, as for FAT (`TestExfatDeletedSetFlagged`). The File entry's `NameHash` is not verified; the entry-set checksum is, and a set that fails it is still listed, flagged `checksum=bad` (`TestExfatSetChecksumBadFlagged`); a set with no Stream Extension or too many secondaries is flagged `set=damaged` and cannot be opened. TexFAT (a second FAT and allocation bitmap) is ignored: the first FAT and the first bitmap are read. Bytes between `ValidDataLength` and `DataLength` read as zeros and are recorded as a hole run, as the format defines. exFAT has no Unix permissions either: `Mode` is 0. A name that is "." or ".." (or holds '/' or NUL) is shown in the `~raw~` form (`TestExfatDotNamesUseRawForm`), and an entry set at or past a directory's first end-of-directory entry cannot be opened by ID (`TestExfatEntryBeyondEndMarkerIsNotFound`). `Unallocated` never reports the allocation bitmap, the up-case table, the root directory or the clusters the FAT marks bad as free, even if the bitmap says they are, and reports at most 1<<24 runs (a warning says when the rest is cut off; `TestExfatUnallocatedExcludesSystemAndBadClusters`, `TestExfatUnallocatedRunCap`). At most 1<<18 entry sets are read per directory (`TestExfatDirRecordCapDefault`), and at most 1M distinct directories are remembered by first cluster (past that, a warning says the rest cannot be reached by id).
- F2FS reader, read-only and as found (`internal/filesys/f2fs`): the image is read as of its last checkpoint. Roll-forward recovery (the fsync'd node chains written after the last checkpoint, which the kernel replays at mount) is not applied, so later data may exist in such a chain yet is not shown; when the last checkpoint is not an unmount checkpoint the reader warns "last checkpoint is not an unmount checkpoint (data written after it is not reflected)" (`TestUncleanCheckpointWarns`). Analysing that node chain belongs to sub-project 3. Only single-device, non-zoned volumes are supported: the superblock's device table is not read and zoned (`blkzoned`) volumes are not interpreted.
- F2FS compressed files (`F2FS_COMPR_FL`) are unsupported: `Open` of one fails with `ErrUnsupported` ("compressed file") and `extract` skips it with an `analysis.warning`; the listing still shows the entry, with attribute `compressed=true` (`TestCompressedFileUnsupported`).
- F2FS deleted dentries are names only: a deleted entry is listed and flagged (`image ls --deleted`) with what its inode still says while the NAT maps it (type, size, attribute `inode`; `inode_reused=true` when the inode now belongs to another directory, `inode_unreadable=true` when it cannot be read), but its content is neither recovered nor extracted, and F2FS records no deletion time (sub-project 3; `TestReadDirFlagsDeletedEntries`).
- F2FS names and content: encrypted (FBE) names are shown as `~enc~<base64url of the raw name>`, names that are not valid UTF-8 as `~raw~<base64url>`, and path lookup accepts both displayed forms; encrypted file content is extracted as ciphertext (flagged `Derived.Encrypted`), and decryption is sub-project 10 (`TestEncryptedDentryNames`, `TestRawEncryptedContent`). In casefold directories name lookup is approximate (`strings.EqualFold` on valid UTF-8 names, not the kernel's casefold table), so a path may resolve differently than on a live system; `.` and `..` are never matched by casefold, and listing is unaffected (`TestLookupCasefoldNeverFindsDots`).
- F2FS inline data whose `DATA_EXIST` flag is clear (the kernel reads such a file as empty) is returned as stored, with attribute `data_exist=false` on the entry and a warning (`TestInlineDataWithoutDataExist`).
- F2FS free space: `Unallocated` is built from the SIT, with the journal in the checkpoint applied over the SIT blocks. A SIT journal whose entry count exceeds its block makes the export empty, with a warning (no free space is reported rather than guessed); a SIT block that cannot be read, or a segment whose entry is inconsistent, is not reported as free; the segments the current logs write into are not excluded, because the SIT is authoritative; at most 1<<24 runs are reported (a warning says when the rest is cut off). A NAT journal whose entry count exceeds its block is ignored, with a warning that file locations may be stale: inodes then resolve through the NAT blocks only (`TestSITJournalHostile`, `TestNATJournalFullAndOverfull`, `TestUnallocatedIgnoresCurrentSegmentCursor`, `TestUnallocatedBoundsAndCap`).
- F2FS caps: a directory is read up to 64 MiB and 262144 entries (deleted entries at most half of that, so live ones come first), a file maps at most 1<<20 runs and node blocks, and one filesystem instance reads at most 1 GiB of directory data in total; past a cap the reader warns and stops, and a directory that cannot be read because the budget is spent is an error, never an empty listing. Every `image` command (`ls`, `unalloc`, `extract`) opens its own instance, so these budgets, like the FAT and exFAT ones, start over with each command (`TestDirectoryReadBudget`, `TestDirEntryCapPrefersLiveEntries`, `TestRunCapIsCorrupt`).
- F2FS real-image coverage: the committed fixtures (`f2fs-extra-attr`, `f2fs-default`) have no deleted entries (F2FS keeps no deletion time and `sload.f2fs` cannot delete; deleting needs a kernel mount, and the Docker Desktop kernel has no f2fs module), no holes (`sload.f2fs` writes holes out as zero blocks), no indirect or double-indirect node (`sload.f2fs` cannot place a single 7 MiB file) and no inline-dentry directory. Those paths are covered by the `f2fstest` builder tests only and have never been validated against an image written by a real kernel. The generator tries the kernel mount and the removals when it runs where f2fs is available (`tools/fixtures/README.md`).
- FAT and exFAT directory read budgets: each filesystem instance reads at most 1 GiB of directory data in total (exFAT) or at most 4M directory entries, 128 MiB (FAT, which counts entries), so a hostile volume whose chains overlap cannot cost unbounded time. Once the budget is spent, directories are no longer read (a directory read after that is an error, one being read when it ran out is cut short) and the filesystem reports a single budget warning (`TestDirectoryReadBudget`, `TestExfatDirectoryReadBudget`, `TestExfatBudgetExhaustedBeforeFirstEntryIsAnError`). A FAT directory also holds at most 65536 entries, an exFAT directory at most 256 MiB. The budgets are never reset within an instance, so one huge but legitimate volume can reach them. A directory that cannot be read because the budget is spent is an error, never an empty listing: `image ls -r` and `image extract` report it and do not treat the directory as empty. The budgets belong to the filesystem instance, and every `image` command (`ls`, `unalloc`, `extract`) opens its own session and so its own instance: the budgets start over with each command.
- `File.Runs` prefix rule: normally the runs cover exactly `[0, Size())`. A file whose allocation is truncated or corrupt (a FAT chain that ends, loops or leaves the volume) may report only a leading prefix of it; every read at or beyond the end of that prefix fails with `ErrCorrupt`, never zeros, so the covered bytes can be told from the missing ones (`filesys.CheckRunsPrefix`, `TestCheckRunsPrefix`, `TestImageRunsAcceptsOnlyAValidPrefix`).
- Regenerating the real-image fixtures needs Docker; running the tests never does. The exFAT fixture additionally needs `docker run --privileged` (a loop device plus the FUSE driver `exfat-fuse`, because no exFAT image tool copies files into an image and the Docker Desktop kernel has no exfat driver); without it only that fixture cannot be regenerated, the committed `exfat.img.gz` and the builder-based `exfattest` tests still run.
- Hardware: as of v1.0.0 the device backends (ADB, iOS, serial) have NOT been validated on real hardware, only against fakes. Before relying on them in casework, run the hardware acceptance steps with authorized/trusted devices attached and confirm `case verify` reports OK:

